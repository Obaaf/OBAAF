### D-001 Framework name

**Decision.** The framework is the Open Build and Agent Assurance Framework (OBAAF). **Reason.** Chosen by the maintainer. A web search found no existing framework with the name; no trademark search has been done. **Status.** Accepted, 2026-10-05.

### D-002 Release condition

**Decision.** The maintainer authorized making the repository public and publishing the resource site, and stated that written employer approval is not necessary for that publication. Use the default GitHub Pages address until a custom domain is acquired. This supersedes the private-repository requirement accepted on 2026-10-05. It does not grant a license, change copyright ownership, or authorize submission of the research papers. **Status.** Accepted, 2026-10-10.

### D-003 Copyright notice and ownership; license grant

**Decision.** Grant the intended licenses (NFR1): Apache License 2.0 for the code, templates, tools and tests (`src/`, `templates/`, `actions/`, `tests/`); Creative Commons Attribution 4.0 International for the specifications, guides and documentation (`spec/`, `docs/`, and the data in `src/obaaf/data/`). The data files are dual-covered, so the package declares `Apache-2.0 AND CC-BY-4.0`. Copyright is held by Osita Sean Keluo-Udeke, as stated before public draft. The license texts (`LICENSE`, `LICENSE-docs`), the `NOTICE`, the `pyproject.toml` metadata and the [LICENSING.md](LICENSING.md) statement are in place. **Reason.** The licenses were always the intended ones (LICENSING.md); a studio cannot pilot or redistribute OBAAF without a granted license, so the grant is a prerequisite to the independent-studio pilot and to award and funding programs that require an OSI-approved license. **Maintainer acceptance.** Confirm the copyright holder and the affiliation shown on the papers and the repository, then accept by committing these files; change this status to Accepted with the date. Until then the texts are implemented as written but not yet accepted. **Status.** Proposed, 2026-10-21.

### D-004 Profile titles, rationales and tests

**Decision.** Paper 2, Table 4 gives each requirement's statement and mappings. FR1 also requires a test procedure. This repository adds a short title, a rationale, a pass-or-fail test and the evidence to inspect for each of the 28 requirements, in `src/obaaf/data/profile.yaml`. Some tests add thresholds the paper does not state (for example, G6.4's rollback test "within the last six months"). **Reason.** FR1 acceptance criterion. **Review.** Read each entry in [spec/profile.md](spec/profile.md); edit the data file, not the generated document. **Status.** Proposed.

### D-005 Not-applicable answers

**Decision.** Paper 2, DR6 allows N/A only when an item's condition is absent, naming three conditions: no self-hosted updater (item 2.10), no AI agents (items 3.6, 3.7, 4.5) and no target that can build in a container (item 3.3). Item 3.3's N/A condition here reads "fresh container or virtual machine", following the item's own wording, which names both. This repository also allows N/A for item 3.4 when a studio has no persistent release hosts, because Table 9 treats 3.3 and 3.4 as alternatives. No other item can be N/A. **Consequence.** If accepted, Paper 2's DR6 should name the fourth condition. Items 1.2 and 2.8 can also have an absent subject (no automated uploads, no partners); the pilot should show how studios answer them. **Status.** Proposed.

### D-006 Ranking fixes

**Decision.** Open items are ranked by tier (lowest first), then effort (hours, days, weeks), then the number of documented compromises the item would have prevented, then the number it would have detected or limited (Paper 2, Table 7), then item number. **Reason.** DR3 (prioritized by documented attack paths) and DR4 (effort-aware). The Python scorer and the offline form implement the same rule, and a test checks they agree. **Status.** Proposed.

### D-007 Predicate type URIs

**Decision.** OBAAF's in-toto predicate types and its generic SLSA build type live under `https://www.obaaf.com/`, the project's own domain, for example `https://www.obaaf.com/attestation/agent-run/v0.1`. They are defined once in `src/obaaf/predicates.py` and used in the templates. Each type URI resolves to a page that describes its format, and each JSON Schema's `$id` resolves to the schema; `site/build.py` publishes both. A changed format gets a new version and a new URI, and published pages stay as they are. **Reason.** A type URI should be under a namespace the project controls and should lead a reader to the format it names. `www.obaaf.com` is the site's canonical host, so the URIs resolve without depending on a redirect. Version 0.1 used the reserved `obaaf.example` domain until the project had a domain. **Consequence.** Breaking, which is acceptable before 1.0: records signed with the 0.1 URIs do not verify under 0.2 and must be signed again with the 0.2 templates. **Status.** Accepted, 2026-10-26 (previously Open, before release).

### D-008 Trust levels for GitHub roles

**Decision.** The snapshot step asks GitHub for each author's repository role: admin and maintain map to Maintainer; write and triage to Contributor; read and none to Public. Without a role it falls back to `author_association`: OWNER maps to Maintainer, and everything else, including MEMBER and COLLABORATOR, to Public, because those say nothing about write access to this repository. A pull request's changes are always labeled Public. The floor is Public in every repository unless the workflow raises it with `--floor`: the snapshot cannot see who else wrote what the agent's token can read (in a private repository, read-only users and, in internal repositories, every enterprise member). **Reason.** Paper 1, section 3.2 places principals by what they can do; write access can push unprotected branches and apply labels (Contributor). This mapping is right only when repository secrets live in protected environments, as the templates arrange; otherwise write access can read secrets and is Maintainer-equivalent. The security review found the earlier Contributor floor for private repositories, and the Contributor fallback for MEMBER and COLLABORATOR, too generous. **Status.** Proposed.

### D-009 Approvals in a second attestation

**Decision.** Paper 1, Table 3 lists Approvals among the agent-run record's fields, produced by the effect lane. Because approval happens after the attestation step signs, the effect lane signs a second attestation, `agent-approval`, over the same proposal files. The two together form the record. **Consequence.** Paper 1, section 7.3 could say so in one sentence. **Status.** Proposed.

### D-010 Agent records travel with the change

**Decision.** When the effect lane applies a patch, it adds `.obaaf/records/<bundle digest>.json` (the proposal and both signed attestations) in the same commit as the change and names it in an `OBAAF-Agent-Record:` commit trailer. The release verifier finds agent commits by trailer, by an added record file, or by the effect lane's commit identity, and requires each to add exactly one record, named after its digest and used by no other commit in the range. **Reason.** `gh attestation verify` needs the attested file; artifacts expire; a record in the repository is archived with the source and reviewed in the pull request. Requiring the record in the same commit stops an old, valid record from vouching for a later change. **Limit.** A squash merge that combines an agent's change with other changes fails the exact-diff check (D-026). **Status.** Proposed.

### D-011 Pinning pipeline dependencies

**Decision.** Workflows pin every action to a full commit SHA. `actions/setup-obaaf` and the PyPI release workflow install every dependency, including the build backend, from `actions/setup-obaaf/requirements.txt` by exact version and SHA-256 hash, as wheels only (`--require-hashes --only-binary=:all:`). That file lists the hash of every file PyPI publishes for each version, so one list serves every operating system and Python version. It is generated from `constraints.txt` by `scripts/lock_setup_obaaf.py`. CI checks it against PyPI, attaches the expected file to the run when it is out of date, and runs the action on Linux, macOS and Windows. The project's own test and site jobs install OBAAF in editable mode, which pip's hash-checking mode does not support, so they keep the exact versions in `constraints.txt`. **Distribution.** PyPI via OIDC trusted publishing (`pip install obaaf`), documented in [docs/releasing.md](docs/releasing.md). A GitHub Marketplace listing for `setup-obaaf` is documented there; pre-built single-file binaries remain deferred. **Status.** Accepted, 2026-10-26 (previously Open, before release).

### D-033 Empty binary manifest

**Decision.** A project that vendors no binaries declares `vendored_binaries: none` in `obaaf-sources.yaml` (components absent or empty). `obaaf manifest create` writes `format: obaaf-manifest/v0.1` with `vendoredBinaries: "none"`, `components: []` and `entries: []`, so the build-record digest binds the claim. Bare empty `components` without that declaration is rejected. `manifest check` validates the JSON claim and emptiness; it does not re-read the sources file or scan the tree for undeclared binaries. Release policies for such projects set `build_record.require_sdks: false`. An empty claim answers assessment items 1.8 and 2.6 as yes with evidence (the reviewed declaration), not as N/A (D-005 unchanged). **Reason.** G2.1 and FR5 assume a manifest; many non-game projects (including OBAAF) have no vendored binaries and could not previously produce a build record. **Status.** Accepted, 2026-10-26.

### D-013 Language and dependencies

**Decision.** Python 3.10 or later, with PyYAML and jsonschema; `cryptography` only for verifying key-signed envelopes. Tests use the standard library's `unittest`. **Reason.** Python runs on every CI runner a studio uses; few dependencies keep the tools auditable. **Status.** Proposed.

### D-014 GitHub Actions first

**Decision.** The first reference templates target GitHub Actions; a second CI system follows for version 1.0, chosen from pilot data. Requirements stay tool-neutral (NFR6). **Reason.** The specification's scope and roadmap. **Status.** Accepted, 2026-10-05.

### D-015 Isolation tier from the workflow definition

**Decision.** The build record's isolation tier comes from the workflow file: a build job on standard GitHub-hosted runner labels is Tier A, including single-CPU runners, which start each job in a fresh container rather than a new virtual machine (Paper 2 counts a fresh container as Tier A); a self-hosted job, or one whose labels are not standard hosted labels, must declare `OBAAF_TIER` as a literal A or B. The build job never reports its own tier. **Reason.** FR4 requires the build record to state the tier; reading it from the workflow definition, as Paper 1 does for an agent's authority, keeps a compromised build from misreporting it. The publish workflow then checks that the release commit, and so the workflow file, is on the protected branch (D-024). **Limit.** Whether a self-hosted Tier A runner is really destroyed after each job is still a claim in the workflow. **Status.** Proposed.

### D-016 Release approvals checked at upload time

**Decision.** The publish job reads its own run's approvals from GitHub's approvals API, and `obaaf verify release` counts distinct approvers other than anyone who pushed the tag or started or re-ran the release or publish run (`--actor`, repeatable). Approvals are not part of the build record, which is signed before approval. The approvals API covers every attempt of the run; an approval from an earlier attempt still counts, because every attempt publishes the same artifacts from the same release run. **Consequence.** An administrator who bypasses the environment leaves no approval, so the release is blocked. GitHub environments proceed after one approval, so two-person release (item 4.3) uses two environments in sequence, and covers only the pipeline's path, not the store's own interface (see the F6 guide). **Status.** Proposed.

### D-017 What starts the agent lane

**Decision.** The agent template runs when a maintainer labels an issue `agent`, or a collaborator comments `/agent`. **Reason.** Cost control only: the agent still runs at the level of everything it reads, as Paper 1 requires, because invoker checks do not establish context trust. **Status.** Proposed.

### D-018 The effect lane opens pull requests only

**Decision.** The effect lane turns an approved patch into a branch and a pull request; it never pushes to a protected branch. The merge then needs ordinary review. Comments and allow-listed labels are applied directly. **Reason.** Two endorsements for code (the environment approval and the merge review), one for low-risk effects. **Status.** Proposed.

### D-019 Using GitHub's `cache-mode`

**Decision.** Release, agent and effect jobs set `cache-mode: none`. **Reason.** GitHub's changelogs describe `cache-mode`, enforced with scoped cache tokens ([September 2026](https://github.blog/changelog/2026-09-10-control-github-actions-cache-access-with-cache-mode)), and a read-only cache default for untrusted triggers that use the default branch's cache scope, such as `pull_request_target`, `issue_comment` and `workflow_run` runs that follow a pull request from a fork ([June 2026](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers)). The June change ships to GitHub.com and GitHub with data residency; neither changelog says when either reaches GitHub Enterprise Server, where the checker's other cache rules still apply. **Status.** Proposed; recheck GitHub Enterprise Server before release.

### D-020 Inference proxy

**Decision.** Version 0.1 specifies the proxy's contract ([docs/inference-proxy.md](docs/inference-proxy.md)) and ships a stub agent that calls no model, so the lanes can be tested end to end. A reference proxy is planned for version 0.2. **Reason.** R3 and FR7 keep the model credential outside the agent job; a proxy is a server that needs its own design review. **Status.** Proposed. Not built in 0.2 or 0.3; the flagship plan first tests the proxies that other tools ship (docs/flagship.md, slice 2a.2).

### D-021 Checker severities

**Decision.** High: a documented attack path is open. Medium: a safeguard is missing. Low: hardening. CI fails on medium and above. **Status.** Proposed.

### D-022 Retired

This proposal is withdrawn at the maintainer's request. The identifier is reserved and will not be reused. **Status.** Retired, 2026-10-07.

### D-023 Plan scope of version 0.1

**Decision.** Version 0.1's agent and release templates need artifact attestations and environment reviewers, so for private repositories they need GitHub Enterprise Cloud. Version 0.1 says so plainly ([github-settings.md](docs/github-settings.md#plan-limits), [traceability.md](docs/traceability.md)) instead of offering weaker substitutes, and NFR3 is marked as not met for private repositories on other plans. **Planned.** A merge-review mode for the effect lane (the protected branch's review as the approval, recorded and checked) and a key-signing release template, both for studios on the Team plan. **Consequences.** On plans without environment reviewers, `release.min_approvals` must be 0, and the person's approval comes from the store (a person sets builds live, item 1.3). On GitHub Free, release branches in a private repository cannot be protected at all, so items 1.6, 2.2, 3.7 and 4.1 cannot be met there. **Reason.** The consistency review found that the earlier Team-plan advice could not work: `obaaf attest approval` refuses to sign without an environment approval. **Status.** Proposed.

### D-024 Releases build from tags and publish from the default branch

**Decision.** `obaaf-release.yml` builds and attests on a push of a protected `v*` tag. A separate `obaaf-publish.yml`, started by `workflow_run` and therefore run from the default branch, verifies the release before anyone approves it (the result goes to the run summary), waits for the `release` environment, verifies again with the approvals, and uploads. The verifier requires the released commit to be on the policy's protected branch (`release.branch`, default `main`), and blocks when it is not given the repository and the release commit to check this; `release.branch: ""` turns the check off for repositories that release from several branches. **Reason.** The specification's FR4 says releases start only from a protected branch, and the security review showed that a workflow run by a tag push uses the workflow file and policy from the tagged commit, so a tag on an unreviewed commit could switch the checks off. Running publication from the default branch, and checking ancestry, closes that path while keeping tag-based release builds, which game teams expect. **Status.** Proposed.

### D-025 Agent commits are checked from a baseline in the policy

**Decision.** `obaaf verify release` checks agent-authored commits from the policy's `agents.since` commit to the released commit, or the whole history when `agents.since` is not set. When the policy sets `agents.since`, a `--range` on the command line is refused, so the range cannot be narrowed outside the reviewed policy. A shallow clone is refused too. Maintainers move the baseline forward in a reviewed change to the policy, only to a commit whose release passed. **Reason.** The earlier range started at the previous `v*` tag, and the security review showed that tagging a blocked commit (for example a release candidate) dropped the bad commit out of the next range. A baseline that only a reviewed policy change can move has no such gap. **Cost.** Without a baseline, every agent commit in history is verified on every release. A signed "published" marker could replace the manual baseline later. **Status.** Proposed.

### D-026 The committed change must equal the approved proposal

**Decision.** `agents.require_exact_diff` defaults to true: the verifier blocks a release when an agent commit's change differs from the approved patch, or when a commit that changes files names a record with no patch. "Differs" is decided by applying the approved patch to the commit's parent in a temporary index and comparing the result with the commit, outside the records directory, so the same lines moved to another place with identical surroundings are caught (the second security review showed that comparing diff text without line numbers missed this). **Reason.** With the default off, an old valid record could accompany any change with only a warning (security review). **Consequence.** Maintainers merge agent pull requests unchanged and make follow-up changes in separate pull requests. **Status.** Proposed.

### D-027 Proposal checks read the patch with Git and fail closed

**Decision.** `obaaf proposal check` takes the touched paths from Git itself (`git apply --numstat`, forwards and in reverse, and `--summary`), compares them with its own strict parser, and refuses the patch when they disagree, when it contains anything but plain git-format file changes, renames, copies, binaries, symbolic links, submodules or unusual modes, or when it touches a protected path or any path under a name starting with `.` (unless allowed). With `--repo` it also applies the patch to a temporary index of the default branch and checks the result. Comments are refused if they contain `](`, `]:`, `<`, `//`, `www.`, URL schemes or email addresses. **Reason.** The security review found four patch forms (quoted octal names, quoted instruction files, and two kinds of old-style hunks) that reached protected files, and Markdown forms that slipped past the comment filter. **Cost.** Some harmless proposals are refused; a person can make those changes instead. **Status.** Proposed.

### D-028 The effect lane is split, and has its own commit identity

**Decision.** The effect lane has an `approve` job (the environment approval, `obaaf verify agent-run`, the proposal check, the approval record, with `id-token` but read-only contents) and an `apply` job (write access, no `id-token`), which checks the record's digest and applies the patch. Its commits use the identity `OBAAF effect lane <obaaf-effect-lane@noreply.invalid>`, which the policy lists in `agents.effect_identities`. **Reason.** No job should hold both a signing identity and write access while it handles agent output (security review), and commits that other workflows make as `github-actions[bot]` should not be mistaken for agent changes. **Status.** Proposed.

### D-029 Who may not approve an agent's change

**Decision.** An approval does not count if it comes from anyone who started or re-ran the agent run or the effect run, the principal who triggered the agent, or anyone who wrote one of the agent's inputs, such as the issue's author. **Reason.** Paper 1, R4 requires approval by someone other than the requester; the security review showed that the author of an issue, who wrote the agent's task, could otherwise approve its result. **Status.** Proposed.

### D-030 Checker strictness

**Decision.** A declared lane (`OBAAF_LANE` or the configuration) can move a job only into a lane with stricter rules, never out of the agent, effect, release or untrusted lane the checker infers. On pull requests, the pipeline check reads its configuration from the target branch. Ignore entries cannot match every file. Runner labels that are not standard GitHub-hosted labels are reported at medium (OBAAF-GHA-013). OBAAF-GHA-016 counts only a verification whose failure stops the upload, and reports a provenance-only check at medium. OBAAF-GHA-020 reports an egress policy that is only declared, or enforced by a monitor that runs only under a condition. OBAAF-GHA-021 needs both the record verification and the proposal check, and reports one alone at medium. Steps inside `parallel` groups are checked like other steps; a `background: true` verification does not count as a gate; a job whose `if:` uses `success()` in an `||`, or `always()`, `failure()` or `cancelled()`, is treated as able to run after the jobs it needs failed or were skipped; and a step the checker cannot read (no `run` or `uses`, and not a known step form) is an error. **Reason.** Each closes a gap the first or second security review demonstrated. **Consequence.** The installed templates keep one low finding (OBAAF-GHA-020) until egress is enforced. **Status.** Proposed.

### D-031 Code signing of game binaries is deferred

**Decision.** Version 0.1 signs attestations through Sigstore but does not sign the game binaries themselves (Windows Authenticode, Apple, Android). The publish workflow marks where a managed signing step goes: after verification, in a job that runs no build code, followed by an attestation of the signed files. FR11 and G5.2 are marked as partly met. **Reason.** Signing services differ by platform and need the pilot's studios to choose; the consistency review found the earlier claims overstated. **Status.** Proposed.

### D-032 Contributions after release

**Decision.** After public release, contributions need a Developer Certificate of Origin sign-off (`git commit -s`), and security reports get an acknowledgment within five working days (SECURITY.md). **Reason.** The DCO is a light-weight, common way to record the right to contribute; five working days is achievable for one maintainer. **Status.** Proposed.

### D-034 Jenkinsfiles are read by a syntax-only parser in Python

**Decision.** `obaaf check` reads Jenkinsfiles with its own Groovy tokenizer and parser, written in Python, instead of the pinned JVM syntax helper the Jenkins integration design proposed. It never compiles, loads classes or evaluates expressions, and stops at 1 MiB, 400,000 tokens, 64 levels of nesting or 10 seconds per file. **Reason.** The design's requirement is that analysis runs no Groovy and has bounded failure; a JVM helper meets it only with a separately packaged runtime, image digest and dependency review, while the Python parser ships inside the existing package and has no dependencies. It is a structural reader for the constructs Jenkins pipelines use, not a full Groovy grammar: statements it cannot read are recorded as not analyzed and make the file's coverage unknown. The Declarative linter of a disposable controller remains the right compatibility oracle for the fixtures. **Consequence.** Groovy syntax the parser does not know lowers coverage instead of crashing; the parser was run over 512 public pipeline files with no file-level failure. **Status.** Proposed.

### D-035 The Jenkins adapter sits beside the workflow checker

**Decision.** The Jenkins rules live in `src/obaaf/checker/jenkins/` and share the catalog, findings, ignores, reports and CLI with the workflow checker, without first extracting platform-neutral contracts under `src/obaaf/ci/`. **Reason.** Extracting contracts first would touch every workflow rule before any Jenkins rule exists, and the design itself requires that GitHub Actions behavior be preserved; adding beside it leaves the 26 workflow and repository rules and their tests unchanged. **Consequence.** The contracts (CiContext, PipelineModel and the rest) are extracted when the evidence and admission phases need a shared model. **Status.** Proposed.

### D-036 Jenkins results are advisory, and unknowns are coverage, not findings

**Decision.** The OBAAF-JEN rules report what a Jenkinsfile shows. What only the controller can show (authorization, build authorization, agent placement, library trust and version overrides, Replay, credential scopes, network policy), and code the file does not contain (shared-library steps, `load`, generated parallel branches), is reported as a coverage unknown per rule, never as a pass. Unknowns do not change the exit status in advisory mode; the report says that exit 0 is not a conformance decision. Generic file transfer (`scp`, `rsync`, `sshPublisher`, `ftpPublisher`) is not treated as publishing. **Reason.** The design requires that missing evidence never appear as an empty finding list, and that enforcement come only with authenticated controller evidence. Counting generic transfer as publishing produced high findings on pipelines that only copy test reports. **Consequence.** A clean Jenkins report means nothing was found in the file. Enforcement, controller inventory and signed Jenkins run evidence are later phases. **Status.** Proposed.

### D-037 The Jenkins release lane signs with a key service and reads approvals from the controller

**Decision.** On Jenkins, the release lane is two jobs: a build job in a multibranch project that discovers only tags and builds them with no credentials, and a publish job, read only from the default branch and taking no parameters, that finds the tag build that started it from its own start cause, resolves the tag through the SCM, copies that build's artifacts, signs SLSA provenance and the build record as DSSE envelopes through a key service (`obaaf dsse prepare` and `assemble`), and runs `obaaf verify release` before and after a named approver. The verifier reads both builds' JSON from the controller and ties them together: the publishing build was started by exactly one build, which is the one passed as the producing build, is the tag build `release.jenkins_project/<tag>` for the tag in the signed build record, and checked out the release commit (`lastBuiltRevision`). It counts approvals (`ApproverAction`) only from people in `release.approvers` who started neither build, blocks Replays, stage restarts, builds started by hand and causes it cannot classify, and fails closed when either build's JSON is missing. Run identity in Jenkins records comes from the build's environment and is marked self-reported. **Reason.** Jenkins has no per-job identity the public Sigstore service accepts; credentials scoped to a multibranch project reach every branch and pull request; a branch can carry a tag-like name and its own Jenkinsfile; administrators can approve any input step; and the controller, not the pipeline, is where approvals and start causes are recorded. A parameterized publish job would trust whoever started it to name the right build. **Consequence.** The lane's guarantees depend on controller settings OBAAF cannot see yet (who may Replay or configure the publish job, credential scope, which jobs use the release agents) and on the tag's Jenkinsfile; docs/jenkins.md lists them. Signed controller evidence comes with the inventory phase. **Status.** Proposed.

### D-039 A workflow job is in every lane it qualifies for, and a declaration only adds a lane

**Decision.** The workflow checker decides each lane on its own (agent, effect, release, untrusted) and applies the rules of every lane a job is in. Being in one lane never keeps a job out of another: a job that uses a release environment is a release job whatever can start it, and a job that only pull requests can start is an untrusted job whatever else it does. `OBAAF_LANE` and a `lanes:` entry add a lane to those and never remove one; every declaration for a job counts, whichever file it is in. A declaration that does nothing (a value that is not a lane, `OBAAF_LANE` on a step, a `lanes:` entry for a job, stage or file that was not found) is reported in the notes, not refused: an adopter's configuration that carries one today keeps working, and the note says what to fix. `lanes:` that is neither a mapping nor empty is a configuration error. `--lanes` and the `lanes()` function still give one lane per job, the first in the order agent, effect, release, untrusted, and name the others in the reason. Proposed in the flagship work (slice 2d.2a). The Jenkins analyser keeps its own code for what a stage does, decided step by step, and follows the same rule for declarations: every lane declared for a step counts (in `lanes:` for the file, the stage or a stage it is nested in, and with `OBAAF_LANE` anywhere on the way to the step), and none hides another.

**Reason.** With one lane per job, chosen in a fixed order, a job that did two things was checked for one, and a declaration that disagreed with the inferred lane was dropped. A reviewer showed two cases (an agent job that publishes got no release rules; a declared agent job that publishes got no agent rules). More of the same class turned up in the fix and in a second review of it; the changelog lists them all, and one of them let a declaration remove a finding. SECURITY.md counts a false negative as a vulnerability. Baselines key on a finding's message, and an entry that no longer matches fails the check, so what is shown is kept as it was wherever a job's lanes did not change: the single displayed lane, a declaration as the reason when a lane is both declared and inferred, and OBAAF-GHA-017 on the first publishing job that is only a release job. The messages that do change without a change of lanes are for a declaration that used to be ignored and is now read (another case or spacing, a declaration behind the first one, a `lanes:` entry for a workflow checked on its own); reading it is the point. **Status.** Proposed, 2026-11-11.

### D-040 The settings audit only reads, and records what it could not read

**Decision.** `obaaf audit` reads repository settings through GitHub's REST API with GET requests only; the client has no other verb. It works with whatever access the caller's token has, and with none on a public repository. It never creates a token and never asks for more than read access: the two things GitHub shows only to a caller who could also change them (who may bypass a ruleset, and Actions policies) are asked for when a token is given and are otherwise reported as not read. Every setting the audit covers is in its snapshot as read, partly read, not read (with a reason code, GitHub's stated requirement and GitHub's own error) or not applicable; none is ever left out. An answer that does not have the shape GitHub documents is recorded as not read, and a field whose absence could pass for "none" must be present. Where GitHub's reference leaves a reading open, the audit takes the one that cannot turn "unknown" into "fine": an empty bypass list is never recorded as "nobody may bypass"; a 404 from classic branch protection counts as "no protection" only with GitHub's message "Branch not protected"; an environment whose answer lacks the branch policy field is not taken to allow every branch; and a section missing from a classic branch protection is recorded as not required, the reading that reports less protection. The audit covers only settings that the repository's own workflows depend on. The snapshot keeps the names of secrets, the logins and team names that the settings themselves name (environment reviewers, classic protection's push and review-bypass lists), and counts of collaborators; never a token, a secret's value, or the list of collaborators. A snapshot file is checked in full before it is used, because a committed one can be edited in a pull request. Proposed in the flagship work (slice 2b.1 of [the plan](docs/flagship.md); plan decision F-23). This first part applies no rule.

**Reason.** The first adopter's incidents were all settings (an environment open to every branch, an administrator bypass on the ruleset, approvals nobody could give, one required check of eleven, an Actions policy that blocked a trigger), and `obaaf check` reads none of them. A tool that reads settings with a maintainer's token must not be able to change them, and a tool that reports on settings must not let what it could not see pass as clean: the tools compared in [the landscape](docs/landscape.md) need an owner's token for full results, and the adopter's own gate had answered "0 new" while seeing nothing of this. GitHub answers 404 for what a caller may not see, omits fields by permission, and documents neither what a caller without write access gets in place of a bypass list nor the "Branch not protected" message, so each of those is read the cautious way until a run with an administrator's token settles it. The cost is stated in the guide: until then the audit can show that someone may bypass a ruleset, and cannot show that nobody may. **Status.** Accepted, 2026-11-12.

### D-041 An acceptance needs an owner, a reason and an expiry date, and a finding is identified by what it is, not by its message

**Decision.** A finding is in one of four states: new, accepted, fixed (every control that clears it was verified by the checker) or cannot tell (a control could not be read). Only accepted and fixed findings pass a gate. An acceptance, whether an `ignore` entry or a baseline entry, must name an owner (`@user`, `@org/team` or an e-mail address), give a reason, and carry an expiry date that has not passed and is at most 366 days ahead; an entry that does not accepts nothing, and its finding counts as new. Baselines are written in a new format, `obaaf-baseline/v0.2`, in which an entry is the finding's rule, file, job, step, case (`kind`) and values (`facts`) with the severity it was accepted at and the three fields above, and has no fingerprint and no message. Workflow and repository rules build each message from a template and named values, and those values are the finding's facts, so what a message says about a finding is in what identifies it. Line and column numbers are the exception everywhere: they are shown and never identify a finding. Two facts are text: why a job is an agent job (OBAAF-GHA-003), and a digest of the line a hidden character is on (OBAAF-INS-001). A reason must have at least four letters or digits. The agent reason tells apart what the checker's text tells apart and no more: another command in a step of the same name, or another agent in a job declared an agent job, is the same finding. `obaaf-baseline/v0.1` files are still read and accept nothing until `obaaf baseline migrate` converts them with an owner, a reason and a date. `--write-baseline` keeps valid entries as they are and needs `--owner`, `--reason` and `--expires` for anything newly accepted. Jenkins findings keep their message as their identity. Proposed in the flagship work (slice 2a.1).

**Reason.** The first adopter's baseline accepted all 38 of its findings in a file that named nobody, gave no reason and never expired, and was regenerated three times in one day to add more: a gate whose answer is always "accept" checks nothing. An expiry date with no upper limit is a permanent acceptance with a date on it, hence the year. A v0.1 entry tied an acceptance to the wording of a message, which is why slice 2d.2a had to keep old wording in three places, and it carried a fingerprint that had to be checked against the text beside it. Old-format baselines and owner-less ignore entries could have been honoured with a warning; they are not, because a warning in a CI log is read by nobody and the acceptances they hold are exactly the ones this decision is about. The cost is that an adopter who upgrades has a red gate until they run one command and add one line per ignore entry.

**Consequence.** Upgrading past 0.3.0 turns a gate red for any repository with a baseline or an ignore entry, until the baseline is migrated and each ignore entry has an owner. Expectrail is pinned to a commit and is not affected until it moves its pin. The state "fixed" exists and no rule produces it yet; "cannot tell" is produced since slice 2a.2 (D-042). A lane declaration that does nothing stays a note in this change; it is to become a finding with its own rule id, so that it can fail a gate or be accepted like any other (flagship decision F-40). **Status.** Accepted, 2026-11-12.

### D-042 A finding names the controls that clear it, and a control is verified only from what the checker read

**Decision.** OBAAF-GHA-005 (a secret in an agent job) and OBAAF-GHA-020 (no egress restriction) list the controls that would clear them, each with a verdict: verified, not met or cannot tell. OBAAF-GHA-005 needs four: the job's secrets are listed in `protected_secrets` and the job declares the environment named there; the secrets are stored only in that environment and only protected branches may use it; no pull request, issue or comment can start the job or supply its code or text; and a recognised control limits the job's network access to an allow-list. OBAAF-GHA-020 needs the last one. A verdict is "verified" only for something the checker read. The environment's settings are not read by `obaaf check`, so that control is always "cannot tell"; and no egress control is credited yet, so a blocking Harden-Runner step with no condition, which used to clear OBAAF-GHA-020, is "cannot tell" as the job's first step and "not met" anywhere else, and a baseline entry that accepts the first is for the workflow file as it stood, byte for byte. A proxy that holds the model key is not counted as a control. Which events can start a job is read from the tokens of its `if:`, where it was matched as text, and input names under `with:` are read with A to Z in either case, as GitHub reads them.

**Reason.** A finding that can only be accepted is noise, and the first adopter accepted the same two findings on all 19 of its agent jobs. Agent control R2 gives an agent job no secrets and R3 keeps the model key in a proxy that OBAAF never built, so in practice every agent job holds a key; the controls are the conditions under which that is defensible, and they are the ones the adopter already half meets. The old test for an egress control passed any blocking Harden-Runner step whatever its version and wherever it stood, including after the agent, which is a pass on something nobody read. The two key proxies that exist were not run (the session that built this had no Docker), and crediting one untested would be the same mistake. The event reading was changed in the same change because a "verified" verdict rested on it and text that only looked like an event test could remove an event.

**Consequence.** Neither finding can be cleared yet: the settings and a verified egress control come with the settings audit's rules and the egress action. Until then the report says what each agent job has and lacks, and the finding is accepted or fails. A workflow that relied on Harden-Runner to pass OBAAF-GHA-020 now has a finding to accept. Workflows whose `if:` only looked like an event test get the findings they were missing. **Status.** Accepted, 2026-11-12.

### D-043 Every report begins with the accepted risk, and SARIF says an acceptance in its message as well as in a suppression

**Decision.** The text, JSON and SARIF reports of `obaaf check` begin with the accepted risk: how many findings are accepted, at what severity, by which owner, and the first date on which an acceptance runs out. Acceptances that run out within 30 days are listed as expiring soon (`--expiry-warning DAYS`; 0 turns the list off), and the list never changes the exit status. The text report keeps the lines it had, below the new ones, with four differences: a finding ignored by configuration is listed with its owner; the migrate command it prints repeats the `--config` and `--platform` the check was given; where a file's path heads its findings it is quoted unless, with characters that do not print written as escapes, it is made only of visible ASCII characters, so that a directory cannot be named like a line of the report and pass for one; and the Jenkins coverage lines show a character that does not print as an escape. JSON keeps every field and adds `acceptedRisk`, and `daysLeft` in a finding's `acceptance`. Every acceptance in a report is judged on one day, read once while the check runs. In SARIF an accepted finding is a result with a suppression whose status is `accepted`, the accepted risk is in the run's properties and its first notification, errors and notes are notifications, and the message of a result also says in words who accepted it and until when, why an entry does not count, and what was established about its controls.

**Reason.** The first adopter's gate was green with 38 accepted findings and its log said "0 new"; the count of accepted findings was one line near the end and named nobody. An acceptance has had an owner and an expiry date since D-041, and nothing showed them together or warned before a date passed, so a gate went red on the day with no notice. For SARIF, the standard's way to say "accepted" is a suppression, and that is what other readers of SARIF expect. GitHub's page on the SARIF fields code scanning uses (read on 2026-11-12) does not list suppressions, notifications or the property bags of a run or a result, and says fields not listed are ignored, so there the message is the only place a reader can see that a finding was accepted. Saying it in both places costs a longer message.

**Consequence.** A script that reads the first line of the text report, or matches the `ignored:` lines, sees different text; the line `Baseline: N finding(s) accepted by the baseline, M new.` is unchanged. A consumer of SARIF that hides suppressed results now hides findings accepted by a baseline, which it showed before. In GitHub code scanning an accepted finding stays an open alert, and the accepted-risk total, the expiry warning and a file the checker could not read are not shown there, going by GitHub's page; no upload was made to check it. A file that could not be read still exits 1 whatever `--fail-on` says, which is how it shows in CI. For code scanning to show an unread file or an ignored lane declaration, each would have to be a result with a rule id; slice 2a.4 of the flagship plan does that for lane declarations, and nothing is planned yet for an unread file. A finding's state or the exit status can differ from before in two cases. A command that ended in a traceback because standard output was ASCII exited 1, and now exits as its findings decide. And in a check that crosses midnight a baseline entry is judged on the day the check read: one whose last day is that day is accepted, and one dated 367 days after it is refused, where each was the other way round when the baseline was applied after midnight. `--write-baseline` and `obaaf baseline migrate` still read the clock again when they decide what to write. **Status.** Accepted, 2026-11-12.

### D-044 A lane declaration that does nothing is a finding, high unless nothing can be missing

**Decision.** A lane declaration that changes nothing is reported as a finding with a rule of its own, `OBAAF-CFG-001`, the first of a family (`OBAAF-CFG`) for the checker's own configuration. It covers what the notes listed since D-039: `OBAAF_LANE` set to a value that is not a lane, `OBAAF_LANE` in a step's, container's or service's `env`, a Jenkinsfile's `OBAAF_LANE` that is not a lane or is computed when the build runs, and a `lanes:` entry whose value is not a lane or that names a job, a stage or a file that is not there. It also covers two the notes missed, the variable under another spelling in a workflow (`obaaf_lane`) and `OBAAF_LANE` in the `env` of a `parallel` group, and reports a `lanes:` key that is not text also when one file is checked on its own. One thing the notes listed is not a finding: an entry for a Jenkins stage that is in the file and holds no step. The finding is reported in the file the declaration is written in, the configuration file included. Its severity is high, and low where no rule can be missing because of it: it names `trusted`; it is written where it is not read, or under another spelling, and names a lane the job is in anyway; or it is an entry for a Jenkins stage that is not there and names a lane that changes nothing on a stage. It is identified by where it is written (the file, the job and step, the names of the stages a Jenkinsfile's declaration reaches), the `lanes:` key, the variable's name and the declared value, never by its line or wording; two Jenkins stages with one label (the name, with the stages it is nested in) are one stage, as everywhere in the Jenkins reader. It is accepted by a baseline entry, with an owner, a reason and an expiry date (D-041). It cannot be accepted by an `ignore` entry: one that names the rule is a configuration error. The notes no longer list these declarations; `--lanes`, which reports no findings, still prints them.

**Reason.** Declaring which jobs are agent jobs is the part of OBAAF that other tools do not have, and the first adopter declares 17 of its 19 agent jobs by hand because the checker does not recognise them. A declaration that silently does nothing removes the agent rules from the job it was written for, and a note that changes no exit code leaves the gate green: the misspelling `OBAAF_LANE: agnet` passed. A separate state or an error that stops the check would each need machinery of its own and would have broken the first adopter's configuration with no way to accept it; a finding uses the lifecycle that exists. High, not medium: the rules' own scale would call a missing safeguard medium, but the safeguard missing here is the checker's reading of the job, and what goes unreported includes high-severity rules, so a gate at `--fail-on high` would otherwise pass a job whose agent rules never ran. Low where nothing is lost, so that a stale `trusted` entry does not read as an open attack path. No `ignore` entry, because an `ignore` entry accepts a rule in a file whatever the finding says, and for this rule that is a standing permission for any declaration in the file to do nothing: the reviewer of the change accepted one entry that way, renamed an agent job, misspelt its lane, and the check passed. Every rule's `ignore` entries are that broad; this is the rule whose findings stand for other rules not running.

**Consequence.** A repository with such a declaration fails a gate at the default `--fail-on medium`, where it passed. Accepting one takes a baseline, so a repository that has none has to start one or correct the declaration. The first adopter has such a declaration on purpose: it uses `lanes:` as its own inventory and gives one job the value `probe`, which its own audit script reads. On upgrade that is one high finding, to be accepted in its baseline with a reason or replaced by `trusted` and a list kept elsewhere; OBAAF has no way to carry a label of the adopter's own on a job, and none is planned. OBAAF's own example configuration declared a lane for a file its templates do not install, and `obaaf templates install` writes that example as the live configuration; its examples are comments now, and a repository that installed it earlier has the finding. The configuration file can appear in a report as a file with findings. A reader of the JSON `notes` no longer sees these declarations there. Still unreported: in a Jenkinsfile, the variable under another spelling and an assignment to `env.OBAAF_LANE`, which the checker does not read as a declaration; and a second configuration file that the first one hides. **Status.** Accepted, 2026-11-13.

### D-045 A settings rule compares a setting with what a workflow uses, and answers "cannot tell" when it could not read one

**Decision.** `obaaf audit` applies rules, `OBAAF-SET-001` to `OBAAF-SET-015`, a family of their own beside `OBAAF-GHA` and `OBAAF-CFG`. Twelve compare a setting in the snapshot with something the repository's workflow files use or assume, read from a clone with the checker's parser. Three read settings only, who may bypass a branch's rules, whether its required approvals can be given and whether a workflow can give one, because the checks and reviews they concern are what every workflow's result feeds (and, for the third, because a workflow on any branch can ask for the token). A rule's result is about one thing (an environment, a branch, a job) and is a finding with a severity or "cannot tell": the second when a setting or a workflow file the rule needs was not read, was partly read, or is not in a form the rule understands. A rule with neither says what it compared or why it had nothing to compare; nothing is called a pass. A rule that fails while running is "cannot tell" and the command exits 1. The command exits 1 on a finding at or above `--fail-on`, `medium` by default, as `obaaf check` does; "cannot tell" fails only with `--fail-on-cannot-tell`. The workflow files are taken from the directory given when it is the top level of a clone whose origin remote names the audited repository, or when the directory is named on the command line, and otherwise not at all. The rules are defined in `src/obaaf/audit/rules.py`, not in the checker's `rules.yaml`, and a settings finding cannot be accepted: there is no baseline and no `ignore` for the audit. `--format json` becomes a report that holds the snapshot, where it was the snapshot; with `--expected` (D-046) the comparison is in the same document under `drift`, where it was a document of its own; it keeps its own `format` field, `obaaf-settings-drift/v0.1`. The drift schedule (the optional template and this repository's own job) runs with `--fail-on never`, so that it fails on drift and not on a rule's finding.

**Reason.** Reading settings and judging nothing left the adopter where it was: every incident of its first two days was a setting, and the audit could describe each and say nothing about it. Comparing with the workflows keeps the audit from becoming a second organisation checklist beside tools that do that with far more users (plan decision F-23), and it is what makes a finding specific: not "an environment has no branch limit" but "this job names it". "Cannot tell" as a result of its own follows D-040: with no token GitHub withholds something every rule reads, and a report that listed only findings would read as clean. It does not fail the command by default because then no run without an administrator's token could ever succeed. A default of `medium` matches `obaaf check`; the command is in no release, so no released behaviour changes. Acceptances are left out on purpose for now: the first adopter's baseline held 38 findings that could only ever be accepted, and every settings finding names a change that clears it, a setting or a line of a workflow, which the next run verifies. Whether the audit should share the checker's acceptances is open. The rules stay out of `rules.yaml` because that file belongs to the checker's shared code, which slices change one at a time, and because the catalogue's requirement mapping for these rules has not been done.

**Consequence.** A workflow that runs `obaaf audit` from a commit after 0.3.0 can now fail where it exited 0, and a script that read its JSON finds the snapshot one level down. A finding someone decides to live with (a bypass kept for emergencies is one) can only be kept out of the exit status by a higher `--fail-on`, which also hides every other finding of that severity; that will need an answer before the audit is a gate anyone keeps. Three of the six incidents' rules need settings that only an administrator's token reads and a fourth needs a count a workflow's token was given once; the audit has never been run with an administrator's token, so those rules have met only answers written by hand, and the two about Actions policies read a form no real policy has been checked against. Several statements about what GitHub does, in the rules' own texts, rest on the author's knowledge and not on a page read on a date; the guide lists them. The rules are not in the catalogue, so `obaaf catalog` and the generated rule pages do not list them; the guide's table does, and a test keeps each rule's row, title and severity in it. **Status.** Accepted, 2026-11-13.

### D-046 Drift is any difference from a committed snapshot, and a setting that could not be compared fails

**Decision.** `obaaf audit --expected FILE` compares the `settings` part of a committed settings snapshot with the settings read now (or with another snapshot file) and reports each part that differs (a ruleset, an environment, a branch, a secret's name, a field) as one finding of `OBAAF-DRIFT-001`, a rule of the settings audit, not of the checker's catalogue. Any difference counts, tighter or looser, and has no severity; it is resolved by putting the setting back or committing a new snapshot, not by an acceptance. Lists are compared as multisets and values as JSON. The command exits 1 when anything differs, when a setting or a part of one was read by one side and not by the other ("not compared", in both directions), and when nothing was compared; only what neither side read in full is "not covered" and does not fail (of an environment both read in part, the rest is compared). The committed file must be of the same repository and API address, may not give two parts one key, and must hold data for exactly the branches it lists (exit 2 otherwise). The schedule is an optional template that `obaaf templates install` does not install. (D-045 is the settings rules of slice 2b.2.)

**Reason.** The settings audit exists because the first adopter's incidents were settings (D-040). A setting changes without any file changing, so only a comparison with a recorded state notices it. Judging whether a change is a weakening is the settings rules' job (2b.2); the snapshot is the reviewed record of what the settings are, so any departure means the record or the setting is wrong. A drift check that could not read a setting has not shown that it did not change, and the rule that "cannot tell" is never "pass" (D-042) applies to its exit code too, which a scheduled job is read by. It has to apply in both directions: the first review of the slice showed that a part the committed snapshot did not read (a bypass list GitHub sent empty, an environment whose branch and tag patterns failed to load, a "problem" written into the file by hand) hid every later change in it while the check passed. The template is optional because it fails until a snapshot is committed, and the other templates are installed together.

**Consequence.** A job whose token reads less, or more, than the token that took the committed snapshot fails until the snapshot is taken again with the job's access. Adding the first bypass actor to a ruleset, or removing the last, shows as "not compared", because GitHub's empty bypass list is never believed (D-040). A job that uses the workflow's own token never watches what that token cannot read: the bypass lists, classic branch protection, the names of secrets and the Actions settings. Whoever can change the committed file decides what counts as drift, so it needs code-owner review. Nothing changes for a command line without `--expected`. Proposed by the flagship agent in slice 2b.3. **Status.** Accepted, 2026-11-13.

### D-047 The egress control confines one command under a pinned AWF, narrows its writes to a scratch copy, and fails closed

**Decision.** `actions/egress` runs one command under the Agent Workflow Firewall at one version (binary by SHA-256, each image by digest) in AWF's default network-isolation mode, from a command line the action builds itself. The allow-list is plain host names; an entry with a wildcard, an address, a port, a scheme or a single label is refused. The command gets no environment from the runner except variables the workflow names, and variables that change a shell, a loader or the network cannot be named. It can write only to a scratch directory under `/tmp` that holds a copy of the workspace, its own home and its own `TMPDIR` (AWF's `filesystem.allowWrite`), and to AWF's own directories under `RUNNER_TEMP`, which the action deletes after the run (failing the step if it cannot); the runner's workspace, home, `/tmp` and file-command files are read-only or absent inside. Model keys and GitHub tokens, which AWF withholds from the command for its API proxy, are refused rather than dropped, until the API proxy is tested. A probe inside the sandbox must fail to get out before the command starts, or the command does not run and the step fails with status 3; workflow commands are stopped while the command's output is printed; and the step fails if the runner's file-command files changed. Whether it holds is decided by escape tests in CI judged from a packet capture outside the sandbox, with each attempt first made outside it as a control.

**Reason.** OBAAF-GHA-020 had no fix an adopter could apply (the first adopter accepted it 19 times), and decision F-20 chose to wrap AWF rather than write a firewall. Running AWF with its defaults left the workspace, the host's `/tmp` and the tool directories of the home directory writable, which is enough for a confined command to plant a program that a later step or post step runs with the full network; narrowing the writes is what turns a wrapper into a control for the rest of the job. A fixed command line keeps the options AWF itself says remove the protection out of an adopter's reach, and the probe turns a sandbox that did not start, or did not hold, into a failure instead of an unconfined run.

**Consequence.** An agent that writes to its workspace now writes to a copy; the workflow must collect the result from the `workspace` output and treat it as data. A workspace whose `.git/config` holds a token is refused. An agent that reads a model key from its environment cannot run under the action until AWF's API proxy is tested and supported (plan slice 2c.4). IPv6 could not be tested on hosted runners, which had no IPv6 route. The control confines one command: it does not cover agents that are actions, other steps or post steps, and it does not stop data sent to a listed host, a different `Host` behind a listed name, or data in a host name the command asks the proxy for, which the escape tests showed leaving the runner in a DNS query although the proxy refused the request. Changing the pinned AWF version is a change to the control and must pass the escape tests. Proposed by the flagship agent in slice 2c.2. **Status.** Accepted, 2026-11-13.

### D-048 A pull-request rule's parameters are each read or named, and one the rules do not know makes them "cannot tell"

**Decision.** The two settings rules about approvals, `OBAAF-SET-005` and `OBAAF-SET-013`, place every parameter of a ruleset's `pull_request` rule in one of two lists in the code: read by the rules, or about neither how many approvals a branch needs nor who can give them. The lists are the nine parameters of GitHub's REST reference for rulesets, read on 2026-11-13. A parameter in neither list, or a known one in a form the reference does not give (an object with a field the reference does not list included), makes `OBAAF-SET-005` "cannot tell" for its branch, and `OBAAF-SET-013` too where workflows may approve pull requests, naming it and its value, whatever the value, unless the count alone is a finding; a "cannot tell" given for another reason, and a finding by count, name it as well. The parameters read are taken as GitHub's pages describe them, and where a page leaves the effect open the rule says "cannot tell": `require_last_push_approval` where no approval is counted, and a team that `required_reviewers` asks for an approval (who is in it is not read). `require_extra_approval_for_unattributed_changes` on a ruleset that counts zero does nothing, as GitHub's page says of "the ruleset"; on one that counts N, a pull request Copilot opens without a person needs N + 1, asked of "people with write access" in the page's example, which the accounts with write access can give when the count alone is no finding, because none of them is its author. `OBAAF-SET-005` is "cannot tell" for a branch that requires a code owner's review unless its count alone is a finding, because who the code owners are is not read.

**Reason.** Slice 2b.4 found the first adopter's ruleset carrying an approval parameter that no rule read, and the report said nothing of it: "not read" passed as "nothing wrong", which the settings audit exists to prevent (D-040, D-045). Listing the known parameters is what lets a new one be noticed; reading an unknown one as adding nothing would be a pass on something the audit has not looked at. "Cannot tell" whatever the value, because the meaning of a value of a parameter nobody has read is not known either. The code-owner change is the same fault in a parameter the rule already had in hand: a branch whose only code owner is the one person who writes the changes cannot merge without a bypass, and the rule said "no finding".

**Consequence.** A new parameter from GitHub turns the rules into "cannot tell" for a branch whose rule carries it, where neither the count alone nor the workflows' permission to approve already decides the answer, until OBAAF places it, which takes a release. A repository that requires a code owner's review gets "cannot tell" from `OBAAF-SET-005` where it got "no finding", for as long as the CODEOWNERS file is not read. The reading of `require_extra_approval_for_unattributed_changes` rests on GitHub's pages, which speak only of pull requests Copilot opens; nobody here has run it. Classic branch protection is read into a fixed form, so a field GitHub adds there is dropped before the rules see it, which this decision does not change. Whether Copilot may approve pull requests, which GitHub's changelog of 2026-09-01 says can count towards the required approvals, is not read. Proposed by the flagship agent in slice 2b.5. **Status.** Accepted, 2026-11-13.

### D-049 A ruleset's rule types and classic protection's fields are each read or named, and one the rules do not know makes them "cannot tell"

**Decision.** The settings rules that read a branch's requirements (`OBAAF-SET-004` to `OBAAF-SET-008` and `OBAAF-SET-013`) place each of the 25 rule types of GitHub's REST reference for rulesets, read on 2026-11-13, in one of six groups in the code: the two they read (`required_status_checks`, `pull_request`); seven that make a merge wait for a result workflows, tools or deployments give (`merge_queue`, `required_deployments`, `workflows`, `code_scanning`, `code_quality`, `code_coverage`, `license_compliance_scanning`), which `OBAAF-SET-004` counts as something a bypass skips, `OBAAF-SET-006` answers "cannot tell" for (`OBAAF-SET-007` for the merge queue) and a finding of `OBAAF-SET-008` names (all but the merge queue); `update`, which `OBAAF-SET-005` names as something it cannot weigh; `copilot_code_review`, which a finding of `OBAAF-SET-005` names; and fourteen that neither ask for a check or a review nor decide who may merge. A type in none of the groups makes those rules "cannot tell" for its branch, naming it, whatever its parameters, wherever they would otherwise answer from the branch's requirements (`OBAAF-SET-013` only where workflows may approve pull requests, `OBAAF-SET-004` only for a ruleset someone may bypass or whose bypass list was not read), with a finding by count staying a finding and naming it. The reader keeps every field of classic branch protection that the reference's two examples and the update's body do not show (inside an entry of the required checks included), and every known one in another form that the reader would otherwise record as not known and pass over (a known object that is something other than an object or null, a flag's `enabled` that is not true or false or is missing; some other forms make the whole setting unread instead), with its value, under `other_fields` in the snapshot, written only when there is one; such a field makes the same rules "cannot tell" (one about the checks for the check rules, one about the reviews for the approval rules, any other for both, and `OBAAF-SET-004` for all). A parameter of a ruleset's `required_status_checks` rule, or a field of one of its checks, outside the reference makes the check rules "cannot tell". Classic push restrictions and a locked branch are named by `OBAAF-SET-005` as `update` is. A "cannot tell" about how many approvals or which checks a branch requires names what could not be read.

**Reason.** The same fault as D-048, one level up: a rule type or a field nobody has read was read as asking for nothing, so "not read" passed as "nothing wrong" (D-040, D-045). Listing what is known is what lets a new one be noticed. The seven result-waiting types are named rather than left out because each can block a merge or be skipped by a bypass, and what gives their result is not something the audit reads. Keeping a classic field's value, not only its name, lets drift (D-046) see it change. Writing `other_fields` only when there is one keeps every snapshot taken before this decision valid and equal to one taken now of the same settings.

**Consequence.** A new rule type or classic field from GitHub turns those rules into "cannot tell" for the branch that carries it until OBAAF places it, which takes a release. Repositories with a merge queue, required deployments, required workflows, code scanning, code quality, coverage or licence compliance rules get a "cannot tell" from `OBAAF-SET-006` or `OBAAF-SET-007` for each, for as long as the audit does not compare them with the workflow files; and a bypass of a ruleset whose only gate is one of four of them (deployments, code quality, coverage, licence compliance) is now a finding of `OBAAF-SET-004`. A snapshot with `other_fields` is refused by a version older than this one; a snapshot taken before it, compared with one taken after, shows `other_fields` as added where GitHub's answer has such a field, which may be a field it sent all along. No real answer for classic protection has been read, so which fields GitHub really sends beyond its examples is not known. Proposed by the flagship agent in slice 2b.6. **Status.** Accepted, 2026-11-13.

### D-051 The egress control gives AWF's proxy a resolver that answers only listed names, and gives model keys to AWF's API proxy only

**Decision.** `actions/egress` starts a resolver of its own on the runner for each run, on the address of Docker's `docker0` bridge, and gives it to AWF with `--dns-servers`. The resolver forwards a query to the runner's own resolver only when its one question, in class IN, names a host the allow-list covers or exactly the API host of a model key given, every label being letters, digits, hyphens or underscores and nothing else; what it forwards is rebuilt from the query's ID, its recursion flag and that question. Every other query is answered `REFUSED` (or `FORMERR`) on the runner. It is started with `sudo` to bind port 53, then runs as `nobody`, logs what it allowed and refused outside the scratch directory, and stops when the step does. Before the command starts, the action checks that it refuses the probe's unlisted name and answers the first listed one; if not, or if it stops before the command ends, the step fails with status 3. The escape tests assert that a name asked of the proxy (over HTTPS and over plain HTTP, the proxy named explicitly) reaches the resolver and is refused there without leaving the runner, that a name the command looks up itself does not leave the runner either (it goes to Docker's resolver, not this one), and fail if any unlisted name the attempts use leaves the runner in a DNS query. A new input, `model-keys`, takes `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` from the step's environment and puts them in AWF's environment, from which AWF gives them to its API proxy sidecar; the command gets AWF's base URLs and placeholders, never the keys. AWF's policy for the providers' hosted web tools is set to `enabled: false` on every run; by AWF's source, it applies to HTTP requests whose body AWF's proxy parses as JSON, not to WebSocket upgrades. Other model keys and GitHub tokens stay refused under both inputs. This decision amends D-047, which refused all model keys, and D-050 where it ties a credential given to the confined step to this slice: such a step stays "cannot tell", now because the checker does not yet read `model-keys` or tell a key given to AWF's API proxy from one passed to the command (plan slice 2c.5), not because the DNS channel is open or model keys are refused.

**Reason.** Slice 2c.2 showed a refused name leaving the runner in a DNS query, a channel for data out of the sandbox. AWF's proxy resolves a name to test an access rule of type `dst` placed ahead of the rule that refuses unlisted names, and neither that order nor the API proxy can be changed from outside AWF in its default mode; choosing the resolver it uses can. A resolver that answers only listed names closes the channel without changing AWF, and it fails closed: if it stops, nothing resolves. Labels limited to plain characters stop a label holding a dot from passing for a listed name while being a name under another domain. Model keys: the first adopter's 19 agent jobs each hold a model key, so an egress control that refused them could not be used by any of them; AWF's API proxy is an inference proxy of the kind OBAAF-GHA-005's fix text asks for: it keeps the key out of the command's reach, though the step still holds it. The hosted web tools would let the provider's servers fetch what the agent asks, out of the proxy's sight, and AWF can refuse them.

**Consequence.** A name under a listed name still leaves the runner and reaches that domain's DNS servers; a listed name under which anyone can register a host gives that channel to anyone. With a model key, the API proxy reaches the provider whatever the allow-list says, and anything the agent puts in a request reaches the provider; remote MCP servers named in a request, and other ways of asking the provider to fetch a URL, are not refused, so a provider could be made to connect elsewhere for the agent. The tests use made-up keys, which each provider refused, so no successful model call went through the sandbox. The action now needs `sudo` on the runner for the resolver, as it already did for cleanup, and Docker's `docker0` bridge. Proposed by the flagship agent in slice 2c.4; for the maintainers to accept or reject.

### D-052 The checker places each credential given to the egress action's step, and a key behind AWF's API proxy or passed to the command does not stop the control from being verified

**Decision.** `obaaf check` reads a step that uses OBAAF's egress action as the action reads its inputs from the merge of slice 2c.4 on, and places each credential given to it. A credential set in the step's `env` under a name the `model-keys` input names (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) goes to AWF's API proxy: the command can use it and cannot read it, and the proxy reaches that provider's API host whatever `allow` says. One set under a name the `env` input names, or written in the `run` input, is passed to the command; so is one of the step's `env` written into `run` through the `env` context (`${{ env.KEY }}`), which GitHub fills with the step's own `env` when it writes the inputs, whatever `model-keys` says. One set under a name neither input names, and written into no input, reaches neither. A credential that reaches the command or the proxy is the evidence that the agent is the confined command (D-050); one that reaches neither is not. **Neither a key given to the proxy nor a credential passed to the command stops `egress-enforced` from being verified.** Where a model key is named, the finding shows the provider's API host after the allow-list (`api.anthropic.com (through AWF's API proxy)`), so it is part of what the finding is; beside a cleared finding the report names the credentials passed to the command (with which a listed host can be made to act for it), the provider channel (anything the command sends the provider through the proxy, and whatever the provider is asked to fetch or connect to: remote MCP servers, URLs; the proxy refuses only the providers' hosted web search and fetch tools, in requests it can read), and the job's log and artifacts. These names, with which the action refuses to run, are "not met": a model key, GitHub token or other name AWF withholds under `env`, a name `model-keys` does not take, something that is not a variable name, a model key no `env` of the step, job or workflow sets; other refusals at run time (a name under `env` set nowhere, an empty key, a line break in a value, a reserved name) are not read. "Cannot tell": `env` or `model-keys` computed when the job runs or not written as text, a computed step `env` that holds a credential, two step `env` names that differ only in case, a step `env` name not written as text (`true:`) holding a credential, the whole `env` context written into `run`, a credential or an `env` value holding one in another input, a credential anywhere else in the step. OBAAF-GHA-005's fourth control says, whatever its verdict, where each credential the checker could place goes, what it could not place and what would make the action refuse; no new control is added to OBAAF-GHA-005, so a key out of the command's reach clears nothing there (plan slice 2c.7 is to decide whether it should). Only commits at or after `f0bfbd7` (the merge of #128) may be listed in `egress_action_releases`; a test refuses an older one against the repository's history, which CI's test job now fetches in full. Beside a cleared finding of GitHub's native firewall, the report now also says that the job's log and artifacts are not blocked. This amends D-050 and D-051 where they made a credential given to the confined step "cannot tell".

**Reason.** The control is named for what it establishes: that the agent's network is limited to an allow-list. A key the command holds, or one AWF's API proxy holds for it, does not change that; it changes what the agent can send through the hosts it may reach, which is what the report beside a cleared finding is for. GitHub's native firewall has been verified since D-050 with a model key in the agent's own environment and the provider's host on its list, and it should not be easier to clear the finding by handing the agent its key under the firewall than by keeping the key from it under OBAAF's action. Keeping "cannot tell" here would have misused the verdict, which means the checker could not read what decides the control; it can. The provider channel is real and is not closed (the API proxy has no rule for remote MCP servers, and a provider can be asked to fetch a URL), but every egress control that lets an agent reach its model has it, the native firewall included, so it is named rather than counted against one control only. The job's log and its artifacts are a way out of every sandbox that no network rule touches, and the reports did not say so. The provider's host is shown with the allow-list because the allow-list is one of the finding's facts and the proxy's reach belongs beside it; an acceptance of a job that already used `model-keys` before this change stops matching after it (any change to the workflow file already makes a new finding, through its digest). The floor exists because the checker's reading of `model-keys`, and the text beside a cleared finding, are true only for the action from 2c.4 on (plan decision F-92).

**Consequence.** An agent job that wraps its command in OBAAF's action and needs an Anthropic or OpenAI key can have OBAAF-GHA-020 cleared once a commit is listed, which is what the first adopter's 19 agent jobs would need; until then it is "cannot tell", as every use of the action is. A job that passes the agent a credential in `env` can be cleared too, and its report says the credential can leave through a listed host or the job's log: the finding no longer pushes such a job towards `model-keys`, which only OBAAF-GHA-005's text and the action's own refusals do. The checker now copies three lists from the action (the names `model-keys` takes with their hosts, the names AWF withholds, and what a variable name is); a test keeps them equal to the action's, and a listed commit that reads its inputs another way must not be listed until the checker does too. Names the action reserves for other reasons (`PATH`, the proxy variables and others) are not copied: a credential under one is reported as passed to the command, where the action would refuse to run. The evidence that the agent is the command is still text the workflow's author writes: a credential written in `run`, even in a comment, counts. A credential that lets a listed host act for the command (a token that can start a workflow, say) gives that host's reach to the command; the report says so in general words and does not read what each credential can do. The checker has not been run against a real workflow that uses `model-keys` on GitHub; it was tested on workflows written for the tests and on a scratch adaptation of the first adopter's `byo-live.yml`. Proposed by the flagship agent in slice 2c.5; for the maintainers to accept or reject.

### D-053 A step before the egress action that only installs an agent's CLI is not taken for running the agent

**Decision.** Where the checker asks whether an agent runs outside OBAAF's egress action (D-050), a step before the action is not counted when its shell script does nothing but install, globally, packages listed in `agent_installs` (`@anthropic-ai/claude-code`, `@openai/codex`, `@google/gemini-cli`) with `npm install`/`i`/`add -g`, `pnpm add`/`install`/`i -g`, `yarn global add` or `bun add`/`install`/`i -g` (after `sudo` with only `-E`, `-H` or `-n`; an `@version` allowed; options only from `-g`, `--global`, `--no-fund`, `--no-audit`, `--ignore-scripts`, `--silent`; every install naming a listed package and nothing else), and print the CLI's version (`claude --version`, `codex --version`, `gemini --version`). Every line, and every command on it separated by `&&` or `;`, must be one of those two; comment lines are skipped. A script with `$`, a backtick, a quote, a pipe, a redirection, `&`, brackets or braces, a glob, a backslash or a `#` after a command is not read as an install; nor is a step with another shell, an action, `env`, `working-directory` or any key beyond `name`, `id`, `run`, `shell`, `if`, `timeout-minutes` and `continue-on-error`, a job or workflow with any `env` or with `defaults.run`, a step that runs in the background or in a group with the action, or one after it. A step before the action that names a listed package and is not read as an install is "cannot tell", unless it also matches another agent pattern, fetches and runs a package (`npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx`) or names a path into the package (`…/claude-code/cli.js`), which stays an agent outside ("not met"). Which jobs are agent jobs does not change: the install still makes a job an agent job.

**Reason.** The agent patterns match the packages' names so that `npx @anthropic-ai/claude-code` is recognised, and in doing so they took an install for a run, which made the control "not met" for the most natural use of the action with Claude Code (install it, then run it confined), as a scratch adaptation of the first adopter's `byo-live.yml` showed in slice 2c.5. Reading the whole script against a short list of exact forms, rather than looking for a run pattern, means a step that also runs the agent in a form no pattern knows is not read as an install; the review of this slice found that the step's `env` and the `env` it inherits from the job and the workflow (`BASH_ENV`, `NODE_OPTIONS`, `PATH`, `npm_config_*`), a default shell, options that take a path (`--script-shell`, `--userconfig`, `--prefix`), an install with options alone or without `-g` (which runs the project's own scripts) and `sudo -b`, `-i` or `-s` could each make the same words run something else, so all of them are excluded. Where the checker cannot vouch for the step it says "cannot tell", as the plan asked, rather than claim the agent runs there. An install runs the package's own install scripts with the full network, as any build step does; the egress control is about the agent acting on what it reads, not about the build.

**Consequence.** Many real install steps are still not read as installs (a registry option, a line continuation, a quoted name, a local install, a package outside the list, another command in the same step, an `env` on the step) and are "cannot tell" where they were "not met"; neither clears the finding. As before this slice, an earlier step that names no agent at all (`make build` with `BASH_ENV`, `sudo -b make build`) is not read for what it runs. Two things can still make an accepted install run something else, and the workflow does not show them: what an earlier step writes to `GITHUB_ENV`, `GITHUB_PATH` or the home directory (setup actions do so as a matter of course, so it cannot be refused), and package-manager configuration in the working directory, which `pnpm`, `yarn` and `bun` may read (not checked here). A plain prompt after an install (`claude 'fix it'`) is "cannot tell", under the plan's "cannot tell where it cannot be told", where it was "not met". The list of packages and the forms are data and code that must be kept current. Proposed by the flagship agent in slice 2c.8; for the maintainers to accept or reject.

### D-054 The egress control keeps the runner's listening programs out of the command's reach, and hands back only files and directories

**Decision.** Before the run, `actions/egress` finds every socket and named pipe then in the runner's `/tmp` (which AWF mounts into the sandbox), on its own file system, that the runner's user could write, and sets each one's mode to none for the run. It gives the modes back only once AWF has exited and Docker shows no container started for the run still running; if one is left or Docker does not answer, the modes stay as they are for the rest of the job and the step fails with status 3, and if the run ends in an error they stay as well and the step fails. The probe fails, and the command does not run, if the command can still write a socket or pipe under `/tmp`, `/run`, `/var`, `/home` or `/etc` outside the scratch directory. After the run every symbolic link, named pipe, socket and device file under the scratch directory is deleted, as root and without following links, and listed in a new output, `removed`, which keeps only the characters of a plain path; if any is left the step fails with status 3. A workspace is refused, with the new output `refused` set to `credential` (the inputs the first step refuses leave it empty), when the `config` or `config.worktree` file of any repository in it holds an `extraheader`, includes another file (`include`, `includeIf`) or has a remote URL with a password: the first two are how `actions/checkout` before v6 and from v6 on keep the token. The `denied` output takes a refused request's target, not its `Host` header, and keeps only the characters of a host name and port.

**Reason.** The first review of the whole action on Opus 5.5 (slice 2c.6) found two ways out through the runner's disk rather than its network, and the escape tests confirmed the first on GitHub-hosted `ubuntu-24.04`: the runner's `/tmp` held two .NET diagnostic sockets and four .NET debugger pipes, and from outside the sandbox both sockets answered a diagnostics request and all four pipes were writable. A read-only mount does not stop a connection to a socket, and the diagnostics protocol can make a .NET program write a dump of its memory or load a library; the command runs as the runner's user, so only the socket's mode stood in its way. The command cannot change a mode on a read-only mount and has no capability that would let it ignore one. The second: a link left in the copy is followed by a later step that reads or uploads the copy with the runner's access, so the copy would carry `/proc/self/environ` or a file under `RUNNER_TEMP` out of the job. Checkout v6 and later write an `includeIf` instead of the token, so the old refusal no longer fired.

**Consequence.** The copy loses its symbolic links, those the repository had included (`node_modules/.bin`, for one); a later step sees them named in `removed`. A .NET program on the runner cannot be reached through its diagnostic socket or debugger pipes while the command runs (the runner's own diagnostics tools neither). A socket or pipe a program creates in `/tmp` after the probe is not covered. The action needs `sudo` for `find`, `chmod` and the deletion, as it already did for its resolver and clean-up. A workflow that relied on `persist-credentials: true` with checkout v6 or later now fails before the command runs. The checker's floor for a listed release of the action (`egress_action_floor`, slice 2c.5) moves to this slice's last change to the action, so no commit without these fixes can be listed. Proposed in plan slice 2c.6. **Status.** Proposed, 2026-11-14.

### D-056 A runner label written as `matrix.x || 'label'` is resolved from the matrix, and a matrix the checker cannot read to the end is not

**Decision.** `runs-on` written as one `${{ }}` expression with nothing outside it is read from the expression's tokens. `matrix.x` and `matrix.x || 'label'` (a written string after the two bars, and nothing else) are resolved against a matrix written out in the file: the labels are every value of `x` in the matrix's key and its `include` entries, and the default too wherever a row may lack `x` (unless `x` is a key with a list of values and every `include` entry sets it, because an `include` entry that cannot be added to any combination makes a row of its own) or gives an empty text. The labels can be more than the job runs on, never fewer, and the job is GitHub-hosted only when every one is a standard hosted label. The values of `x` computed when the job runs, an `include` computed when the job runs or an `include` entry that is not a mapping, a key that differs from `x` only in case (GitHub compares property names without regard to case), any key of the matrix or of an `include` entry that is not plain ASCII text with no `${{ }}` (a key YAML reads as true or a number, a computed key, a key with a letter outside ASCII, which GitHub may fold to `x`), a value YAML 1.2 could read as a number, null, true or false (`0o0`, which GitHub would take as false and replace with the default), a YAML merge key (`<<`) anywhere in the file (this reader merges it, a YAML 1.2 reader takes it for a key), and every other expression leave the labels unresolved, which OBAAF-GHA-013 reports at medium for a job an outsider can start or an agent runs, as before.

**Reason.** Slice 3.1's review found the form on `pallets/flask`'s workflows, where every value is GitHub-hosted, and it failed a stranger's first gate. The old reading matched `${{ matrix.x }}` as text and fell back to "unknown" for anything else; it also read a matrix key computed at run time as absent when `include` entries set the same key, and passed over an `include` written as one expression, both of which could resolve a job to hosted labels it might not run on. Reading from tokens and resolving to a superset keeps the answer on the side of a finding. The refusal of keys that are not plain ASCII text came from the slice's review, which got GitHub's native firewall verified for a job whose matrix had a key `True:` (read by this reader as a boolean, and maybe by GitHub as a name `matrix.True` finds; GitHub's reader was not checked), a computed key, a key spelt with `ſ`, or a merge key: each was skipped or read one way only, the default filled in, and every label looked hosted.

**Consequence.** Jobs written in the new form whose labels are all hosted lose a medium OBAAF-GHA-013. Jobs can gain one where the labels used to resolve and now do not, in the plain `${{ matrix.x }}` form too: a computed matrix key beside `include` entries, a computed `include` (both of which the old reading resolved wrongly), a key that is not plain ASCII text, a value YAML 1.2 could read as other than text (quoted `'0'` or `'null'` included), and a merge key anywhere in the file, even in a step that has nothing to do with the matrix. A label that ends in a line break is no longer taken for a hosted label (the pattern ended in `$`). The same resolution is used wherever the checker reads a job's runner (the egress controls' runner conditions among them). On this repository, its fixtures and templates, and Expectrail's files at `13e8f70`: no change. Proposed in plan slice 2d.7. **Status.** Proposed, 2026-11-14.

### D-061 Triggers, scripts and release jobs: every field and capability counts, and a label or selector the checker cannot vouch for is "cannot tell"

**Decision.** OBAAF-GHA-010 reports every outsider-written field a step reaches, through its scripts, its `shell`, the inputs of actions listed as running a script, other jobs' outputs written in the file and an `env:` written as one expression, with the fields, the expressions and the triggers as facts; it is high in a reusable workflow, on `commit_comment`, `check_suite`, `check_run` and `status`, and for a commit's text on `push`, `merge_group` and a `workflow_run` after a push. Each class came from a list of spellings where GitHub accepts more, or from facts that did not hold what the message said. `head.repo.fork && 'ubuntu-latest' || 'self-hosted'`, made informational for issue #19, picks the self-hosted runner when `head.repo` is null (a pull request whose fork was deleted; whether GitHub starts a run then is not verified), so it is medium. `id-token: write` is not counted as a capability on its own because OBAAF's templates use it to sign and attest, which is what the framework asks for. A commit's text on push is high because a merge commit's default message holds the fork's branch name, which reviewers rarely read.

**Consequence.** A gate can fail where it passed: fields, scripts and spellings now read; higher severities for OBAAF-GHA-010 and for some selectors; labels shaped like hosted ones; jobs now recognised as release jobs, which also get OBAAF-GHA-006, 014, 016 and 017; the new `capability` case; and every v0.2 acceptance of the three rules, whose facts changed. Some findings go away: a calling job's OBAAF-GHA-013, environments such as `kitchen`, and OBAAF-GHA-015 at high on pull request events only (now medium). The hosted-label list was written from GitHub's runner reference as known on 2026-11-14 without reading the page from the session; a missing label gives a medium "cannot tell", never a missed self-hosted runner.
