### D-001 Framework name

**Decision.** The framework is the Open Build and Agent Assurance Framework (OBAAF). **Reason.** Chosen by the maintainer. A web search found no existing framework with the name; no trademark search has been done. **Status.** Accepted, 2026-10-05.

### D-002 Release condition

**Decision.** The maintainer authorized making the repository public and publishing the resource site, and stated that written employer approval is not necessary for that publication. Use the default GitHub Pages address until a custom domain is acquired. This supersedes the private-repository requirement accepted on 2026-10-05. It does not grant a license, change copyright ownership, or authorize submission of the research papers. **Status.** Accepted, 2026-10-10.

### D-003 Copyright notice and ownership; license grant

**Decision.** Grant the intended licenses (NFR1): Apache License 2.0 for the code, templates, tools and tests (`src/`, `templates/`, `actions/`, `tests/`); Creative Commons Attribution 4.0 International for the specifications, guides and documentation (`spec/`, `docs/`, and the data in `src/obaaf/data/`). The data files are dual-covered, so the package declares `Apache-2.0 AND CC-BY-4.0`. Copyright is held by Osita Sean Keluo-Udeke, as stated before public draft. The license texts (`LICENSE`, `LICENSE-docs`), the `NOTICE`, the `pyproject.toml` metadata and the [LICENSING.md](LICENSING.md) statement are in place. **Reason.** The licenses were always the intended ones (LICENSING.md); a studio cannot pilot or redistribute OBAAF without a granted license, so the grant is a prerequisite to the independent-studio pilot and to award and funding programs that require an OSI-approved license. **Maintainer acceptance.** Confirm the copyright holder and the affiliation shown on the papers and the repository, then accept by committing these files; change this status to Accepted with the date. Until then the texts are implemented as written but not yet accepted. **Status.** Proposed, 2026-10-21.

### D-004 Profile titles, rationales and tests

**Decision.** Paper 2, Table 4 gives each requirement's statement and mappings. FR1 also requires a test procedure. This repository adds a short title, a rationale, a pass-or-fail test and the evidence to inspect for each of the 28 requirements, in `src/obaaf/data/profile.yaml`. Some tests add thresholds the paper does not state (for example, G6.4's rollback test "within the last six months"). **Reason.** FR1 acceptance criterion. **Review.** Read each entry in [spec/profile.md](spec/profile.md); edit the data file, not the generated document. **Status.** Proposed.

### D-005 Not-applicable answers

**Decision.** Paper 2, DR6 allows N/A only when an item's condition is absent, naming three conditions: no self-hosted updater (item 2.10), no AI agents (items 3.6, 3.7, 4.5) and no target that can build in a container (item 3.3). Item 3.3's N/A condition here reads "fresh container or virtual machine", following the item's own wording, which names both. This repository also allows N/A for item 3.4 when a studio has no persistent release hosts, because Table 9 treats 3.3 and 3.4 as alternatives. No other item can be N/A. **Consequence.** If accepted, Paper 2's DR6 should name the fourth condition. Items 1.2 and 2.8 can also have an absent subject (no automated uploads, no partners); the pilot should show how studios answer them. **Status.** Proposed.

### D-006 Ranking fixes

**Decision.** Open items are ranked by tier (lowest first), then effort (hours, days, weeks), then the number of documented compromises the item would have prevented, then the number it would have detected or limited (Paper 2, Table 7), then item number. **Reason.** DR3 (prioritized by documented attack paths) and DR4 (effort-aware). The Python scorer and the offline form implement the same rule, and a test checks they agree. **Status.** Proposed.

### D-007 Predicate type URIs

**Decision.** OBAAF's in-toto predicate types and its generic SLSA build type live under `https://www.obaaf.com/`, the project's own domain, for example `https://www.obaaf.com/attestation/agent-run/v0.1`. They are defined once in `src/obaaf/predicates.py` and used in the templates. Each type URI resolves to a page that describes its format, and each JSON Schema's `$id` resolves to the schema; `site/build.py` publishes both. A changed format gets a new version and a new URI, and published pages stay as they are. **Reason.** A type URI should be under a namespace the project controls and should lead a reader to the format it names. `www.obaaf.com` is the site's canonical host, so the URIs resolve without depending on a redirect. Version 0.1 used the reserved `obaaf.example` domain until the project had a domain. **Consequence.** Breaking, which is acceptable before 1.0: records signed with the 0.1 URIs do not verify under 0.2 and must be signed again with the 0.2 templates. **Status.** Accepted, 2026-10-26 (previously Open, before release).

### D-008 Trust levels for GitHub roles

**Decision.** The snapshot step asks GitHub for each author's repository role: admin and maintain map to Maintainer; write and triage to Contributor; read and none to Public. Without a role it falls back to `author_association`: OWNER maps to Maintainer, and everything else, including MEMBER and COLLABORATOR, to Public, because those say nothing about write access to this repository. A pull request's changes are always labeled Public. The floor is Public in every repository unless the workflow raises it with `--floor`: the snapshot cannot see who else wrote what the agent's token can read (in a private repository, read-only users and, in internal repositories, every enterprise member). **Reason.** Paper 1, section 3.2 places principals by what they can do; write access can push unprotected branches and apply labels (Contributor). This mapping is right only when repository secrets live in protected environments, as the templates arrange; otherwise write access can read secrets and is Maintainer-equivalent. The security review found the earlier Contributor floor for private repositories, and the Contributor fallback for MEMBER and COLLABORATOR, too generous. **Status.** Proposed.

### D-009 Approvals in a second attestation

**Decision.** Paper 1, Table 3 lists Approvals among the agent-run record's fields, produced by the effect lane. Because approval happens after the attestation step signs, the effect lane signs a second attestation, `agent-approval`, over the same proposal files. The two together form the record. **Consequence.** Paper 1, section 7.3 could say so in one sentence. **Status.** Proposed.

### D-010 Agent records travel with the change

**Decision.** When the effect lane applies a patch, it adds `.obaaf/records/<bundle digest>.json` (the proposal and both signed attestations) in the same commit as the change and names it in an `OBAAF-Agent-Record:` commit trailer. The release verifier finds agent commits by trailer, by an added record file, or by the effect lane's commit identity, and requires each to add exactly one record, named after its digest and used by no other commit in the range. **Reason.** `gh attestation verify` needs the attested file; artifacts expire; a record in the repository is archived with the source and reviewed in the pull request. Requiring the record in the same commit stops an old, valid record from vouching for a later change. **Limit.** A squash merge that combines an agent's change with other changes fails the exact-diff check (D-026). **Status.** Proposed.

### D-011 Pinning pipeline dependencies

**Decision.** Workflows pin every action to a full commit SHA. `actions/setup-obaaf` and the PyPI release workflow install every dependency, including the build backend, from `actions/setup-obaaf/requirements.txt` by exact version and SHA-256 hash, as wheels only (`--require-hashes --only-binary=:all:`). That file lists the hash of every file PyPI publishes for each version, so one list serves every operating system and Python version. It is generated from `constraints.txt` by `scripts/lock_setup_obaaf.py`. CI checks it against PyPI, attaches the expected file to the run when it is out of date, and runs the action on Linux, macOS and Windows. The project's own test and site jobs install OBAAF in editable mode, which pip's hash-checking mode does not support, so they keep the exact versions in `constraints.txt`. **Distribution.** PyPI via OIDC trusted publishing (`pip install obaaf`), documented in [docs/releasing.md](docs/releasing.md). A GitHub Marketplace listing for `setup-obaaf` is documented there; pre-built single-file binaries remain deferred. **Status.** Accepted, 2026-10-26 (previously Open, before release).

### D-033 Empty binary manifest

**Decision.** A project that vendors no binaries declares `vendored_binaries: none` in `obaaf-sources.yaml` (components absent or empty). `obaaf manifest create` writes `format: obaaf-manifest/v0.1` with `vendoredBinaries: "none"`, `components: []` and `entries: []`, so the build-record digest binds the claim. Bare empty `components` without that declaration is rejected. `manifest check` validates the JSON claim and emptiness; it does not re-read the sources file or scan the tree for undeclared binaries. Release policies for such projects set `build_record.require_sdks: false`. An empty claim answers assessment items 1.8 and 2.6 as yes with evidence (the reviewed declaration), not as N/A (D-005 unchanged). **Reason.** G2.1 and FR5 assume a manifest; many non-game projects (including OBAAF) have no vendored binaries and could not previously produce a build record. **Status.** Accepted, 2026-10-26.

### D-012 Retired

This proposal is withdrawn at the maintainer's request. The identifier is reserved and will not be reused. **Status.** Retired, 2026-10-07.

### D-013 Language and dependencies

**Decision.** Python 3.10 or later, with PyYAML and jsonschema; `cryptography` only for verifying key-signed envelopes. Tests use the standard library's `unittest`. **Reason.** Python runs on every CI runner a studio uses; few dependencies keep the tools auditable. **Status.** Proposed.

### D-014 GitHub Actions first

**Decision.** The first reference templates target GitHub Actions; a second CI system follows for version 1.0, chosen from pilot data. Requirements stay tool-neutral (NFR6). **Reason.** The specification's scope and roadmap. **Status.** Accepted, 2026-10-05.

### D-015 Isolation tier from the workflow definition

**Decision.** The build record's isolation tier comes from the workflow file: a build job on standard GitHub-hosted runner labels is Tier A, including single-CPU runners, which start each job in a fresh container rather than a new virtual machine (Paper 2 counts a fresh container as Tier A); a self-hosted job, or one whose labels are not standard hosted labels, must declare `OBAAF_TIER` as a literal A or B. The build job never reports its own tier. **Reason.** FR4 requires the build record to state the tier; reading it from the workflow definition, as Paper 1 does for an agent's authority, keeps a compromised build from misreporting it. The publish workflow then checks that the release commit, and so the workflow file, is on the protected branch (D-024). **Limit.** Whether a self-hosted Tier A runner is really destroyed after each job is still a claim in the workflow. **Status.** Proposed.

### D-016 Release approvals checked at upload time

**Decision.** The publish job reads its own run's approvals from GitHub's approvals API, and `obaaf verify release` counts distinct approvers other than anyone who pushed the tag or started or re-ran the release or publish run (`--actor`, repeatable). Approvals are not part of the build record, which is signed before approval. The approvals API covers every attempt of the run; an approval from an earlier attempt still counts, because every attempt publishes the same artifacts from the same release run. **Consequence.** An administrator who bypasses the environment leaves no approval, so the release is blocked. GitHub environments proceed after one approval, so two-person release (item 4.3) uses two environments in sequence, and covers only the pipeline's path, not the store's own interface (see the F6 guide). **Status.** Proposed.

### D-017 What starts the agent lane

**Decision.** The agent template runs when a maintainer labels an issue `agent`, or a collaborator comments `/agent`. **Reason.** Cost control only: the agent still runs at the level of everything it reads, as Paper 1 requires, because invoker checks do not establish context trust. **Status.** Proposed.

### D-018 The effect lane opens pull requests only

**Decision.** The effect lane turns an approved patch into a branch and a pull request; it never pushes to a protected branch. The merge then needs ordinary review. Comments and allow-listed labels are applied directly. **Reason.** Two endorsements for code (the environment approval and the merge review), one for low-risk effects. **Status.** Proposed.

### D-019 Using GitHub's `cache-mode`

**Decision.** Release, agent and effect jobs set `cache-mode: none`. **Reason.** GitHub's changelogs describe `cache-mode`, enforced with scoped cache tokens ([September 2026](https://github.blog/changelog/2026-09-10-control-github-actions-cache-access-with-cache-mode)), and a read-only cache default for untrusted triggers that use the default branch's cache scope, such as `pull_request_target`, `issue_comment` and `workflow_run` runs that follow a pull request from a fork ([June 2026](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers)). The June change ships to GitHub.com and GitHub with data residency; neither changelog says when either reaches GitHub Enterprise Server, where the checker's other cache rules still apply. **Status.** Proposed; recheck GitHub Enterprise Server before release.

### D-020 Inference proxy

**Decision.** Version 0.1 specifies the proxy's contract ([docs/inference-proxy.md](docs/inference-proxy.md)) and ships a stub agent that calls no model, so the lanes can be tested end to end. ### D-023 Plan scope of version 0.1

**Decision.** Version 0.1's agent and release templates need artifact attestations and environment reviewers, so for private repositories they need GitHub Enterprise Cloud. Version 0.1 says so plainly ([github-settings.md](docs/github-settings.md#plan-limits), [traceability.md](docs/traceability.md)) instead of offering weaker substitutes, and NFR3 is marked as not met for private repositories on other plans. **Planned.** A merge-review mode for the effect lane (the protected branch's review as the approval, recorded and checked) and a key-signing release template, both for studios on the Team plan. **Consequences.** On plans without environment reviewers, `release.min_approvals` must be 0, and the person's approval comes from the store (a person sets builds live, item 1.3). ### D-024 Releases build from tags and publish from the default branch

**Decision.** `obaaf-release.yml` builds and attests on a push of a protected `v*` tag. A separate `obaaf-publish.yml`, started by `workflow_run` and therefore run from the default branch, verifies the release before anyone approves it (the result goes to the run summary), waits for the `release` environment, verifies again with the approvals, and uploads. The verifier requires the released commit to be on the policy's protected branch (`release.branch`, default `main`), and blocks when it is not given the repository and the release commit to check this; `release.branch: ""` turns the check off for repositories that release from several branches. **Reason.** The specification's FR4 says releases start only from a protected branch, and the security review showed that a workflow run by a tag push uses the workflow file and policy from the tagged commit, so a tag on an unreviewed commit could switch the checks off. Running publication from the default branch, and checking ancestry, closes that path while keeping tag-based release builds, which game teams expect. **Status.** Proposed.

### D-025 Agent commits are checked from a baseline in the policy

**Decision.** `obaaf verify release` checks agent-authored commits from the policy's `agents.since` commit to the released commit, or the whole history when `agents.since` is not set. When the policy sets `agents.since`, a `--range` on the command line is refused, so the range cannot be narrowed outside the reviewed policy. A shallow clone is refused too. Maintainers move the baseline forward in a reviewed change to the policy, only to a commit whose release passed. **Reason.** The earlier range started at the previous `v*` tag, and the security review showed that tagging a blocked commit (for example a release candidate) dropped the bad commit out of the next range. A baseline that only a reviewed policy change can move has no such gap. **Cost.** Without a baseline, every agent commit in history is verified on every release. A signed "published" marker could replace the manual baseline later. **Status.** Proposed.

### D-026 The committed change must equal the approved proposal

**Decision.** `agents.require_exact_diff` defaults to true: the verifier blocks a release when an agent commit's change differs from the approved patch, or when a commit that changes files names a record with no patch. "Differs" is decided by applying the approved patch to the commit's parent in a temporary index and comparing the result with the commit, outside the records directory, so the same lines moved to another place with identical surroundings are caught (the second security review showed that comparing diff text without line numbers missed this). **Reason.** With the default off, an old valid record could accompany any change with only a warning (security review). **Consequence.** Maintainers merge agent pull requests unchanged and make follow-up changes in separate pull requests. **Status.** Proposed.

### D-027 Proposal checks read the patch with Git and fail closed

**Decision.** `obaaf proposal check` takes the touched paths from Git itself (`git apply --numstat`, forwards and in reverse, and `--summary`), compares them with its own strict parser, and refuses the patch when they disagree, when it contains anything but plain git-format file changes, renames, copies, binaries, symbolic links, submodules or unusual modes, or when it touches a protected path or any path under a name starting with `.` (unless allowed). With `--repo` it also applies the patch to a temporary index of the default branch and checks the result. Comments are refused if they contain `](`, `]:`, `<`, `//`, `www.`, URL schemes or email addresses. **Reason.** The security review found four patch forms (quoted octal names, quoted instruction files, and two kinds of old-style hunks) that reached protected files, and Markdown forms that slipped past the comment filter. **Cost.** Some harmless proposals are refused; a person can make those changes instead. **Status.** Proposed.

### D-028 The effect lane is split, and has its own commit identity

**Decision.** The effect lane has an `approve` job (the environment approval, `obaaf verify agent-run`, the proposal check, the approval record, with `id-token` but read-only contents) and an `apply` job (write access, no `id-token`), which checks the record's digest and applies the patch. Its commits use the identity `OBAAF effect lane <obaaf-effect-lane@noreply.invalid>`, which the policy lists in `agents.effect_identities`. **Reason.** No job should hold both a signing identity and write access while it handles agent output (security review), and commits that other workflows make as `github-actions[bot]` should not be mistaken for agent changes. **Status.** Proposed.

### D-029 Who may not approve an agent's change

**Decision.** An approval does not count if it comes from anyone who started or re-ran the agent run or the effect run, the principal who triggered the agent, or anyone who wrote one of the agent's inputs, such as the issue's author. **Reason.** Paper 1, R4 requires approval by someone other than the requester; the security review showed that the author of an issue, who wrote the agent's task, could otherwise approve its result. **Status.** Proposed.

### D-030 Checker strictness

**Decision.** A declared lane (`OBAAF_LANE` or the configuration) can move a job only into a lane with stricter rules, never out of the agent, effect, release or untrusted lane the checker infers. On pull requests, the pipeline check reads its configuration from the target branch. Ignore entries cannot match every file. Runner labels that are not standard GitHub-hosted labels are reported at medium (OBAAF-GHA-013). OBAAF-GHA-016 counts only a verification whose failure stops the upload, and reports a provenance-only check at medium. OBAAF-GHA-020 reports an egress policy that is only declared, or enforced by a monitor that runs only under a condition. OBAAF-GHA-021 needs both the record verification and the proposal check, and reports one alone at medium. Steps inside `parallel` groups are checked like other steps; a `background: true` verification does not count as a gate; a job whose `if:` uses `success()` in an `||`, or `always()`, `failure()` or `cancelled()`, is treated as able to run after the jobs it needs failed or were skipped; and a step the checker cannot read (no `run` or `uses`, and not a known step form) is an error. **Reason.** Each closes a gap the first or second security review demonstrated. **Consequence.** The installed templates keep one low finding (OBAAF-GHA-020) until egress is enforced. **Status.** Proposed.

### D-031 Code signing of game binaries is deferred

**Decision.** Version 0.1 signs attestations through Sigstore but does not sign the game binaries themselves (Windows Authenticode, Apple, Android). The publish workflow marks where a managed signing step goes: after verification, in a job that runs no build code, followed by an attestation of the signed files. FR11 and G5.2 are marked as partly met. **Reason.** Signing services differ by platform and need the pilot's studios to choose; the consistency review found the earlier claims overstated. **Status.** Proposed.

### D-032 Contributions after release

**Decision.** After public release, contributions need a Developer Certificate of Origin sign-off (`git commit -s`), and security reports get an acknowledgment within five working days (SECURITY.md). **Reason.** The DCO is a light-weight, common way to record the right to contribute; five working days is achievable for one maintainer. **Status.** Proposed.

### D-034 Jenkinsfiles are read by a syntax-only parser in Python

**Decision.** `obaaf check` reads Jenkinsfiles with its own Groovy tokenizer and parser, written in Python, instead of the pinned JVM syntax helper the Jenkins integration design proposed. It never compiles, loads classes or evaluates expressions, and stops at 1 MiB, 400,000 tokens, 64 levels of nesting or 10 seconds per file. **Reason.** The design's requirement is that analysis runs no Groovy and has bounded failure; a JVM helper meets it only with a separately packaged runtime, image digest and dependency review, while the Python parser ships inside the existing package and has no dependencies. It is a structural reader for the constructs Jenkins pipelines use, not a full Groovy grammar: statements it cannot read are recorded as not analyzed and make the file's coverage unknown. The Declarative linter of a disposable controller remains the right compatibility oracle for the fixtures. **Consequence.** Groovy syntax the parser does not know lowers coverage instead of crashing; the parser was run over 512 public pipeline files with no file-level failure. **Status.** Proposed.

### D-035 The Jenkins adapter sits beside the workflow checker

**Decision.** The Jenkins rules live in `src/obaaf/checker/jenkins/` and share the catalog, findings, ignores, reports and CLI with the workflow checker, without first extracting platform-neutral contracts under `src/obaaf/ci/`. **Reason.** Extracting contracts first would touch every workflow rule before any Jenkins rule exists, and the design itself requires that GitHub Actions behavior be preserved; adding beside it leaves the 26 workflow and repository rules and their tests unchanged. **Consequence.** The contracts (CiContext, PipelineModel and the rest) are extracted when the evidence and admission phases need a shared model. **Status.** Proposed.

### D-036 Jenkins results are advisory, and unknowns are coverage, not findings

**Decision.** The OBAAF-JEN rules report what a Jenkinsfile shows. What only the controller can show (authorization, build authorization, agent placement, library trust and version overrides, Replay, credential scopes, network policy), and code the file does not contain (shared-library steps, `load`, generated parallel branches), is reported as a coverage unknown per rule, never as a pass. Unknowns do not change the exit status in advisory mode; the report says that exit 0 is not a conformance decision. Generic file transfer (`scp`, `rsync`, `sshPublisher`, `ftpPublisher`) is not treated as publishing. **Reason.** The design requires that missing evidence never appear as an empty finding list, and that enforcement come only with authenticated controller evidence. Counting generic transfer as publishing produced high findings on pipelines that only copy test reports. **Consequence.** A clean Jenkins report means nothing was found in the file. Enforcement, controller inventory and signed Jenkins run evidence are later phases. **Status.** Proposed.

### D-037 The Jenkins release lane signs with a key service and reads approvals from the controller

**Decision.** On Jenkins, the release lane is two jobs: a build job in a multibranch project that discovers only tags and builds them with no credentials, and a publish job, read only from the default branch and taking no parameters, that finds the tag build that started it from its own start cause, resolves the tag through the SCM, copies that build's artifacts, signs SLSA provenance and the build record as DSSE envelopes through a key service (`obaaf dsse prepare` and `assemble`), and runs `obaaf verify release` before and after a named approver. The verifier reads both builds' JSON from the controller and ties them together: the publishing build was started by exactly one build, which is the one passed as the producing build, is the tag build `release.jenkins_project/<tag>` for the tag in the signed build record, and checked out the release commit (`lastBuiltRevision`). It counts approvals (`ApproverAction`) only from people in `release.approvers` who started neither build, blocks Replays, stage restarts, builds started by hand and causes it cannot classify, and fails closed when either build's JSON is missing. Run identity in Jenkins records comes from the build's environment and is marked self-reported. **Reason.** Jenkins has no per-job identity the public Sigstore service accepts; credentials scoped to a multibranch project reach every branch and pull request; a branch can carry a tag-like name and its own Jenkinsfile; administrators can approve any input step; and the controller, not the pipeline, is where approvals and start causes are recorded. A parameterized publish job would trust whoever started it to name the right build. **Consequence.** The lane's guarantees depend on controller settings OBAAF cannot see yet (who may Replay or configure the publish job, credential scope, which jobs use the release agents) and on the tag's Jenkinsfile; docs/jenkins.md lists them. Signed controller evidence comes with the inventory phase. **Status.** Proposed.

### D-039 A workflow job is in every lane it qualifies for, and a declaration only adds a lane

**Decision.** The workflow checker decides each lane on its own (agent, effect, release, untrusted) and applies the rules of every lane a job is in. Being in one lane never keeps a job out of another: a job that uses a release environment is a release job whatever can start it, and a job that only pull requests can start is an untrusted job whatever else it does. `OBAAF_LANE` and a `lanes:` entry add a lane to those and never remove one; every declaration for a job counts, whichever file it is in. A declaration that does nothing (a value that is not a lane, `OBAAF_LANE` on a step, a `lanes:` entry for a job, stage or file that was not found) is reported in the notes, not refused: an adopter's configuration that carries one today keeps working, and the note says what to fix. `lanes:` that is neither a mapping nor empty is a configuration error. `--lanes` and the `lanes()` function still give one lane per job, the first in the order agent, effect, release, untrusted, and name the others in the reason. Proposed in the flagship work (slice 2d.2a). The Jenkins analyser keeps its own code for what a stage does, decided step by step, and follows the same rule for declarations: every lane declared for a step counts (in `lanes:` for the file, the stage or a stage it is nested in, and with `OBAAF_LANE` anywhere on the way to the step), and none hides another.

**Reason.** With one lane per job, chosen in a fixed order, a job that did two things was checked for one, and a declaration that disagreed with the inferred lane was dropped. A reviewer showed two cases (an agent job that publishes got no release rules; a declared agent job that publishes got no agent rules). More of the same class turned up in the fix and in a second review of it; the changelog lists them all, and one of them let a declaration remove a finding. SECURITY.md counts a false negative as a vulnerability. Baselines key on a finding's message, and an entry that no longer matches fails the check, so what is shown is kept as it was wherever a job's lanes did not change: the single displayed lane, a declaration as the reason when a lane is both declared and inferred, and OBAAF-GHA-017 on the first publishing job that is only a release job. The messages that do change without a change of lanes are for a declaration that used to be ignored and is now read (another case or spacing, a declaration behind the first one, a `lanes:` entry for a workflow checked on its own); reading it is the point. **Status.** Proposed, 2026-11-11.

### D-040 The settings audit only reads, and records what it could not read

**Decision.** `obaaf audit` reads repository settings through GitHub's REST API with GET requests only; the client has no other verb. It works with whatever access the caller's token has, and with none on a public repository. It never creates a token and never asks for more than read access: the two things GitHub shows only to a caller who could also change them (who may bypass a ruleset, and Actions policies) are asked for when a token is given and are otherwise reported as not read. Every setting the audit covers is in its snapshot as read, partly read, not read (with a reason code, GitHub's stated requirement and GitHub's own error) or not applicable; none is ever left out. An answer that does not have the shape GitHub documents is recorded as not read, and a field whose absence could pass for "none" must be present. Where GitHub's reference leaves a reading open, the audit takes the one that cannot turn "unknown" into "fine": an empty bypass list is never recorded as "nobody may bypass"; a 404 from classic branch protection counts as "no protection" only with GitHub's message "Branch not protected"; an environment whose answer lacks the branch policy field is not taken to allow every branch; and a section missing from a classic branch protection is recorded as not required, the reading that reports less protection. The audit covers only settings that the repository's own workflows depend on. The snapshot keeps the names of secrets, the logins and team names that the settings themselves name (environment reviewers, classic protection's push and review-bypass lists), and counts of collaborators; never a token, a secret's value, or the list of collaborators. A snapshot file is checked in full before it is used, because a committed one can be edited in a pull request. Proposed in the flagship work (slice 2b.1 of [the plan](docs/flagship.md); plan decision F-23). This first part applies no rule.

**Reason.** The first adopter's incidents were all settings (an environment open to every branch, an administrator bypass on the ruleset, approvals nobody could give, one required check of eleven, an Actions policy that blocked a trigger), and `obaaf check` reads none of them. A tool that reads settings with a maintainer's token must not be able to change them, and a tool that reports on settings must not let what it could not see pass as clean: the tools compared in [the landscape](docs/landscape.md) need an owner's token for full results, and the adopter's own gate had answered "0 new" while seeing nothing of this. GitHub answers 404 for what a caller may not see, omits fields by permission, and documents neither what a caller without write access gets in place of a bypass list nor the "Branch not protected" message, so each of those is read the cautious way until a run with an administrator's token settles it. The cost is stated in the guide: until then the audit can show that someone may bypass a ruleset, and cannot show that nobody may. **Status.** Accepted, 2026-11-12.

### D-041 An acceptance needs an owner, a reason and an expiry date, and a finding is identified by what it is, not by its message

**Decision.** A finding is in one of four states: new, accepted, fixed (every control that clears it was verified by the checker) or cannot tell (a control could not be read). Only accepted and fixed findings pass a gate. An acceptance, whether an `ignore` entry or a baseline entry, must name an owner (`@user`, `@org/team` or an e-mail address), give a reason, and carry an expiry date that has not passed and is at most 366 days ahead; an entry that does not accepts nothing, and its finding counts as new. Baselines are written in a new format, `obaaf-baseline/v0.2`, in which an entry is the finding's rule, file, job, step, case (`kind`) and values (`facts`) with the severity it was accepted at and the three fields above, and has no fingerprint and no message. Workflow and repository rules build each message from a template and named values, and those values are the finding's facts, so what a message says about a finding is in what identifies it. Line and column numbers are the exception everywhere: they are shown and never identify a finding. Two facts are text: why a job is an agent job (OBAAF-GHA-003), and a digest of the line a hidden character is on (OBAAF-INS-001). A reason must have at least four letters or digits. The agent reason tells apart what the checker's text tells apart and no more: another command in a step of the same name, or another agent in a job declared an agent job, is the same finding. `obaaf-baseline/v0.1` files are still read and accept nothing until `obaaf baseline migrate` converts them with an owner, a reason and a date. `--write-baseline` keeps valid entries as they are and needs `--owner`, `--reason` and `--expires` for anything newly accepted. Jenkins findings keep their message as their identity. Proposed in the flagship work (slice 2a.1).

**Reason.** The first adopter's baseline accepted all 38 of its findings in a file that named nobody, gave no reason and never expired, and was regenerated three times in one day to add more: a gate whose answer is always "accept" checks nothing. An expiry date with no upper limit is a permanent acceptance with a date on it, hence the year. A v0.1 entry tied an acceptance to the wording of a message, which is why slice 2d.2a had to keep old wording in three places, and it carried a fingerprint that had to be checked against the text beside it. Old-format baselines and owner-less ignore entries could have been honoured with a warning; they are not, because a warning in a CI log is read by nobody and the acceptances they hold are exactly the ones this decision is about. The cost is that an adopter who upgrades has a red gate until they run one command and add one line per ignore entry.

**Consequence.** Upgrading past 0.3.0 turns a gate red for any repository with a baseline or an ignore entry, until the baseline is migrated and each ignore entry has an owner. Expectrail is pinned to a commit and is not affected until it moves its pin. The state "fixed" exists and no rule produces it yet; "cannot tell" is produced since slice 2a.2 (D-042). A lane declaration that does nothing stays a note in this change; it is to become a finding with its own rule id, so that it can fail a gate or be accepted like any other (flagship decision F-40). **Status.** Accepted, 2026-11-12.

### D-042 A finding names the controls that clear it, and a control is verified only from what the checker read

**Decision.** OBAAF-GHA-005 (a secret in an agent job) and OBAAF-GHA-020 (no egress restriction) list the controls that would clear them, each with a verdict: verified, not met or cannot tell. OBAAF-GHA-005 needs four: the job's secrets are listed in `protected_secrets` and the job declares the environment named there; the secrets are stored only in that environment and only protected branches may use it; no pull request, issue or comment can start the job or supply its code or text; and a recognised control limits the job's network access to an allow-list. OBAAF-GHA-020 needs the last one. A verdict is "verified" only for something the checker read. The environment's settings are not read by `obaaf check`, so that control is always "cannot tell"; and no egress control is credited yet, so a blocking Harden-Runner step with no condition, which used to clear OBAAF-GHA-020, is "cannot tell" as the job's first step and "not met" anywhere else, and a baseline entry that accepts the first is for the workflow file as it stood, byte for byte. A proxy that holds the model key is not counted as a control. Which events can start a job is read from the tokens of its `if:`, where it was matched as text, and input names under `with:` are read with A to Z in either case, as GitHub reads them.

**Reason.** A finding that can only be accepted is noise, and the first adopter accepted the same two findings on all 19 of its agent jobs. Agent control R2 gives an agent job no secrets and R3 keeps the model key in a proxy that OBAAF never built, so in practice every agent job holds a key; the controls are the conditions under which that is defensible, and they are the ones the adopter already half meets. The old test for an egress control passed any blocking Harden-Runner step whatever its version and wherever it stood, including after the agent, which is a pass on something nobody read. The two key proxies that exist were not run (the session that built this had no Docker), and crediting one untested would be the same mistake. The event reading was changed in the same change because a "verified" verdict rested on it and text that only looked like an event test could remove an event.

**Consequence.** Neither finding can be cleared yet: the settings and a verified egress control come with the settings audit's rules and the egress action. Until then the report says what each agent job has and lacks, and the finding is accepted or fails. A workflow that relied on Harden-Runner to pass OBAAF-GHA-020 now has a finding to accept. Workflows whose `if:` only looked like an event test get the findings they were missing. **Status.** Accepted, 2026-11-12.

### D-043 Every report begins with the accepted risk, and SARIF says an acceptance in its message as well as in a suppression

**Decision.** The text, JSON and SARIF reports of `obaaf check` begin with the accepted risk: how many findings are accepted, at what severity, by which owner, and the first date on which an acceptance runs out. Acceptances that run out within 30 days are listed as expiring soon (`--expiry-warning DAYS`; 0 turns the list off), and the list never changes the exit status. The text report keeps the lines it had, below the new ones, with four differences: a finding ignored by configuration is listed with its owner; the migrate command it prints repeats the `--config` and `--platform` the check was given; where a file's path heads its findings it is quoted unless, with characters that do not print written as escapes, it is made only of visible ASCII characters, so that a directory cannot be named like a line of the report and pass for one; and the Jenkins coverage lines show a character that does not print as an escape. JSON keeps every field and adds `acceptedRisk`, and `daysLeft` in a finding's `acceptance`. Every acceptance in a report is judged on one day, read once while the check runs. In SARIF an accepted finding is a result with a suppression whose status is `accepted`, the accepted risk is in the run's properties and its first notification, errors and notes are notifications, and the message of a result also says in words who accepted it and until when, why an entry does not count, and what was established about its controls.

**Reason.** The first adopter's gate was green with 38 accepted findings and its log said "0 new"; the count of accepted findings was one line near the end and named nobody. An acceptance has had an owner and an expiry date since D-041, and nothing showed them together or warned before a date passed, so a gate went red on the day with no notice. For SARIF, the standard's way to say "accepted" is a suppression, and that is what other readers of SARIF expect. GitHub's page on the SARIF fields code scanning uses (read on 2026-11-12) does not list suppressions, notifications or the property bags of a run or a result, and says fields not listed are ignored, so there the message is the only place a reader can see that a finding was accepted. Saying it in both places costs a longer message.

**Consequence.** A script that reads the first line of the text report, or matches the `ignored:` lines, sees different text; the line `Baseline: N finding(s) accepted by the baseline, M new.` is unchanged. A consumer of SARIF that hides suppressed results now hides findings accepted by a baseline, which it showed before. In GitHub code scanning an accepted finding stays an open alert, and the accepted-risk total, the expiry warning and a file the checker could not read are not shown there, going by GitHub's page; no upload was made to check it. A file that could not be read still exits 1 whatever `--fail-on` says, which is how it shows in CI. For code scanning to show an unread file or an ignored lane declaration, each would have to be a result with a rule id; slice 2a.4 of the flagship plan does that for lane declarations, and nothing is planned yet for an unread file. A finding's state or the exit status can differ from before in two cases. A command that ended in a traceback because standard output was ASCII exited 1, and now exits as its findings decide. And in a check that crosses midnight a baseline entry is judged on the day the check read: one whose last day is that day is accepted, and one dated 367 days after it is refused, where each was the other way round when the baseline was applied after midnight. `--write-baseline` and `obaaf baseline migrate` still read the clock again when they decide what to write. **Status.** Accepted, 2026-11-12.

### D-044 A lane declaration that does nothing is a finding, high unless nothing can be missing

**Decision.** A lane declaration that changes nothing is reported as a finding with a rule of its own, `OBAAF-CFG-001`, the first of a family (`OBAAF-CFG`) for the checker's own configuration. It covers what the notes listed since D-039: `OBAAF_LANE` set to a value that is not a lane, `OBAAF_LANE` in a step's, container's or service's `env`, a Jenkinsfile's `OBAAF_LANE` that is not a lane or is computed when the build runs, and a `lanes:` entry whose value is not a lane or that names a job, a stage or a file that is not there. It also covers two the notes missed, the variable under another spelling in a workflow (`obaaf_lane`) and `OBAAF_LANE` in the `env` of a `parallel` group, and reports a `lanes:` key that is not text also when one file is checked on its own. One thing the notes listed is not a finding: an entry for a Jenkins stage that is in the file and holds no step. The finding is reported in the file the declaration is written in, the configuration file included. Its severity is high, and low where no rule can be missing because of it: it names `trusted`; it is written where it is not read, or under another spelling, and names a lane the job is in anyway; or it is an entry for a Jenkins stage that is not there and names a lane that changes nothing on a stage. It is identified by where it is written (the file, the job and step, the names of the stages a Jenkinsfile's declaration reaches), the `lanes:` key, the variable's name and the declared value, never by its line or wording; two Jenkins stages with one label (the name, with the stages it is nested in) are one stage, as everywhere in the Jenkins reader. It is accepted by a baseline entry, with an owner, a reason and an expiry date (D-041). It cannot be accepted by an `ignore` entry: one that names the rule is a configuration error. The notes no longer list these declarations; `--lanes`, which reports no findings, still prints them.

**Reason.** Declaring which jobs are agent jobs is the part of OBAAF that other tools do not have, and the first adopter declares 17 of its 19 agent jobs by hand because the checker does not recognise them. A declaration that silently does nothing removes the agent rules from the job it was written for, and a note that changes no exit code leaves the gate green: the misspelling `OBAAF_LANE: agnet` passed. A separate state or an error that stops the check would each need machinery of its own and would have broken the first adopter's configuration with no way to accept it; a finding uses the lifecycle that exists. High, not medium: the rules' own scale would call a missing safeguard medium, but the safeguard missing here is the checker's reading of the job, and what goes unreported includes high-severity rules, so a gate at `--fail-on high` would otherwise pass a job whose agent rules never ran. Low where nothing is lost, so that a stale `trusted` entry does not read as an open attack path. No `ignore` entry, because an `ignore` entry accepts a rule in a file whatever the finding says, and for this rule that is a standing permission for any declaration in the file to do nothing: the reviewer of the change accepted one entry that way, renamed an agent job, misspelt its lane, and the check passed. Every rule's `ignore` entries are that broad; this is the rule whose findings stand for other rules not running.

**Consequence.** A repository with such a declaration fails a gate at the default `--fail-on medium`, where it passed. Accepting one takes a baseline, so a repository that has none has to start one or correct the declaration. The first adopter has such a declaration on purpose: it uses `lanes:` as its own inventory and gives one job the value `probe`, which its own audit script reads. On upgrade that is one high finding, to be accepted in its baseline with a reason or replaced by `trusted` and a list kept elsewhere; OBAAF has no way to carry a label of the adopter's own on a job, and none is planned. OBAAF's own example configuration declared a lane for a file its templates do not install, and `obaaf templates install` writes that example as the live configuration; its examples are comments now, and a repository that installed it earlier has the finding. The configuration file can appear in a report as a file with findings. A reader of the JSON `notes` no longer sees these declarations there. Still unreported: in a Jenkinsfile, the variable under another spelling and an assignment to `env.OBAAF_LANE`, which the checker does not read as a declaration; and a second configuration file that the first one hides. **Status.** Accepted, 2026-11-13.

### D-045 A settings rule compares a setting with what a workflow uses, and answers "cannot tell" when it could not read one

**Decision.** `obaaf audit` applies rules, `OBAAF-SET-001` to `OBAAF-SET-015`, a family of their own beside `OBAAF-GHA` and `OBAAF-CFG`. Twelve compare a setting in the snapshot with something the repository's workflow files use or assume, read from a clone with the checker's parser. Three read settings only, who may bypass a branch's rules, whether its required approvals can be given and whether a workflow can give one, because the checks and reviews they concern are what every workflow's result feeds (and, for the third, because a workflow on any branch can ask for the token). A rule's result is about one thing (an environment, a branch, a job) and is a finding with a severity or "cannot tell": the second when a setting or a workflow file the rule needs was not read, was partly read, or is not in a form the rule understands. A rule with neither says what it compared or why it had nothing to compare; nothing is called a pass. A rule that fails while running is "cannot tell" and the command exits 1. The command exits 1 on a finding at or above `--fail-on`, `medium` by default, as `obaaf check` does; "cannot tell" fails only with `--fail-on-cannot-tell`. The workflow files are taken from the directory given when it is the top level of a clone whose origin remote names the audited repository, or when the directory is named on the command line, and otherwise not at all. The rules are defined in `src/obaaf/audit/rules.py`, not in the checker's `rules.yaml`, and a settings finding cannot be accepted: there is no baseline and no `ignore` for the audit. `--format json` becomes a report that holds the snapshot, where it was the snapshot; with `--expected` (D-046) the comparison is in the same document under `drift`, where it was a document of its own; it keeps its own `format` field, `obaaf-settings-drift/v0.1`. The drift schedule (the optional template and this repository's own job) runs with `--fail-on never`, so that it fails on drift and not on a rule's finding.

**Reason.** Reading settings and judging nothing left the adopter where it was: every incident of its first two days was a setting, and the audit could describe each and say nothing about it. Comparing with the workflows keeps the audit from becoming a second organisation checklist beside tools that do that with far more users (plan decision F-23), and it is what makes a finding specific: not "an environment has no branch limit" but "this job names it". "Cannot tell" as a result of its own follows D-040: with no token GitHub withholds something every rule reads, and a report that listed only findings would read as clean. It does not fail the command by default because then no run without an administrator's token could ever succeed. A default of `medium` matches `obaaf check`; the command is in no release, so no released behaviour changes. Acceptances are left out on purpose for now: the first adopter's baseline held 38 findings that could only ever be accepted, and every settings finding names a change that clears it, a setting or a line of a workflow, which the next run verifies. Whether the audit should share the checker's acceptances is open. The rules stay out of `rules.yaml` because that file belongs to the checker's shared code, which slices change one at a time, and because the catalogue's requirement mapping for these rules has not been done.

**Consequence.** A workflow that runs `obaaf audit` from a commit after 0.3.0 can now fail where it exited 0, and a script that read its JSON finds the snapshot one level down. A finding someone decides to live with (a bypass kept for emergencies is one) can only be kept out of the exit status by a higher `--fail-on`, which also hides every other finding of that severity; that will need an answer before the audit is a gate anyone keeps. Three of the six incidents' rules need settings that only an administrator's token reads and a fourth needs a count a workflow's token was given once; the audit has never been run with an administrator's token, so those rules have met only answers written by hand, and the two about Actions policies read a form no real policy has been checked against. Several statements about what GitHub does, in the rules' own texts, rest on the author's knowledge and not on a page read on a date; the guide lists them. The rules are not in the catalogue, so `obaaf catalog` and the generated rule pages do not list them; the guide's table does, and a test keeps each rule's row, title and severity in it. **Status.** Accepted, 2026-11-13.

### D-046 Drift is any difference from a committed snapshot, and a setting that could not be compared fails

**Decision.** `obaaf audit --expected FILE` compares the `settings` part of a committed settings snapshot with the settings read now (or with another snapshot file) and reports each part that differs (a ruleset, an environment, a branch, a secret's name, a field) as one finding of `OBAAF-DRIFT-001`, a rule of the settings audit, not of the checker's catalogue. Any difference counts, tighter or looser, and has no severity; it is resolved by putting the setting back or committing a new snapshot, not by an acceptance. Lists are compared as multisets and values as JSON. The command exits 1 when anything differs, when a setting or a part of one was read by one side and not by the other ("not compared", in both directions), and when nothing was compared; only what neither side read in full is "not covered" and does not fail (of an environment both read in part, the rest is compared). The committed file must be of the same repository and API address, may not give two parts one key, and must hold data for exactly the branches it lists (exit 2 otherwise). The schedule is an optional template that `obaaf templates install` does not install. (D-045 is the settings rules of slice 2b.2.)

**Reason.** The settings audit exists because the first adopter's incidents were settings (D-040). A setting changes without any file changing, so only a comparison with a recorded state notices it. Judging whether a change is a weakening is the settings rules' job (2b.2); the snapshot is the reviewed record of what the settings are, so any departure means the record or the setting is wrong. A drift check that could not read a setting has not shown that it did not change, and the rule that "cannot tell" is never "pass" (D-042) applies to its exit code too, which a scheduled job is read by. It has to apply in both directions: the first review of the slice showed that a part the committed snapshot did not read (a bypass list GitHub sent empty, an environment whose branch and tag patterns failed to load, a "problem" written into the file by hand) hid every later change in it while the check passed. The template is optional because it fails until a snapshot is committed, and the other templates are installed together.

**Consequence.** A job whose token reads less, or more, than the token that took the committed snapshot fails until the snapshot is taken again with the job's access. Adding the first bypass actor to a ruleset, or removing the last, shows as "not compared", because GitHub's empty bypass list is never believed (D-040). A job that uses the workflow's own token never watches what that token cannot read: the bypass lists, classic branch protection, the names of secrets and the Actions settings. Whoever can change the committed file decides what counts as drift, so it needs code-owner review. Nothing changes for a command line without `--expected`. Proposed by the flagship agent in slice 2b.3. **Status.** Accepted, 2026-11-13.

### D-047 The egress control confines one command under a pinned AWF, narrows its writes to a scratch copy, and fails closed

**Decision.** `actions/egress` runs one command under the Agent Workflow Firewall at one version (binary by SHA-256, each image by digest) in AWF's default network-isolation mode, from a command line the action builds itself. The allow-list is plain host names; an entry with a wildcard, an address, a port, a scheme or a single label is refused. The command gets no environment from the runner except variables the workflow names, and variables that change a shell, a loader or the network cannot be named. It can write only to a scratch directory under `/tmp` that holds a copy of the workspace, its own home and its own `TMPDIR` (AWF's `filesystem.allowWrite`), and to AWF's own directories under `RUNNER_TEMP`, which the action deletes after the run (failing the step if it cannot); the runner's workspace, home, `/tmp` and file-command files are read-only or absent inside. Model keys and GitHub tokens, which AWF withholds from the command for its API proxy, are refused rather than dropped, until the API proxy is tested. A probe inside the sandbox must fail to get out before the command starts, or the command does not run and the step fails with status 3; workflow commands are stopped while the command's output is printed; and the step fails if the runner's file-command files changed. Whether it holds is decided by escape tests in CI judged from a packet capture outside the sandbox, with each attempt first made outside it as a control.

**Reason.** OBAAF-GHA-020 had no fix an adopter could apply (the first adopter accepted it 19 times), and decision F-20 chose to wrap AWF rather than write a firewall. Running AWF with its defaults left the workspace, the host's `/tmp` and the tool directories of the home directory writable, which is enough for a confined command to plant a program that a later step or post step runs with the full network; narrowing the writes is what turns a wrapper into a control for the rest of the job. A fixed command line keeps the options AWF itself says remove the protection out of an adopter's reach, and the probe turns a sandbox that did not start, or did not hold, into a failure instead of an unconfined run.

**Consequence.** An agent that writes to its workspace now writes to a copy; the workflow must collect the result from the `workspace` output and treat it as data. A workspace whose `.git/config` holds a token is refused. An agent that reads a model key from its environment cannot run under the action until AWF's API proxy is tested and supported (plan slice 2c.4). IPv6 could not be tested on hosted runners, which had no IPv6 route. The control confines one command: it does not cover agents that are actions, other steps or post steps, and it does not stop data sent to a listed host, a different `Host` behind a listed name, or data in a host name the command asks the proxy for, which the escape tests showed leaving the runner in a DNS query although the proxy refused the request. Changing the pinned AWF version is a change to the control and must pass the escape tests. Proposed by the flagship agent in slice 2c.2. **Status.** Accepted, 2026-11-13.

### D-048 A pull-request rule's parameters are each read or named, and one the rules do not know makes them "cannot tell"

**Decision.** The two settings rules about approvals, `OBAAF-SET-005` and `OBAAF-SET-013`, place every parameter of a ruleset's `pull_request` rule in one of two lists in the code: read by the rules, or about neither how many approvals a branch needs nor who can give them. The lists are the nine parameters of GitHub's REST reference for rulesets, read on 2026-11-13. A parameter in neither list, or a known one in a form the reference does not give (an object with a field the reference does not list included), makes `OBAAF-SET-005` "cannot tell" for its branch, and `OBAAF-SET-013` too where workflows may approve pull requests, naming it and its value, whatever the value, unless the count alone is a finding; a "cannot tell" given for another reason, and a finding by count, name it as well. The parameters read are taken as GitHub's pages describe them, and where a page leaves the effect open the rule says "cannot tell": `require_last_push_approval` where no approval is counted, and a team that `required_reviewers` asks for an approval (who is in it is not read). `require_extra_approval_for_unattributed_changes` on a ruleset that counts zero does nothing, as GitHub's page says of "the ruleset"; on one that counts N, a pull request Copilot opens without a person needs N + 1, asked of "people with write access" in the page's example, which the accounts with write access can give when the count alone is no finding, because none of them is its author. `OBAAF-SET-005` is "cannot tell" for a branch that requires a code owner's review unless its count alone is a finding, because who the code owners are is not read.

**Reason.** Slice 2b.4 found the first adopter's ruleset carrying an approval parameter that no rule read, and the report said nothing of it: "not read" passed as "nothing wrong", which the settings audit exists to prevent (D-040, D-045). Listing the known parameters is what lets a new one be noticed; reading an unknown one as adding nothing would be a pass on something the audit has not looked at. "Cannot tell" whatever the value, because the meaning of a value of a parameter nobody has read is not known either. The code-owner change is the same fault in a parameter the rule already had in hand: a branch whose only code owner is the one person who writes the changes cannot merge without a bypass, and the rule said "no finding".

**Consequence.** A new parameter from GitHub turns the rules into "cannot tell" for a branch whose rule carries it, where neither the count alone nor the workflows' permission to approve already decides the answer, until OBAAF places it, which takes a release. A repository that requires a code owner's review gets "cannot tell" from `OBAAF-SET-005` where it got "no finding", for as long as the CODEOWNERS file is not read. The reading of `require_extra_approval_for_unattributed_changes` rests on GitHub's pages, which speak only of pull requests Copilot opens; nobody here has run it. Classic branch protection is read into a fixed form, so a field GitHub adds there is dropped before the rules see it, which this decision does not change. Whether Copilot may approve pull requests, which GitHub's changelog of 2026-09-01 says can count towards the required approvals, is not read. Proposed by the flagship agent in slice 2b.5. **Status.** Accepted, 2026-11-13.

### D-049 A ruleset's rule types and classic protection's fields are each read or named, and one the rules do not know makes them "cannot tell"

**Decision.** The settings rules that read a branch's requirements (`OBAAF-SET-004` to `OBAAF-SET-008` and `OBAAF-SET-013`) place each of the 25 rule types of GitHub's REST reference for rulesets, read on 2026-11-13, in one of six groups in the code: the two they read (`required_status_checks`, `pull_request`); seven that make a merge wait for a result workflows, tools or deployments give (`merge_queue`, `required_deployments`, `workflows`, `code_scanning`, `code_quality`, `code_coverage`, `license_compliance_scanning`), which `OBAAF-SET-004` counts as something a bypass skips, `OBAAF-SET-006` answers "cannot tell" for (`OBAAF-SET-007` for the merge queue) and a finding of `OBAAF-SET-008` names (all but the merge queue); `update`, which `OBAAF-SET-005` names as something it cannot weigh; `copilot_code_review`, which a finding of `OBAAF-SET-005` names; and fourteen that neither ask for a check or a review nor decide who may merge. A type in none of the groups makes those rules "cannot tell" for its branch, naming it, whatever its parameters, wherever they would otherwise answer from the branch's requirements (`OBAAF-SET-013` only where workflows may approve pull requests, `OBAAF-SET-004` only for a ruleset someone may bypass or whose bypass list was not read), with a finding by count staying a finding and naming it. The reader keeps every field of classic branch protection that the reference's two examples and the update's body do not show (inside an entry of the required checks included), and every known one in another form that the reader would otherwise record as not known and pass over (a known object that is something other than an object or null, a flag's `enabled` that is not true or false or is missing; some other forms make the whole setting unread instead), with its value, under `other_fields` in the snapshot, written only when there is one; such a field makes the same rules "cannot tell" (one about the checks for the check rules, one about the reviews for the approval rules, any other for both, and `OBAAF-SET-004` for all). A parameter of a ruleset's `required_status_checks` rule, or a field of one of its checks, outside the reference makes the check rules "cannot tell". Classic push restrictions and a locked branch are named by `OBAAF-SET-005` as `update` is. A "cannot tell" about how many approvals or which checks a branch requires names what could not be read.

**Reason.** The same fault as D-048, one level up: a rule type or a field nobody has read was read as asking for nothing, so "not read" passed as "nothing wrong" (D-040, D-045). Listing what is known is what lets a new one be noticed. The seven result-waiting types are named rather than left out because each can block a merge or be skipped by a bypass, and what gives their result is not something the audit reads. Keeping a classic field's value, not only its name, lets drift (D-046) see it change. Writing `other_fields` only when there is one keeps every snapshot taken before this decision valid and equal to one taken now of the same settings.

**Consequence.** A new rule type or classic field from GitHub turns those rules into "cannot tell" for the branch that carries it until OBAAF places it, which takes a release. Repositories with a merge queue, required deployments, required workflows, code scanning, code quality, coverage or licence compliance rules get a "cannot tell" from `OBAAF-SET-006` or `OBAAF-SET-007` for each, for as long as the audit does not compare them with the workflow files; and a bypass of a ruleset whose only gate is one of four of them (deployments, code quality, coverage, licence compliance) is now a finding of `OBAAF-SET-004`. A snapshot with `other_fields` is refused by a version older than this one; a snapshot taken before it, compared with one taken after, shows `other_fields` as added where GitHub's answer has such a field, which may be a field it sent all along. No real answer for classic protection has been read, so which fields GitHub really sends beyond its examples is not known. Proposed by the flagship agent in slice 2b.6. **Status.** Accepted, 2026-11-13.

### D-050 An egress control clears OBAAF-GHA-020 only where every condition that makes it hold is read from the workflow and the repository

**Decision.** `obaaf check` reads every egress control an agent job might have and keeps the one that comes out best. Two can be verified. GitHub's native egress firewall is verified when every run of the job is on `ubuntu-24.04-firewall` and the repository's `.github/egress-firewall.yaml` (that name exactly) sets `mode: enforce`, with a token that has `contents` permission; it is read only when a repository is checked. OBAAF's egress action is verified at a commit OBAAF lists as released (`egress_action_releases`, empty today), with a written allow-list with no public suffix at or under any name (OBAAF ships the public suffix list, MPL-2.0), on GitHub-hosted `ubuntu-24.04` and not in a container, with no step but `actions/upload-artifact` after it or beside it, no earlier step that names `/tmp` or the scratch directory, uses `&` as an operator, or mentions a container engine, a terminal multiplexer or a detaching command (a process started another way is not read), and with the agent as its command. Where the agent runs is read from where credentials go: a secret (`GITHUB_TOKEN` included) or `github.token` given in the workflow to another step or to the job's or workflow's `env`, `id-token: write`, a token with the `models` permission (every action receives the token), or an agent the checker recognises in another step, is "not met"; undeclared token permissions are "cannot tell"; a credential given to the confined command is "cannot tell" until slice 2c.4; and a job that gives no step a credential is "cannot tell" unless the checker recognises the agent in the action's command or a script it runs. Harden-Runner is never verified: whether the repository is one its tier covers is not in the workflow. It is "not met" at a listed release before v2.16.0, without `disable-sudo-and-containers: true`, or in a container on a GitHub-hosted runner, with its version read only from a list of release commits OBAAF ships. The Agent Workflow Firewall from a script is "cannot tell", or "not met" with `--enable-dind`. A cleared finding's control says what the control does not stop.

**Reason.** The plan's entry for 2c.3 asks for a control to clear the finding "structurally: the step, not a declaration", and for "cannot tell" wherever a condition cannot be established. The firewall's README gives everything needed to read it from the repository, and sits outside the runner. The action wraps one command, so the questions are whether the agent is that command and whether anything with the full network runs what it wrote. The second cannot be read from scripts, which can reach the scratch directory in endless ways (the first review of this slice found several), so only a step that saves files as data may follow. On the first, the checker recognises few agents by name, and an agent needs a key, so the key is the evidence (the plan's own suggestion, from slice 2c.1). For a job with no key the evidence is gone, and the plan asked this slice to say what to do: an agent that needs no key could run in any step, so only an agent the checker recognises inside the action counts. A credential inside the action is not counted as verified because the action refuses model-key names and the proxy's DNS channel is open (2c.4). No commit of the action is listed because listing one is a maintainer's act on a commit the escape tests passed on; until then the action is "cannot tell". Harden-Runner's own source at v2.16.0 falls back to audit mode when it cannot reach its cache, and on some errors in fetching from its policy store, which a workflow cannot show; it sets up nothing in a container on a GitHub-hosted runner; and its free tier does not cover private repositories.

**Consequence.** An adopter on GitHub's native firewall can clear the finding today. One that wraps its agent in OBAAF's action gets "cannot tell" until a maintainer lists a released commit, and then "verified" only for an agent that needs no key or that the checker recognises, until slice 2c.4 supports model keys. A Harden-Runner step without `disable-sudo-and-containers: true`, or before v2.16.0, is now "not met", a new case of the rule (`weak-monitor`), so a baseline entry that accepted it as "cannot tell" stops counting. A job that runs `awf` in a script is the case `awf`, not `none`. The release lists (Harden-Runner's and OBAAF's) are data in `detection.yaml` that must be kept current; a release of Harden-Runner after 2026-11-13 is "cannot tell" until it is added. The public suffix list ships as of 2026-11-13 (commit `71c235d` of `publicsuffix/list`) and ages too. Proposed in plan slice 2c.3. **Status.** Accepted, 2026-11-13.

### D-051 The egress control gives AWF's proxy a resolver that answers only listed names, and gives model keys to AWF's API proxy only

**Decision.** `actions/egress` starts a resolver of its own on the runner for each run, on the address of Docker's `docker0` bridge, and gives it to AWF with `--dns-servers`. The resolver forwards a query to the runner's own resolver only when its one question, in class IN, names a host the allow-list covers or exactly the API host of a model key given, every label being letters, digits, hyphens or underscores and nothing else; what it forwards is rebuilt from the query's ID, its recursion flag and that question. Every other query is answered `REFUSED` (or `FORMERR`) on the runner. It is started with `sudo` to bind port 53, then runs as `nobody`, logs what it allowed and refused outside the scratch directory, and stops when the step does. Before the command starts, the action checks that it refuses the probe's unlisted name and answers the first listed one; if not, or if it stops before the command ends, the step fails with status 3. The escape tests assert that a name asked of the proxy (over HTTPS and over plain HTTP, the proxy named explicitly) reaches the resolver and is refused there without leaving the runner, that a name the command looks up itself does not leave the runner either (it goes to Docker's resolver, not this one), and fail if any unlisted name the attempts use leaves the runner in a DNS query. A new input, `model-keys`, takes `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` from the step's environment and puts them in AWF's environment, from which AWF gives them to its API proxy sidecar; the command gets AWF's base URLs and placeholders, never the keys. AWF's policy for the providers' hosted web tools is set to `enabled: false` on every run; by AWF's source, it applies to HTTP requests whose body AWF's proxy parses as JSON, not to WebSocket upgrades. Other model keys and GitHub tokens stay refused under both inputs. This decision amends D-047, which refused all model keys, and D-050 where it ties a credential given to the confined step to this slice: such a step stays "cannot tell", now because the checker does not yet read `model-keys` or tell a key given to AWF's API proxy from one passed to the command (plan slice 2c.5), not because the DNS channel is open or model keys are refused.

**Reason.** Slice 2c.2 showed a refused name leaving the runner in a DNS query, a channel for data out of the sandbox. AWF's proxy resolves a name to test an access rule of type `dst` placed ahead of the rule that refuses unlisted names, and neither that order nor the API proxy can be changed from outside AWF in its default mode; choosing the resolver it uses can. A resolver that answers only listed names closes the channel without changing AWF, and it fails closed: if it stops, nothing resolves. Labels limited to plain characters stop a label holding a dot from passing for a listed name while being a name under another domain. Model keys: the first adopter's 19 agent jobs each hold a model key, so an egress control that refused them could not be used by any of them; AWF's API proxy is an inference proxy of the kind OBAAF-GHA-005's fix text asks for: it keeps the key out of the command's reach, though the step still holds it. ### D-054 The egress control keeps the runner's listening programs out of the command's reach, and hands back only files and directories

**Decision.** Before the run, `actions/egress` finds every socket and named pipe then in the runner's `/tmp` (which AWF mounts into the sandbox), on its own file system, that the runner's user could write, and sets each one's mode to none for the run. It gives the modes back only once AWF has exited and Docker shows no container started for the run still running; if one is left or Docker does not answer, the modes stay as they are for the rest of the job and the step fails with status 3, and if the run ends in an error they stay as well and the step fails. The probe fails, and the command does not run, if the command can still write a socket or pipe under `/tmp`, `/run`, `/var`, `/home` or `/etc` outside the scratch directory. After the run every symbolic link, named pipe, socket and device file under the scratch directory is deleted, as root and without following links, and listed in a new output, `removed`, which keeps only the characters of a plain path; if any is left the step fails with status 3. A workspace is refused, with the new output `refused` set to `credential` (the inputs the first step refuses leave it empty), when the `config` or `config.worktree` file of any repository in it holds an `extraheader`, includes another file (`include`, `includeIf`) or has a remote URL with a password: the first two are how `actions/checkout` before v6 and from v6 on keep the token. The `denied` output takes a refused request's target, not its `Host` header, and keeps only the characters of a host name and port.

**Reason.** The first review of the whole action on Opus 5.5 (slice 2c.6) found two ways out through the runner's disk rather than its network, and the escape tests confirmed the first on GitHub-hosted `ubuntu-24.04`: the runner's `/tmp` held two .NET diagnostic sockets and four .NET debugger pipes, and from outside the sandbox both sockets answered a diagnostics request and all four pipes were writable. A read-only mount does not stop a connection to a socket, and the diagnostics protocol can make a .NET program write a dump of its memory or load a library; the command runs as the runner's user, so only the socket's mode stood in its way. The command cannot change a mode on a read-only mount and has no capability that would let it ignore one. The second: a link left in the copy is followed by a later step that reads or uploads the copy with the runner's access, so the copy would carry `/proc/self/environ` or a file under `RUNNER_TEMP` out of the job. Checkout v6 and later write an `includeIf` instead of the token, so the old refusal no longer fired.

**Consequence.** The copy loses its symbolic links, those the repository had included (`node_modules/.bin`, for one); a later step sees them named in `removed`. A .NET program on the runner cannot be reached through its diagnostic socket or debugger pipes while the command runs (the runner's own diagnostics tools neither). A socket or pipe a program creates in `/tmp` after the probe is not covered. The action needs `sudo` for `find`, `chmod` and the deletion, as it already did for its resolver and clean-up. A workflow that relied on `persist-credentials: true` with checkout v6 or later now fails before the command runs. The checker's floor for a listed release of the action (`egress_action_floor`, slice 2c.5) moves to this slice's last change to the action, so no commit without these fixes can be listed. Proposed in plan slice 2c.6. **Status.** Accepted, 2026-11-16.

The findings' facts gain what was read, the triggers, the job's and step's `if:` (OBAAF-GHA-002 and 012), for "cannot tell" a digest of everything in the file the value can depend on, the credential kept, whether the job runs an agent and what the job token can write (OBAAF-GHA-011), and the triggers and the value (OBAAF-GHA-019). ### D-071 The egress action removes every `OPENSSL_` variable from its own step process before the import that initialises libcrypto

**Decision.** From flagship slice 2c.11 (issue #195). Before `egress.py` imports `hashlib` — which initialises the runner's libcrypto in the action's own step process, where the model key is held — it removes from that process's environment every variable whose name, trimmed and upper-cased, begins `OPENSSL_`. Only `os` is imported before the removal; `hashlib`, `secrets` and `urllib.request` (and so `ssl`) are imported after it. The name is matched trimmed and upper-cased (`OPENSSL_CONF`, `openssl_conf`, `" OPENSSL_ODD "` all go), a superset of the exact upper-case names libcrypto reads, so no spelling is left for a later import. libcrypto also reads `SSL_CERT_FILE` and `SSL_CERT_DIR`, which do not begin `OPENSSL_` and are the one class of libcrypto-read variable the removal deliberately leaves alone: they redirect which certificates TLS trusts (data, not code), and the action's only download (AWF's binary) is checked against a pinned SHA-256, so redirected trust changes nothing it accepts. The removal changes only the action's own three step processes: not the job's other steps (each is a new process), and not the command AWF runs, which is given a clean environment of its own (`child_env` in `run()`, and AWF's env-file). The dynamic loader's variables stay handled in `action.yml` (each step's `env` empties `LOADER_VARIABLES`, D-069), because `ld.so` reads them before Python starts; OpenSSL's are read later, from inside Python, so they are removed in code. An `openssl-modules` escape job on GitHub-hosted `ubuntu-24.04` plants a shared object whose constructor writes a marker line when libcrypto loads it — and only in a process that holds `OBAAF_EGRESS_SCRIPT`, as the action's steps do — sets `OPENSSL_CONF` through the job's `env` and the action step's `env` and the FIPS pair (`OPENSSL_MODULES` with `OPENSSL_FORCE_FIPS_MODE` and `OPENSSL_FIPS_MODE_SWITCH_PATH`) through `GITHUB_ENV` — the three ways a workflow can set a variable for the step, which the in-process removal treats alike — and requires the marker for a plain step and for the action at the floor `c1b590c` (slice 2c.9, before this fix) and none for the action now, while the action still runs its command in a sandbox that held.

**Reason.** Slice 2c.10b found (D-070) that the loader's variable list is not the only way to make a library load code the workflow named into the key-holding step: `egress.py` imports `hashlib`, so libcrypto is initialised there, and libcrypto reads `OPENSSL_CONF`, which can name a provider or engine module it then loads; on Ubuntu it also loads a module from `OPENSSL_MODULES` under `OPENSSL_FORCE_FIPS_MODE` or a `OPENSSL_FIPS_MODE_SWITCH_PATH` file holding `1`. These are read from inside the process, after it starts, so — unlike `ld.so`'s variables — they can be removed from `os.environ` before the import that reads them, rather than having to be emptied in the step's `env`. Removing every `OPENSSL_` name, not the few shown to load a module, matches D-070's checker side (libcrypto reads more names than were tried) and lets the checker later drop all `OPENSSL_` names rather than a list. Removing (not refusing) was chosen because the action's own steps need no OpenSSL configuration — the system default at `/etc/ssl/openssl.cnf` still loads when `OPENSSL_CONF` is unset, so TLS in the install step's download is unaffected (checked: a TLS context still builds and `hashlib` still computes after the removal) — and because a job may legitimately set `OPENSSL_CONF` for its own other steps, which the in-process removal leaves alone. Reproduced for this slice on Ubuntu 24.04 with `/usr/bin/python3.12 -I -S` and libssl3 3.0.13 (the runner's versions): with `OPENSSL_CONF` (or either FIPS route) set, the floor's `egress.py` loaded the planted module when run the way a step runs it, and this slice's `egress.py` loaded nothing, while still producing the same digest.

### D-074 A result file to send back holds counts and OBAAF's own words only, checked before it is written, and comes from `python -m obaaf.result` until a core slice adds it to `obaaf`

**Decision.** From flagship slice 3.8 (issue #89). `python -m obaaf.result PATH --output FILE` runs `obaaf check` on PATH with the `--config`, `--baseline`, `--fail-on` and `--platform` it is given (the command line's own code, in the same process, so the counts and the exit status are those `obaaf check` gives) and writes a JSON file, format `obaaf-result/v0.1`, for someone who tried OBAAF to send to its authors. The ceiling on numbers and one row per rule bound how much an altered report can carry; they do not stop it, as the second review showed with twenty rows of small counts. The file is only as honest as the reports it counts, and the page has the reader write those reports and read them. Counting the jobs in each lane with and without the configuration measures what OBAAF's distinctive idea depends on (on the first adopter, 19 agent jobs with its configuration and 2 without), with no names. `cli.py` is the checker's shared code, which the plan lets only a core slice change, and a core slice was held by another run when this was built, so the command is a module of its own, with its own parser, that a core slice can add as `obaaf result` in one line.

**Consequence.** No finding, report or exit status of `obaaf check` or `obaaf audit` changes. The file counts what this version knows: a rule, control, lane or setting added later is counted as `other` until the vocabulary has it, and a test fails when the checker gives a control or lane the vocabulary does not have. The counts can still say something about a repository (how many agent jobs, how many findings of a rule, whether it is private), and the page says so and asks the reader to read the file before sending it. The page pins a commit, which has to be moved whenever `src/obaaf/result.py` changes (a test compares the two), and once a release has the module the page should install that release instead. The page's install takes Python 3.10 to 3.14: the locked PyYAML 6.0.3 has no file pip takes for 3.15, which is the `python3` of GitHub's macOS runner, so the block stops there with a message and the page says to name another Python in `OBAAF_PYTHON`. CI runs the page's blocks as written on GitHub-hosted Ubuntu and macOS runners, as an advisory job. **Status.** Accepted, 2026-11-18.

Under `selected` and `local_only`, a file that uses a local action, a `docker://` image (in any letter case) or an empty `uses` is one GitHub may not run, because a local composite action's steps, and whether the setting covers an image, are not read; so is every file under a value of `allowed_actions` the audit does not know. (4) A file in a cycle of calls (one that calls itself included), or that starts a chain of more than three nested calls, is one GitHub may not run. The spread of "may not run" to callers is a breadth-first walk, and a file's reason is its first call, in job order, to a file found one step nearer the cause. (5) `OBAAF-SET-007` weighs a job in a file GitHub may not run (one in a file GitHub may read otherwise never decides its answer): a paths filter, activity types or triggers that keep a required check from reporting do so whether the file runs or not. Such a job never stands for the check. Where the route that decides gives a finding, any other job that may report the check on a route that gives none, a job under names that could not be written out or in a file GitHub may read otherwise included (read at its widest), or a paths or activity-type route in a second file, makes the answer "cannot tell", and so does any other job that may report the check where every job known to report it is in a file GitHub may not run and reports it on every pull request (counted widely there: another job of the same file, or one that never runs on a pull request's commit, also counts, which can give "cannot tell" where there is nothing to find; issue #209); a job that never runs on a pull request's commit changes nothing.

**Reason.** Each gap gave "no finding" or a pass where the audit could not tell: a file GitHub refuses counted as reporting its checks, an empty allow list let every action through, and `$/` calls were not compared at all. The pages that would settle what GitHub does could not be read from the session that wrote this (each fetch of docs.github.com and github.blog timed out waiting for an approval): the job-id form is GitHub's workflow syntax as the author knew it, the 100-character limit is in GitHub's error message as the author knew it and so is only a doubt, and the matching of the allow list was not read, so only the two forms whose meaning does not depend on how GitHub matches are credited. The nesting limit (the caller and three levels of reusable workflows) is GitHub's reference as the author knew it; a later limit may be higher, so a deeper chain is a doubt. That is safe for the rules about required checks; if the limit is higher (the review recalled ten levels, which was not read either), a chain of four calls or more, up to that limit, loses `OBAAF-SET-008`'s findings to "cannot tell", and `OBAAF-SET-006` says "cannot tell" where it said nothing. The review of the slice found that the first version silenced `OBAAF-SET-007`'s paths finding for every file it newly took as one GitHub may not run, which is why (5) is part of the decision; the second review found that its first form let such a file stand for the check and hide the finding of a file sure to run, and that naming a cycle's members cost the square of its size; the third found that a job whose names could not be written out was no rival either, and that an equal entry let another repository's reusable workflow, whose jobs are not read, count as running; the fourth found that comparing routes by rank let a dispatch route, a skipped job with a computed name or a second filter sit beside a finding, and that taking `Docker://` for an image (as the checker does) made a file GitHub may refuse one that runs, so that change was taken out (issue #209); the fifth found that a file GitHub may not run could still stand for the check when every known route was in one, that a never-running rival counted or not by its name, and that two jobs of one file were taken for two filters. Reading the `$/` call is the widest reading for the rules that ask which events reach a job (`OBAAF-SET-002`, `OBAAF-SET-011`); not counting it as running is the safe reading for the rules about required checks.

**Consequence.** More answers are "cannot tell" (which fails only with `--fail-on-cannot-tell`): every required check whose job uses an action under `selected` that is not GitHub's own or listed exactly, a wildcard entry included, or a local action or image under `selected` or `local_only`. A repository that allows actions by wildcard loses those answers until the matching is read and written; that is the price of not guessing it. A gate can pass where it failed: every rule that reads workflow files gives "cannot tell" for a file with a job id GitHub refuses, where it gave that file's findings; `OBAAF-SET-008` is "cannot tell" for a job in a file GitHub may not run, `OBAAF-SET-007` where another job may report the check on a route that gives no finding or a second filtered route may cover what the first leaves out, `OBAAF-SET-012` no longer reports an undeclared `$/` caller of a workflow whose jobs all declare their permissions, and `OBAAF-SET-002` and `OBAAF-SET-011` can answer "no finding" about a `$/` call where they said "cannot tell". `OBAAF-SET-002`, `007`, `011` and `012` can report what they did not, in the shapes in the upgrade note. On this repository's committed snapshot and the first adopter's recorded settings, the JSON report is byte-identical before and after; neither snapshot holds the Actions permissions, so that does not exercise (3). Not covered: whether GitHub takes `$/` in a job's `uses:`; GitHub's matching of `patterns_allowed`; the owner's own actions under `selected` and `local_only`; what another repository's action uses in turn, which the list may also have to allow; whether GitHub reads `docker://` in another letter case, or a `uses` with space around it, and whether its pinning requirement covers images (issue #209); GitHub's current nesting limit. **Status.** Accepted, 2026-11-18.

### D-077 Every settings rule says in one sentence why a finding matters, printed before its fix, and the JSON report carries the sentence and the fix

**Decision.** From flagship slice 3.2c (issue #202, left by slice 3.2b). Each rule of `obaaf audit`, `OBAAF-SET-001` to `OBAAF-SET-015`, has a `why` in `src/obaaf/audit/rules.py`: one sentence of at most 160 characters, ending with a full stop, held to the same form as the `why` of the rules of `obaaf check` (D-073), and written to hold for every kind of finding the rule gives, with "may" where a kind does not show the consequence. The field is required: a rule defined without one is an error when the module loads. The text report prints it as `Why:` under each rule's findings, just before its `Fix:`; `--no-fixes` leaves out both, and its help says so. A rule whose only answers are "cannot tell" gets neither. In the JSON report each entry under `rules` gains `why` and `fix`, the rule's own sentences. `docs/settings-audit.md` lists every sentence, and a test keeps the two equal.

**Reason.** The brief asks that a first run explain each finding, why it matters and the exact fix. After D-073 `obaaf check` did, and `obaaf audit` gave the finding and the fix only. The audit's rules are not in the catalogue (they live beside the code that applies them), so their sentences live there too, checked by a test that applies the catalogue's sentence tests (the same pattern and limit, imported from `obaaf.catalog`) rather than by `obaaf catalog`. The line goes once per rule, before the fix, because the audit's report groups a rule's findings under one heading and prints one fix for them; printing it per finding would repeat the same sentence. A "cannot tell" gets no `Why:` because a sentence about what a finding exposes would read as if something had been found. The JSON entry had the title and no fix; a tool that turns the report into comments or annotations needs both, and adding the fix with the sentence costs one key.

**Consequence.** A text report without `--no-fixes` is one line longer for each rule that has findings; a report with `--no-fixes` is unchanged. A JSON consumer sees two new keys on each rule's entry; the format stays `obaaf-settings-audit/v0.1`, and `python -m obaaf.result --audit` reads the report as before and writes neither sentence. `scripts/check_live_audit.py` rebuilds the report with the same function, so the scheduled live run is unaffected. No finding, "cannot tell", exit status or snapshot changes. The fifteen sentences are claims about each rule's risk, not about what the audit reads; they were written by the run that made the change and reviewed by an agent that did not write them, which built a fixture for each kind of finding it doubted. It found five that stated as certain what some of the rule's findings contradict or do not support (`OBAAF-SET-002` in a private repository, `003` where the environment does not exist, `005` beside Copilot's review, `008` beside another rule a merge waits for, `011` where the called job declares the environment), and five more whose wording did not fit some kind (`004`, `007`, `010`, `012`, `014`); those ten, and `001` for plainness, were reworded. Not covered: `obaaf audit --expected`'s drift lines, which are not rules, get no sentence; the website does not show the audit's output. Two faults older than this decision, found by its review, are issue #212: `OBAAF-SET-011` may report a secret passed by name to a called job that declares the environment (its sentence says "may" for that reason), and `OBAAF-SET-001` and `002` do not weigh custom deployment protection rules, which their sentences' "at most one reviewer's approval" and "no reviewer to approve" do not account for either. **Status.** Accepted, 2026-11-18.

### D-078 The settings report quotes every name it lists, and prints a single value bare only when it is one plain word

**Decision.** From flagship slice 2b.8 (issue #125, found by the review of slice 2b.6). In the "What was read" part of `obaaf audit`'s text report, every item of a list of names (required checks, an environment's patterns, reviewers and other protection rules, secret names, a policy's events and workflow paths) is printed with `quoted`, as the rules' findings already print names. A single value from GitHub or a snapshot (a ruleset's enforcement, target and source, a policy's enforcement and source, the repository's visibility, default branch and owner, a bypass actor's type and mode, a pattern's kind, the enforcement level of the public view's checks, the default token permission, the fork approval policy, the allowed actions, an unknown policy rule's type, and the header's repository asked for and address read from) is printed as it is when it is one word of ASCII letters, digits and `_ . : / @ + -` beginning with a letter or digit, and quoted otherwise. Inside quotes, a character that reads as `"` or `\` becomes `?`: the list `quoted` had, more look-alikes the review found, and any character whose compatibility form holds either. The dated record `docs/expectrail-settings-audit.md` keeps the report's words of 2026-11-13 and says so; its test compares the record, to the character, with today's report after undoing this one change (the quotes on names after the first on each line).

**Reason.** `plain` takes out what moves the cursor or hides, but leaves commas, brackets and quotation marks, so a name could close a list early and read as the next entry: issue #125's check name read as a second rule of a type the audit does not know, and a check named `test (3.13)` already read as a name and a remark. A name in quotes, with its own quotes escaped and the listed look-alikes of the quote and the backslash replaced, cannot close early by those characters; the review found two kinds it does not catch (below). GitHub's own words for a setting are plain words, so they print as before; a branch or owner name with other characters is now quoted, which costs a pair of quotes. Quoting every single value as well would make every line harder to read for no gain. A record of a dated run is evidence of what was printed; rewriting it to the current wording would make it a record of nothing. The review showed that comparing only the names it holds missed 15 of 20 changes to the record, so the test undoes the known change and compares exactly; a later change of wording adds its own step there.

**Consequence.** Every report's "What was read" lines change where they list names; a script that picks names out of the text must take the quotes off, and the upgrade note says the JSON report is the place to read them. For a name that holds one of the newly listed look-alikes, `quoted` now shows `?` there wherever the audit quotes it: in the rules' subjects and messages (text and JSON), in drift lines, and in the labels of problems in a new snapshot, and results sorted by subject may come in another order. Which findings and "cannot tell" answers there are, their severities, the exit status and the keys drift compares by do not change; for names without such characters the JSON report and the snapshot are byte-identical. Not covered, and still printed with `plain`: the reasons a setting was not read or does not apply (GitHub's error messages among them), what GitHub's reference says a setting needs, the permissions GitHub said it would accept, the part a problem names, the reader's own label for a branch it could not read (`NOT READ: branch ...`, which comes from `settings.py` and is kept in snapshots), and a job's file and id in the rules' messages (`_job_label`); the rules' messages quote the other names they give. Right-to-left letters can reorder a quoted name in a viewer that applies the bidirectional algorithm, and a long line can wrap. A combining mark such as U+030B after a space, and two apostrophes, can still pass for a double quote inside a quoted name. These are older than this decision. **Status.** Accepted, 2026-11-18.

### D-081 An agent inside a local composite action makes the job an agent job

**Decision.** From flagship slice 2d.4a (issue #80). A step that uses an action from the repository itself (`./path`, `$/path`, and for an agent also `.\path` and the path with space around it) makes its job an agent job when the action is a composite action and an agent runs in its steps. The steps are read for an agent as a job's steps are, with more put in: each `${{ inputs.name }}` from the using step's `with:` or the action's `default` (also inside `( )`, `||`, `&&` and `format()`, and any other expression as each input it reads), the using step's `env` (also as `env.NAME`, with its own inputs put in), `github.action_path` in any spelling, and scripts looked for from the repository's root, and from the action's folder when the step goes there with `working-directory`, `cd` or `pushd`; further local actions are followed up to ten deep. Both `action.yml` and `action.yaml` are read when both exist, and the path is read with and without what follows an `@` and with backslashes as slashes, because what GitHub does there was not checked; an agent in any reading counts. A reading is kept for other uses of the same folder, values of the inputs its expressions read and environment; one a cycle or the depth limit cut short only for a use in the same place in a chain. The step is recorded for OBAAF-GHA-020, which names the action when the agent runs outside the confined command.

What cannot be read through is named in one note (the first five places, and a count of the rest): a JavaScript or Docker action, a missing file, a path outside the repository or with an expression, an expression that reads an input or the environment nested more than 64 parentheses, or eight `||`, `&&` or `format()`, deep, or that can give more than 16 texts, an input or `env` value too long once put in, a `runs.using` it does not read, `runs.steps` not a list, a step not a mapping, a cycle, a chain more than ten deep, and any local action of a file checked on its own. An action file that is not YAML the checker reads (a parse error, a duplicate key, a tag, a disputed line break), is not a mapping, cannot be opened or is over 1 MB is an error of the check, as is a check whose local actions would cost more units to read than it spends on them (30,000 for the check, and 100 for each step of a job that uses a local action, which only that step's reading may spend; a reading costs one, three for each step read, and one for each 200 bytes of its files or characters its caller's inputs add), or nesting too deep for Python.

**Reason.** Slice 2d.2b's reviewers showed that wrapping an agent in a local composite action took the job out of OBAAF-GHA-003, 004, 005 and 020, the rules that apply to a repository's agent jobs. This slice's reviewer then got past its first version in eight ways (a reading cut short in one workflow reused in another; `@` and `.\` in the path; other spellings of `github.action_path`; the using step's `env`; inputs inside larger expressions; and slow inputs), found three more faults in its second (a slow `env`, deep parentheses, and a bound an ordinary large repository could reach) two in its third (a comparison inside a function that dropped an input, and a bound that counted readings rather than steps) three in its fourth (an `env` value set from an input, values dropped past the limit without a note, and a bound blind to a step's size) two in its fifth (`format()` that did not combine its arguments' values, and a bound blind to the text a caller hands on) and two in its sixth (`format()` combinations not made and not named, and a bound an ordinary large repository with realistic actions reached) and one in its seventh (cheap uses that bought budget for a heavy one), each now a test. The time reading local actions takes grows with the size of the workflows and actions and no faster; measured on 2026-11-18, a 150 KB workflow whose 2,500 steps each give a 30-step local action a different input took 17 s (a 250 KB workflow of 2,500 `actions/checkout` steps took under 1 s), and an action whose one step puts its input in 850 times costs about three times as much for each use (about 26 s for 2,500 uses, extrapolated from 200); these are examples, not a proven worst case. That is accepted: it is linear, so a pull request can make the check slow only in proportion to what it adds, and a CI job's time limit fails it closed. Unreadable action files are errors because a workflow file in the same state is one, and its author writes the action as freely. What can be read but not through is a note, not a finding, because taking every JavaScript action of a repository's own for an agent would report every job that uses one, and the lane notes already say where an agent may be missed.

**Consequence.** A job whose agent runs in a local composite action now gets the agent rules, and a repository with an action file the checker cannot read now fails the check; either can turn a gate red (`docs/upgrading.md` has the rows). A run with local actions it cannot read through has one more note. Not covered, and left to slice 2d.4b: a called local reusable workflow (its caller's triggers, secrets and runner); and an action's own `uses`, uploads, caches and checkouts for the rules other than the agent lane's. An action from another repository is not read. A job's `env`, `GITHUB_ENV`, the matrix, scripts without a `.sh` suffix and scripts called by scripts are not followed into an action, as they are not from a job's own steps. The first adopter's report and this repository's are byte-identical before and after. **Status.** Accepted, 2026-11-18.

### D-082 A called local reusable workflow is read with what its callers give it

**Decision.** From flagship slice 2d.4b1 (issue #80). `obaaf check` and `obaaf check --lanes` read every workflow file before they check any. A job that calls a workflow of the same repository (`uses: ./.github/workflows/x.yml` or `$/...`; the path with and without what follows an `@`, and with backslashes as slashes, are each a candidate, as D-081 reads them for an action, but a candidate that leads outside the repository is dropped on its own) gives that workflow's jobs the events that can start the calling job, after the calling job's `if:` and the jobs it needs; the called jobs keep `workflow_call`, which stands for a caller in another repository. A path is matched as git stores it, letter case included, among the files being checked, and a link by its own name, not its target's; a candidate path that leads outside the repository is dropped on its own; a call written as `owner/repo/...@ref` is not matched, even to this repository. A workflow without `on: workflow_call` is given nothing, because GitHub refuses to call it. OBAAF-GHA-001, OBAAF-GHA-005 and OBAAF-GHA-018 (signing secrets, and a job that can read every secret) on a called job carry a new fact, `passed`: for each calling job, what it passes for each secret the job reads (the secret names its expression reads, or the value as written when it names none, `secrets: inherit`, or a computed secret as any secret), followed through callers that are themselves called, each workflow once for each name. A key is compared in any letter case and without space round it, and a key that is not text (`null:`, `true:`, a number) is taken for every name. Each entry is bounded (a long list of secrets in one value is its digest), and past five entries or 1,000 characters the fact is at most the first three and a digest of all of them, so the fact does not grow with what callers pass; working it out still costs what the walk visits, which is quadratic in the length of a chain of calls (about 46 seconds for a chain of 3,000 files; GitHub limits how deep calls nest, which this session did not read). Only a baseline entry names the fact; an `ignore` entry names the rule and the job and still covers any mapping. A workflow no job of the repository calls has no such fact, so its findings are as before. A note names each called workflow read with events its own `on` does not name.

**Reason.** Slices 2d.2b, 2d.2c and 2d.2d recorded ways past rules the first adopter's gate rests on, all through a local reusable workflow: a `pull_request_target` workflow that called a workflow which checks out the pull request's head got no OBAAF-GHA-002; a self-hosted runner reached from a pull request through a call got no OBAAF-GHA-013; and an accepted OBAAF-GHA-005 on a called agent job named only the parameter it reads, so a caller could map another secret onto it and nothing changed. In a called workflow `github.event` is the caller's event and `secrets.NAME` is what the caller passes, so reading the file with `workflow_call` alone missed both.

**Consequence.** A called workflow's jobs can get findings they did not get before, and findings whose facts list triggers can list more of them; OBAAF-GHA-001, 005 and 018 on a called job whose callers pass secrets have a new fact, so an acceptance of any of them no longer matches. Either can turn a gate red (`docs/upgrading.md` has the row). On the first adopter's files the findings are unchanged and the report has one more note. The review's ways past the first version are tests in `tests/test_local_reusable_workflows.py`: an output about 850 times its input through the fact (and again through one long entry, found by the second review), a pass over every call for each file of a chain (and behind a cycle, the second review), a `null:` key read as `NONE`, an `@` reading outside the repository that dropped the one inside, a link given its target's callers, and every file of a chain of invented events holding every name (the third review: 1.1 GB for 4,800 files, now 78 MB). A walk that went through every key of a mapping again for each name (the second review) is fixed by indexing each mapping once and has no test of its own; it was measured (10.2 s before, 5.2 s after, on 10 callers of 1,000 keys into 4,000 jobs). Not covered, and left to slice 2d.4b3: the inputs a caller passes (a checkout of `inputs.ref` stays "cannot tell" at medium), and what a called workflow does counted for its caller (publishing, caches, the token it is given). Left to slice 2d.4b2: a local composite action's own `uses`, uploads, caches and checkouts. A caller in another repository is not seen, and the calling job is not read as an agent job. **Status.** Accepted, 2026-11-18.

### D-083 Every rule reads a local composite action's steps as the job's own

**Decision.** From flagship slice 2d.4b2 (issue #225). After `obaaf check` reads a workflow, each step of a job that uses a local composite action (`./path`, `$/path` or `.\path`, the folders D-081 reads) is given that action's steps, in the order they run:
- the action's inputs put into each expression that reads them, as an expression that gives what the using step hands over: a string for plain text, the expression in parentheses for one `${{ }}`, `format()` for text with expressions in it. A reference to another context stays one. An expression that is then one string is that text (`push: ${{ inputs.push }}` given `false` is `false`), except in `if:` and `continue-on-error`, where it stays an expression: GitHub reads `${{ '' }}` there as false, and the checker reads an empty text there as no condition. A reference to `inputs` the checker does not work out (`toJSON(inputs)`, `(inputs).x`, `inputs.*`, a computed index) is replaced by `format()` of every input's value, the wider reading, and named in the note D-081 gives. A using step whose `with:` is one expression (or any value that is not a mapping) gives that value to every input, and is named in the note;
- `${{ github.action_path }}` as the action's folder;
- the using step's `env` under each step's own;
- the using step's `if:` and the step's own, both, as one expression. A value YAML gives as `false` or `0` is that expression. A condition GitHub reads as a string is always true and adds nothing;
- the using step's `continue-on-error`, when it may be true, over the step's own;
- the workflow line of the job's step that uses the action;
- a name that says where the step is (`./.github/actions/x: actions/checkout@v4`), after the using step's own name, joined by ` > `, when that step has one.

A step that uses another local action is followed by that action's steps. A step with neither `run` nor `uses` is named in the note.

Every rule then runs a second time on a copy of the workflow. In the copy, each such step is followed by the steps it was given, and each job is put in the lanes those steps put a job in (the release lane, for a step that publishes), without changing the lane it is shown in, which decides where its lane notes go. The job itself stays in its own lanes for the first pass. OBAAF-GHA-023 reads the actions' steps as their files write them. The second pass's findings are taken:
- every finding on a step of an action, one for each step, as for steps written in the job;
- a finding on a step of the job, or on the job, of a case (rule, step and kind) the first pass gave there, in place of the first pass's, matched one for one. Its facts, controls and severity then say what the action's steps do, as for steps written in the job, with two limits: it is never less severe than the first pass's, and it is not taken when it is nearer to cleared (fixed before cannot tell before new). Reading through never clears a finding or lowers one;
- a finding of another case on a step of the job, or on the job, when the first pass has none of that rule there at the same or a higher severity, or when the action's steps put the job in a lane it was not in (the release case of OBAAF-GHA-015 beside the first pass's `capability`).

A first-pass finding the second pass does not give is kept as it was. `obaaf check --lanes` shows the lanes of the copy.

Bounds:
- for one job, 1,000 steps of local actions and 2,000,000 characters of their text, counted as the rules read them: with the inputs put in, each alias once for each place it is given, and one for each key and item;
- for the check, 10,000 steps and 10,000,000 characters;
- one text of more than 200,000 characters once the inputs are put in.

Past any of these, the job's actions are not read for the rules and the check has an error for that job; past the check's bound there is one error, and later jobs are not read. There is no error when 2d.4a's reader has already stopped reading the check's local actions: its own error says so. A long text the action writes itself, with no input put in, is read as written. An action's files are read once for the check. An action file the checker cannot read is the error 2d.4a's reader gives; one that only this reading reaches is an error of its own.

**Reason.** Slices 2d.2c, 2d.2e and 2d.2f recorded ways past OBAAF-GHA-002, 006, 008, 014, 015, 016 and 017 through a local action:
- a checkout of the pull request's head given as an input (2d.2c);
- a cache (attempt 015);
- a publish (attempt 111);
- an unpinned action inside one (attempt 015 of 2d.2f; A185 of the audit).

GitHub runs a composite action's steps in the job that uses it. Running every rule again on a fuller copy, rather than teaching each rule to look inside, fixes the class for every rule that reads a job's steps. It also means the rules that weigh what came before (a check before an upload, a step that changes the `PATH` before a check) see the order the steps run in.

A first-pass finding with no counterpart is kept, so that no finding is lost. A counterpart replaces it: the second review showed that keeping the first pass's version let an acceptance survive what the action does. A "cannot tell" finding's digest of what feeds a value did not cover a `GITHUB_ENV` write inside the action, and OBAAF-GHA-005's control "no outsider's input" said verified beside a fetch of a pull request's code inside the action. A replacement is never less severe and never nearer to cleared, so what an action's author writes cannot clear a finding. Lanes are added to the copy only, and its shown lane is left as it was. Adding one to the job, or settling the copy's lane, changed the reason a release finding gives: the first review found a job declared trusted that an action made an effect job, whose OBAAF-GHA-015 lost "declared trusted".

Inputs are put in as expressions because putting in their values (as 2d.4a does for an agent) turns `inputs.ref || github.event.pull_request.head.ref` into the first operand alone and loses the head. A text that would be too long is an error, not left as written: left as written, it hides what its inputs hold. Aliases are counted for each place because the rules read them there.

The bounds are per job and per check. The first adopter's 27 workflow files already give 730 steps of local actions across the check, and 1,000 steps in one job is past what a job written by hand runs. Measured on 2026-11-18:
- the rules over 990 such steps in one job took under a second, once `_bash_env` was worked out once per job. Before, it read every earlier step again for each check of each upload: 98 s for 990 steps read through a local action; 200 steps written in a job took 1.0 s before and 0.3 s after;
- a check that reaches the check's bound (30 jobs each using a 49-step action of 100 KB 20 times) took 11 s, where the code before this slice took 0.4 s;
- 499 uses of a 900 KB action took 1.1 s once its file was read once (102.7 s when it was read for each use);
- 1,000 aliases of a 900 KB text are an error after 26 s, which the code before this slice also takes for that file (in 2d.4a's reading).

These are examples, not a proven worst case.

**Consequence.** A job whose local action checks out a pull request's head, publishes, uses an unpinned action or image, keeps the checkout's token, holds a template placeholder, or expands an outsider's text through an input now gets the findings the same steps written in the job get. A test holds this for 14 cases. A job whose local action publishes gets the release rules, and a job's own finding can become more severe for it (OBAAF-GHA-008 low to high in a release job); a baseline entry written at the lower severity then no longer accepts it. A job's own finding whose facts or controls depend on the steps before it changes when a local action is before it, whatever the action does (a "cannot tell" finding's digest of the steps before it covers the action's steps, and changes again with any edit to the action), and an acceptance of it no longer matches. A check after a local action whose steps write `GITHUB_PATH` can no longer be vouched for: OBAAF-GHA-016 "cannot tell" is added beside what the first pass said. This repository's release job is one, accepted in `.github/obaaf.yml` in Sean's name for him to confirm. Any of these can turn a gate red (`docs/upgrading.md` has the row).

Not changed:
- A local action is still taken to restore a cache whatever it holds (D-062). OBAAF-GHA-006 gives one finding for a job, on the first step that restores, so a cache step inside the action adds no finding to it.
- A check, a monitor or OBAAF's egress action inside a local action clears no finding the first pass gave. A check inside an action does count for an upload later in the same action, as it would in a job.
- What a JavaScript or Docker action does, and an action of another repository.
- An action's `outputs` read in the job.
- `steps.<id>` inside an action is read as the job's. GitHub's metadata page suggests, by an example and without saying so, that it means the action's own steps.
- The secrets rules read the job's own text, so `secrets.X` in an action's step gives no secrets finding. GitHub's contexts page, as the session read it through a summary and not word for word, says the `secrets` context is not available to composite actions.
- The pages read did not say whether the using step's `env` reaches the action's steps, or whether its `if:` and `continue-on-error` cover them. Each is read the way that finds more.
- Rules that read the job's or the workflow's own text, not its steps (the secrets rules), and a release rule's case for a job that holds what publishing needs (OBAAF-GHA-015 `capability`, medium), which the first pass gives and which stays beside the second pass's release finding for a job whose action publishes.
- A template placeholder in an action input's `default` (OBAAF-GHA-023 reads each use of an action's steps as its file writes them; a YAML alias from one step of an action to another gives a finding for each step, where the same in a job gives one).
- A step of the job named like a step of an action (`./.github/actions/x: step 1`) is taken for one.
- A job that publishes in its own step after an action that publishes gets OBAAF-GHA-014 and 016 for each.

Left to slice 2d.4b3: what a called local workflow is given and does. The first adopter's report (27 files, 730 steps of local actions) is byte-identical before and after.

**Status.** Accepted, 2026-11-18. With it, the maintainer chose what becomes of the acceptance written in his name: the `ignore` entry for OBAAF-GHA-016 on `release-pypi.yml` job `publish` is to be replaced by a baseline entry that names that one finding exactly, and the release job is not changed before the release.

### D-084 A called local workflow is read with what its callers hand its inputs and grant its token

**Decision.** From flagship slice 2d.4b3a (issue #228, the first part of 2d.4b3). After every workflow file is read and the calls between them are found (D-082), each workflow that a job of the repository calls, and that names `inputs` anywhere outside `on`, has each `inputs` reference there (`inputs.x`, `inputs['x']`, in any letter case; in `env`, `run-name`, `concurrency`, jobs, steps, and a job's or step's `if:` written without `${{ }}`; not in a job's or step's `name`, which is part of what every finding on it is, nor in a job's `runs-on`) replaced by `format()` of the reference as written and each value a calling job of the repository hands the input:
- the calling job's `with:` value for that name (names compared with A to Z folded and space round them taken off), or, when it hands nothing, the input's `default` as written, or `''`;
- the value as GitHub hands it where the caller runs: the caller's own `matrix`, `strategy`, `needs`, `inputs`, `job`, `steps`, `runner` and `env` are moved under `caller.`, a context no rule reads as anything but a value it cannot work out; `github` and `vars`, the same in both, stay;
- beside it, what the caller's matrix lists for a `matrix.x` it reads (under `include` too, and an `include` or an item of it written as one expression for every name; the whole matrix for a reference to all of it, or for a matrix written as one expression), and what a needed job's `outputs.x` gives (every output of every job the caller needs for `needs.*`, `toJSON(needs)` or a computed name; nothing for `needs.x.result`), each read in the terms of the job that writes it, and followed so to three levels; a `secrets` reference in such a value is moved under `caller.` too, because GitHub refuses a secret in a matrix and leaves an output that holds one out;
- a name the workflow does not declare is put in too, and a `with:` that is not a mapping, a key that is not text and a name with a letter outside ASCII give every input their value, with a note; so does a reference the checker does not work out (`toJSON(inputs)`, `inputs.*`, a computed index).

Workflows are taken callers first (D-082's groups), so a caller that is itself called has had its own callers' values put in first, and a chain carries the first caller's value to the last; a cycle, which GitHub refuses, takes its values as they stand, in one pass. The values are replaced where they are in the parsed YAML, so every rule and its line numbers read them, and only once every replacement is worked out. Each value is read once however many times YAML gives it through an alias, and counted each time it is given. A value's size is counted, alias by alias, before its text is made, and a text in a job's or the workflow's `env` or `defaults` is counted once for each step it reaches, the steps of the local composite actions its jobs use included (counted once those are known, slice 2d.4b2; past the bound the values are put back as written and the local steps read again, counted once; the lanes worked out from the values put in stay, which only adds findings beside the error), since each step reads it again. The values handed to one input may hold at most 500,000 characters, since every reference to it is given them all (the fourth review's 50,000 failed a reusable "run this script" workflow that 20 jobs each hand a 2.9 KB script). Past 1,000,000 characters in one text, 5,000,000 of values and texts for the check, or 1,000,000 places looked at in one workflow, nothing is replaced and the file has a problem, an error of the check that names the bound.

OBAAF-GHA-003's and 004's `inherited` findings (an agent job of a callable workflow that declares no permissions) gain a fact, `granted`: for each calling job of the repository, the write scopes it grants (003) or its `id-token` level (004), followed through callers that declare nothing to the first that declares; a caller that declares nothing and can start on its own grants the repository's default, which the check does not read; one that only another repository can call grants what that caller grants; and a called workflow that can also start on its own holds the default then. The fact is bounded as D-082's `passed` is. The kind and severity do not change.

**Reason.** Slice 2d.2c recorded a way past OBAAF-GHA-002 that the first adopter's kind of gate rests on: a `pull_request_target` workflow that hands the pull request's head to a local workflow as an input, which checks it out. Since D-082 that was "cannot tell" at medium; GitHub's `inputs` in a called workflow are what the calling job's `with:` evaluates to, so the head is what is checked out. The same reading makes an outsider's text handed to an input and expanded in a script OBAAF-GHA-010, where it was nothing. The reference as written stays among the values because another repository may call the workflow (as `workflow_call` stays among the events in D-082); it never lowers a finding, so a checkout of an input handed only the base is still "cannot tell". The caller's own contexts are moved under `caller.` because the called workflow's `matrix` and `needs` are other values: the first review showed nothing, but a test shows that reading the caller's `matrix.t` as the called job's would have reported the called job's matrix. The first review then found an outsider's text in the caller's matrix, or a needed job's output, handed on with no finding at all, so those are followed; the second found the wider forms (`needs.*`, `toJSON(needs)`, two levels of outputs, an output that reads its job's matrix, a matrix made from an output), so they are followed to three levels, and a false OBAAF-GHA-001 from a secret in an output, which GitHub does not pass on. Putting the values in place, rather than teaching each rule to look up a caller, is how slice 2d.4b2 read a local action's inputs (D-083): every rule that reads a value reads them. For the grant, GitHub gives a called job that declares no permissions the calling job's token, so an acceptance of `inherited` written while every caller granted read only covered a caller that grants `contents: write`.

The bounds are the reviews': 100 jobs handing 100 aliases of a 100 KB value took 128 s; a 1 KB caller whose matrix doubles through aliases at each of 22 levels ended in a `MemoryError` traceback, because its text was made before it was counted; a wide matrix scanned again for each reference took 147 s for 48 KB; 10,000 inputs sharing a 200 KB default took 1.9 GB and, at 20,000, ended in a `MemoryError` traceback; 1,700 callers handing distinct values to 100 steps put 9.2 M characters in and took 26 s; one 85 KB text given through 100 aliases of a step took 26 s. Measured on 2026-11-18 after the fixes, on the reviewer's files: 4.8 s, 1.8 s, 1.4 s and 1.1 s (the code before this slice: 5.1 s, 1.8 s, 1.1 s and 1.2 s). The first two now do no work at all, because their called workflow names no input outside `on`; with a reference added (tests in `tests/test_called_workflow_inputs.py`) they are errors in 4.5 s, all of it the caller's own file, and 0.7 s. The last two are errors past the check's bound. `granted` is worked out once per workflow and scope: 1,000 agent jobs and 2,000 callers took 22 s, and take 2.1 s (1.8 s before this slice). These are examples, not a proven worst case. GitHub's own pages on reusable workflows were not read in the session; the readings above are the wider ones where it was not sure (an undeclared name, a name outside ASCII, whether a caller's `env` exists there).

**Consequence.** A called workflow that reads `inputs` can get findings it did not get before (OBAAF-GHA-002 high, 010), and a "cannot tell" finding there lists the caller's values in what it reads and in its facts, so an acceptance of it no longer matches; so does an accepted OBAAF-GHA-003 or 004 `inherited` on a called agent job whose callers are in the repository. Either can turn a gate red (`docs/upgrading.md` has the rows). This repository's report and the first adopter's (its one call hands no input and its called workflow declares its permissions) are byte-identical before and after.

Not changed, and stated:
- A job's `runs-on` is left as written: OBAAF-GHA-013 does not work out `format()` there, and the third review found its fork-safe selector (`... && inputs.runner || 'ubuntu-latest'`) raised from info to medium once it was put in. So `runs-on: ${{ inputs.runner }}` handed `self-hosted` is still "other labels" at medium.
- A list or mapping `runs-on` (`[...]`, `labels:`) is left as written too (the fourth review).
- A job's and a step's `name` are left as written: the third review found an edit to a caller's matrix change the acceptance of an unrelated pinning finding on a step named `Test on ${{ inputs.os }}`.
- Literal text in a value is an argument of `format()`, not part of its template (2d.4b2's reading of a local action's inputs too): the third review found `${PREFIX}` in a value, written `${{PREFIX}}` in a template, make a condition without `${{ }}` read as text, so it stopped narrowing to `push`; the fourth found GitHub's own escape, `${{ '${{' }}`, do the same, so `${{` in any string of a value is written `${ {`. - What a called workflow does (a publish, a cache, a release) counted for the job that calls it, a same-repository call written `owner/repo/...@ref`, and a called job's own `if: github.event_name == ...` with a caller of another repository are slice 2d.4b3b's.

### D-085 What a called local workflow does counts for the job that calls it

**Decision.** From flagship slice 2d.4b3b (issue #228, the rest of 2d.4b3). `obaaf check` and `obaaf check --lanes` now classify every workflow file, and read the repository's scripts and local actions it uses, before they check any; what that reports for a file (an action file that cannot be read, a bound passed) is held back and reported with the file, in the order it was before. Then, for each job that calls a workflow of the same repository by its path (the calls D-082 matches), what the called jobs do is worked out, callees first, through the calls they make in turn (a cycle, which GitHub refuses, is read as one, the wider way):

- **Release lane.** A calling job is put in the release lane when a called job is in it, whatever put it there (its steps, its local actions' steps as D-083 reads them, an environment, a declaration), with the reason "calls `<file>`, whose job '`<id>`' is a release job (`<its reason>`)", or "where, in `<file>`, job ..." for one further down. A job that was declared `trusted` gets the note `classify` gives such a job. A lane a declaration gives is kept as it is.
- **What such a job is held to.** A job in the release lane only through a call has no steps and cannot name an environment, and the called jobs already carry OBAAF-GHA-006, 014, 015 and 016 with its events (D-082), so it is not given those again. What it holds is read as before, as OBAAF-GHA-015 when untrusted input can start it, under a new kind, `capability-call`, whose message says that a called job releases and that the called release jobs are read with these triggers after their own `if:`, instead of "cannot tell whether it releases". When it needs jobs of its own workflow that restore a cache and a called release job downloads the run's artifacts, it gets OBAAF-GHA-006 `needed-job-restores`, as the same jobs written in one workflow would; a called job that does not release and downloads them does not count, as it would not there. Its OBAAF-GHA-018 is high, as any release job's is.
- **A declared release job that calls.** A calling job declared a release job (by the configuration or `OBAAF_LANE`) gets OBAAF-GHA-006 kind `called-restores` (high) when a step of a called job that is not itself a release job may restore a cache, and neither that job's cache-mode nor that of a calling job between forbids it (`none` or `write-only`, as D-062 reads them), unless its own cache-mode forbids it: GitHub gives a called workflow no more cache access than its caller, so `cache-mode: none` on the calling job clears it. It replaces the low `no-cache-mode` it had. A called release job's own restores are its own finding, as before. A job between that is a release job only through its own call passes on what the jobs it calls restore, so a workflow between does not hide them. Such a declared job gets `needed-job-restores` when any called job downloads the run's artifacts, because its call is the release it declares. The steps are one bounded fact: up to five named, and past that the first few, the count and a digest of every distinct entry (two paths to one step are one entry, and the entries named and the digest are taken in sorted order, so the order of the jobs does not change the finding). Past 2,000 distinct entries the count is "more than" a true lower bound, the entries named are those of the part that was kept, the digest covers the rest by part, and then it can depend on the order the parts were added in, so reordering jobs can make an acceptance stop matching.
- **A needed job that calls.** For `needed-job-restores` (on any release job), a needed job that calls workflows of the repository restores what any job it calls restores, a release job or not, through further calls and unless a cache-mode on the way forbids it, so a release job that needs `build: uses: ./.github/workflows/build.yml` is read as the same jobs in one workflow would be.
- **Callers' cache-mode.** In a workflow whose `on` names only `workflow_call`, called by jobs of the repository each of which forbids restoring, by its own cache-mode or by being in such a workflow (up to ten calls up), each OBAAF-GHA-006 finding gets a control, "Every job that calls it forbids restoring caches", that cannot be told: a caller in another repository is not seen. The finding is then "cannot tell", which still fails the check, and its fix is to set `cache-mode: none` on the job itself (for `needed-job-restores`, on the jobs it needs that restore). A caller in a file the checker could not read is not seen; the check then fails on that file's error. A workflow some job calls by a repository's name (below) never gets the control.
- **A call by a repository's name.** A job that calls `owner/repo/.github/workflows/<file>@ref` is not matched to this repository's `<file>`, even when it names this repository: the checker cannot tell offline which repository it is in, and the file at that ref is not the file in the working tree. Where this repository has a workflow at that path that can be called, a note says the call was not read as a call of it.
- **A called job's own test of the event.** In a workflow that `workflow_call` can start, a part of a job's `if:` that is exactly `github.event_name == '<event>'` adds `<event>`, when GitHub documents it, to the events the job can run on, because a caller in another repository can raise it. A needed job does not narrow it away when such a caller raising it may run that job (`workflow_call` can start it and its own `if:` does not rule the event out); the jobs that job needs in turn are not followed, the wider reading, and whether a caller in another repository may run a needed job is worked out once for each job and event. The jobs that need such a job are not given the event (they run after it on whatever it ran on), which is narrower than the same jobs written in a `pull_request_target` workflow. A test with `!=` adds nothing, and a test in any other form (`!(... != ...)`, `contains(...)`) is not read.

**Reason.** Attempts 026 (slice 2d.2d), 034, 035 and 103 (slice 2d.2e) in `docs/bypass-attempts.md`: a job that calls a workflow which publishes was not a release job; a declared release job whose called workflow restores a cache got only the low `no-cache-mode`; and a called release job whose callers set `cache-mode: none` could not be read past. A called workflow's jobs run in the caller's run, with its token, its secrets, its artifacts and no more cache access than it has (GitHub's changelog of 2026-09-10 on `cache-mode`), so what they do is the caller's. The two decisions were left open by D-082. The first review of this slice found that counting every called job's restores for the caller gave a high finding the same jobs written in one workflow do not, which this decision does not do.

**Consequence.** A calling job can change lane, and a gate can fail where it passed: `called-restores` replaces `no-cache-mode` on a declared release job, `capability-call` replaces `capability` on a job a call makes a release job, `needed-job-restores` is new there and on a release job that needs a job which calls a workflow that restores, OBAAF-GHA-018 rises to high on a job a call makes a release job, and a reusable workflow whose jobs test `github.event_name` can get findings for the event they name. A called job whose callers all forbid restoring changes from "new" to "cannot tell", which fails as before. `docs/upgrading.md` has the rows. SARIF's rule help for OBAAF-GHA-006, which is the rule's description, changes. This repository's report and the first adopter's are byte-identical before and after. Left: the other rules that read a called job's undeclared permissions (OBAAF-GHA-009, 011, OBAAF-GHA-015's capability, the egress controls) could read the callers' grant as OBAAF-GHA-003 and 004 do since D-084; whether a private repository lets other repositories call its workflows is a setting `obaaf audit` could read, which would settle the callers' control; a `uses: ./...` call's own outputs are not followed. **Status.** Accepted, 2026-11-18.

### D-086 An agent job that installs its tool at a version that can change is a finding

**Decision.** From flagship slice 2d.5a (issue #81, part 3 of 2d.5). A new rule, OBAAF-GHA-025, high, for agent jobs only (control R6, requirement G2.1). It reads every script a step runs, as OBAAF-GHA-010 reads them (the `run`, a github-script script, the command OBAAF's egress action runs, the listed script inputs), a `docker://` step's `entrypoint` and `args` as one command line, and local composite actions' steps through the second pass of D-083. Expressions are put in as the runner puts them in (`${{ env.NAME }}` as the literal the env sets, any other as a value set at run time); whole-line comments are dropped and continued lines joined. One finding per step and case:

- **`piped-download`.** A download (`curl`, `wget`, `irm`, `iwr`, `Invoke-WebRequest`, `Invoke-RestMethod`, `aria2c`) whose output is piped to a program that runs its input (a shell, PowerShell, `iex`, Python, Node, Perl, Ruby and others; after `sudo`, `env`, `exec` and other wrappers and their options; a program named by a variable; `tee` passes it on; a program given a script file reads the download as data), or that sits inside `$(...)`, backticks, `<(...)`, `(...)` or after `<<<` where what stands before it on the line evaluates or interprets (`eval`, `source`, `.`, `iex`, `bash -c`), whatever tool the script installs. Quotes are not read: the line is taken as a whole, the wider reading. The commands are the finding's facts (a command over 1,000 characters by its start and a hash).
- **`agent-cli`.** An agent CLI the catalogue names (`agent_packages`, `agent_install_urls`) installed or run by npm, pnpm, yarn, bun, npx, pip, pipx, uv or uvx without an exact version (none, a range, a tag such as `latest`, or a version set at run time), updated (`claude update`, or `npm update -g` after one was installed in that step or an earlier one of the job), or installed by its own downloaded install script (named by its URL). This is the reader OBAAF-JEN-008 uses since slice 2d.2k, called with no Jenkinsfile behind it, on the script with `$(`, backticks, parentheses and braces read as command boundaries and quoted `;`, `&` and `|` as spaces. Quotes are not otherwise read, so a package manager's command written in text (an `echo` of usage, a `grep` for it, a heredoc) is reported as if it ran: the wider reading. A variable the script, the step, the job or the workflow sets to one literal is put in; a nearer `env` written as one expression, or an earlier step that writes `GITHUB_ENV`, makes the job's and the workflow's values unknown.

A step whose scripts are over 400,000 characters with their variables put in is not read and gives kind `too-long` (medium). A package manager given a package named at run time is not reported: in a script it is mostly an option's value or the agent's prompt, and the review found eight ordinary commands it would have flagged.

**Reason.** Slice 1.1 found poutine reporting `curl -fsSL ... | bash` in ten of the first adopter's agent jobs, and the landscape called it "the most relevant miss: it is squarely OBAAF's subject"; Semgrep's `gha-curl-pipe-shell` reported the same ten (H2). Decisions F-22 and F-24 chose to report it in OBAAF, for agent jobs only, and to leave the same pattern in other jobs to poutine. The download case does not ask which tool the script installs: the first adopter's ten install a CLI no catalogue names (`dev.meta.ai/install.sh`), the checker cannot tell what a downloaded script fetches, and in an agent job it runs with the job's keys and token. Reusing OBAAF-JEN-008's reader keeps one reading of package managers for both platforms.

**Consequence.** A gate can fail where it passed, on any agent job that installs its tool this way. On the first adopter's files at `8868a131`, read-only, the rule adds 12 high findings (10 `piped-download`, 2 `agent-cli`) and changes nothing else (findings, lanes); this repository and its templates are unchanged. OBAAF-JEN-008's reader is now linear on a line of many installers or many pipes. Not followed, and stated in the rule: a script saved to a file and run by a later command (except an agent's own install script), what the downloaded script itself installs, a package named at run time, an agent the catalogue does not name installed by a package manager, installers other than those listed and installs from a git URL, and an agent action's own input that chooses its CLI's version (part 2 of 2d.5). The catalogue as data and the settings rules are slices 2d.5b and 2d.5c.

**Status.** Accepted, 2026-11-18.

### D-088 Agent actions given a setting their own documentation warns about

**Decision.** From flagship slice 2d.5c1 (issue #81, part of part 2 of 2d.5). A new rule, OBAAF-GHA-026, reports a step that gives an agent action a value of one of its inputs that the tool's own documentation warns about. The values are data, the `settings` of each agent tool's entry in `detection.yaml` (D-087). Each setting names the action, the input, the values warned about (or any value that is not empty), a severity, the date read, the documentation's words quoted exactly, and the file at a commit and the lines they are on. The finding prints the words and the source. Its facts are the action without its ref, the input, the value and the setting's `<tool>/<id>`; the words and source are shown and are not facts, so re-reading the documentation does not change which finding it is. Where two settings name one input, the first that matches is reported (`allowed_non_write_users: "*"` is high, any other value medium). A value is compared trimmed and in any letter case. A value that is not plain text (an expression, a list, a mapping, or text with a control, format, separator, private-use or unassigned character other than a space, a tab, a carriage return or a line feed left inside once the white space Python or JavaScript trims is taken off its ends) is "cannot tell", case `computed`, at the highest severity of that input's settings but at most medium, with the value as its fact (its digest beyond 200 characters; a list or a mapping, which GitHub refuses as inputs, by its kind); so is a `with:` that is neither a mapping nor empty (inputs written as one expression, `with: ${{ fromJSON(...) }}`), for every setting of the action. The rule reads every job's steps, and the steps of the local composite actions they use with the using step's inputs put in (D-083), and maps to agent controls R2 (who may give the agent a prompt) and R7 (what the agent's process can reach).

Read on 2026-11-19 from `openai/codex-action` at `4aac6da` and `anthropics/claude-code-action` at `5a85689` (and `anthropics/claude-code-base-action` at `78702a3`): `safety-strategy: unsafe` (high: "This is extremely dangerous, as the default user for this Action likely has sudo privileges ...") and `read-only` (medium: "... so it could read `openai-api-key` from memory and reveal it by printing it ..."); `allow-users: "*"` (high: "... you might find yourself the target of API key abuse"); `allowed_non_write_users` ("WARNING: Use with extreme caution - this bypasses security checks ..."); `allowed_bots: "*"` (medium: "On public repos with '*', external Apps may be able to invoke this action with prompts they control"); `show_full_output: true` (medium: "These logs are publicly visible in GitHub Actions"). Both actions take `*` as everyone only when it is the whole value (read in their source), so `alice,*` is not reported for the two `*` settings.

**Reason.** The plan (decisions F-22 and F-24, part 2 of 2d.5) asks for rules that report the settings an agent tool's own documentation warns about, each citing its sentence, and nothing that only another scanner's data calls dangerous. Quoting the words in the finding lets a reader judge the warning without trusting OBAAF's reading of it. Severity follows what the words say the value exposes. High: the key and whatever else the job holds within the agent's reach (`unsafe`), or the agent started by anyone with a prompt they write, on the job's key (`allow-users: "*"`, whose words warn of API key abuse, and `allowed_non_write_users: "*"`). Medium: the key printed to the log (`read-only`), prompts from Apps on public repositories only (`allowed_bots: "*"`), named outsiders, or the agent's tool output in a public log.

**Consequence.** A gate can fail where it passed. Settings given as command-line options (`claude_args`, `codex-args`, a CLI's own flags such as `--dangerously-skip-permissions`) and the other 21 tools' settings are not read yet (slice 2d.5c2, F-264). A value the action itself would refuse (`UNSAFE` where it compares exactly) is reported; that is the wider reading. A setting an action reads from a configuration file (`settings`, `codex-home`) is not read, nor `display_report`, `ACTIONS_STEP_DEBUG` or a key written in clear, nor these actions inside another repository's composite action or reusable workflow. A `uses:` with an empty path segment, a leading `/` or a backslash is not matched to the action at all, here or by the agent lane (#245).

**Status.** Proposed.

### D-089 How a team reviews and applies the first configuration

**Decision.** Running `obaaf init` shows the proposed configuration and workflow. The user runs `obaaf init --apply` to write them. If either target already exists with different contents, show the conflicting path and diff and stop before writing either file. A first CI workflow reports findings. The team chooses its gate threshold later.

When the tool detects a secret name but cannot establish its GitHub environment, list the name for review. Write a protection rule only when the environment is known. The team resolves ambiguous names.

**Reason.** Someone adopting OBAAF can inspect both files and the detected jobs and secrets before changing their repository. A configuration assembled from a new workflow and an existing, conflicting file can give misleading results. A first report lets the team see the effect of choosing a threshold.

**Consequence.** Setup takes a preview and an explicit apply. A conflict requires reconciliation before the pair can be written. The first workflow does not block on finding severity. Secret values are unnecessary for proposing rules from workflow references.

### D-090 Agent CLIs run with an option their own documentation warns about

**Decision.** From flagship slice 2d.5c2a (issue #81, part of part 2 of 2d.5). OBAAF-GHA-026 (D-088) also reports a command-line option that an agent tool's own files warn about. The options are data: `flags` in each agent tool's entry in `detection.yaml`, each with its spellings (`options`), the values warned about where it takes one (`equals`), a severity, the date read, the words quoted exactly and the file at a commit with its lines; an action's `args_inputs` name the inputs it hands the tool's program as options. They are read in an argument input (`claude_args`, `codex-args`), case `option`, as each action reads it (`codex-args` that starts with `[` is a JSON array; a line of `claude_args` that starts with `#` is left out, and a word that would be a warned option once a `$NAME` claude-code-action's tokenizer may put in as nothing is taken out is "cannot tell"); and where a step runs the tool's program or package, case `command-option`, in the steps of local composite actions too (D-083). A bash or sh script is read twice, the two added together: as bash splits it, with known variables put in and nested scripts read again, and the widest way, with quotes removed and the text cut where a command starts. The program counts where a command starts, after the commands that run another (`sudo`, `env`, `xargs`, `find -exec`, `npx`, `yarn`), and as an argument of any command whose arguments are not data (a fixed list: `echo`, `grep`, `git`, `cp`, the package installers and the like); a quoted argument of such a command that names the tool is read again as a command line. No variable is taken as known where a script runs a command that can set a name the checker cannot read (`eval`, `source`, a nameref, or `declare`, `export`, `printf -v` or `read` with a quoted or computed name) or an `env` is written as one expression; after an earlier step that writes `GITHUB_ENV` or calls `exportVariable`, only the step's own `env` is read (that a step's `env` takes precedence over `GITHUB_ENV` was not verified on GitHub). Code in another language (an interpreter's code, github-script, another shell) is read the widest way, the program found anywhere in it; there, a warned option written literally is reported and one whose start is written in pieces is "cannot tell"; options built from variables there (an argument array in a variable, a shell string joined with a variable, `"--" + "yolo"`) are not read yet, and are flagship slice 2d.5c2c, because each language joins and splits arguments its own way and a fourth review pass still found ways past a heuristic reader. What the first reading cannot read, in a step that names the tool, is "cannot tell", case `command-computed`, at the highest severity of the options left open but at most medium: an unquoted expansion, `"$@"`, a glob or an expression in the program's command; a quoted word that could start a warned option; a warned option given a value it cannot read; `xargs` or `parallel` running the program; a command it cannot name; a new name made for a program; `IFS` set; `eval` or a shell given text it cannot read; a script file written in the step and run; text it cannot split; nesting deeper than four levels; and a step in another shell, or a github-script script that runs a command, where nothing is found. A finding's facts are the tool (or the action and input), the option as written with its value, and the flag's `<tool>/<id>`, or for "cannot tell" the words (with the `env` value a variable comes from where the checker cannot read it) and the flags left open; the words and source are shown and are not facts.

Read on 2026-11-19: from `anthropics/claude-code-action` at `5a85689`, `--dangerously-skip-permissions` and `--allow-dangerously-skip-permissions` (high: "claude_args turns off permission checks, so commands that are not on the deny list run without approval", the warning the action logs when its own test, `SKIPS_PERMISSION_CHECKS`, matches these two or the next) and `--permission-mode bypassPermissions` (high: "... commands outside the list run without approval ..."); from `openai/codex` at `333ea31`, the CLI's help for `--dangerously-bypass-approvals-and-sandbox` and its alias `--yolo` (high: "EXTREMELY DANGEROUS. Intended solely for running in environments that are externally sandboxed") and `--dangerously-bypass-hook-trust` (medium: "DANGEROUS. Intended only for automation that already vets hook sources"); from `google-gemini/gemini-cli` at `3aa930d`, `--yolo`, `-y` and `--approval-mode yolo`, with the `--y` and `--approvalMode` spellings yargs also takes (medium: "A mode where all tools are auto-approved (use with extreme caution)"; its configuration reference says these turn the sandbox on by default).

**Reason.** The plan (decisions F-22, F-24 and F-264) asks for these settings given as command-line options, each citing its sentence, with a value the checker cannot read as "cannot tell", and nothing that only another scanner's data calls dangerous. A workflow passes the options the actions do not take as inputs through these two places, so a rule that read only inputs was easy to step around. Two Opus 5.5 reviewers of a first version found about a hundred ways past a reader that split commands only roughly, and a second pass about seventy more in the bash reader that replaced it, so this one reads scripts as bash does, reads the arguments of every command that is not on a short list of data commands, and fails closed where it cannot in bash and sh: in a step that names the tool, what it cannot read in the program's command, or a command it cannot name, is "cannot tell" rather than nothing. Two limits are stated rather than read: a program name the step builds at run time, which the agent lane does not see either, and options built from variables in code in another language (slice 2d.5c2c). The widest reading is added because it finds what the shell's reading cannot see as a command (an argument list in JavaScript or Python, a string handed to an interpreter). Severity follows the words: high where they say every command runs without approval or sandbox; medium for hooks run without trust and for Gemini's mode, whose documentation turns the sandbox on with it.

**Consequence.** A gate can fail where it passed: a step that runs one of these CLIs in a way the checker cannot read is "cannot tell" until the options are written out. An option written in a prompt's text, or in prose in another input that starts with the program (`claude -p "never pass --dangerously-skip-permissions"`), is reported, the wider reading. A quoted word that starts with a variable or substitution (`claude -p "$PROMPT"`) is read as one word that is not an option, although a CLI's own parser may take a value that begins with `-` as one; that case is #254. Codex's `--sandbox danger-full-access` and `-c` overrides, settings given to `--settings`, options in configuration files or environment variables the tools read, a program name a step builds at run time (braces, globs, `printf`, another step's `GITHUB_ENV` or outputs, `vars`), `python -m` and repository scripts, a local Docker or JavaScript action, and the other 20 tools' settings and options are not read (slice 2d.5c2b). A `with:` written as one expression now names these options among the settings it cannot tell, so an acceptance of that finding stops matching. `codex-args` that codex-action itself refuses for the run's other inputs is still reported, the wider reading.

**Status.** Proposed.

### D-091 How a finding gets a next action in the cause catalogue

**Decision.** Give each checker rule one cause for its remaining kinds. When a kind needs different advice, explicitly exclude it from that group and assign it to one named cause. The catalogue check fails on missing or overlapping assignments. A cause has a stable ID, a sentence, a fix kind and a next action. Jenkins causes direct the reader to a manual change.

**Reason.** Two findings under the same rule can require different work. For example, a tool installed at a changeable version and an install line too long to inspect call for different advice. Naming both sides of an exception lets the catalogue catch a deleted assignment before a report gives the wrong advice.

**Consequence.** A new rule needs an entry before the catalogue check passes. A new kind takes the rule's remaining-kinds advice until the author assigns a more specific cause. A fix kind describes the work involved. Whether a particular edit can be offered depends on the evidence for that finding. This slice adds the catalogue only. Report grouping and the commands that apply fixes follow separately.

**Status.** Proposed, 2026-11-19 (A1a, #252).

### D-092 Group outstanding findings by their next action

**Decision.** Count each outstanding finding once. An invalid acceptance takes priority over its rule. Prohibited acceptances, severity increases and legacy entries take priority over missing fields. Keep each remaining validation reason separate. Show a stale baseline match only for a shared rule, file and job, with at most one hint per stale entry and per finding. Skip ambiguous groups. These hints never accept a finding. List a currently available mechanical action first, then use highest severity, count and cause ID for reproducible ordering.

**Reason.** Someone upgrading a baseline needs to know which decision to make first. Counting a finding twice would inflate the work. Similar locations give an upgrade clue without establishing that an old entry still covers the risk.

**Consequence.** JSON gains a `todo` array. A changeable tool version is one cause with counts for pin candidates and manual fixes. An eligible literal install can be considered for a user-supplied pin. The later fix command must still prove the patch. Existing JSON fields, SARIF, gate results and acceptance identities are preserved.

**Status.** Proposed, 2026-11-19 (A1b, #257). Sean explicitly confirmed the shared install entry with separate counts.

### D-094 The other agent tools' settings and options

**Decision.** Every entry of `agent_tools` either lists the settings and options its own files warn about, each with the words and the file, commit and lines (as D-088 and D-090), or says in a new field, `no_warnings`, what was read and why nothing is reported; `obaaf catalog` refuses an entry with neither, or with both. Read on 2026-11-19 for the twenty entries D-088 and D-090 did not read, and for run-gemini-cli's inputs: `gemini_debug: true` on run-gemini-cli and `qwen_debug: true` on qwen-code-action, read as GitHub's `fromJSON` reads it (`json: true`: the first token, in either quotes or up to a separator), and `enable-uv-cache: true` or `auto` on OpenHands' pr-review action (medium); Qwen Code's `--yolo` and `--approval-mode yolo`, Kilo Code's `--auto` with its hidden `--yolo` and `--dangerously-skip-permissions`, Cline's `--yolo` with `--zen` and `--auto-approve` with any value but `false` (`unless`), Copilot CLI's `--allow-all-tools`, `--allow-all` and `--yolo`, and OpenHands' `--always-approve`, `--yolo` and `--headless` (high); Qwen Code's `--insecure`, Copilot CLI's `--show-secrets`, `--trust-folder`, `--share-gist` and `--share`, Continue's `cn --auto`, OpenCode's `--hostname 0.0.0.0` and goose's `--dangerously-unauthenticated` (medium); PR-Agent's `--config-branch` given `$GITHUB_HEAD_REF`, which its documentation names (high; a value the checker cannot read, such as the `${{ github.head_ref }}` it also names, is "cannot tell"). An entry may say `shared_program` when another well-known program has its program's name (AWS's `copilot`, pressly's `goose`), with that program's own words in `other_program`; a command the checker cannot read is then not "cannot tell" where every place the step names the program is followed by them. A field, not a comment, makes "read and found nothing" a fact `obaaf catalog` can check. Where a tool's files describe a mode with no sentence of warning (OpenCode's `--auto`, Aider's `--yes-always`), nothing is reported, as F-267 decided for the actions. An option the tool's own code or README says does what a warned option does, or more (Kilo Code's hidden options, Cline's `--zen` and `--auto-approve true`), is read with that option's sentence, the wider reading (F-280). Qwen Code's yolo is high where Gemini CLI's is medium because Qwen's documentation says `--yolo` turns on no sandbox. Without `shared_program`, AWS Copilot and pressly goose workflows would fail the default gate on "cannot tell" for commands that run no agent (found by the review).

**Consequence.** A gate can fail where it passed: a step that runs `qwen`, `kilo`, `cline`, `copilot`, `openhands`, `cn`, `opencode`, `pr-agent` or `goose` with one of these options, or in a way the checker cannot read, and the three action inputs. OpenHands' documented CI command, `openhands --headless`, is now a high finding. A dangerous mode a tool runs in by default (a one-shot `cline` run, the three actions that run their CLI with `--yolo` themselves) is not reported, because no setting names it. Kiro CLI and Amp document their options only on web pages, which a source at a commit cannot cite. For every agent CLI, `-dy=true` and a versioned program after `uvx`, `uv tool run` or `pipx run` are now read.

**Status.** Proposed, 2026-11-19 (slice 2d.5c2b, #81).

### D-095 Code in another language that runs an agent tool

**Decision.** From flagship slice 2d.5c2c (issue #81). OBAAF-GHA-026 (D-088, D-090, D-094) reads, by its tokens, the code given to an interpreter from a bash step (`python3 -c`, `node -e`, `perl -e`, `ruby -e`, `php -r`, an awk program, a heredoc or `echo '...' |` fed to one), a github-script script, and a step whose `shell` is python, node, ruby, perl, php or pwsh; PowerShell and cmd lines are read word by word. In such code: (1) an argument list with a splat or spread, joined with another, held in a name the code changes, or given whole as a value to a call that takes the list (`exec.exec('claude', flags)`) is "cannot tell"; (2) a string that names the program and reaches a call that runs a command line (directly, through calls that only change its form, after a shell's name in a list, or through a name given to such a call) is read as bash, with every value joined into it or put in it as text outside the string's own quotes, because text put into a string can end them; a list joined into such a string is read the same way; (3) a value pasted into the code's text before it runs (a `${{ }}` expression, a shell expansion in a heredoc whose delimiter is not quoted) is words the checker cannot read; (4) literal pieces are joined and matched, a name given a literal string is that string where it is used, and a list held in a name the code does not change is read where it is given; (5) a value whose known start or end could be a warned option, or that holds one as a literal, is "cannot tell"; (6) one value in one place of a list, or given as one argument where the language gives it as one (Python and Ruby call arguments, a Perl scalar), is one word that is not one of these options, unless it is the value of a warned option that takes one; (7) a string that is logged, posted or compared is not read as a command line; (8) in PowerShell an unquoted variable is still "cannot tell" (F-274: it may hold an array, which PowerShell passes as several words), but `$env:NAME` is always one string and one inside double quotes is one word; in cmd a `%VAR%` or `!VAR!` is "cannot tell" inside double quotes too, because cmd puts the text in before it reads quotes; (9) a list held in a name is read with what the code adds to it where it adds literals or one value at a time; a value of a loop over what the checker cannot read (or a callback's parameter), added on its own once for each turn, is any number of words, but not where it is the value of an option the same change adds (`cmd += ['--allowedTools', t]`) or the loop goes over literal strings; (10) in JavaScript and PHP, the program's name as an argument of a call that does not run a command is read only for literal options after it.

**Reason.** The plan asks that an argument array held in a variable, a shell string joined with a variable and an option built from pieces be "cannot tell", and that a literal argument list and a single variable in a prompt's place stay quiet (slice 2d.5c2c). Reading code by its tokens, not by regular expressions on its text, is what lets a list be told from an index, a call from a log line, and a string from a comment. (6) keeps the choice D-090 made for `"$PROMPT"` in bash (#254), so a team's ordinary `["claude", "-p", prompt]` does not fail the default gate. (2), (5) and (7) come from the first review, (8) to (10) from the second: the first version took any string that started with the program for a command line (`f"claude exited with {rc}"` was "cannot tell") and any `"--" + x` in the code for an option (argparse's `add_argument("--" + name)` was "cannot tell"), and treated a value put into a string's quotes as one word, though `os.system(f'claude -p "{x}"')` passes `--dangerously-skip-permissions` when `x` holds `" --dangerously-skip-permissions "` (checked with python and a stub program). Literal pieces are matched, not only "cannot tell", because the joined text is known exactly.

**Consequence.** A gate can fail where it passed: `exec.exec('claude', flags)` was quiet and is now "cannot tell"; `os.system(f'claude -p "{x}"')` is "cannot tell"; options written in literal pieces were "cannot tell" and are now a finding at the option's own severity. Not read: a program name given by escapes or pieces (`"\x63laude"`, `"cl" "aude"`), which the step's check for the tool's name does not see, or by a path built at run time; a list held in a mapping; Perl's `exec { ... }`; code written into another process's input; AppleScript and Tcl beyond the widest reading; a shell that runs another interpreter on the script.

**Status.** Proposed, 2026-11-19 (slice 2d.5c2c, #81).

### D-096 Which actions and called workflows are an agent's

**Decision.** From flagship slice 2d.11 (issue #236). (1) A job that calls a workflow (`jobs.<id>.uses`) is under an agent action, the catalogue's or a repository's own `agents.actions`, when its `owner/repo` and folders are, as a step's action is: the same name in any letter case, or one with a `/` after it, read after spaces round the value are taken off and `..` is worked out without leaving `owner/repo`. Where the action is a whole repository, a workflow of that repository is the agent's; where it is a folder of a larger repository, that repository's workflows are not (a workflow is always at `owner/repo/.github/workflows/`). A repository whose name only begins like the action's is not the action's. A repository's own `agents.actions` entry is read without space round it, an `@ref` or a `/` at its end, for steps and calls alike (a local `./` entry names a called local workflow by its first characters, as before); `agents.actions` and `agents.commands` must be lists of text, and an entry that names nothing once those are taken off is refused. (2) A catalogue entry may list, under `not_agents`, actions in a folder under its actions that run no agent, each with the action's own words, the file, commit and lines they were read from, what was read to know it runs no agent, and the date. A job that uses only such an action is not an agent job; OBAAF-GHA-026 reads none of the agent action's settings on it; it is not an agent before or beside OBAAF's egress action. (3) A listed path is taken out only as it is written: its owner and repository in any case, the folder exactly as the catalogue writes it, and no folder under it. (4) Every other path under an agent action is the agent. (5) A repository's own `agents.actions` are never narrowed by the list. (6) The one path listed is `anthropics/claude-code-action/agent-approval-check`, read at `f431ada` and taken out at every ref. (7) A step whose `uses:` leaves its repository (a local path whose `..` climbs out of the workspace, a local action whose path goes through a link out of the repository, or another repository's action whose `..` climbs to or above its `owner/repo`, a backslash read as a `/`) is taken for an agent's action in any job, with no tool named. (8) An `agents.actions` entry that names no action (empty without its `@ref` and a `/` at its end, or a `docker://` image) and an `agents.commands` entry that is not a regular expression are refused.

**Reason.** The plan's "done" for 2d.11 is that an approval-only action and a reusable workflow in a similarly named repository acquire no agent findings or attribution, and documented agent actions still do. A finding that a team can only accept is noise, and both cases were reported on a repository's first run. The data says what the action says of itself and where, as the agent entries' settings do (D-088), so a reviewer can check it. (4) keeps the wider reading: a folder the checker has not read may run the agent (`base-action` does), so a path is taken out only when its files were read. (3) follows how a Linux runner finds the folder (a git tree is case-sensitive); a macOS or Windows runner may find another case too, so another case stays the agent. (5) because `agents.actions` is the repository's own word about its own agents. (7) was found by the slice's review: the runner keeps the whole repository of each action a job uses in one folder beside the workspace, so after the approval check a step could reach Claude Code's own action by such a path (not run on a runner; it rests on how the runner lays out that folder). It holds for any repository that holds an agent action, so it is read in every job. A `run:` step that copies or clones an agent's action into the workspace for a later `uses: ./...` is not caught: the checker reads a local action as it is checked out. (8) because such an entry names no action, so a repository that wrote one believed it had declared an agent it had not. A local entry (`./...`) is kept, read as before against a called local workflow by its first characters, because a job that calls a workflow takes no `env` and so cannot carry `OBAAF_LANE` (found by the slice's fourth review). Before, a step was never matched by an `agents.actions` entry with an `@ref` or a `/` at its end and a call only by its first characters, and a string was read one character at a time (as `agents.commands`, each letter a pattern that almost every script matches); reading both the same way, and refusing what names nothing, keeps a repository's declaration from silently matching less.

**Consequence.** Fewer jobs are agent jobs: a job whose only agent was the approval check, or that calls a workflow of a repository like `owner/agent-docs`, loses OBAAF-GHA-003, 004, 005, 012, 020 and 025, and a baseline entry for one of those findings no longer matches, which fails a check at or above `--fail-on` until the baseline is written again. The listed path in another case, a folder under it and any action not read are still reported. A job with a step whose `uses:` leaves its repository is now an agent job, which can turn a passing gate red; so can a configuration that is not a list of text. The listed path is taken out at every ref, so a later change to the action at `@v1`, or a fork's commit GitHub serves under the parent's name, is not read. Each new sub-action a tool publishes is the agent until it is read and listed. The other folders with an action file under listed actions on 2026-11-19 (four of `sst/opencode`'s build steps, `cline/cline`'s Windows signing step) were not listed, because only their action files were read; `coderabbitai/ai-pr-reviewer` could not be read without signing in.

**Status.** Proposed, 2026-11-19 (slice 2d.11, #236).

### D-097 `npm publish --provenance` counts as provenance

**Decision.** From flagship slice 2d.12 (issue #201). OBAAF-GHA-017 does not count an upload that is `npm publish --provenance` when: (1) the step's whole script is that one command, every word read as written, with no variable, expression, backquote, glob or `|| exit`; (2) its words after `publish` are only `--provenance` or `--provenance=true` (at least one), `--access public` or `--access=public`, and `--tag NAME` or `--tag=NAME`; (3) the job's permissions, or its workflow's when it declares none, give `id-token: write`; (4) every runner the job may run on is GitHub-hosted, and it has no `container` and no `services` (another image, which can change npm); (5) the shell is a POSIX shell the checker reads, with no `BASH_ENV` and no earlier write to `GITHUB_PATH`, nothing runs beside the step, and no `env` of the step, the job or the workflow is one expression or names `PATH`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `EXECIGNORE`, a `BASH`, `LD_` or `NPM_CONFIG_` variable, or a `NODE_` one but `NODE_AUTH_TOKEN`; (6) an earlier `actions/setup-node` step sets Node.js 20 or later (or `lts/*`, `latest`, `current`, `node`), and every earlier step, with no `env`, `if` or `continue-on-error`, is `actions/checkout`, such a setup-node step with no input but `node-version`, `registry-url` (npm's own registry), `scope`, `cache`, `package-manager-cache`, `always-auth` and `check-latest`, or a `run` step whose lines are `npm ci`, `npm install`, `npm test` or `npm run NAME`, with no default `shell` in the job or the workflow. Every other upload of the workflow is weighed as before, so the finding can move to another publishing job. Not read: `NPM_CONFIG_PROVENANCE`, `publishConfig.provenance`, `.npmrc`, trusted publishing, `pnpm publish --provenance`, `yarn npm publish --provenance`, an action that publishes.

**Reason.** The issue's "done" is that a job whose only publish is `npm publish --provenance`, in the forms the checker can read, with `id-token: write`, gets no OBAAF-GHA-017, and a form it cannot read stays reported. npm's documentation (npm/documentation at `507a73e`, `generating-provenance-statements.mdx`, lines 51 to 70) asks for `id-token: write`, a GitHub-hosted runner and the flag. npm's CLI (npm/cli at `787f152`, `workspaces/libnpmpublish/lib/publish.js`, lines 53 to 64, 153 to 162 and 195 to 244) generates and signs the provenance in `buildMetadata`, before the request that sends the package. It throws a usage error when the job has no ID token request URL (no `id-token: write`) or the package is new or private without `--access public`, and the signing itself throws when it fails, so the same step either publishes with provenance or publishes nothing. That makes the provenance part of the upload, which no other provenance step is. (4) follows the documentation; the CLI itself does not check the runner. (2) is a closed list because npm's option reader, nopt, takes `true` or `false` after a boolean option as its value, reads `no-` in any case after any number of dashes, and gives an option that takes a value the next word, `--provenance` included (found by the slice's review), and because a folder or a package named to publish may be one this workflow did not build. (6) because npm before 9.5.0 does not know `--provenance` (the documentation's line 37) and Node.js before 20 may ship npm 8, and because any other earlier step may change npm or what it is given. The environment variable and the files are left out because the checker does not yet weigh what an earlier step writes into `GITHUB_ENV` or the repository's files; keeping the finding there is the wider reading.

**Consequence.** Fewer workflows get OBAAF-GHA-017, so a baseline entry for one it no longer reports no longer matches, which fails a check at or above `--fail-on` until the baseline is written again; where another job also publishes, the finding moves to it and an acceptance of the first job no longer matches. Most release workflows have more earlier steps than (6) allows, and keep the finding. What the repository's own files (`package.json`, `.npmrc`) and the package's scripts do when `npm ci` or `npm publish` runs them is not read; nor is where a proxy the runner uses sends the package, nor whether `actions/setup-node`'s commit is one of a fork that GitHub serves under the parent's name (as for every action, D-096), nor a shell given by a path (`shell: ./bash -e {0}`, `/tmp/x/sh -e {0}`, as for OBAAF-GHA-016). The second review found the earlier steps' `env`, bash's `SHELLOPTS` and `PS4`, and a default shell, and the third a service container, each a way past, before the merge. A workflow that also uploads anything else still needs provenance for that upload. `npm publish --provenance || exit 1` is still reported, although npm signs there too. An npm with an option that takes a value before `publish` (`npm --workspace a publish`) is not read as an upload at all, which is older than this decision. Not run: npm itself, or a publish on GitHub.

**Status.** Proposed, 2026-11-19 (slice 2d.12, #201).

### D-098 Property tests, and what they found: another run's download in more spellings, and values shared through YAML aliases

**Decision.** From flagship slice 2d.3a (issue #79). (1) `tests/test_properties.py` states four properties of the workflow and expression readers and tries each on every workflow of OBAAF's published test set, the templates and this repository's own workflows, with seeded random choices, in CI: the same data in other YAML (block or flow collections, quoted, literal or folded text, keys in another order, anchors and aliases, comments, indentation, line width, a document start) gives the same findings and the same number of errors, and the generator checks that the loader reads the same data before anything is compared; an expression respelled as `obaaf.checker.expr` documents (letter case in context and property names, `.name` for `['name']` and back, spaces, parentheses round the whole and round a reference's first names) never loses a finding, lowers its severity or moves it nearer to cleared, and the reader reads at least the fields and secrets the original reads; a workflow in another form GitHub documents as the same (one label, job or event as a list of one, an event as an empty mapping, the workflow's `env` written into each job, an `if` with and without `${{ }}`, `owner/repo` of a `uses` in another letter case) never loses a finding; and corrupted text never makes the checker raise or take more than five seconds. (2) A job started by `workflow_run` with write access is in the effect lane when `actions/download-artifact` is given a `run-id` other than `${{ github.run_id }}` (compared without spaces or letter case), or a `repository`, whatever the value, or inputs that are not a mapping, or names `workflow_run` in any letter case; when another action whose name ends in `download-artifact` or holds `/download-artifact` or `artifact-download` is used (dawidd6's and its forks); and when the run script, a github-script script, the egress action's command or a `docker://` step's arguments, with continued lines joined and quotes taken out, run `gh run download` with options before either word or name `archive_download_url`, as well as the routes read before. (3) OBAAF-GHA-023 walks each place (a top-level key, a job's key, a step, a local action's step) on its own, each list and mapping in it once, and searches each text once however often it is reached, and a text with a placeholder reached again through an alias in the same place counts once there, so a step shared by two jobs, or used twice in one job, is reported at each, while a placeholder written out twice is two findings; a file whose places together reach more than 500,000 values is an error for the file, and the rule's findings so far and the other rules' findings stand.

**Reason.** The plan's "done" for 2d.3 is property tests of the expression and workflow readers that run in CI, and the brief asks that every way past a rule be a test and its class fixed. On their first run the properties found two: `run-id: ${{ GITHUB.EVENT.WORKFLOW_RUN.ID }}` took the job out of the effect lane, and with it OBAAF-GHA-021 and 022 (high), because the lane matched `workflow_run` as written; and a step reached through an alias in a second job lost its OBAAF-GHA-023, because the reader skipped a value it had seen, whoever reached it. A `run-id` or a `repository` is what makes `actions/download-artifact` read outside its own run, so the class is any value there, not the spellings of one. The slice's review found that the first fix's memo of shared values gave one short-lived value's results to the next (placeholders at workflow and job level lost or put on the wrong job) and made an alias bomb a million findings, and that the same function matched scripts as written (`gh run \` continued, `gh 'run' download`, `gh -R`); its second pass found that walking per place searched a long text again at every alias (a 32 KB file took 18 seconds) and that running out of the walk dropped the file's other findings, and that listing artifacts read as a download; its third pass found that each alias of one placeholder text was a finding of its own at every place (16.6 KB gave 402,001 findings and a 298 MB SARIF file), that the pass over local actions still dropped the file's findings, and that any later word `download` counted for `gh`. Walking per place with each text searched once, a bounded walk that fails the file without hiding the rest, and reading scripts as the shell does are what this decision keeps. Equality is required for the YAML respellings because GitHub reads the same data; for expressions and forms only "never lose" is required, because the reader may take a wider reading of a spelling (inside a function's arguments `(needs).plan.outputs.x` is all of `needs`).

**Consequence.** A gate can fail where it passed: a `workflow_run` job with write access that downloads in one of the newly read ways is now in the effect lane and gets OBAAF-GHA-021 and 022 (high) unless its checks and approval are in place; a template placeholder in a step or job reached through an alias is reported for each place, so a baseline written before may not cover the new findings. Counting a `run-id` or `repository` given without `github-token`, or `repository: ${{ github.repository }}`, is the wide reading: download-artifact may ignore them, so such a job may be in the effect lane while it reads only its own run. A download given only `github-token`, or `run-id: ${{ github.run_id }}`, is not counted. A fork's download step is not one of the steps that only prepare, so checks after it do not count for OBAAF-GHA-021: an action that downloads may also apply. Still not read: the inputs of other actions (a retry wrapper's `command`), what a variable or a `gh alias` stands for, a job with no `permissions:` block (which may hold the repository's default write token) and a push with a personal token from a read-only job, which stay outside the effect lane as before. A finding at a place reached through an alias is reported at the line of the anchor. The properties claim what the checker does with each spelling; none was run on GitHub. Merge keys (`<<`) are not generated: GitHub does not read them and the checker refuses them (slice 2d.2f). The zizmor parity test the plan also asks for is the separate slice 2d.3b.

**Status.** Proposed, 2026-11-19 (slice 2d.3a, #79).

### D-099 Proving an adoption edit before offering it

**Decision.** Slice A2a (#261) checks the working files against an unedited private copy, applies the candidate to the copy, and reruns the checker for the selected path, configuration, baseline, platform and threshold. Only the promised findings may disappear or become accepted. Each new acceptance must agree with the proposed source, owner, reason and expiry. Other findings retain their severity, state, controls and acceptance. Every remaining baseline and ignore entry must match a finding. The proof compares parsed structures outside the named YAML or JSON keys and checks every copied file's bytes, type and mode against the proposed edit.

**Reason.** A preview promises a specific change to the adopter's gate. The same finding count can hide a lost acceptance, an unrelated finding or a different set of working files.

**Consequence.** A2b will call this proof for its paperwork preview. The preview lists each refused candidate under “Could not be made automatically”, together with the proof's single-line reason. A YAML-named file that a Jenkinsfile loads as Groovy (`load 'ci/steps.yml'`), or that a Jenkins controller names as its script path, is known to neither the checker nor the proof, and is compared as YAML. A document holding a value the comparison cannot hold (a set, an ordered map of mappings) or more than 500,000 values once its aliases are expanded is withheld. A malformed document, unexpected file change, failed check read, missing CI input, changed source bytes (each edited file is read again from the source after every other check, no more than one byte past its expected length), or difference between the original and unedited-copy results also withholds the candidate. For Git working trees, an advisory about folder pruning may appear only on the private copy. The proof checks that the actual CI and Jenkins files, Jenkins coverage and all other notes agree. It declines edits that change Jenkins file selection.

**Status.** Proposed, 2026-11-19 (slice A2a, #261).

### D-102 Paperwork changes in the fix preview

**Decision.** `obaaf fix` previews changes to OBAAF’s configuration and an explicitly selected baseline. Completing an ownerless ignore requires an explicit owner. Migrating an old baseline also requires an explicit reason and expiry. The preview names each finding the user would accept and lists each stale entry it would remove. A lane correction needs exactly one matching lane one insertion, deletion, substitution or adjacent transposition away, and is shown only when the proof finds no other finding changed, so it is withheld when its lane's rules add or change a finding. A check of anything but the repository's own folder is partial (a check of `.github` or `.github/workflows` does not read Jenkinsfiles), and with a partial check the preview withholds changes whose scope it cannot establish, lane corrections included.

**Reason.** An acceptance changes which risk counts at the gate. The user needs to see its owner, reason and expiry before deciding whether to take it. A unique spelling correction can be checked on a copy. Plausible alternatives need a human decision.

**Consequence.** The preview tries the combined changes on an isolated copy. When they cannot be proved together, it checks smaller groups and shows only a verified cumulative diff. A conflicting change is listed with its reason. An entry of a flow-style YAML list is not removed when a comment lies in the text the removal would delete, or after the last removed entry on its line. ### D-103 Applying the paperwork preview

**Decision.** `obaaf fix --apply` runs the preview again with the supplied check and acceptance options, prints the unified diff, flushes it, and reproves those exact edits on a fresh private copy. Before writing any file it checks every target's original bytes and executable mode against HEAD, the index and the proven working file. Each target must be tracked, clean and an existing regular file. Unrelated local changes can remain. The command leaves the Git index alone and makes no commit.

**Reason.** The adoption design asks for a change an adopter can review as its own commit. Using the same preview and proof keeps both invocations on the same rules. A target Git's index marks assume-unchanged or skip-worktree is refused, because Git would then show none of the written change (added by the review, `review-gpt` #282).

**Consequence.** Apply runs only on Linux, where Python has the extended attribute functions it needs to keep access controls; elsewhere it refuses before printing the preview. A directory lock keeps a second OBAAF apply out: it fails at once rather than waiting. All replacement bytes are prepared before installation, and a filesystem without hard links, which install and restore both use, is refused then, before any original is moved (both added by the review, `review-gpt` #282). Each original is retained through validation of the complete set. A recoverable failure restores the originals in reverse order. The replacement must preserve ownership, group, permission bits and every extended attribute visible to the process, including Linux POSIX access ACLs. Inherited attributes that the original lacked are removed. The command verifies this before installation and again before releasing the originals. A filesystem that cannot represent the original metadata, or a file with a capability or integrity signature, requires manual editing. It supports ordinary Git text line-ending conversion and declines targets with external filters, working-tree encodings or ident expansion. Repeating apply when the checker offers no further edit succeeds without writing.

The operation needs POSIX directory locks and a filesystem supporting hard links and renames. A reader can observe different files at different points in a multi-file apply, and a target name is briefly vacant while its original is retained. Other programs can edit files without taking OBAAF's lock, including after final validation. The last proof must agree with the checker result displayed in the preview. If such an edit prevents restoration, the command preserves the competing file and reports the saved original for manual recovery. Power loss, process termination and filesystem failure can also require manual recovery.

**Status.** Proposed, 2026-11-19 (slice A2c, #279).

### D-115 Legacy baseline migration reports current acceptance eligibility

**Decision.** Direct migration matches legacy entries using their existing identities and applies the same eligibility policy used to write new baseline entries. The receipt names prohibited matches and explains the reason. When nothing can be carried over and at least one match is left open (prohibited, or waiting on an ignore entry), a nonempty input is preserved, including when a separate output path was supplied. An entry that names a finding a valid ignore entry accepts is counted and not carried over; when such entries are the only matches, the file is converted with no entries. When it writes a file, the receipt counts every finding outside the old file that the gate will count, and names those no entry can accept and those waiting on an ignore entry (both added by the review, `review-gpt` #313).

**Reason.** In an in-place upgrade from 0.3.0, migration reported that it accepted a missing ownership finding that the next gate kept open. The receipt must count the acceptances the gate honors. An existing ignore decision stays with its configuration owner. Preserving a file whose only matches an ignore entry accepts left the gate asking for a migration that refused, with no reason given; the review found that and converts such a file.

**Consequence.** A 0.3.0 ignore entry names no owner, so a finding both ignored and in the old file is not carried over: once the ignore entry is completed it keeps accepting the finding; once it is removed, migration carries the finding if the old file was kept, and after a conversion the finding is accepted with `obaaf check --write-baseline` like any new one. A preserved file whose matches were prohibited has nothing left to carry over once their files get an owner; migration then finds no match and says to delete it.

**Status.** Proposed, 2026-11-20 (A2d, #312).

### D-116 Comparing JSON edits in the adoption proof

### D-125 What an earlier step writes to `GITHUB_ENV` and an `env` can change what a check runs

**Decision.** From flagship slice 2d.13 (F-278). A check counted where its failure stops the job (OBAAF-GHA-016; OBAAF-GHA-021's record and proposal checks; a provenance command OBAAF-GHA-017 counts as signing; all three use the same reader) no longer counts when (1) an `env` of its step, its job or its workflow names a variable that changes what bash or the check's program runs: `PATH`, `HOME`, `ENV`, `SHELLOPTS`, `PS4`, `PROMPT_COMMAND`, `EXECIGNORE`, `GCONV_PATH`, `ACTIONS_ALLOW_UNSECURE_COMMANDS`, any `BASH...`, `LD_...` or `DYLD_...` name, or any `PYTHON...` name but `PYTHONUNBUFFERED`, `PYTHONDONTWRITEBYTECODE`, `PYTHONIOENCODING`, `PYTHONUTF8`, `PYTHONHASHSEED` and `PYTHONNOUSERSITE`, read with space trimmed and in any letter case, or a name written as an expression (before, only `BASH_ENV`, `ENV` and `BASH_FUNC...`); or (2) an earlier step of the job may set such a variable for the steps after it. (2) holds when an earlier step's bash or sh `run` script, read with the checker's bash lexer, uses a file command's variable (`GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_OUTPUT`, `GITHUB_STATE` or `GITHUB_STEP_SUMMARY`: the runner names a step's files side by side with one suffix, so any of their paths leads to `GITHUB_ENV`'s) anywhere but as a plain redirection target (`$NAME`, `${NAME}`, `${NAME:-/dev/stdout}`) of a command other than `exec`, or a file `tee` writes an output or the summary to with its own output sent to no file command; writes to `GITHUB_ENV` other than with `echo` (no option) or `printf` (a literal format whose only conversion is `%s` and whose only escape is a line break at its end), redirected with `>>`, `>`, `&>>`, `&>`, `>|` or `>&` (`<>` writes over an earlier line), with no backslash, line break or `$'...'` in its words (dash, Ubuntu's `sh`, does not read `$'...'` and its `echo` reads the backslash), no command substitution in them (nested or not) that assigns such a variable in upper case, and a plain word before the first `=` (or `<<`) that is not such a variable; names `BASH_ENV`, `BASH_FUNC`, `GITHUB_PATH` (as before), `addPath`, `exportVariable`, `set-env`, `add-path`, `_runner_file_commands` or `ACTIONS_ALLOW_UNSECURE_COMMANDS`; lists names with `${!GITHUB_E*}`; or reaches `github.env`, `github.path`, the runner's other file contexts or the whole `github` context in an expression. Names are searched with continued lines joined, `$'...'` decoded and quotes taken out. Any other write to the file (a computed name, `cat`, a here-document, a group, a variable holding a file command's path, a script that can replace `echo` or `printf`) counts as setting such a variable. The finding is the one a check the reader cannot vouch for already gets: OBAAF-GHA-016 kind `cannot-tell`, high, with the check named in `checks`.

**Reason.** The reviewer of #256 found that a step writing `PATH=...` to `GITHUB_ENV` before `obaaf verify release` left the check counted, though the `obaaf` it runs is then whatever that step put first on the PATH. actions/runner at v2.338.2 (`d1eb12d`) gives every later step of the job what a step writes to the file (`SetEnvFileCommand` in `src/Runner.Worker/FileCommandManager.cs` refuses only `NODE_OPTIONS`; `StepsRunner.cs` merges the values into each step's `env` context, the step's own `env` after them; `ActionRunner.cs` hands that to the step's process). bash 5.2.21, the version on Ubuntu 24.04, imports `SHELLOPTS` from its environment: with `noexec`, `bash --noprofile --norc -eo pipefail` reads a script ending in `false` and exits 0, so a check's step can succeed without running. CI's new job `github-env-premise` shows both on a GitHub-hosted runner. The names are the ones the check's own script may not assign (slice 2d.2e) less Node.js's, Perl's, Ruby's and Java's, which change neither bash nor the programs OBAAF counts as checks (`obaaf` in Python; `gh`, `cosign` and `slsa-verifier` in Go), plus `HOME` and `GCONV_PATH`, which load code into Python outside a virtual environment and into any program that converts a character set, and `DYLD_...`, the loader's variables on macOS, where the runner keeps `DYLD_INSERT_LIBRARIES` for each step's process (`Handlers/ScriptHandler.cs`). An Opus 5.5 reviewer that did not write the change got past the first version in four ways (a macOS loader variable, a continued line inside `$GITHUB_ENV`, the output file's path changed into the env file's, and a write in the step's `shell`), and the second in five more (other ways to copy the output file's path, a substitution nested in `${...}`, a continued line in an `env` value, a write held in the job's `env` or matrix, `$'...'` escapes), with a slow case; each is a test. The second version searched for listed constructs; the third reads every file command's variable with the lexer and accepts only plain redirections and `tee`, which also removed most false positives the second review found. The third review found four more (`tee`'s own output sent to the env file, `$'...'` in an `sh` step, a `<>` redirection, a container's `env`), now tests too. A write whose name the checker cannot read may set any of them, so it counts as one (F-02: the gap is published with its fix).

**Consequence.** A release job that writes such a name to `GITHUB_ENV` before its check, writes the file in a form the checker does not read, or sets such a name in an `env`, gets OBAAF-GHA-016 `cannot-tell` (high) where it had none, an effect job's checks stop counting, which gives OBAAF-GHA-021, and a provenance command run after it no longer counts as signing, which can give OBAAF-GHA-017; each can turn a passing gate red. A write the checker reads with a harmless name (`echo "VERSION=$V" >> "$GITHUB_ENV"`) changes nothing. Writing a step's outputs from code in another language, or giving a tool the output file's path (`--github-output="$GITHUB_OUTPUT"`), before the check also counts, because the checker cannot follow that path. Moving such a step after the check, or into a job the release job needs (the file is per job), keeps the check counted. Not read: a name or a path a script assembles otherwise (`eval`, a glob over the runner's temporary folder, a value read from another program or from `/proc`), what a program or action an earlier step runs writes to the runner's files, a line break that a variable, a file or a command's output puts in a value at run time (an outsider's text there is also #232), a runner that sets `ACTIONS_ALLOW_UNSECURE_COMMANDS` for every job, and the settings a check's program reads for itself (`GIT_...`, `GH_...`, `SSL_CERT_FILE`).

**Status.** Proposed, 2026-11-20 (slice 2d.13).

Where a local action's steps make the job a release job, the second pass's release finding replaces the first pass's `capability...` finding of the same rule on the same step or job when it is at least as severe (OBAAF-GHA-006 and 015); on another step both stay. (2) An image push is an upload, so its job is a release job: a `docker/build-push-action` output of type `registry`, of type `image` with `push` or `push-by-digest` not false or with an expression in it, whose type is an expression, or with no type and an expression in it, its fields read as buildx reads CSV; a `docker/bake-action` `set` override (`=` or `+=`) of an `output` read the same way, of `push` not false, or with an expression before its `=`; both, and `push`, read through a matrix written out in the file (a value YAML could read as a boolean or a number is not read, so the step may push); the same read, expressions included, from `-o`/`--output` and bake's `--set` in a `docker build`, `docker image build`, `docker builder build`, `docker buildx build`/`b` or `bake` command, up to 8,192 characters or quoted strings into it, past quoted text but not past an unquoted `;`, `&` or `|`, each output read for its first 256 characters or expressions; and `docker buildx imagetools create` without `--dry-run`.

**Reason.** The zizmor parity test (D-108) found a job a release event starts that restores setup-uv's cache and then runs `uv build publish` with `PYPI_PUBLISH_TOKEN`, a name OBAAF's own patterns take for a publishing credential, and OBAAF said nothing. Release jobs are recognised by lists, which miss many publishing commands; code from a poisoned cache entry runs with whatever the job holds, and can publish with it whether or not the job does. Medium, as for OBAAF-GHA-015's `capability` case, because the checker cannot tell whether the job releases. `contents: write` can create a GitHub release and upload its assets, but it is common in jobs that commit back, so it counts only where a release, a tag or a caller's event can start the job; `workflow_call` stands for any event of a caller, as everywhere in the checker. GitHub gives a called job that declares no permissions its caller's token, as OBAAF-GHA-003 and 004 already read. A job that can read every secret can read a publishing credential if the repository stores one, which the workflow does not show (as OBAAF-GHA-018 reads it). An image build that cannot push publishes nothing, and image builds with a GitHub Actions cache are common, so they are left out. The review's sample of the workflows of 20 public projects found seven jobs in four projects that pushed images through build outputs or `docker buildx imagetools create`, which the release lane did not read; the class is fixed in the lane rather than left to this case. Its first version took every expression in an output or override for a push and matched `type=registry` anywhere on a command line, which made a cache import, a platform from the matrix and a `docker` output release jobs, and its command pattern tripled the time of a 120 KB line; both are fixed. A second review found expressions in commands and bake keys, `+=` and quoted fields not read, which are read now; bounding the existing `--push` pattern made a long continued command fall silent, so that pattern is left as it was (its cost is #179's).

**Consequence.** Such a job gets a new medium finding, and a job that pushes an image those ways is now a release job with OBAAF-GHA-006, 014, 015, 016 and 017, and OBAAF-GHA-008 and 018 at high; either can turn a passing gate red. `cache-mode: none` or `write-only` on the job, or on the jobs it needs that restore, clears the new case, and so does moving the credential to a job that restores no cache. A job that may publish but restores no cache gets nothing (the low `no-cache-mode` stays for release jobs). Two of zizmor's test cases are now answered (`cache-poisoning.yml`, and `issue-343-repro.yml`, a tag-push job given `contents: write`), and their entries in `tests/parity/zizmor.yaml` are gone. Not counted: permissions nobody declares (OBAAF-GHA-009 reports them), `contents: write` on other events, a credential whose name matches no pattern, a credential passed under another name to a workflow of the repository that restores a cache (that workflow is read with the names its jobs use), what a bake file says, options written before `buildx` or `imagetools`, an output option more than 8,192 characters into its command or after an unquoted `;`, `&` or `|` in it, and image pushes by other tools.

**Status.** Proposed, 2026-11-20 (slice 2d.14).

### D-127 Which Jenkins steps share a workspace

**Decision.** From flagship slice 2d.2j (#210). The Jenkins model records the workspace each step runs in: a top-level `agent` allocates one for every stage without an agent of its own, the pipeline's `post` and the stages' `post` blocks; a stage's own agent, `node()` and a `matrix` agent allocate a new one; `agent none` on a stage, `dir()`, `container()`, `docker.image(...).inside` and a docker or dockerfile agent with `reuseNode true` (or a `reuseNode` the file does not fix) stay in the enclosing one; `ws()` is another directory on the same node; `node(POD_LABEL)` in a `podTemplate` is the pod's; a method nothing in the file calls and the body of a step whose code is not in the file get one of their own. OBAAF-JEN-003 then reports, at high, a push, a `build` step or a publish that runs after an AI agent in the same workspace or on the same node, or after an `unstash` (same name, or one the file does not fix) or `unarchive` of what was stashed or archived there after the agent; "after" includes a sibling parallel branch and a loop, `retry` or `waitUntil` around both. An effect before the agent in a workspace Jenkins keeps between builds is medium, unless the workspace is a pod's own or a full `deleteDir()` or `cleanWs()` certainly runs between them. Separate allocations that may be one machine (the same label, label expressions that require a common label, any agent, a computed label, the same `customWorkspace` or `ws()` path, pods on the same workspace claim) are an unknown. Steps with no known workspace keep the old reading: every agent and effect of one stage. OBAAF-JEN-002 also counts an AI agent's work on a persistent label shared with a privileged stage, and label expressions that can select the built-in node. OBAAF-JEN-006 reads docker run options with a shell's splitting and pod specs as YAML. OBAAF-JEN-007 passes a stage whose agent's shell steps run in a container with exactly one network, `none`, nothing that reaches the host and no host path mounted.

**Reason.** Reviewer B's 111 attempts on 2026-11-17 found that most ways past OBAAF-JEN-003 needed only a second stage: a top-level `agent any` with the agent in one stage and `git push` in the next, a pipeline `post`, a nested stage, `reuseNode`, a stash. The rule's own text says "in the same workspace", which in Jenkins is not the stage. The Jenkins handbook's Pipeline Syntax says the top-level agent is where "the entire Pipeline ... will execute" and that `reuseNode` runs a container "on the node specified at the top-level of the Pipeline, in the same workspace"; where it says nothing (a stage's `post`, a nested stage), the reading under which more steps share a workspace is taken. Jenkins keeps a job's workspace directory on an agent between allocations and builds, so an effect that runs first still meets what an earlier build's agent left (a Git hook, `.git/config`). It is medium, not high, because it needs a second build. The same fact makes separate allocations on one label a question only the controller can answer. A second Opus 5.5 reviewer wrote 115 attempts on the first version. It found 43 ways past and 7 false positives, mostly in docker option parsing, pod specs, `agent none` stages and `retry`. 34 of the ways past and 2 of the false positives are fixed by class and are tests. Its second pass, 62 attempts on the fixes, found 26 more ways past and 9 false positives. The fixes are: Jenkins splits `args` unlike a shell, so both readings count; docker's booleans and `--mount` CSV; system folders count whole but not their subfolders, after `/root/.m2` from Jenkins's own Maven tutorial came out high; projected tokens; computed pod labels; and Jenkins's label operators. 24 of the ways past and 8 of the false positives are fixed. A third pass, 35 attempts, found 11 ways past and 5 false positives: a built-in node that carries only one of its two labels, a computed label in a pod template that is another agent, a user's whole home and its credential folders, rootless Docker's socket folder, and NFS exports without their server. 10 of the ways past and 3 of the false positives are fixed. A fourth pass on that commit found the controller's home under the official image's path and its init scripts, a pod label written out in both places, and credential files; all are fixed. The rest are listed in docs/jenkins.md and #330.

**Consequence.** A Jenkinsfile with an agent stage and a push, a publish or a `build` step in another stage of the same agent, or in the pipeline's `post`, gets a high OBAAF-JEN-003 where it had none. A push before the agent in a kept workspace gets a medium one. Either can turn a passing gate red. A pipeline that keeps them on separate labels or pods, and moves the agent's output only as an artifact applied by a separate job, gets none. Two stages under one label get an unknown, not a pass. OBAAF-JEN-006 can report a docker agent's mount of a system folder, a device, a `CAP_`-named capability or a JSON pod spec's privileged container that it did not, and stops reporting `--privileged=false`. OBAAF-JEN-007 stops reporting an agent in a container started with `--network none` and nothing that reaches the host. Not decided by the file: which machines carry which labels, what a controller-defined pod template mounts, what an agent leaves outside the workspace, matrix cells kept apart only by `when` conditions (read as one workspace), values that carry an agent's output, and commands the checker does not recognise (#330).

**Status.** Proposed, 2026-11-20 (slice 2d.2j).
