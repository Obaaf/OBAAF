# Changelog

All notable changes to OBAAF. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow semantic versioning: drafts are numbered 0.x, and version 1.0 follows the first pilot.

## [Unreleased]

### Save a proven fix as a patch

`obaaf fix --patch FILE` saves a proven paperwork, checkout, pin or gate diff for review with `git apply --check FILE` and application with `git apply FILE`. The output preserves the proved bytes, including CRLF and a missing final newline. The destination must be new. Windows proofs refuse reparse points and hard-linked files.

### OpenSSL's variables can make an action run unread code

A name beginning `OPENSSL_` in the `env` of a step outside OBAAF's egress action, or of its job or workflow, now makes that step one that can run code the checker did not read (slice 2c.13). Node.js, which runs every JavaScript action, loads the configuration `OPENSSL_CONF` names, and the libraries that configuration names, when it starts. So `actions/checkout` with `OPENSSL_CONF` in its `env`, before the egress action, now makes OBAAF-GHA-020 and `key-out-of-reach` (OBAAF-GHA-005) "cannot tell", where both were verified. On GitHub's firewall, where `actions/checkout` before the agent was already "cannot tell" (D-133), what changes is such a name in the agent step's, the job's or the workflow's `env`, or on an `actions/download-artifact` or `actions/cache/restore` step before the agent: each was verified and is now "cannot tell", as the other names are under D-133. Nothing changes on this repository or on the first adopter.

### The workflow `obaaf init` writes can read a settings snapshot

From #367 (#355 item 6), with the review's changes; decisions D-109 and D-111. **The generated workflow now installs the checker at `8caddd6`** (it installed `4e2ba22`), and with the repository variable `OBAAF_USE_SETTINGS` set to `true` both its report and its gate give `obaaf check` the snapshot at `.github/obaaf-settings.json`, with `--settings`. On a pull request the snapshot's bytes come from the target commit, read from Git and written over the pull request's copy at the same path, so the code-owner check still names that path; on a push they come from the pushed commit. A snapshot that is missing, not a regular file, or not in the snapshot format fails the run; one that is too old or for another repository does not, and its evidence stays "cannot tell" ([how to turn it on](docs/ci-integration.md#a-required-check-in-github-actions)).

**A pull request run of the newly generated workflow fails when `.github` on the target commit is a link or a submodule**, with or without the variable. The earlier template read no configuration there and went on with `{}`; a workflow still on that template, which the gate command leaves as it is, still does.

**`obaaf fix --gate` keeps recognising every workflow an earlier build generated** after the template changes: each gate-capable template ships as it landed, and each is recognised at the commit it installed and at the current template's commit, as [upgrading.md](docs/upgrading.md#enable-the-generated-workflows-gate) tells a team to move it. For a workflow that can read a snapshot, when the repository holds `.github/obaaf-settings.json`, the preview says that its count does not use it.

### Jenkins checks under a changed `PATH`

From the review of #365; decision D-135. **A check before a Jenkins publish no longer clears OBAAF-JEN-010, 011 or 012 when a variable can change the program its shell runs, so a Jenkinsfile that passed can get "cannot tell", or a high OBAAF-JEN-011 for a publish in a later stage's failure-path `post` block.** The shell reader stopped at an `export` inside the check's own script, but a `withEnv` entry, an `environment { }` block or `env.PATH = ...` in a script changed nothing: `withEnv(["PATH+X=${env.WORKSPACE}/tools"])` around `obaaf verify release` cleared all three rules whatever `tools` held. Now a `withEnv` entry (through any receiver), an `environment { }` block, a matrix axis or a credential binding's variable around the check, and a write to the build's `env` anywhere in the file (also through `this.env`, `script.env`, `getProperty('env')` or a method pointer; every node of the parsed file is read, and every `${...}` of its strings, so a `when` expression or a GString counts too), count when they set a name the GitHub Actions rules read since slice 2d.13 (`PATH`, `HOME`, `ENV`, `SHELLOPTS`, `PS4`, `PROMPT_COMMAND`, `EXECIGNORE`, `GCONV_PATH`, `ACTIONS_ALLOW_UNSECURE_COMMANDS`, and names beginning `BASH`, `LD_`, `DYLD_` or `PYTHON` other than six that load nothing), in any letter case, or a name the checker cannot read; so do `env` used as a value (an alias, a closure's delegate, an argument), which the checker does not follow, a call or method pointer whose name is computed, and a place the file names `withEnv` that the checker does not read as a call. A check whose failure the step ignores stays a finding. Jenkins coverage is advisory, so no exit status changes.

**Groovy octal escapes are read in every Jenkins rule.** `'\120'` is `P`, as Groovy 2.4 reads it; it was read as `120`, so `withEnv(['\120ATH+X=...'])` set no `PATH` the checker could see, and a script written with octal escapes was read with other text than it runs.

### Jenkins publish template

`templates/jenkins/obaaf-release-publish.Jenkinsfile` (#344, #365) now verifies the approval in a stage of its own before the stage that binds the upload credential, and disables Declarative stage restarts (`disableRestartFromStage()`), so a restarted run cannot start at the upload. Both checks run under `withEnv(["PATH+OBAAF=..."])` after a step that fails unless the shell finds `obaaf` in the job's virtual environment (the signing step checks the same); nothing checks that file again after the install. The tag's commit is passed with the new `obaaf verify release --revision-file FILE`, which reads one full lower-case commit ID (40 or 64 hex digits, at most one line ending) and refuses anything else. OBAAF's own rules still cannot tell about the template under OBAAF-JEN-010, 011 and 012, because of the `PATH` change (above). On a Jenkins controller, only the stage-restart option was run, by the lead session.

### Preview missing ignore owners

The full report, summary and JSON to-do list give a scoped `obaaf fix --owner OWNER` preview command for ignore entries missing their owner, after a check of the whole repository on every platform with no scan errors, a baseline in the current format, and a configuration, baseline and settings snapshot inside the repository (a link from inside to a file outside is not yet caught, #369); otherwise they say which of these to settle first. Replace `OWNER` with the person or team responsible for these entries: the preview writes that owner into every ignore entry missing one, proposes removing the baseline and ignore entries that match no finding, and lists every finding you would accept. A baseline entry missing its owner still needs review by hand.

### Reviewed egress action pin

The development checker can clear OBAAF-GHA-020 for jobs that pin `Obaaf/OBAAF/actions/egress@80db1e68769165c9ecf24e553254fa35d6e168d5` and meet the [egress control conditions](docs/checker-configuration.md#egress-controls). The [usage example](docs/egress-control.md#using-it) includes the full pin. The commit is on the `flagship` branch; it is not a tagged release.

Two conditions the checker did not read are now read the narrow way, because the listing made each one clear a finding it should not (decision D-134, from the review of #248):

- **Only `npm install -g` is read as installing an agent's CLI.** `pnpm add -g`, `yarn global add` and `bun add -g` before the confined step are now "cannot tell" where they were taken for installs only (slice 2c.8, D-053). Each reads configuration from the working directory, which a checkout fills, and Yarn 1 runs the program a `.yarnrc` names in `yarn-path` in its own place, outside the sandbox and with the runner's `sudo`. Nor is an npm install whose "version" ends `.tgz`, `.tar` or `.tar.gz`, which npm installs as a file from the working directory. This also applies to D-133's reading of uploads, so on GitHub's firewall such a step now withholds verified egress.
- **A cache whose path the checker cannot read to the end is "cannot tell".** An `actions/cache` step before the confined step saves its `path` after the job. A path that names `/tmp` or the command's output was already "not met"; a path from an expression (`${{ env.OUT }}`), one with a `..` part, one that starts `~` and a user's name, and an absolute path outside `/home` (`/`, `/proc/self/root/t?p`) could reach the same files without naming them, and were verified. Inputs that are not a mapping, and a `path` that is not text, are "cannot tell" too.

### Artifact uploads affect GitHub Actions egress verdicts

When the checker sees a possible artifact upload in an agent job, OBAAF-GHA-020 stays open even for an inspection-only upload with no visible downloader. Under either GitHub's native firewall or OBAAF's egress action, otherwise verified `egress-enforced` becomes "cannot tell". Under the action, the same applies to `key-out-of-reach`. An independently established "not met" verdict stands. OBAAF-GHA-005 loses credit for the affected controls (#354). A possible upload is an upload step; a step that uses any action other than `actions/checkout`, `actions/download-artifact`, `actions/cache`, OBAAF's egress action and Harden-Runner at commits OBAAF lists (so an `actions/setup-` action, or an agent run through an action, counts); a script other than plain `echo` lines and an agent's CLI with literal arguments (so `npm ci` or `make` anywhere in the job); every step of a job in a container; a step otherwise not counted when an `env` sets a variable such as `NODE_OPTIONS`, `LD_PRELOAD`, `BASH_ENV` or `GIT_CONFIG_COUNT` or an earlier step may change later steps; and, under the firewall, an action after the agent's step or one with a post step before it, `actions/checkout` included (D-133; the last three from the review of #357).

### Companion scanner diagnostics in GitHub Actions

New workflows generated by `obaaf init --with-scanner` combine each scanner's standard output and standard error before suspending workflow command processing (#340). `--with-scanner` is not yet in a release; workflows written by development builds before this change keep their scanner steps unchanged when `obaaf fix --gate` changes the threshold. To adopt the new steps in such a workflow, review the diff from init with the same scanner selections.

### Migration waits for a complete scan

With an old-format baseline, the full and summary text reports now ask you to resolve scan errors before migrating it, instead of printing `obaaf baseline migrate` for an incomplete scan. When the migration command cannot be printed on one line, the action list names it and identifies the baseline, and so does a JSON to-do item whose migration is a step before a checkout or pin preview. Otherwise the JSON and SARIF reports are unchanged.

### Lane commands keep the check's inputs

Lane follow-up commands in text findings and JSON reports now retain the original check inputs, including custom configuration and baseline files, after the label `Lane check:`. A path that cannot be printed on one line names `obaaf check --lanes` to run by hand. Suggested `obaaf fix` and `obaaf baseline migrate` commands now print a path that begins with `=` as `./=...`, as the check commands do, because zsh expands such a word. [Issue #262, item 6](https://github.com/Obaaf/OBAAF/issues/262)

### Init handoff and explicit gate activation

`obaaf init` ends with the to-do list and a fix-preview command. `obaaf fix --gate LEVEL` previews a blocking threshold on a generated workflow and, on a supported Linux host, `--apply` writes the proven edit. Pull requests use the target configuration and acceptances common to both commits. A pull request can fix a finding and retire its acceptance together. Init gives commands to run from inside the selected repository when its path cannot be displayed on one line, and names the folder it worked on when the given path passes through a symbolic link. Changing the gate threshold preserves the checker commit installed by an earlier generated workflow.

### Installing the GitHub Actions templates from a wheel

The wheel includes the templates used by `obaaf templates install`. Give it the repository and full OBAAF commit for the generated workflows. Use `--source` to select your own template directory. The closing instructions identify the CODEOWNERS example for the templates you selected. Release 0.3.0 users can still use the clone instructions in the README. [Issue #142](https://github.com/Obaaf/OBAAF/issues/142)

### Offline settings evidence

`obaaf check --settings FILE` reads an explicitly named audit snapshot and reports its date; a repository scan also checks the snapshot file's code ownership (OBAAF-REPO-001). Evidence older than 30 days or missing required observations stays uncertain. OBAAF-GHA-005 uses this evidence for its environment control and clears when all five controls verify. It assesses each secret name a job reads, in the environment `protected_secrets` names for it, a glob entry included; a plain-list entry alone names no environment and cannot verify. A settings path the system refuses, such as one too long, is a usage error (exit 2), not a traceback. The production catalogue still lists no released egress action commit for its credential-isolation control. The `obaaf-pipeline-check.yml` template passes `.github/obaaf-settings.json` when the repository variable `OBAAF_USE_SETTINGS` is `true`, read from the target branch on a pull request.

### Checking edits to JSON files

The adoption edit proof reads a file as the checker does: the baseline as JSON and the checker configuration as YAML, whether named `.json`, `.yml` or `.yaml` and through any link, and any other `.json` file as JSON. A file with another suffix is still withheld. It checks decoded strings and the exact spelling of numbers outside the proposed changes, and declines invalid JSON or a repeated object member. Other files continue to use the workflow YAML reader.

### Jenkins: untrusted text is read from what the value is

Slice 2d.2; decision D-132. **OBAAF-JEN-009 now reads each value built into a command from its structure, so a Jenkinsfile that passed can get a new finding or "cannot tell", and one that had a finding can pass.**

- **New findings:** `env` reached through an alias (`def e = env`, `this.env`, `env.getEnvironment()`), `?.`, a comment or another letter case; `env[n]` where `n` holds a literal; a closure's or `for` loop's parameter over an untrusted value; a closure variable called with one; what a method of the file returns; named arguments and varargs; `def (a, b) = ...`; builders, lists and maps filled with `<<`, `append`, `add` or `put`; `env.setProperty`, `binding.setVariable`, `this.X =`, `env['X'] =`; `withEnv` entries written with `+`; Bitbucket Push and Pull Request variables, `gitlabTriggerPhrase`, ghprb e-mail variables, `pullRequest.*`, `currentBuild.changeSets`, build causes and `input` answers; commit text from `.split('\n')[0]`, `git cat-file -p`, `git rev-list --format`, a format in a variable, `%%B` in `bat` and a second git command on a line; file names from `git diff --name-only` and `git status`; branch names from `git rev-parse --abbrev-ref` and `git describe` (low); `\u0024{...}` and comments inside `${...}` (a slashy string there is text); `bat`'s `%NAME%`; Docker Pipeline's `build`, `run`, `withRun`, `push`, `tag`, `pull` and `inside(args)`; Publish Over SSH `execCommand`; SSH Steps `command`; `"...".execute()`; `Eval.me`, `GroovyShell`, script engines and Job DSL `scriptText` (high); `build` parameters in a variable, in the `$class` form, from `params` or wrapped in `.trim()` or `?:`.
- **"Cannot tell"** for any value past the reader's budget (per value, and about 300,000 steps per file), and for a value from a caller outside the file: a local copy of an uncalled method's parameter, `${goals ?: 'x'}`, `cfg['x']`, a closure parameter over one, `env.X` set from one, a helper called only from such a method, and the map a `vars/` step's closure fills through `body.delegate` or `body.setDelegate`; for a computed environment name; for an interpolation the parser cannot read; for a chain of more than twelve methods, unless the names in the call say more; and for a recursive method only as far as what it is given.
- **Also new:** a declared string parameter read as `env.NAME`; `this` held in a variable or parameter (`ctx.env.X` after `deploy(this)`); chained `sb << 'a' << x` and `sb.append('a').append(x)`; a closure held in a map or in another variable and called; `bat`'s `%NAME:~0,5%` and lower-case names, and a `bat` script held in a variable; `env.getEnvironment()` and `System.getenv()` as a whole; `"...".execute(env, dir)`.
- **No longer reported:** results that are numbers, booleans or digests (`.length()`, `.toInteger()`, `as Integer`, comparisons, `.contains()`, `.encodeBase64()`), ternaries choosing literals, `URLEncoder.encode`, a `[^...]` whitelist `replaceAll`, `booleanParam` and `choice` parameters, and `env.Y` after `env['X'] = value`. A parameter of an uncalled method no longer makes a step elsewhere "cannot tell". A method of a literal (`'a,b'.split(',')`) no longer makes every Jenkins rule "cannot tell".
- **Severity:** a Generic Webhook payload variable is high unless its path ends in a number, count or identifier (`$` and `$.pull_request` were medium, `$.pull_request.comments` was high).
- **Read as Groovy 2.4 reads it:** `\uXXXX` is turned into its character before lexing, so a file with `\u000a` inside a single-line string can no longer be read (every Jenkins rule "cannot tell"), and a `\u000a` in a comment or a multi-line string counts as a line break, so the line numbers after it (in every Jenkins rule's findings) are one more than an editor shows.
- **Other rules:** a closure stored with `this.name = { ... }` and called is no longer an unknown step, so every Jenkins rule can decide such a file; OBAAF-JEN-014 can move from "not applicable" to "pass" where `this` is held in a variable.
- **OBAAF-JEN-013 follows secrets further:** a secret copied with `this.T =`, `binding.T =`, `env.setProperty`, `binding.setVariable`, `def (a, b) = ...`, a `withEnv` entry written with `+`, or `sb.append` and then interpolated is a new medium finding. Its messages are unchanged where it reported before.
- **Messages are unchanged** where OBAAF-JEN-009 names the source itself (`env.X`, `params.X`, a declared parameter, a webhook variable, git output) or a variable assigned directly from one, so those baseline entries still match. Where a variable is assigned from another variable (a webhook variable, a method's parameter, a map), the message now names only the root source (`u (from CHANGE_TITLE)` for what was `u (from t (from CHANGE_TITLE))`); such an entry must be accepted again.

### Jenkins: a check before a publish is read as the shell runs it

Slice 2d.2o; decision D-131. **OBAAF-JEN-011 now reads every check before a publish as the shell runs it, so a Jenkinsfile that passed can get "cannot tell" or a new finding, and one that had a finding can pass or get "cannot tell".**

- **Which checks:** `obaaf verify ...`, `gh attestation verify`, `cosign verify...`, `slsa-verifier verify...`, `sha256sum -c` and its kin, `gpg --verify` and `gpgv FILE`, as a command's name or after a wrapper (`sudo`, `env`, `timeout`). Before, `sha256sum -c` and `cosign verify` were found but never read for a failure the script ignores. Every check in a step counts.
- **A finding** where the step decides that the check's failure does not fail it: `returnStatus: true`, `|| true`, `|| :`, `|| echo`, `|| printf`, `|| exit 0`, a trailing `&` (not followed by `wait $!`), a pipe without pipefail set before it, `set +e` or a `#!` line without `-e` with more commands after the check, a trap on EXIT or ERR that runs `exit 0`, or more lines after it in a `bat` script. Also where its place cannot stop the publish: a parallel branch beside it, a `catchError`, `warnError` or `catch` block the publish is not in, a condition the publish does not share. A check and a publish in the same catching block, the check first, no longer give a finding. `post { notBuilt }` is a failure path (this also changes OBAAF-JEN-005, 010 and 012, which share the list).
- **"Cannot tell"** where the file does not decide: a check the shell reader of slice 2d.2e does not vouch for and no listed form decides (`if check; then`, `cd d && check`, `bash -c '...'`, a check run by `uv run`, `docker run` or `ssh`, Groovy text in the script, a computed `returnStatus`, a path to the program, `export PATH=...` before it); `powershell`, `pwsh` and other `#!` programs that name a check; a check or publish read only where a closure or uncalled method is written; a publish in a Declarative `post` block under a guard on the build's result; and a check in a catching block when the publish runs only on `post { success }` or under such a guard.
- **No longer reported:** a publish in a stage's own `post` block when no check runs in that stage and a check that stops its step runs in an earlier stage before it.
- **Messages are unchanged** where the rule reported the same check against the same publish before, so baseline entries still match. Where the finding now names a later publish (the first one is in the same catching block, or runs only on a result), the message changes.

### Jenkins: a provenance check must stop the publish

Slice 2d.2n; decision D-130. **OBAAF-JEN-012 now reads its checks as the shell runs them and counts only one that stops the publish, so a Jenkinsfile that passed can get "cannot tell" or a new finding, and one that had a finding can get "cannot tell".**

- **A check is read by the shell reader of slice 2d.2e**: `obaaf verify release` on a line of its own, in an `sh` step that stops at a failed command (no `#!` line, `-e` on it, or `set -e` first), with `returnStatus` absent or `false`. `--pre-approval` (or an abbreviation argparse accepts, such as `--pr`) makes it a provenance check: medium.
- **"Cannot tell"** where the reader does not vouch for a check the older text reading found: Groovy text put into the script (`"... ${x}"`, concatenation), a computed `returnStatus`, a shell expansion or substitution among the check's arguments (`--policy "$POLICY"`), a path or wrapper (`.venv/bin/obaaf`, `timeout 600 obaaf`), `.trim()` before a `#!` line, `bat`, `powershell` and `pwsh` steps, and a line before the check the reader cannot read (`set -Eeuo pipefail`, `export PATH=...`; #347). Also for a publish read where a closure or uncalled method is written, a check read only there and never seen called, and a publish in a `catch` or `finally` block after a check.
- **No check**: the name only in an `echo` argument or a comment, `--help`, and a check in a closure or method nothing is seen calling no longer clears a publish.
- **Failure paths**: a publish in the pipeline's `post` block is high whatever check runs before it (it was a pass after any check); one in a stage's `post` block is checked by a check in an earlier stage.
- Messages are unchanged, so baseline entries still match. OBAAF's own Jenkins release template now gets "cannot tell" (advisory) for this rule: its checks follow `export PATH=...` (#344). The record is [bypass-attempts.md](docs/bypass-attempts.md#2d2n-a-provenance-check-before-the-publish).

### Jenkins: another job's artifacts need `obaaf verify release` before the publish

Slice 2d.2m (issue #341); decision D-129. **OBAAF-JEN-010 now reads a copy as Groovy builds it and clears it only with an `obaaf verify release` that stops the publish, so a Jenkinsfile that passed can get a new high or medium finding, or "cannot tell".**

- **More copies are read**: `copyArtifacts` on any receiver, `step([$class: 'CopyArtifact', ...])`, a map given as the only argument or kept in a variable, and Jenkins URLs to another build's artifacts or workspace in a shell step or `httpRequest` (`job/b/lastSuccessfulBuild/artifact/`, `job/b/ws/`, a URL kept in `environment`).
- **Selectors by their value**: `specific` is fixed only for digits, or for the number of a `build` the file runs; other text (`specific('lastSuccessfulBuild')`) moves; `upstream(fallbackToLastSuccessful: true)` moves; `selector: null` is the default.
- **Only `obaaf verify release` clears a copy**, run as a command whose failure stops the `sh` script, after the copy and before each publish it covers. A `sha256sum -c`, `cosign verify` or `gpg --verify` there now gives "cannot tell" instead of a pass, because its sums may come from the build that was copied. A check in an `echo` or a comment, after `|| true`, after the publish, in a parallel branch, or under a condition the publish does not share (other than a condition on parameters that the copy shares) no longer counts, and nothing clears a publish in `post { always }` or `failure`, a `catch` block, or before the copy in the same `retry` block or loop.
- **"Cannot tell"** for a computed selector, build number, project or `$class`, a spread map, `downstream`, `invokeMethod`, a method pointer or computed method name, and a copy in a method or closure, read where it is written (which was a finding), even when the closure is also called.
- **Severity**: high only when an unchecked publish after the copy is in the copy's own stage, its `post` blocks included. A baseline written for a publish before the copy in its stage (high, "...in the same stage.") now matches nothing and the medium finding is new; one for a publish in the stage's `post` block (medium) does the same the other way. No other message changed. OBAAF's own Jenkins release template now gets "cannot tell" (advisory) for this rule: its build number is computed, and its checks run after `export PATH=...`, which the reader cannot vouch for (#344).
- **Cost**: the rule no longer compares every copy with every step of its stage; 744 bytes of nested helpers took 11.7 s in this rule. The record is [bypass-attempts.md](docs/bypass-attempts.md#2d2m-artifacts-from-another-build).

### Jenkins: an approval must stop the publish

Slice 2d.2l (issue #337); decision D-128. **OBAAF-JEN-005 now asks whether an `input` step really stops each publish until someone approves, so a Jenkinsfile that passed can get a new medium finding.**

- **An input that does not stop the publish no longer counts**: one caught when aborted (`try`/`catch` without a rethrow, `catchError`, `warnError`, a caught `timeout`), one a condition may skip (`if`, `else`, `switch`, a loop, `.each`, `.times`, `&&`, `||`, `?:`, a `when` with `beforeInput true`, a `when` on a stage whose `steps` hold the input), one in a sibling parallel branch or a failure path, and one in a closure or method that may never run. An input in the same `catchError` or `try` block as the publish, before it, still counts. A Declarative stage's `input` is asked before its `when`, as Jenkins does.
- **Every publishing stage is checked**, not only the first. A publish in `post { always }`, `aborted`, `failure` or another failure path, or in a `catch` or `finally` block, is never gated by an input.
- **Submitter values as the plugin reads them**: blank, empty or `null` is no submitter (a finding; it was "cannot tell" or nothing), as are `'\u0020'` and the Declarative `submitter ''`; the group `authenticated` is a finding; a repeated key takes the last value; a map given as the only argument is read; a spread map or a map variable is "cannot tell" (it was a finding).
- **"Cannot tell" instead of a finding** when part of the file was not read, or a publish is read only where its closure is written, not where it runs.
- **The Jenkins lexer decodes `\uXXXX`** in strings (it read `u0020`), for every Jenkins rule.
- **The model's conditions are wider and sharper for every Jenkins rule**: a step under `&&`, `||`, `?:` or in a closure given to `.each`, `.times`, `.sum`, `.sort` and other iteration methods may not run, as a step in a `for` loop already could not be relied on; each branch of a `?:` and each `switch` case is its own condition; conditions are compared by their whole structure (operators, grouping, numbers, lists, closure bodies, `expression { return ... }`), so `==` and `!=`, or `> 5` and `> 0`, differ; inside an inlined method, a condition that reads anything but properties of `env`, `params` and `currentBuild` (`env.BRANCH_NAME`, not a bare `BRANCH_NAME`), or calls anything, is tied to that call; a closure given to an inlined method that never calls it may never run, and a trailing closure binds to the method's last parameter (`def withTimeout(int m = 60, Closure body)`); `beforeAgent`, `beforeInput` and `beforeOptions` are not part of a `when`'s condition; a `catch` that throws only under a condition no longer counts as rethrowing (a `throw` inside `stage { }`, `dir { }` or another step that runs its body once still counts, and so does `steps.error`). A check in any of these places no longer counts for OBAAF-JEN-011 and 012, which can add high findings there. Because a trailing closure now runs inside the helper it is given to, credentials the helper binds (`withCredentials` in `def withRelease(int m = 60, Closure body)`) now reach the closure's steps, which can add OBAAF-JEN-001 and 013 findings. The text OBAAF-JEN-011 prints for a condition is unchanged.
- Not changed: which steps publish (OBAAF-JEN-012's reader; a command held in a variable, `gradlew jib` and `buildah push` are not seen, left to slice 2d.2). The record is [bypass-attempts.md](docs/bypass-attempts.md#2d2l-release-approvals).

### Jenkins: which steps share a workspace

Slice 2d.2j (issue #210); decision D-127. **OBAAF-JEN-003 now follows an AI agent's workspace across stages, so a Jenkinsfile that passed can get a new high or medium finding; OBAAF-JEN-002 and 006 can report settings they missed; OBAAF-JEN-007 can pass a stage it reported.** Every case is an inert test input in `tests/test_jenkins_workspaces.py`; [docs/jenkins.md](docs/jenkins.md) has the table and what the checker cannot decide.

- **OBAAF-JEN-003** read an agent and a push, a `build` step or a publish as sharing a workspace only inside one stage. The model now records a workspace for every step. The top-level agent holds one for every stage without its own agent and for the pipeline's `post`; `reuseNode` and `agent none` stay in it; `node()` and stage agents allocate their own; `ws()` is another directory on the same node. An effect after the agent in the same workspace, or after an `unstash` or `unarchive` of what was stashed or archived after it, is high. An effect before the agent in a workspace Jenkins keeps between builds is medium (what the agent leaves there is in place next build), unless it runs in a fresh pod or after a full `deleteDir()` or `cleanWs()`. Separate allocations that may be the same machine are unknown; different labels and separate pods are not findings.
- **OBAAF-JEN-002** parses label expressions with Jenkins's operators. `built-in || linux` and `linux -> built-in` can run on the controller, and `!windows` and `docker -> linux` select like `agent any`. An AI agent's work on a persistent label shared with a stage that holds credentials or publishes, or on labels that require a common one, is a medium finding.
- **OBAAF-JEN-006** reads docker run options as docker and Jenkins split them. It now finds `-v/var/run/docker.sock`, `-itv`, `--mount type=bind,source=/` (CSV fields, keys in any case), `--privileged=t`, `CAP_SYS_ADMIN`, `--device`, `--use-api-socket`, Windows drive roots and whole system folders. It stops reporting `--privileged=false` and ordinary folders inside system folders (`/root/.m2`, `/etc/localtime:ro`). Pod specs are parsed as YAML, so JSON specs, string booleans and projected tokens are read; what cannot be read is an unknown. `podTemplate`'s own `privileged`, `hostPathVolume`, `hostNetwork` and `hostPathWorkspaceVolume` count. The pod a `node(POD_LABEL)` runs in is the template's.
- **OBAAF-JEN-007** passes a stage whose agent's shell steps run in a container with exactly one network, `none`, and nothing that reaches the host. With a host path mounted into it, the finding stays and names the path.
- What the agent's output reaches through values, and commands the checker does not recognise as an agent or an effect, are not in this change (#330).

### Upgrading from 0.3.0

The changes below are on the development branch for the prospective 0.4.0 release. A pinned gate picks them up when its maintainer changes the pin.

- **Keep settings in a fix preview.** Suggested checkout and tool-pin commands carry the selected snapshot into the preview and apply proof. Fixes require a snapshot in the repository working tree. For a snapshot outside it or under `.git`, the report gives manual guidance.
- **Init declares only the agent lanes the checker cannot find.** `obaaf init` no longer writes `agent` in `lanes` for a job the checker already puts in the agent lane (a catalogued action, an agent CLI, a local composite action or repository script that runs one); it lists such a job with the checker's reason, and findings on it give that reason instead of "set in the checker configuration". A job found only by a model-provider key is still declared, and so is a job whose agent the checker does not also find in the files of the last commit, outside submodules, as Git stores them (not a script that is untracked, ignored, in a submodule, edited since the commit or stored through LFS), because the generated workflow checks a checkout that holds only those. A job recognised through a repository script or a local action, and declared by no one, is not an agent job when one workflow file is checked on its own.
- **Preview a first GitHub Actions check.** Run `obaaf init` from the repository and review its configuration and workflow. Run `obaaf init --apply` to create them. The workflow reports findings with `--fail-on never`. Add `--with-scanner zizmor`, `--with-scanner actionlint`, or `--with-scanner poutine` to opt into additional report-only checks from pinned scanner images.
- **Preview paperwork changes before accepting risk.** `obaaf fix` can propose a correction to a lane name, where it changes no other finding, and removal of stale entries. Supply an owner to preview completing an ignore entry. A legacy baseline migration also needs a reason and expiry. The command lists each acceptance and shows a diff verified on a private copy.
- **Apply a verified paperwork diff.** Run the same command with `--apply` to recompute the preview and write its exact changes. Every target must be tracked and clean in Git, and not marked assume-unchanged or skip-worktree. The command preserves its permissions and leaves the changes unstaged for review. Apply runs on Linux only.
- **Generate a confinement work order.** Add `--brief` to `obaaf fix egress --job NAME` on a trusted branch to print a Markdown task with the target step, predicted verdicts and proof command. Availability follows the egress action’s release hold. The ordinary preview now lists each egress-action condition that names several steps as one line per step, each with its explanation, where it printed one joined line.
- **Name the step to confine.** `obaaf fix egress --job NAME --step 'NAME OR ID'` drafts the run step with that exact name or ID, for a harness the checker does not recognise as an agent or a job with several agent steps; `--brief` takes it too. A name or ID that matches no step or more than one is refused. The preview now prints the job as it is written, with the chosen step's `run` moved under the action's `with` and everything else, comments and line endings included, as it was; it no longer re-dumps the job. A job that holds a character Python does not count as printable, other than a tab and a line ending, or a carriage return outside a CRLF ending, is refused: a value holding one was printed escaped, and a comment holding one, never printed before, is now refused too. So are a step written with an explicit `? run` key and a workflow that writes `jobs` as an explicit `? jobs` key.
- **Preview confinement for one agent job.** The development command `obaaf fix egress --job NAME [PATH]` reports that the draft is unavailable when no egress-action commit is listed; with the [listed pin](#reviewed-egress-action-pin) it checks the proposed job on a private copy and prints the control verdicts and remaining manual work.
- **Names the egress action reserves are read.** At a commit OBAAF lists, a step that names `PATH`, `NODE_OPTIONS`, an `ACTIONS_` or `AWF_` name, a `*_BASE_URL` name or another name the action reserves under its `env` input makes the egress control and OBAAF-GHA-005's fifth control *not met*, because the action refuses to run. This changes verdicts only for the [listed pin](#reviewed-egress-action-pin).
- **Pin an agent tool to a version you choose.** `obaaf fix --pin PACKAGE=VERSION` previews exact npm pins on directly identified OBAAF-GHA-025 installs. The to-do list keeps candidate and manual counts together. Use the displayed step name to request one occurrence and, on a Linux host with extended-attribute support, append `--apply` to write its proven diff. While an old-format baseline or a baseline or ignore entry that matches no finding would make the proof refuse, the to-do list gives no pin or checkout command: it says what to settle first, with the paperwork preview that names each unmatched entry, or asks for a check of the whole repository when the scope cannot tell.
- **Tighten a reported checkout on request.** `obaaf fix --tighten checkout-credentials` previews disabling persisted credentials on eligible OBAAF-GHA-011 steps. Select one using its displayed `--candidate` name. A change that disturbs another acceptance stays withheld and reports the impact.
- A refused paperwork preview identifies an invalid baseline or configuration by its path in your repository. The diagnostic retains the reason the checker could not use the file.
- **`ignore: 5` is an error, not a traceback.** A number, `true`, text or a mapping as the checker configuration's `ignore` ended `obaaf check` with a Python traceback or a misleading message. It now ends with an error naming the file and exit status 2. A value that reads as nothing (no value, `null`, `false`, `0`, `''`, `{}`) still means no entries.
- **Writing over a legacy baseline still exits 2 and preserves the file.** The refusal now gives a migration command for the checked path, configuration and platform, or manual guidance when a path or option cannot be printed on one line.
- **Old-baseline migration hints preserve the selected paths.** If a path or option cannot be printed faithfully on one line, the full text report and `--summary` give manual guidance. Printable paths, including spaces and leading dashes, keep a copyable migration command.
- **Read the action list in the terminal.** The full text report groups outstanding findings just before its version line. Add `--summary` to a text check (not with `--format json` or `sarif`, `--lanes` or `--write-baseline`) to see the accepted risk and those actions, with any scan, coverage or baseline warnings. The gate uses the same threshold and exit status in either view.
- **Read the action list in JSON.** The new `todo` array groups outstanding findings and counts the old baseline entries that share a rule, file and job with current work.
- **The suggested `obaaf baseline migrate` command works for a path that begins with `-`.** It is written `./-name`, which the command reads as a path rather than an option.
- **Legacy migration counts only eligible acceptances.** It does not carry over a match no entry can accept, or one waiting on an ignore entry that has expired or is not valid (a 0.3.0 ignore entry names no owner), and its receipt says why for each; entries naming findings a valid ignore entry accepts are counted. When it can carry over no match and leaves one open, it preserves a nonempty legacy baseline and exits 1.
- **Review existing acceptances.** A 0.3.0 baseline accepts nothing until migrated. Each acceptance needs an owner, a reason with at least four letters or digits, and an expiry date within 366 days. The report opens with the risk still accepted and lists entries that no longer match.
- **Review newly checked jobs.** The checker follows local composite actions and calls to local reusable workflows, recognises 23 named agent tools, reports agent jobs that install tools at a version that can change (OBAAF-GHA-025), and reports agent actions given a setting their own documentation warns about (OBAAF-GHA-026). Ineffective lane declarations, checkout and permission handling, ownership of CI files, and revised egress checks can also change a gate's result.
- **Check repository settings separately.** The new `obaaf audit` command compares settings with workflow files and distinguishes findings, settings it could not read, and questions the rules could not answer. The workflow checker and the settings audit each have their own gate.
- **Check consumers of the report.** The text report now starts with accepted risk and ends with the checker version. A named agent can change a finding's JSON facts and whether an existing acceptance matches. The self-assessment describes the tier earned from the answers supplied.

Try the new pin in a dedicated pull request, migrate the old baseline, and run the existing gate before accepting any newly reported findings. The upgrade guide gives the commands, the changes rule by rule, and a measured example from the first adopter. [Upgrade guide](docs/upgrading.md)

### A job that may publish and restores a cache

Slice 2d.14 (issue #289); decision D-126. **A job OBAAF does not count as a release job, that holds what publishing needs and restores a cache, now gets OBAAF-GHA-006 (medium), and a job that pushes an image through its build's outputs or `docker buildx imagetools create` is now a release job. Either can turn a passing gate red.**

- **The gap.** OBAAF-GHA-006 was about release jobs only, and a job is a release job when OBAAF knows one of its steps publishes, its environment's name says releases go there, or it is declared one. The parity test against zizmor found a job a release event starts that restores setup-uv's cache and then runs `uv build publish` with `UV_PUBLISH_TOKEN: ${{ secrets.PYPI_PUBLISH_TOKEN }}` (zizmor's test workflow `cache-poisoning.yml`): OBAAF reported nothing. Code from a poisoned cache entry runs with what such a job holds, whether or not the job itself publishes.
- **What is reported now.** A job outside the release lane that holds what publishing needs and restores a cache its `cache-mode` lets through gets OBAAF-GHA-006, case `capability-restores` (`capability-restores-self-hosted` on a self-hosted runner), at medium, saying the checker cannot tell whether it releases. One that downloads artifacts from a job it needs that restores a cache gets case `capability-needed-job-restores`. What the job holds is a fact of the finding, so an acceptance written for one credential does not cover another one added later. A step that uses a local composite action counts as a cache step only when its steps could not be read; when they were, they decide.
- **What counts as holding what publishing needs.** What OBAAF-GHA-015 already counts for a job that may release (`packages: write`, a secret whose name says it publishes, a step using an action under `publishing_actions`), except a `docker/build-push-action` step that can only build; a reference that can read every secret (`toJSON(secrets)`, a computed name, `secrets: inherit`); and `contents: write`, which can create a GitHub release and upload its assets, in a job that a release event, a tag push (a `push` whose filters do not keep tags out), a tag's creation (`create`) or another workflow's call (`workflow_call`, any event of the caller) can start. A job of a called workflow that declares no permissions holds what the jobs of the repository that call it grant.
- **What clears it.** `cache-mode: none` or `write-only` on the job (or on the jobs it needs that restore), turning the cache off in the step, or moving the credential to a job that restores no cache. A job with no cache step gets no finding: the low `no-cache-mode` is for release jobs. Where a local action's steps make the job a release job, its release finding replaces the "cannot tell" one on the same step or job, here and for OBAAF-GHA-015.
- **Image pushes the release lane did not read.** These now make a job a release job, with OBAAF-GHA-006, 014, 015, 016 and 017, and OBAAF-GHA-008 and 018 at high:
  - a `docker/build-push-action` step with an output of type `registry`, of type `image` with a `push` or `push-by-digest` that is not false or with a value set when the job runs, whose type is set when the job runs, or with no type and a value set when the job runs (a field may be quoted, and a key is trimmed, as buildx reads them);
  - a `docker/bake-action` step whose `set` overrides an `output` the same way (with `=` or `+=`), sets `push` to anything but false, or has a value set when the job runs before its `=`; a build argument (`*.args.PUSH=true`) does not count;
  - both read through the job's matrix where it is written out in the file;
  - `docker build`, `docker image build`, `docker builder build`, `docker buildx build` (or `b`) and `docker buildx bake` with `-o`/`--output`, or bake's `--set`, read the same way, expressions included;
  - `docker buildx imagetools create`, which pushes a manifest list unless it is given `--dry-run`.
  A cache import or export (`--cache-to type=registry`), a `docker` or `local` output and a platform override do not count. The command pattern looks at most 8,192 characters or quoted strings into one command, past quoted text but not past an unquoted `;`, `&` or `|`, and reads each output's first 256 characters or expressions; on the long lines the reviews built to slow it down, a search costs at most about six times what the older `--push` pattern's does on the same line (a full check about four times), and much less on others; it grows with the line's length, not its square.
- **Not counted.** Permissions nobody declares (OBAAF-GHA-009 reports them), `contents: write` on other events (common in jobs that commit back), a credential whose name matches no pattern, a credential passed under another name to a workflow of the repository that restores a cache (that workflow is read with the secret names its jobs use), what a bake file says, options written before `buildx` or `imagetools` (`docker --context x buildx ...`), an output option more than 8,192 characters into its command or after an unquoted `;`, `&` or `|` in it (an escaped quote inside a quoted argument is not read as the shell reads it), and image pushes by other tools.
- **The parity test** now answers 32 of zizmor's 56 test cases (it was 30): `cache-poisoning.yml` and `issue-343-repro.yml`, a tag-push job given `contents: write` that restores setup-go's cache. `scripts/zizmor_parity.py` counts the new case for each cache step of its job, as it counts `restores`.
- **On the first adopter and on OBAAF itself** the reports are unchanged. On the workflows of 20 public projects sampled for the review, seven jobs in four projects that push images through `outputs` or `docker buildx imagetools create` became release jobs, and four jobs of one project that call a workflow of the repository with `secrets: inherit` after jobs that restore caches got `capability-needed-job-restores`.

### What an earlier step writes to GITHUB_ENV can change what a check runs

Slice 2d.13 (F-278); decision D-125. **A release job that writes `PATH` (or another variable that changes what a later step runs) to `GITHUB_ENV` before its check now gets OBAAF-GHA-016 `cannot-tell` (high). It can turn a passing gate red.**

- **The gap.** A check (`obaaf verify release`, `gh attestation verify` and the others) counted after a step that wrote `echo "PATH=$PWD/fake:$PATH" >> "$GITHUB_ENV"`, though the runner gives every later step what a step writes there (actions/runner v2.338.2 refuses only `NODE_OPTIONS`), so the check ran whatever `obaaf` that step put first on the PATH. `SHELLOPTS=noexec` written the same way makes bash read the check's step and run none of it, and the step succeeds. Only `BASH_ENV`, `BASH_FUNC` and `GITHUB_PATH` in an earlier step's text, and `BASH_ENV`, `ENV` and `BASH_FUNC...` in an `env`, were looked for.
- **What counts now.** A variable that changes what bash or the check's program runs (`PATH`, `HOME`, `ENV`, `SHELLOPTS`, `PS4`, `EXECIGNORE`, `GCONV_PATH`, `ACTIONS_ALLOW_UNSECURE_COMMANDS`, any `BASH...`, `LD_...` or `DYLD_...` name, any `PYTHON...` name but six that load nothing), in the `env` of the check's step, its job or its workflow, or written to `GITHUB_ENV` by an earlier step of the job. A write OBAAF cannot read the names of counts as one. In a bash or sh script, the variables of the runner's file commands (`GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_OUTPUT`, `GITHUB_STATE`, `GITHUB_STEP_SUMMARY`), whose files sit side by side so that any of their paths leads to `GITHUB_ENV`'s, may appear only as a plain redirection target (`>> "$GITHUB_OUTPUT"`, `${GITHUB_OUTPUT:-/dev/stdout}`) or the file `tee` writes an output or the summary to; anywhere else (an argument, a copy, `set --`, `read`, a parameter expansion that changes it), a computed name, `cat`, a here-document or a group counts. So does any of them in code in another language, an action, a step's `env`, `shell` or inputs, or the workflow's or job's `env`, `defaults` or matrix; a write to `GITHUB_ENV` through `<>` or with `$'...'`; a steering variable in a container job's `env`, and any `-e` or `--env` in its `options`; and `core.exportVariable`, `core.addPath`, `::set-env`, `${{ github.env }}` and `${{ github.path }}`. `echo "VERSION=$V" >> "$GITHUB_ENV"` and `printf 'VERSION=%s\n' "$V" >> "$GITHUB_ENV"` change nothing; writing outputs from Python before the check, or giving a tool the output file's path, now counts.
- **Also changed by it.** OBAAF-GHA-021's record and proposal checks, and a provenance command (`cosign attest`, `obaaf attest build-record`) that OBAAF-GHA-017 counts as signing, are read the same way.
- **Shown on GitHub.** CI's new advisory job `github-env-premise` writes a stand-in `obaaf` onto the PATH and `SHELLOPTS=noexec` through `GITHUB_ENV` on a GitHub-hosted runner, and checks that the stand-in ran and that a step ending in `exit 1` succeeded without running.
- **Not read.** A name or a path a script assembles otherwise, what a program or action an earlier step runs writes to the runner's files, and a line break that a variable, a file or a command's output puts in a value at run time.

### `npm publish --provenance` counts as provenance

Slice 2d.12 (issue #201); decision D-097. **OBAAF-GHA-017 is reported for fewer workflows; a baseline entry for one it no longer reports no longer matches, which fails a check at or above `--fail-on`.**

- A release upload that is `npm publish --provenance` signs its own provenance, and OBAAF-GHA-017 ("Release builds without provenance") no longer counts it. npm's documentation asks for `id-token: write`, a GitHub-hosted runner and the flag; npm's CLI throws before it publishes when it cannot sign (`ensureProvenanceGeneration`, read in npm/cli at `787f152`), so such a step publishes nothing without provenance.
- **Only the documented form is read:**
  - the step's whole script is `npm publish` with only `--provenance` (or `--provenance=true`), `--access public` and `--tag NAME`, each read as written (a comment or a line continued with a backslash aside);
  - the job's declared permissions, or its workflow's, give `id-token: write`; every runner it may run on is GitHub-hosted, and it has no container and no services;
  - an earlier `actions/setup-node` step sets Node.js 20 or later, or `lts/*`, `latest`, `current` or `node` (npm 9.5.0 or later, which npm's documentation asks for), with npm's own registry if it names one, and every earlier step is `actions/checkout`, such a setup-node step, or a `run` step of `npm ci`, `npm install`, `npm test` or `npm run NAME`, none with an `env`, an `if` or `continue-on-error`, nothing run beside them, and no default `shell` in the job or the workflow;

### Agent CLIs given options built in code in another language

Slice 2d.5c2c (issue #81, the rest of part 2 of 2d.5); decision D-095. **OBAAF-GHA-026 reads more, and it can turn a passing gate red.**

- A new reader, `src/obaaf/checker/agent_code.py`, reads by its tokens the code given to an interpreter (`python3 -c`, `node -e`, `perl -e`, `ruby -e`, `php -r`, awk, a heredoc or a pipe into one), a github-script script and a step whose `shell` is python, node, ruby, perl, php or pwsh. Strings, escapes, interpolation (`f"..."`, `` `${}` ``, `#{}`, `$x`), heredocs, `qw`, `%w`, here-strings and regular expressions are read as each language reads them.
- **Now "cannot tell" (medium `command-computed`):** an argument list with a splat or spread, joined with another, held in a name the code changes, or given whole as a value (`exec.exec('claude', flags)`, which was quiet); a command line in a string given to a call that runs one and joined with or holding a value (`os.system("claude " + os.environ["F"])`, `"claude #{ENV["F"]}"`, `"claude $ENV{F}"`), a list joined into one, a `${{ }}` expression or an unquoted heredoc's expansion pasted into the code, and a value whose known start or end could be a warned option.
- **Now matched (`command-option`):** literal pieces (`"--" + "dangerously-skip-permissions"`, `"-" + "y"` for Gemini CLI), which were "cannot tell"; a name given a literal (`f = "--" + "yolo"`, `p = "claude"`); a list held in a name the code does not change.

- PowerShell and cmd are read word by word: quotes (curly ones too in PowerShell), groups, `{ }` blocks, `;`, `|`, redirections, `&`, `--%`, `Start-Process`, `call`, `start`, `cmd /c`, `npx`, `for ... do`, `if`, and continuation lines (a backtick or a caret at a line's end). In PowerShell a variable inside double quotes, and `$env:NAME` anywhere, is one word, and another variable outside quotes is "cannot tell", as before. **In cmd a `%VAR%` inside double quotes is now "cannot tell"** (`claude -p "%PROMPT%"`): cmd puts the text in before it reads quotes.
- Node's `{shell: true}` joins the program's arguments into one shell line, so a value among them is "cannot tell"; a command line given with an argument list (`exec.exec('claude -p x', flags)`) reads both.
- Fixed in the interpreter reader: `php -r` was taken for an option with a value and its code never read; `python3 -I -c`, `perl -Mautodie -e`, `ruby -rtime -e` and `awk -v f=x` read the wrong word as the code; `pypy` is an interpreter; a `shell` of `/usr/bin/env python3 {0}` or `uv run --script {0}` is python.

### A local composite action's steps are read as the job's own

Slice 2d.4b2 (issue #225, the rest of 2d.4b with 2d.4b3); decision D-083. Ways past OBAAF-GHA-002, 006, 008, 014, 015, 016 and 017 recorded by slices 2d.2c, 2d.2e and 2d.2f (attempts 015 and 111, and a checkout of the head given as an input).

- **Every rule that reads a job's steps reads the steps of a local composite action as steps of the job that uses it.** Before, only the agent lane looked inside `uses: ./.github/actions/x` (slice 2d.4a). The other rules saw one step with a local path, so any of these could sit inside an action of the repository's own and give nothing: a checkout of a pull request's head, a publish, an unpinned action, a kept checkout token, a template placeholder in a step (not in an input's `default`), or an outsider's text in a script. (A cache was already reported: a local action is taken to restore one.)
  - The using step's `with:` is put into the expressions that read the action's inputs, as expressions:
    - `ref: ${{ inputs.ref }}` given `${{ github.event.pull_request.head.sha }}` is a checkout of the head;
    - `${{ inputs.ref || github.event.pull_request.head.ref }}` keeps the head too;
    - a script that echoes `${{ inputs.title }}` given an issue's title is OBAAF-GHA-010;
    - `toJSON(inputs)`, `(inputs).x` or `inputs.*` is read as every input it is given, and a `with:` written as one expression as every input;
    - an input that comes out as plain text is that text, `push: ${{ inputs.push }}` given `false` does not push; not in `if:` or `continue-on-error`, where `${{ '' }}` stays an expression (false).
  - The using step's `env`, `if:` and `continue-on-error` reach the action's steps (an `if: false` inside too). A local action inside a local action is followed.
  - A finding on a step of an action names it after the action, `./.github/actions/x: actions/checkout@v4`, with the using step's name before it when it has one, at the workflow line of the using step.
  - A job whose action publishes gets the release rules, and `obaaf check --lanes` shows it as a release job.
  - A test holds 14 cases to the findings the same steps get when written in the job.
- **Reading through never clears a finding or lowers one.**
  - A finding of a job's own step that the action's steps change takes its facts, controls and severity from what the action does, as for the same steps written in the job. So an acceptance of it can stop matching. Examples: a "cannot tell" finding on a step after any local action, whose digest of the steps before it now covers the action's steps (an edit to the action changes it again); OBAAF-GHA-005's control "no outsider's input" beside a fetch of a pull request's code in the action; OBAAF-GHA-008 on a job's own action, high once the job's local action makes it a release job (a baseline entry at the lower severity no longer accepts it). It is never less severe, or nearer to cleared, than before.
  - A finding the second reading does not give is kept as it was.
  - Where the steps of an action give another case of a rule on the same step or job, that case is added beside the first one when it is more severe, or when the action's steps put the job in a lane it was not in (OBAAF-GHA-015's release case beside "cannot tell whether it releases").
  - Where the steps of an action make another case of a rule on the same step more severe, that case is added beside it. For example, `gh attestation verify` after an action that writes `GITHUB_PATH` is OBAAF-GHA-016 "cannot tell", high, beside "provenance only", medium.
  - A check, a monitor, a pin or OBAAF's egress action inside a local action clears no finding of the job's own steps. A check inside an action still counts for an upload later in the same action.
  - A local action is still taken to restore a cache whatever it holds, and OBAAF-GHA-006 gives one finding for the job.
- **What cannot be read** is named in the note 2d.4a added. Its wording now says the other rules may not see it either. New reasons: an expression that reads `inputs` in a way the checker does not work out, a `with:` written as one value, and a step with neither `run` nor `uses`.
- **Errors, which fail the check:**
  - more than 1,000 steps of local actions in one job;
  - more than 2,000,000 characters of their text, with the inputs put in and each alias counted where it is given;
  - more than 10,000 steps or 10,000,000 characters for the check;
  - one text of more than 200,000 characters once its inputs are put in.

  The error is given for each job past its bound, and once past the check's.
- **A check after an action whose steps write `GITHUB_PATH`** can no longer be vouched for: OBAAF-GHA-016 "cannot tell". This repository's release job is one, because its `setup-obaaf` puts its own virtual environment on the `PATH`. The finding is accepted in `.github/obaaf.yml`, in Sean's name for him to confirm.
- **Faster:** whether an earlier step changes the shell or the `PATH` is worked out once per job. Before, each check of each upload read every earlier step again, so a job of 990 steps took 98 s; it now takes under a second. No finding changes from this.
- **Not changed:**
  - what a called local workflow is given and does (slice 2d.4b3);
  - an action's `outputs` read in the job;
  - actions of other repositories, and JavaScript and Docker actions of the repository's own.

  The first adopter's report is byte-identical.

### A called local reusable workflow is read with what its callers give it

Slice 2d.4b1 (issue #80, part of 2d.4b); decision D-082. Ways past OBAAF-GHA-002, 005 and 013 recorded by slices 2d.2b, 2d.2c and 2d.2d.

- **Every workflow file is now read before any is checked.** A job of the repository that calls a workflow of the repository (`uses: ./.github/workflows/x.yml`, or `$/...`) gives that workflow's jobs the events that can start the calling job, after its own `if:` and the jobs it needs. The called jobs keep `workflow_call` too, for a caller in another repository. A chain of calls carries the first caller's events to the last; a cycle, which GitHub refuses, ends with every file in it given all of them.
  - Before, a called workflow was read with `workflow_call` only. A `pull_request_target` workflow that called a local workflow which checks out the pull request's head got no OBAAF-GHA-002, one that ran it on a self-hosted runner from a pull request got no OBAAF-GHA-013, and the jobs had none of the findings of OBAAF-GHA-001, 011, 015 and the other rules that ask which events start a job for the caller's events (OBAAF-GHA-010 already read `workflow_call` as untrusted; its `triggers` fact now lists the callers' events too).
  - The called job's own `if:` narrows the callers' events as it narrows its own.
  - A workflow without `on: workflow_call` is given nothing (GitHub refuses to call it); a call whose path holds an expression or leads outside the repository gives nothing; a path is matched with its letter case, and a link by its own name. A same-repository call written as `owner/repo/.github/workflows/x.yml@ref` is not matched.
  - Workflows are worked out callers first, so a chain takes one pass; the files of a cycle are each given every event that reaches any of them. A caller's event that GitHub does not document and no rule names reaches the called jobs as "an event GitHub does not document", which no rule names either.
  - A file checked on its own knows no callers; files given together know the calls between them.
  - `obaaf check --lanes` reads the files the same way, so a called job's lanes follow its callers' events.
- **OBAAF-GHA-001 and OBAAF-GHA-005 name what each caller passes** for the secrets the called job reads, as a fact of the finding: "Agent job 'agent' receives MODEL_KEY (from the jobs that call its workflow: .github/workflows/caller.yml job 'call' passes MODEL_KEY as PROD_DEPLOY_KEY).". A caller that is itself called is followed to its first caller, through `secrets: inherit` too. A key with space round it is read without it, and a key that is not text (`null:`, `true:`, a number) is taken for every name the job reads. Each entry is bounded, and past five entries (or 1,000 characters) the finding names at most three and a digest of all of them. A baseline entry for the finding no longer covers a caller that maps another named secret onto the parameter; a secret the caller picks with an expression is "any secret", whichever it picks, and an `ignore` entry, which names the rule and the job, still covers it. OBAAF-GHA-018's findings for signing secrets and for a job that can read every secret have the same fact.
- **A note names each called workflow read with events its own `on` does not name**, and the jobs that call it (the first five callers and ten events, and a count of the rest).
- **Not changed:**
  - a caller in another repository is not seen, and the calling job is not read as an agent job;
  - the inputs a caller passes (`with:`) are not put into the called workflow: a checkout of `inputs.ref` in a job an outsider's event can start is "cannot tell" at medium (slice 2d.4b3);
  - what a called workflow does is not counted for its caller (a publish, a cache, the token it is given; slice 2d.4b3);
  - a local composite action's own `uses`, uploads, caches and checkouts (slice 2d.4b2).

### An agent inside a local composite action makes an agent job

Slice 2d.4a (issue #80, part of 2d.4); decision D-081. A way past OBAAF-GHA-003, 004, 005 and 020 found by slice 2d.2b's reviewers.

- **A step that uses an action of the repository itself** (`uses: ./.github/actions/run-agent`, or `$/...`) now makes its job an agent job when the action is a composite action and an agent runs in its steps. The checker reads `action.yml` (and `action.yaml`, when both are there). It looks for:
  - an agent action, or an agent CLI in any command line;
  - each `${{ inputs.name }}` worked out from the using step's `with:` or the action's `default` (also in `( )`, `||`, `&&` and `format()`; any other expression as each input it reads), with the using step's `env`, also as `${{ env.NAME }}` (its own inputs put in);
  - a repository script a step runs, from the repository's root, or from the action's folder when the step goes there with `working-directory`, `cd` or `pushd` (`github.action_path` and `$GITHUB_ACTION_PATH` put in);
  - the further local actions it uses, up to ten deep.

  Before, such a job was in no agent lane and got none of the agent rules. `obaaf check --lanes` gives the same reason, naming the action and its step.
- **OBAAF-GHA-020 names the action** when such an agent runs beside OBAAF's egress action ("runs an agent CLI in step '…' of the local action ./…", outside the confined command).
- **What it cannot read through is named in a note**, never a finding:
  - a JavaScript or Docker action;
  - a missing action file;
  - a path outside the repository or with an expression;
  - an expression that reads an input or the environment nested more than 64 parentheses, or eight `||`, `&&` or `format()`, deep, or that can give more than 16 texts, or an input or `env` value too long once put in;
  - a `runs.using` it does not read, `runs.steps` that is not a list, or a step that is not a mapping;
  - a chain that comes back to itself or is more than ten deep;
  - every local action of a workflow checked on its own.

  The note names the first five places by file, job, action and reason, and counts the rest.
- **An action file it cannot read is an error, which fails the check, as a workflow file is.** That is one that is not YAML the checker reads (a parse error, a duplicate key, a tag, a disputed line break), is not a mapping, cannot be opened or is over 1 MB. So is a check whose local actions would cost more units to read than it spends on them (30,000 for the check, and 100 for each step of a job that uses one, which only that step may spend; a reading of an action costs one, three for each step read, and one for each 200 bytes of its files or characters its caller's inputs add; an action is read once for each set of values of the inputs its expressions read and of the environment it is given).
- **Not changed:**
  - an action from another repository is not read;
  - a called local reusable workflow is read as before (slice 2d.4b);
  - the rules other than the agent lane's do not read a local action's own `uses`, uploads, caches or checkouts;
  - a job's `env`, `GITHUB_ENV` and the matrix are not put into an action's steps, as they are not into a job's own;
  - a script with no `.sh` suffix, or one called by another script, is not followed, as it is not from a job's own step.

### The settings audit: calls, job ids and selected actions

Slice 2b.7 (issue #182, found by the fourth review of slice 2d.2g, and three reviews of the slice); decision D-076. Only `obaaf audit` changes.

- **Calls.** A job-level `uses: $/.github/workflows/x.yml` is read as a call in this repository, as `./` is (the checker has read `$/` so since decision D-065; the audit took it for another repository's workflow). The called jobs get the caller's events and the caller the called workflow's check names, so `OBAAF-SET-002` and `OBAAF-SET-011` now answer what they said "cannot tell" about. A file with such a call is one GitHub may not run: GitHub's changelog of 2026-07-30 introduced `$/` for actions, and whether a job's `uses:` takes it was not established. A `$/` caller never counts as the caller that covers a called workflow's token for `OBAAF-SET-012`. `uses: ./` alone, which names no file, is now a call to a file that was not read; it was skipped.
- **Job ids.** A file with a job id written as text outside GitHub's form (a letter or `_`, then letters, digits, `_` or `-`, judged on its ASCII characters) is one GitHub refuses: no rule counts its jobs, and the rules say "cannot tell" for it. It was read as a file that runs, whose checks counted as reported, and such an id could make a problem the checker reports about the file read as one the audit lets through, because the problem quotes the id. A job id with a character outside ASCII, or of 100 characters or more, and a job whose `uses` is empty (read as a job that reports its own name), make the file one GitHub may not run.
- **Selected actions.** Under `allowed_actions: selected`, a file that uses an action or a reusable workflow of another repository is one GitHub may not run unless the list, as written, allows each reference: a step's action whose owner is `actions` or `github` where GitHub's own actions are allowed, or an entry that is the reference itself. Only a reference written plainly (`owner/repo[/path]@ref` in letters, digits, `.`, `_` and `-`, no part that is `.` or `..`, no `..` in the ref) is matched, even by an equal entry; wildcards, the owner's own actions and verified creators are not matched, and an entry with a `!` anywhere stops all matching. Another repository's reusable workflow is never taken as allowed, an equal entry included, because its jobs are not read; what another repository's action uses in turn (a composite action's steps) is not read either. An empty list let everything through. Under `selected` and `local_only`, a file with a local action, a `docker://` image (in any letter case) or an empty `uses` is also one GitHub may not run (a local composite action's steps, and whether the setting covers an image, are not read), and so is any file under a value of the setting the audit does not know.
- **Call cycles and depth.** A file in a cycle of calls (one that calls itself included), or that starts a chain of more than three nested calls, is one GitHub may not run; both counted as running.
- **`OBAAF-SET-007` weighs a file GitHub may not run.** A paths filter, activity types or triggers that keep a required check from reporting do so whether or not the file runs; such a file was skipped, so the finding went silent. Such a file never stands for the check either. Where the route that decides gives a finding, any other job that may report the check on a route that gives none (no filter, a branch pattern, `pull_request_target`, a dispatch; one under names that could not be written out, or in a file GitHub may read otherwise, read at its widest), or a filtered route in a second file (paths and paths-ignore may cover every pull request between them), makes the answer "cannot tell"; so does any other job that may report the check where every job known to report it is in a file GitHub may not run and reports it on every pull request (counted widely there: another job of the same file, or one that never runs on a pull request's commit, also counts, which can give "cannot tell" where there is nothing to find; issue #209); a job that never runs on a pull request's commit changes nothing. Before the slice a dispatch route or a second filter beside a paths filter, both in files sure to run, gave a finding too.
- **Time.** Spreading "may not run" to the callers of a workflow costs the length of a chain of calls, not its square (4,000 calls: 3.4 s before, 0.03 s now), and a cycle of 20,000 files is named in under two seconds.
- **A gate can pass where it failed.** "Cannot tell" fails only with `--fail-on-cannot-tell`, and it replaces findings here: every rule that reads workflow files (`OBAAF-SET-001`, 002, 008, 010, 012, 014 and 015 among them) for a file with a job id GitHub refuses; `OBAAF-SET-008` (an unrequired check exists only if its file runs) for a job in a file that is now one GitHub may not run; `OBAAF-SET-007` where another job may report the check on a route that gives no finding, or a second filtered route may cover what the first leaves out; and `OBAAF-SET-012` no longer reports an undeclared `$/` caller of a workflow whose jobs all declare their permissions. `OBAAF-SET-002` and `OBAAF-SET-011` can now answer "no finding" about a `$/` call where they said "cannot tell".
- **Not changed:** `obaaf check`. On this repository's committed snapshot and on the first adopter's recorded settings the JSON report is byte-identical before and after, but neither snapshot holds the Actions permissions (they need an administrator's token), so that comparison does not exercise the selected-actions change.

### A result file to send back

Slice 3.8 (issue #89); decision D-074.

- **`python -m obaaf.result PATH --output FILE`** runs `obaaf check` on PATH, with the `--config`, `--baseline`, `--fail-on` and `--platform` your CI uses, and writes a JSON file (`obaaf-result/v0.1`) of counts: findings by rule, severity and state; how each control was judged; accepted risk, with the number of owners and the days to the nearest expiry; files checked and not read; jobs and Jenkins stages in each lane, with the configuration and without it; the check's exit status and how long it took. With `--audit FILE` (a report written by `obaaf audit --format json`) it also counts each settings rule's results and each setting's status and reason code.
- **It holds nothing from the repository.** Every key and every string in the file is checked against OBAAF's own vocabulary before it is written (rule ids, severities, states, verdicts, lanes, setting names, reason codes, the version and the date, in ASCII digits), and every number must be below a million; anything else and nothing is written, with exit status 2. A value it does not know is counted as `other`. `--output` must be outside the repository being checked and may not name the file given with `--audit`, `--config` or `--baseline`; a regular file already there is replaced, and removed when the check itself fails, so an earlier run's file is not sent by mistake. `tests/test_result_file.py` puts a marker word in the places a repository's author writes text (names, scripts, `env`, secrets, environments, actions, runner labels, the configuration, a baseline, CODEOWNERS, an instruction file, a Jenkinsfile, a file that does not parse) and in every string of a settings report, and finds it nowhere in the file.
- **[docs/send-us-the-result.md](docs/send-us-the-result.md)** is the page for people asked to try OBAAF: install a pinned development commit (release 0.3.0 has no result file) with its dependencies hash-checked, on Python 3.10 to 3.14 (the locked PyYAML 6.0.3 has no file pip takes for 3.15, the `python3` of GitHub's macOS runner), check and optionally audit a repository, read the file, and reply with it and five questions, or use one of two new issue forms (`.github/ISSUE_TEMPLATE/`), one of them for a finding that changed what was shipped. CI runs the page's blocks as written on GitHub-hosted Ubuntu and macOS runners (an advisory job).
- **Not changed:** `obaaf check` and `obaaf audit`, their reports and exit statuses. The command is not yet `obaaf result`: `cli.py` is changed only by a core slice.

### Why each finding matters

Slice 3.2b (issue #83); decision D-073.

- **Each finding in the text report says why it matters**, in a `Why:` line under its message: one sentence of at most 160 characters from the rule's new `why` in `src/obaaf/data/rules.yaml`, written from the rule's description. All 43 rules of `obaaf check` have one; `obaaf catalog` (and the catalogue tests) fail on a rule without one, with one longer than that, with one that does not end with a full stop, or with one in which a sentence ends before the last (a `.`, `!` or `?` followed by a space and anything but a lower-case ASCII letter, a `!` or `?` straight before a letter, or a full stop straight before a capital and a lower-case letter). `--no-fixes` leaves the line out together with the `Fix:` line, so a report written with `--no-fixes`, as the first adopter's gate writes it, is unchanged.
- **JSON** has the sentence as `why` on every finding, beside `fix`. **SARIF** begins each rule's help with it (`Why it matters: ...`, and `**Why it matters:**` in the Markdown). **`spec/checker-rules.md`** has it under each rule.
- **`--write-baseline` ends as a check with the new baseline would.** It writes the baseline, then ends with 1 when it left out a finding at or above `--fail-on` (medium unless given): one that an `ignore` entry names without counting (expired, no owner, a reason too short, dated too far ahead), or one that no entry can accept (`OBAAF-REPO-001` and `002` where the files that decide what the check accepts have no owner, and since this slice the baseline being written is one of those files, as it is for the gate that reads it). Each is a `not written:` line on standard error, with its severity, rule, place and why it was left out; for a finding no entry can accept, the line also gives the finding's message, which names the files with no owner (the finding itself is on line 1 of CODEOWNERS). Below the threshold they are a `warning:` and the status is 0. Before, it ended with 0 in both cases, warned only for the first, and said nothing of the second, while the gate it set up then failed.
- **Not changed:** the settings audit's fifteen rules (`obaaf audit`) had no `why` (#202) until slice 3.2c ("The settings audit says why each finding matters"); OBAAF-GHA-017's `Why:` line is printed under a job that publishes with `npm publish --provenance`, which the rule does not yet count as signing provenance (#201, a false positive older than this slice); the website shows what release 0.3.0 printed, which has no `Why:` line, and is to be retaken when a release has it.

### The repository and instruction-file rules attacked

Slice 2d.2h (issue #183); decision D-067. - **The files that decide what the check accepts need an owner** (OBAAF-REPO-001, a second finding): the CODEOWNERS file in use and each place GitHub looks in before it, the checker's configuration (each place it is looked for while there is none), a baseline or configuration given with `--baseline` or `--config`, and the place of `.github/egress-firewall.yaml`. No ignore or baseline entry accepts this finding, nor "no CODEOWNERS file", nor a CODEOWNERS file GitHub does not load: before, an unowned configuration could silence OBAAF-REPO-001 with an ignore entry.

- **OBAAF-GHA-011 covers every job an outsider's event can start**, not only jobs that every trigger puts in the untrusted lane (`on: [pull_request, workflow_dispatch]` was silent). It no longer reports `persist-credentials` written as `${{ false }}`, `${{ 'false' }}` or `off`: actions/checkout keeps the token only for `true`.
- **OBAAF-GHA-019 counts any value but a plainly false one**, an expression included (`${{ true }}` was silent).
- **A "cannot tell" finding is identified with everything in the file its value can depend on**: the workflow's and the job's env, the job's strategy, its earlier steps and the jobs it needs, as one digest. An acceptance of it no longer covers the same checkout after any of them changes.
- **New facts, so acceptances written before the change no longer name these findings**: OBAAF-GHA-002 has what was read and the job's and step's `if:`; OBAAF-GHA-011 the credential kept (the job token, or the token or SSH key given to checkout), the triggers, whether the job runs an agent and what the job token can write; OBAAF-GHA-012 the triggers, the `if:` and what was read; OBAAF-GHA-019 the triggers and the value. A v0.1 baseline (0.3.0) still names them, because each finding carries the message 0.3.0 wrote for it, and `obaaf baseline migrate` carries such entries over.
- **An agent CLI run by its path or quoted** (`$HOME/.local/bin/claude -p`, `"claude" -p`) makes an agent job (lane assignment), for the CLIs matched with a prompt flag or subcommand (claude, gemini, codex, opencode, copilot); `aider` and `cline` are matched as before. Such a job gets the agent rules.
- **This repository's own check** accepts the escape tests' kept-token checkout, now covered by OBAAF-GHA-011, with an `ignore` entry in a new `.github/obaaf.yml`.

### What a job can reach: six rules attacked

Slice 2d.2b; decision D-058. Two reviewers that did not write them tried to get past OBAAF-GHA-001, 003, 004, 005, 018 and 024; every attempt is recorded in [docs/bypass-attempts.md](docs/bypass-attempts.md), and every way past is a test.

- **Permissions written in a form GitHub does not document fail the check** (an error for the file, status 1) and are read as the widest grant they could be: a scope name in another case (`Contents:`, `ID-TOKEN:`), a level other than `read`, `write` or `none` (`WRITE`, `" write"`), a string other than exactly `read-all` or `write-all` (`Write-All`, `write`, an expression, `" read-all"`). Before, each was read as no permissions at all (or, for `" read-all"`, as read-all), with no word. `permissions:` with no value is taken as not written, so a job's empty `permissions:` no longer hides a workflow-level `write-all`.
- **An agent job that declares no permissions in a workflow another can call (`workflow_call`)** is reported as holding what the calling job grants: OBAAF-GHA-003 and OBAAF-GHA-004, case `inherited`. OBAAF-GHA-004 said nothing before.
- **OBAAF-GHA-001 is lowered to medium only by an environment named in plain text.** An environment named by an expression (`tmp-${{ github.run_id }}`, `${{ github.event.pull_request.head.ref }}`), which GitHub creates on first use with no protection rules or the event's author can pick, keeps it high.
- **OBAAF-GHA-024 reports `secrets: inherit`** to a reusable workflow as it reports a protected secret passed by name. It compares environment names by the case of A to Z only; a name equal only under Unicode case folding (the Kelvin sign, `ß`, the long s), or a number or true or false that could be the name in another reader's spelling, is unconfirmed (medium); a blank or missing name is no environment; a list or a mapping is not a name. Two `protected_secrets` entries for one secret name in different case are a configuration error (status 2); before, the second silently replaced the first.
- **OBAAF-GHA-018 reports a job that can read every secret** (a computed name, `toJSON(secrets)`, `secrets: inherit`), new case `any-secret`. It joins a command continued on the next line (backslash, PowerShell backtick, cmd caret) before matching, and knows more: `gpg2`, `/usr/bin/gpg`, `gpg.exe`, options before `--import`, `.P12` and `.pfx` in any case, `Import-PfxCertificate`, the actions `crazy-max/ghaction-import-gpg` and `apple-actions/import-codesign-certs`, and secrets named like `CSC_LINK`, `MACOS_CERTIFICATE`, `KEY_STORE`. `gpg --import-ownertrust` is no longer taken for a key import.
- **The job's environment is part of OBAAF-GHA-001, 005 and 018 findings about secrets**, because a secret of the same name in another environment is another secret: an acceptance written for the job in `sandbox` no longer covers it in `production`. A job with no environment is identified as before.
- **An event under `on:` not written in lower-case letters and underscores** (`Pull_Request_Target`, a mapping inside the list) is an error for the file; before, it was dropped without a word.
- **Fixed: a job whose environment is a number of thousands of digits** no longer ends `obaaf check` in a traceback.

### The lifecycle of a finding

The first adopter's gate asked one question of every finding, "is it new?", and the answer was always to accept it: all 38 findings in its baseline were accepted in a file that names nobody, gives no reason and never expires, and the file was regenerated three times in a day to add more. This changes what accepting a finding takes, and what a finding is.

- **A finding is new, accepted, fixed, or one the checker cannot tell about.** JSON output has `state` on every finding and a `summary` of the counts. Text output prints a line under a finding that was accepted by a baseline entry, that is named by an entry that does not count, or that has controls; a finding with no such line is new. "Fixed" means every control that clears the finding was read and verified, and "cannot tell" means one of them could not be read; a finding the checker cannot tell about fails the check like a new one. Two rules report controls, OBAAF-GHA-005 and OBAAF-GHA-020 (see "Controls" below); every other finding is new or accepted.
- **An acceptance needs an owner, a reason and an expiry date, in an `ignore` entry and in a baseline entry alike.** The owner is a user (`@name`), a team (`@org/team`) or an e-mail address; only its form is checked. The reason needs at least four letters or digits. The date must not have passed and must be at most 366 days ahead. An entry that lacks one of the three, has expired, or is dated further ahead accepts nothing: its finding counts as new, and the report says under the finding what the entry lacks.
- **`ignore` entries need `owner:`.** A configuration written for 0.3.0 still loads, and its entries ignore nothing until an owner is added to each. `until: 2999-01-01` no longer works either. An `until` that is not a plain date (`2027-01-31T10:00:00Z`, `20270131`) is now a configuration error on every Python version; a time of day there used to end in a traceback when the entry matched a finding.
- **New baseline format, `obaaf-baseline/v0.2`.** An entry holds what the finding is (rule, file, job, step, which of the rule's cases, and the values it is about, such as the secrets a job receives), the severity it was accepted at, and the owner, reason and expiry date. It has no fingerprint and no message: the fields a reviewer reads are the acceptance. Entries no longer depend on how a rule's message is worded, so a release that rewords one does not break a baseline. Three kinds of finding still carry text: for OBAAF-GHA-003 the reason the job is an agent job is part of the finding, as the text the checker shows, so an acceptance stops covering the job when that text changes (another recognised action, a command in another step, a declaration added), and it does not tell agents apart beyond that; for OBAAF-INS-001 each hidden character is identified with a digest of the line it is on (a line ends at a line feed or a carriage return), so the same character with other text on its line is another finding; and Jenkins findings are still identified by their whole message. An entry does not cover a finding that has become more severe than the entry says.
- **`obaaf-baseline/v0.1` files (written by 0.2.0 and 0.3.0) are still read, and accept nothing.** Each entry still finds its finding, so the report can say what the file used to cover, but with `--fail-on low` the check fails until the file is converted. `obaaf baseline migrate FILE --owner … --reason … --expires …` converts it: it carries over the findings the old file covers that are still found, and accepts nothing else.
- **`--write-baseline` takes `--owner`, `--reason` and `--expires`, and never renews an acceptance by itself.** Entries of the file it replaces that are still valid keep their own owner, reason and date. Only findings that no valid entry accepts get the ones given on the command line, and without them nothing is written (exit 2). It refuses to write over a v0.1 file, and over any existing file that is not a baseline (0.3.0 wrote over whatever was there, `/dev/null` included).
- **JSON output** keeps every field it had. New: `state`, `kind`, `facts`, `acceptance` and `controls` on a finding, `summary`, `baseline.format`, and `fixed` (findings cleared by verified controls, which are no longer in `findings`). SARIF results carry `obaaf-state`.

What an adopter will see on upgrading:

- With a v0.1 baseline: every finding the baseline covered is reported as new, with the line "Not accepted: the baseline entry that names this finding does not count", and the report ends with the `obaaf baseline migrate` command to run. After converting, the same findings are accepted again, each with an owner, a reason and a date.
- With `ignore` entries: each finding an entry used to ignore is reported, with "because it names no owner", until `owner:` is added. An entry whose reason has fewer than four letters or digits (`reason: ok`), or whose `until` is more than 366 days ahead, stays without effect after that, and the report says which.
- With neither: no change in findings or exit codes. Messages are word for word what they were (compared on this repository, its fixtures and templates, and Expectrail at `16edb91`).

### Controls

The first adopter had the same two findings on each of its 19 agent jobs, a secret in the job (OBAAF-GHA-005) and no egress restriction (OBAAF-GHA-020), and the only thing it could do with any of the 38 was accept it. Both findings now name the controls that would clear them and say what the checker established about each. **Neither can be cleared yet**, and the report says which control stands in the way.

- **OBAAF-GHA-005, for a job that references secrets, lists four controls**, and is fixed only when all four are verified: `secrets-protected` (each secret is listed in `protected_secrets` and the job declares the environment named there), `environment-restricted` (the secrets are stored only in that environment and only protected branches may use it), `no-outsider-input` (no pull request, issue or comment can start the job, no checkout step names a pull request's ref, and no expression or `if:` reads a field an outsider writes) and `egress-enforced` (a control the checker recognises limits the job's network access to an allow-list). Each is reported as verified, not met or cannot tell. The guide has [what is read for each and what is not](docs/checker-configuration.md#controls).
- **`environment-restricted` is never verified.** It is a repository setting. `obaaf audit` reads environments and their branch rules, and `obaaf check` does not use what it reads yet, so it is "cannot tell"; for a job that declares no environment it is "not met".
- **`egress-enforced` is never verified.** A job with no blocking egress control, with one behind an `if:`, with one that is not the job's first step on its own (it starts after other steps, in a `parallel` group or in the background), or with only an `OBAAF_EGRESS` declaration is "not met". A `step-security/harden-runner` step with `egress-policy: block` and no `if:`, as the job's first step, is "cannot tell": whether it limits the agent depends on its version and on the job being unable to undo it with sudo or a container, and the checker reads neither yet.
- **OBAAF-GHA-020 is now reported for every agent job**, with that one control. This is the one place where a workflow that passed is now reported: a job with a blocking Harden-Runner step and no `if:` had no OBAAF-GHA-020 finding, whatever the step's version and wherever it stood in the job, even after the agent. It now has one: "cannot tell" when the monitor is the job's first step, "not met" when it is not. Either fails a gate at `--fail-on low` until it is accepted with an owner, a reason and an expiry date. A baseline entry that accepts the "cannot tell" case is for the workflow file as it stood, byte for byte (the finding carries the first 32 characters of the file's SHA-256), so it stops covering the job when the monitor is repinned, moved or changed in any way, and also on any other change to that file. An ignore entry holds until its date, as before. The three cases reported before keep their messages and their identity, so a baseline entry for one still matches.
- **A proxy that holds the model key is not counted as a control.** Two exist (the Agent Workflow Firewall's, and `openai/codex-action`'s); neither has been run here, so neither is credited.
- **A workflow compiled by GitHub Agentic Workflows (`.lock.yml`) is read like any other workflow file** and gets no credit for how it was made.
- Text output lists the controls under a finding, one to a line, verdict first. JSON output has `id` on each control. For a finding that lists controls the line "Architecture: fixing this means adopting the agent and effect lanes" is no longer printed: the controls are the other way to clear it.

On the first adopter's workflows at `b4e07bc`, with its own configuration: all 19 agent jobs have `secrets-protected` verified; 11 have `no-outsider-input` verified and 8 "cannot tell" (seven check out a second repository, one checks out a ref computed when the job runs); all 19 have `environment-restricted` "cannot tell" and `egress-enforced` "not met". So all 38 findings are still new, and what each job lacks is an egress control.

**A fifth control for OBAAF-GHA-005: the agent's command cannot read the job's secrets** (slice 2c.7, decision D-055). A limit on the network does not stop an agent that holds a key from printing it to the job's log or leaving it in an artifact, so the four controls could all hold with the key in the agent's hands.

- **`key-out-of-reach`** is verified only where every secret of the job (`GITHUB_TOKEN` aside, as for the finding's list of secrets) is set in the `env` of steps that use OBAAF's egress action, at the [listed action pin](#reviewed-egress-action-pin), on GitHub-hosted `ubuntu-24.04`, and goes to AWF's API proxy (named in `model-keys`) or to nothing the command runs. A secret passed to the command, given to another step, to the job outside its steps or to the workflow's `env`, or a job with no step that uses the action is "not met"; GitHub's native firewall holds no key, so a job on it is "not met" here although its egress control is verified. The step that uses the action holds the key in its own process, outside the sandbox, and the action's own bash steps run there with it, so an agent or a credential in a step that can run before or beside it (earlier, in its `parallel` group, or beside a `background` step) is "not met", as is a job that can request OIDC tokens or gives its token the `models` permission; and a variable bash or the loader obeys (`BASH_ENV`, `PATH`, `LD_PRELOAD` and others), or `ACTIONS_ALLOW_UNSECURE_COMMANDS`, in an `env` (issue #139), a step before or beside it whose script names `GITHUB_ENV` or `GITHUB_PATH` or may leave a process running (read from the words in the script; a detached process or a write spelt otherwise is not seen), service containers given volumes or options, a secret the checker cannot place, another runner, a container, the Agent Workflow Firewall run from a script, and a job that calls a reusable workflow are "cannot tell".
- **Where each credential given to the action goes** is now said in this control's detail, whatever its verdict; it was in the fourth control's (`egress-enforced`) since slice 2c.5.
- **No finding, message, exit status or acceptance changes.** Controls are not part of what a finding is, so every baseline entry and ignore entry that matched OBAAF-GHA-005 still matches, and a job that moves its key from the command to the proxy keeps its acceptance. The finding could not be cleared then: `environment-restricted` was never verified by `obaaf check` (since D-111 it can be, from a `--settings` snapshot). A finding that was "cannot tell" because every control was verified or could not be read becomes "new" where the agent holds the key (a job with a Harden-Runner step and a key in the agent's `env`, for one); either fails a gate unless accepted. JSON output has a fifth entry under `controls`; the text report says "it is cleared when all 5 are verified". On this repository, its 16 risky fixtures, its templates and Expectrail's files at `13e8f70`, with and without its baseline: the same findings, states and exit statuses before and after, with `key-out-of-reach` "not met" on every OBAAF-GHA-005 that lists controls.

### Reports begin with the accepted risk

With 38 findings accepted and none new, the first adopter's gate printed its per-file listing and, near the end, "38 finding(s) accepted by the baseline, 0 new". A reader of the log saw a green check and "0 new". The three reports now say first how much risk is accepted, at what severity, by whom and until when. Which findings are reported, their states and the exit status do not change, with two exceptions: a command that ended in a traceback on ASCII output, and a check that crosses midnight (the last two points of this list). The guide has [an example and what each line means](docs/checker-configuration.md#accepted-risk).

- **Text output has new first lines.** `Accepted risk: N finding(s) are accepted and do not fail the check (...)`, then one line for each owner with how many findings they accepted and the first date one of their acceptances runs out, how many were accepted by baseline entries and how many by ignore entries, and the nearest expiry date; or `Accepted risk: none.` Then `Other findings:` with the counts of new, cannot tell and fixed, and a count of errors when there are any. A baseline entry that no longer matches a finding is counted there too, since it can fail a check whose findings are all accepted. Every line the report had before is still there, below these, in the same words, with the four exceptions that follow (the fourth is the Jenkins coverage lines, further down).
- **A file's path is printed in quotes where it heads its findings, unless, with characters that do not print written as escapes, it is made only of visible ASCII characters** (letters, digits and punctuation, no space). That line starts in the first column, like the lines the checker writes in its own words, and a directory could be named `Accepted risk: none. ...` or `Baseline: 38 finding(s) accepted by the baseline, 0 new.`, with spaces or with characters that only look blank, and read as one. A path such as `.github/workflows/ci.yml` is printed as before; `.github/workflows/my build.yml` and `.github/workflows/übersicht.yml` are now in quotes.
- **A finding ignored by configuration is listed with its owner**: `ignored: RULE path:line - accepted by OWNER until DATE: REASON`, where it was `ignored: RULE path:line - REASON (until DATE)`.
- **The `obaaf baseline migrate` command the report prints for an old baseline repeats the `--config` and `--platform` the check was given**, where it said to give them "if any".
- **A warning before an acceptance expires.** Acceptances that run out within 30 days are listed as `Expiring soon:`, the soonest first, in text, in JSON (`acceptedRisk.expiringSoon`) and as a warning in SARIF. Until now nothing warned: the gate went red on the day after the date. `--expiry-warning DAYS` changes the window and `--expiry-warning 0` turns the list off. It never changes the exit status.
- **JSON output** keeps every field it had, under the same name. New: `acceptedRisk` (the numbers above, and `asOf`, the day they were counted from), placed with `summary` before the findings, and `daysLeft` in the `acceptance` of a finding when it is valid.
- **SARIF output.** The run has `properties` with `obaaf-accepted-risk` and `obaaf-summary`, and an `invocations` entry whose notifications begin with the accepted risk and carry the expiry warning, the errors, a baseline in the old format, baseline entries that no longer match, and the notes; `executionSuccessful` is `false` when something could not be read. Until now SARIF carried none of these. A result for an accepted finding has a suppression with `"status": "accepted"` and a justification that names the owner and the date (a finding ignored by configuration had a suppression with the reason and the date and no owner; one accepted by a baseline had none), and `obaaf-acceptance` in its properties. Every other result has `"suppressions": []`, which is how SARIF says "not suppressed". A result that has controls carries them in `obaaf-controls`.
- **The message of a SARIF result is longer** for a finding that is accepted, that is named by an entry that does not count, or that has controls: after the finding's own sentence it says who accepted it and until when, or why the entry does not count, and then each control with its verdict. The `message` in JSON and the text report are unchanged. GitHub's documentation lists the fields code scanning uses, and suppressions, notifications and the property bags of a run and of a result are not among them, so the message is where a reader of code scanning can see that a finding was accepted. That is from GitHub's page, read on 2026-11-12; no upload to code scanning was made to check it.

- **Jenkins coverage lines print a path, an error and a reason on one line.** A directory whose name contains a line break could put lines of its own into the text report, 0.3.0 included; such a character is now shown as an escape, as it already was everywhere else in the report.
- **A letter the output cannot show is printed as an escape.** `obaaf check` ended in a traceback when standard output was ASCII and a job, a path or an owner had a letter outside it (seen with `--lanes` and with the text report). Standard output and standard error now write such a letter as an escape, `\xf8` for `ø`, in every command; only `check` and `baseline migrate` were tried. A command that ended that way exited 1, and now exits as its findings decide.
- **Every acceptance in a report is judged on one day.** Ignore entries were judged while the check ran and baseline entries when the baseline was applied, a moment later, so a check that crossed midnight could accept one entry dated that day and refuse another. The day is now read once, while the check runs, and `obaaf check --baseline` judges the baseline on it. So when midnight falls between the two, a baseline entry gets another answer than before, in either direction: one whose last day is the day the check read is accepted, and one dated 367 days after that day is refused, where each was the other way round. `--write-baseline` and `obaaf baseline migrate` still read the clock again when they decide what to write, as before. `obaaf.checker.baseline.apply` refuses a `today` that differs from the day of a result `check` made.

What this does not do: it does not tell the reader whether the check passed (the exit status does; the report has never printed it), and the accepted-risk total is not shown by GitHub code scanning, going by the same page.

### A lane declaration that does nothing is a finding

A job is an agent job to the checker when the checker recognises its agent or when the repository declares it one, with `OBAAF_LANE` or under `lanes:`. A declaration that does nothing (`OBAAF_LANE: agnet`, a `lanes:` entry for a job that was renamed) leaves the job without the agent rules, and 0.3.0 said so only in a note at the end of the report, which changes no exit code: the gate stayed green on a job nobody was checking. It is now a finding with a rule of its own.

- **New rule, `OBAAF-CFG-001`, "Lane declaration that does nothing"**, the first of a family for the checker's own configuration. It reports the declarations 0.3.0 listed in a note as ignored: `OBAAF_LANE` set to a value that is not a lane in a job's `env`, the workflow's `env` or a Jenkinsfile (a misspelling, an expression, an empty value, or in a Jenkinsfile a value computed when the build runs; in a Jenkinsfile, where it reaches at least one step); `OBAAF_LANE` in a step's `env`, a container's or a service's, where it is not read; and a `lanes:` entry whose value is not a lane, or that names a job or Jenkins stage its file does not have, or a file that is not there. One kind of note is not a finding: an entry for a Jenkins stage that is in the file and holds no step (see "Fixed with it").
- **Two declarations that 0.3.0 said nothing about are reported too**: the variable under another spelling in a job's `env` or the workflow's `env` (`obaaf_lane`, `OBAAF-LANE`, a name with a space after it), which is read under its exact name only; and `OBAAF_LANE` in the `env` of a `parallel` group of steps. A `lanes:` key that is not text (`5:`, `true:`), which is never looked up, was listed in a note when a repository was checked; it is a finding now, also when one file is checked on its own.
- **It is reported where the declaration is written**, on its line: in the workflow or Jenkinsfile, or in the configuration file on the line of the `lanes:` entry. A declaration that reaches a job or a step through a YAML alias or a merge key is reported on the first line of that job or step. A report can therefore list `.github/obaaf.yml` among the files with findings; it is not counted among the workflow files checked.
- **Severity: high, and low where nothing can be missing.** The checker cannot know which findings are missing because of the declaration, and the agent lane has high-severity rules, so a lower severity would let a gate set to `--fail-on high` pass a job whose agent rules never ran. It is low when the declaration names `trusted` (which adds no rule even where it is read); when it is written where it is not read, or under another spelling, in a job that is in the lane it names anyway; and when it is a `lanes:` entry for a Jenkins stage that is not there and names `untrusted` or `effect`, which change nothing on a stage. The category is authority.
- **It is fixed by correcting or deleting the declaration, and it can be accepted with a baseline entry**, which carries an owner, a reason and an expiry date and names the declaration: the file it is written in, the job and step, the names of the stages a Jenkinsfile's declaration reaches, the `lanes:` key, the variable's name where that is misspelt, and the value. The line number and the wording are not part of it. Two declarations that agree in all of these are told apart only by count: each needs an entry. Two Jenkins stages with the same label (the name, with the stages it is nested in) are one stage to the checker, here as elsewhere.
- **An `ignore` entry cannot accept it, and one that names `OBAAF-CFG-001` is a configuration error** (exit 2). An `ignore` entry accepts a rule in a file, whatever the finding says. For this rule that would be every lane declaration in the file, including ones not written yet: a reviewer of this change accepted one `lanes:` entry that way, then renamed an agent job and misspelt its lane, and the check still passed.
- **The notes no longer list these declarations**, in the text report, in `notes` of the JSON report and among the notifications of the SARIF report. They are in `findings` and in SARIF `results`, so GitHub code scanning can show them. `obaaf check . --lanes` still prints them as notes on standard error, now with the file, the line and the rule: `--lanes` lists lanes and reports no findings.
- **The example configuration no longer declares anything.** `templates/github-actions/obaaf.yml.example`, which `obaaf templates install` writes as `.github/obaaf.yml`, had a `lanes:` entry for `.github/workflows/nightly.yml#package`, a file the templates do not install, and an `ignore` entry for another. Both examples are comments now. A repository that installed the templates with 0.3.0 and kept the file as it was has that `lanes:` entry, and gets one high finding for it.
- **Fixed with it:** a `lanes:` entry for a workflow or a Jenkinsfile whose own path contains `#` was cut at the first `#`, so the note said the entry named a file that was not read although the lane had been applied; the key is now matched against the files of the run, and against the files outside it. A `lanes:` entry for a Jenkins stage that holds no step the checker records (`steps { }`, or only a `script` that sets a variable) was listed as naming a stage the file does not have; a stage with a block is now a stage an entry may name, and a stage written without one (`stage 'Build'`), which holds no step, still is not. And `OBAAF_LANE: 0xFF…`, a number of more than 4,300 digits, as a value or as a `lanes:` key, ended `obaaf check` in a traceback; it is reported like any other value that is not a lane.

Not reported, as before: in a Jenkinsfile, the variable under another spelling, and an assignment (`env.OBAAF_LANE = 'agent'`), which is not read as a declaration; and a second configuration file (the checker reads the first of `.github/obaaf.yml`, `.github/obaaf.yaml` and `obaaf.yml` that exists).

What an adopter will see on upgrading:

- A repository with such a declaration and a gate at the default `--fail-on medium`, or stricter: the check fails (exit 1) where it passed, with the finding and its fix. Correcting the declaration can bring the findings it was hiding; that is the point.
- A gate at `--fail-on never`: no change in the exit code; the finding is in the report.
- A script that reads `notes`, or the "Lane declaration ignored" lines of the text report: those lines are gone from `obaaf check`. The text after "Lane declaration ignored:" on `--lanes` is worded differently.
- **Expectrail** has one: `.github/obaaf.yml` gives `.github/workflows/byo-smoke.yml#byo-smoke` the lane `probe`. It is deliberate there: the project's own audit script reads `probe` from the file as a lane of its own, and OBAAF has always ignored it. On a copy of its files at `776ddd3`, with its pinned command, the report gains exactly one finding (`OBAAF-CFG-001`, high, `.github/obaaf.yml` line 36) and loses the note; the exit code was already 1 because of its old-format baseline. When it moves its pin it can accept the finding in its baseline with an owner, a reason and a date, or declare the job `trusted` and keep its own list of probes elsewhere.

### Which events can start a job

Many rules ask which events can start a job, and a job's `if:` can rule an event out. That was decided by searching the text of the `if:` for `github.event_name == '...'`, so text that only looked like such a test removed an event, and every rule that depends on the event (OBAAF-GHA-001, 002, 007, 011, 013 and 015, one case of 012, the severity of 008 and 010, and whether a job builds pull requests) was silent or too mild for a job that does run on it. The condition is now read from its tokens. With `on: [pull_request_target, workflow_dispatch]`, each of these was read as "runs on `workflow_dispatch` only" and is now read as running on both:

- **The test inside a string**: `if: ${{ 'github.event_name == "workflow_dispatch"' != '' }}`, which is always true, and the same text as an argument of `format`.
- **A comparison of the comparison**: `if: github.event_name == 'workflow_dispatch' == false`, which is true on every event except the one named.
- **Text outside `${{ }}`**: `if: ${{ github.event_name == 'workflow_dispatch' }} && ${{ true }}`, a `${{ }}` followed by a space, and a `|` block, whose line break is outside it. GitHub reads each as a text, and a text that is not empty is true.
- **A job that needs a gate and can outrun it**: a job that `needs` a job limited to one event was limited to that event too, unless its `if:` said `always()`, `failure()`, `cancelled()`, `!success()` or `success() || ...`. `success() == false`, `!(success())` and `success()` passed to a function also let it run when the gate was skipped, and were not seen. The same reading decides whether a check in an earlier step or a needed job really stops a release or an applied proposal (OBAAF-GHA-016, 021, 022).
- **A called workflow**: with `on: workflow_call`, `if: github.event_name == 'pull_request_target'` was read as "never runs". In a called workflow `github.event_name` is the caller's event, so no test rules `workflow_call` out.

What rules an event out now: a comparison of `github.event_name` with a text, `==` or `!=`, either way round, alone or joined to other conditions by `&&` and `||`. So the reader is also more exact than it was: a condition with a negation elsewhere in it (`github.event_name == 'push' && !contains(...)`), the text first (`'push' == github.event_name`) and `github['event_name']` now narrow, where before they did not, which can remove a finding from a job that never runs on the event. A comparison with a letter outside ASCII is not read, because what GitHub's comparison makes of it has not been established. A status function still counts wherever the text has it, inside a string and outside `${{ }}` included, as before. Nothing here has been run on GitHub: it rests on GitHub's documentation of expressions and of `if:`.

### Inputs in any case

GitHub hands an action its inputs as environment variables named in upper case, so `REF:` and `ref:` under `with:` are the same input. The checker read input names exactly as written, so a rule that looks at an input did not see one spelt in another case: with `on: pull_request_target`, a checkout with `REF: ${{ github.event.pull_request.head.sha }}` was not reported by OBAAF-GHA-002, `Allow-Unsafe-PR-Checkout: true` not by OBAAF-GHA-019, and an agent job's checkout of the pull request not by OBAAF-GHA-012. The same held for the cache inputs OBAAF-GHA-006 reads and for a monitor's `egress-policy`; and `Persist-Credentials: false` was not seen, so OBAAF-GHA-011 was reported where it should not have been. Input names are now read with A to Z in either case. A step that gives the same input twice in two spellings is an error: the checker cannot tell which value GitHub uses. So is an input name with a letter outside ASCII, since what GitHub's upper-casing makes of one is not established. Found by the review of the controls above; not run on GitHub.

### Settings audit

- New command `obaaf audit`: reads the GitHub settings that workflows depend on and records them in a snapshot file (`obaaf-settings-snapshot/v0.1`). It reads rulesets and who may bypass them, the rules in force on the default branch, classic branch protection, environments and which branches may deploy to them, the names of environment, repository and organisation secrets, Actions permissions, the workflow token's default permissions, approval for fork pull requests, Actions policies, and how many accounts hold each role. The rules that judge what it read are below.
- Every setting is recorded as read, partly read, not read or not applicable. A setting that was not read is listed by name with the reason and with what GitHub's reference says a caller needs; it is never left out. An answer that does not have the documented shape is recorded as not read: a field whose absence could pass for "none" must be there. In a value, `null` means not known, a part that does not apply is left out, and a known "none" is written out. Every snapshot is checked against its schema before it is written or reported, and a value the schema refuses makes that setting not read.
- Read-only by construction: the client sends GET requests and has no other verb. A token is taken from the environment (`GH_TOKEN`, `GITHUB_TOKEN` or `--token-env NAME`), never from the command line, and is sent only to the API address the audit was started with. It is in no output, and is cut out of any answer that echoes it. With no token the audit reads what GitHub shows anyone about a public repository and asks for nothing else.
- An empty list of who may bypass a ruleset is never recorded as "nobody": GitHub shows the real list only to a caller with write access to the ruleset, and it is not established what it sends anyone else. The audit can show that someone may bypass; it cannot yet show that nobody may.
- `obaaf audit --from-snapshot FILE` reports from a saved snapshot with no network, after checking the file against a schema that covers every value. `--fail-on-unread` exits 1 when a setting that applies was not read in full. Reading nothing at all (repository not found, rate limited at the first request) exits 1, and so does any failure the command did not foresee.
- Tested from recordings written by hand from the examples in GitHub's REST reference, and from two recordings of what GitHub itself answered a caller with no token, for this repository and for the first adopter's. Run against GitHub by a workflow in this repository, with the workflow's own token and with no token: the settings GitHub shows anyone were read, and the administrative ones were refused and reported as not read. It has not been run with a token that can read the administrative settings. See [docs/settings-audit.md](docs/settings-audit.md).

### Settings rules

The settings audit read settings and judged nothing. It now applies rules to them. `obaaf audit` is still in no release.

- **Fifteen rules, `OBAAF-SET-001` to `OBAAF-SET-015`.** Twelve compare a setting with something a workflow in the repository uses or assumes: the environment a job names, the checks its jobs report, the events that start it, the secrets it reads. Three read settings only, because what they are about is what every workflow's result feeds: who may bypass a branch's rules (`004`), whether its required approvals can be given (`005`), and whether a workflow can give one (`013`; a workflow on any branch can ask for the token, so the files here decide nothing).
- **The settings behind the first adopter's six incidents each have a rule**: an environment any branch may use (`OBAAF-SET-001`), a ruleset bypass that covers whoever authors changes (`OBAAF-SET-004`), required approvals that cannot be given (`OBAAF-SET-005`), a required-checks list that leaves out jobs that run on every pull request (`OBAAF-SET-008`), an Actions policy that blocks an event a workflow uses (`OBAAF-SET-009`), and a reusable workflow passed a secret its caller cannot read (`OBAAF-SET-011`). Also: a job outsiders can start that names an environment with no reviewers (`002`), a protected secret that is also a repository or organisation secret (`003`), a required check nothing reports (`006`) or that does not report on every pull request (`007`), the `pull_request_target` change of 2026-12-02 (`010`), the default token permissions (`012`), a workflow that can give a required approval (`013`), fork pull requests (`014`) and the pinning requirement (`015`).
- **A rule answers "cannot tell" when a setting or a workflow file it needs was not read**, or is in a form it does not understand, and says what was missing. The report begins with the findings and the count of what could not be told, has one line for every rule (findings, cannot tell, no finding with what was compared, or does not apply with the reason), and never says "pass". Every rule reads at least one setting GitHub shows only to a token; with no token, five of them (`001`, `002`, `006` to `008`) can still give findings from what anyone may read.
- **The workflow files come from a clone.** They are read from the directory the command is given when it is the top level of a clone whose origin remote names the repository audited, or when the directory is named on the command line. The settings of one repository are not compared with the workflows of whichever clone the command was started in; then the twelve rules that need the files answer "cannot tell".
- **`obaaf audit` now fails on findings.** New options: `--fail-on high|medium|low|never` (default `medium`), `--fail-on-cannot-tell`, `--no-fixes`. A commit of the earlier audit exited 0 whenever the repository was read, unless `--fail-on-unread` or `--expected` failed it; pass `--fail-on never` for that. **`--format json` is now a report** (`obaaf-settings-audit/v0.1`: `summary`, `rules`, `results`, `workflows`, and the snapshot under `snapshot`), where it was the snapshot itself; `--snapshot-out` still writes the snapshot.
- **A settings finding cannot be accepted.** There is no baseline and no `ignore` for `obaaf audit`. Each finding names a change to a setting or a workflow that clears it, and a job that is meant to be advisory says so with `continue-on-error: true`. A finding someone decides to keep stays in the report and can only be kept out of the exit status with a higher `--fail-on`.
- **What it rests on.** Tested from recordings: GitHub's own answers to a caller with no token for this repository and the first adopter's, and answers written by hand for everything a token would show. The rules about Actions policies read the one form the hand-written recording has; no real policy has been seen, and GitHub's pages on them could not be re-read when the rules were written. Several sentences about what GitHub does rest on the author's knowledge and were not re-read; the guide lists them. Not run: the audit with a token that can read the administrative settings. An independent review of the first version found 24 faults in the rules by running them, most of them a "no finding" where a rule had not looked; each is fixed and pinned by a test. Its first finding is on this repository: the job `dependency-lock` runs on every pull request and is not a required check; a maintainer chose to keep it advisory, so it now has `continue-on-error: true` and the audit no longer reports it.
- A character that prints as a blank without being a space (the braille blank, the Hangul fillers) is now written as a question mark in the audit's report, like a control character: a run of them could push the rest of a name to the start of a terminal's next line.
- **Every parameter of a ruleset's pull-request rule is read or named** (flagship slice 2b.5). `OBAAF-SET-005` and `OBAAF-SET-013` used to read the count of approvals and the code-owner flag and pass over the rest in silence: the first adopter's `require_extra_approval_for_unattributed_changes: true` changed nothing in the report. The nine parameters GitHub's REST reference lists (read on 2026-11-13) are now each placed in the code, and a parameter that is not among them, or a known one in another form (a field the reference does not list included), makes `OBAAF-SET-005` "cannot tell" for its branch, and `OBAAF-SET-013` too where workflows may approve pull requests, naming it and its value, whatever the value, unless the count alone is a finding. A "cannot tell" given for another reason, and a finding by count, name it as well. A team that `required_reviewers` asks for an approval, and `require_last_push_approval` where no approval is counted (on a ruleset or a classic protection rule), are "cannot tell" too. `require_extra_approval_for_unattributed_changes` is read as GitHub's pages describe it: nothing on a ruleset that counts zero, which the rule's note now says (the first adopter's case), and one more approval than that ruleset's count for a pull request Copilot opens without a person otherwise. `OBAAF-SET-005` is now "cannot tell", where it said "no finding" or "does not apply", for a branch that requires a code owner's review and whose count alone is no finding: who the code owners are is not read. What GitHub's pages establish about each parameter is in the guide, under "The parameters of a pull-request rule".
- **Every rule type of a ruleset, and every field of classic branch protection, is read or named** (flagship slice 2b.6). The rules about a branch's requirements read two rule types, `pull_request` and `required_status_checks`, and passed over every other, and classic protection was read into a fixed form that dropped any field GitHub adds. The 25 types of GitHub's REST reference (read on 2026-11-13) are now each placed in the code; a type that is not among them makes `OBAAF-SET-005` to `OBAAF-SET-008` "cannot tell" for its branch, naming it, whatever its parameters, and `OBAAF-SET-013` too where workflows may approve pull requests (a finding by count stays a finding and names it); `OBAAF-SET-004` names it among what a bypass skips, or cannot tell where it is a ruleset's only such rule. A field of classic protection that the reference does not show (a field of an entry of its required checks included), or a known one in another form that the reader would otherwise record as not known and pass over (an object that is something else, a flag that is not true or false or has no value; some other forms make the whole setting unread), is kept in the snapshot under `other_fields`, with its value, and has the same effect; so does a parameter of a ruleset's `required_status_checks` rule, or a field of one of its checks, outside the reference, for the check rules. Changes in what the rules report: a bypass of a ruleset that only requires deployments, code quality, coverage or licence compliance is now an `OBAAF-SET-004` finding (it was passed over); `OBAAF-SET-006` is "cannot tell" for each rule that makes a merge wait for deployments, workflows, code scanning, code quality, coverage or licence compliance, and `OBAAF-SET-007` for a merge queue, because what gives those results is not compared with the workflow files; a finding of `OBAAF-SET-008` names those six (not the queue); `OBAAF-SET-005` is "cannot tell" where it said "no finding" on a branch with a rule of type `update` (only those who may bypass may push), classic push restrictions or a locked branch, and its finding says Copilot's review may count where a `copilot_code_review` rule is in force. The settings report prints a rule type it does not know in quotation marks. Messages name what could not be read: "a classic protection rule may ask for more" was said whatever the gap, a ruleset's count included. **Snapshot:** `other_fields` is written only when there is one, so earlier snapshots still load and still match; a version before this one refuses a snapshot that has it. On GitHub's recorded answers for this repository and the first adopter, the report is unchanged. The guide's section is "Rule types and classic fields the rules do not know".

### Settings drift

A setting can change without any file changing, and every real incident in the first adopter's first two days was a setting. There was no way to notice one changing.

- **`obaaf audit --expected FILE` compares the settings with a snapshot you committed** (written earlier by `--snapshot-out`) and reports every difference as a finding, `OBAAF-DRIFT-001`: one for each part that differs (a ruleset, an environment, a branch, a secret's name, a field), with each change listed as "was …, now …", "new" or "gone". The report begins with the comparison and is followed by the usual report. Exit 1 if anything differs.
- **What could not be compared fails too.** A setting, or a part of one, that one side read and the other did not is "not compared", never "no drift", and exits 1, in both directions: the committed snapshot holds it and this run could not read it (other access, a refusal, a rate limit), or this run read it and the committed snapshot did not (GitHub left it out then, or someone marked it as not read in the file). So does a comparison in which nothing was compared. Only what neither side read in full is "not covered", listed, and not a failure (of an environment both read in part, the rest is compared).
- Lists are compared without regard to their order and values as JSON, so `true` is not `1` and `null` is not `false`. Only the `settings` part is compared.
- The committed file is checked like `--from-snapshot`, and must also be of the repository audited and the same API address (checked before any request), may not give two rulesets, environments, policies or secrets one id or name, must hold data for exactly the branches it lists, and may name at most 50 branches; otherwise exit 2. Its branches are audited along with the default one. `--snapshot-out` and `--output` may not name the same file as `--expected`.
- `--format json` with `--expected` puts the comparison, with every change, under `drift` in the audit's JSON report (`obaaf-settings-audit/v0.1`, see "Settings rules" above), beside the rules' results and the live snapshot.
- The rules of "Settings rules" run in the same command. The template and this repository's job pass `--fail-on never`, so they fail on drift and not on a rule's finding; run the rules as a gate in a job of their own.
- New optional template [`templates/github-actions/optional/obaaf-settings-drift.yml`](templates/github-actions/optional/obaaf-settings-drift.yml) runs the comparison daily with the workflow's own token; its first run keeps the snapshot to commit, so no file is written by hand. `obaaf templates install` does not install it. This repository runs it as `.github/workflows/settings-drift.yml`. See [docs/settings-audit.md](docs/settings-audit.md#drift).
- Nothing changes for anyone who does not pass `--expected`, except two things found on the way: a snapshot file with a number too large to be finite (`1e999`) is refused, where it was read as infinity and could crash `--format json`; and an unusable `--from-snapshot` file is named in the error.

### Egress control

The first adopter had OBAAF-GHA-020, "agent job without an egress restriction", on all 19 of its agent jobs, and no control it could apply: OBAAF shipped none, and the checker credited none it could verify.

- **New action [`actions/egress`](actions/egress/action.yml)** runs one command with its network limited to a list of host names, on GitHub-hosted Linux runners. It runs the command under GitHub's Agent Workflow Firewall v0.29.13 (binary pinned by SHA-256, images by digest), with no `sudo`, none of the runner's environment except the variables you name, and writes limited to a scratch copy of the workspace, its own home and its own `TMPDIR`; what AWF itself lets the command write is deleted after the run, or the step fails. A probe inside the sandbox must fail to get out before the command starts. Names the proxy refused are listed in the job summary. See [docs/egress-control.md](docs/egress-control.md) for how to use it and exactly what it blocks and does not.
- **Escape tests** in `.github/workflows/egress-escape-tests.yml` try 29 ways out (unlisted hosts, addresses, other resolvers, DNS over HTTPS, raw sockets, a TLS handshake with no name, child and background processes, `sudo`, the Docker socket, data in a host name, and the runner's own programs listening in its `/tmp`) and the ways a command could leave something for a later step. Each is tried outside the sandbox first, and the verdict comes from a packet capture on the runner's external interface. They run on every change to the action and weekly.
- **A refused name no longer leaves the runner in a DNS query** (slice 2c.4). AWF's proxy looked up every name it was asked for before refusing an unlisted one, so a confined command could send data out in the names it asked for. The action now runs its own resolver on the runner for the proxy, answering only names the allow-list covers and refusing every other name on the runner. Two more escape tests ask the proxy for a name holding a label, over HTTPS and over plain HTTP, and the judge requires both names among the resolver's refusals and no query carrying the label outside the runner; two more look a name up from the command itself, which never left the runner and is now asserted; and the judge fails if any unlisted name the attempts use is seen in a DNS query. The plain HTTP attempt of 2c.2 now names the proxy: curl reads only the lower-case `http_proxy`, which AWF does not set, so it had gone direct. New outputs: `dns-refused` and `dns-log`. A name under a listed name still goes to the listed domain's DNS servers; the API host of a model key is answered exactly, not its subdomains.
- **Model keys through AWF's API proxy** (slice 2c.4). The new input `model-keys` takes `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` from the step's `env` and gives them to AWF's API proxy, never to the command, which gets a base URL pointing at the proxy and a placeholder key. The proxy reaches the provider's API host whatever `allow` says. The providers' hosted web search and fetch tools are refused by the proxy, in requests whose body it parses as JSON (by AWF's source, it forwards other bodies and WebSocket upgrades unchecked). Tested with made-up keys: each provider refused the key itself (401), neither key was in the command's environment or in the files searched, and a request with Anthropic's `web_fetch` tool was refused by the proxy (403). Not refused: remote MCP servers named in a request, and other ways of asking the provider to fetch a URL. Under `env`, model keys are still refused, now with a pointer to `model-keys`; other providers' keys are refused under both.
- **The runner's own programs in its `/tmp` are out of the command's reach** (slice 2c.6, decision D-054). AWF mounts the runner's `/tmp` into the sandbox, and a read-only mount does not stop a connection to a socket. On GitHub-hosted runners `/tmp` holds .NET diagnostic sockets, which answered a request from outside the sandbox and can make a .NET program dump its memory or load a library, and .NET debugger pipes. The action now makes every socket and pipe there that the runner's user could write unwritable for the run, and the probe fails if the command can still write one. Three new escape tests: none accepted a connection or was writable from inside.
- **Only files and directories are handed back** (slice 2c.6). After the run every symbolic link, pipe, socket and device file in the scratch directory is deleted and named in the new output `removed` (plain path characters only), so a later step that reads or uploads the copy cannot be pointed at the runner's own files. The copy loses the repository's own links too (`node_modules/.bin`, for one).
- **A workspace where a checkout kept its token is refused again** (slice 2c.6). `actions/checkout` v6 and later keep it in a file that `.git/config` includes, not in an `extraheader`, so the old check missed it. The `config` and `config.worktree` files of every repository in the workspace are now read for either, and for a remote URL with a password; the new output `refused` says `credential` when this refuses a workspace (other refused inputs leave it empty).
- **`denied` is plain text** (slice 2c.6): a refused name is taken from the request's target, not the `Host` header the command chose, and kept to the characters of a host name.
- **The listed host's answer is not required to be 200.** The escape test's request to `api.github.com` got 403 inside and outside the sandbox on one run (GitHub's limit for requests without a token); the judge now requires curl to finish (which checks the server's certificate) with any HTTP answer.
- **What it does not do:** it confines one command, not the job; data sent to a listed host is not stopped, nor data in a name under a listed name, which reaches that domain's DNS servers; with a model key, data sent to the provider is not stopped, and a provider can be asked to connect elsewhere for the agent (remote MCP servers, a URL to fetch), which nothing here refuses; IPv6 could not be tested on hosted runners, which had no IPv6 route.
- **The checker reads it, and two controls can now clear OBAAF-GHA-020** (decision D-050). Every control a job might have is read, and the best one stands:
  - **GitHub's native egress firewall** clears it when every run of the job is on `ubuntu-24.04-firewall` and `.github/egress-firewall.yaml` sets `mode: enforce`. A missing or misspelt file, `mode: log`, or a token without `contents` permission is "not met". A file the checker cannot read to the end, an `allow` entry that is not a plain host name or that is or has under it a public suffix, a workflow other workflows can call, or a job on labels the checker cannot name is "cannot tell". The policy file is read only when a repository is checked.
  - **OBAAF's egress action** clears it at a commit OBAAF lists as released, with a written allow-list that has no public suffix at or under any name (the [public suffix list](https://publicsuffix.org/) now ships in `src/obaaf/data/`, under its own licence, MPL-2.0), on GitHub-hosted `ubuntu-24.04`, with the agent as its command and no step after it or beside it. A possible upload in the agent job withholds otherwise verified egress and key isolation. See [Reviewed egress action pin](#reviewed-egress-action-pin) for the full SHA. Where the agent runs is read from where credentials go: a secret or `github.token` given in the workflow to another step or to the job's or workflow's `env`, `id-token: write`, a token with the `models` permission, or an agent the checker recognises in another step is "not met"; undeclared token permissions, or no credential anywhere and no agent recognised inside the action, is "cannot tell". `actions/cache` with the output or `/tmp` is "not met"; an earlier step that names `/tmp`, uses `&` as an operator, or mentions a container engine, a terminal multiplexer or a detaching command (`nohup`, `at` and others) is "cannot tell"; a process started another way is not read. A job whose only agent command is inside the action's `run` input is now an agent job.
  - **Harden-Runner is "cannot tell" at best**, because whether the repository is one its tier covers is not in the workflow. It is "not met" at a listed commit before v2.16.0, with `sudo` or containers left to the job (`disable-sudo-and-containers` not `true`), or in a container on a GitHub-hosted runner, a new case, `weak-monitor`. Its version is read from a list of its release commits that OBAAF ships, never from a tag or a comment, so a tag is "cannot tell" whatever it says.
  - **The Agent Workflow Firewall run from a script** (`awf ... --` where a command starts) is recognised, as "cannot tell", or "not met" with `--enable-dind`.
  - A cleared finding says what the control does not stop. For the action: anything sent to a listed host, and data in a name under a listed name (since slice 2c.4, a name the proxy refuses no longer leaves the runner).
- **The checker reads the action's `model-keys` and `env` inputs** (slice 2c.5, decision D-052). Until now any credential given to the action's own step made the control "cannot tell". Each one is now placed as the action reads its inputs:
  - a key set in the step's `env` under a name `model-keys` names goes to AWF's API proxy, which the command can use and cannot read. The finding shows the provider's API host after the allow-list, as `api.anthropic.com (through AWF's API proxy)`, because the proxy reaches it whatever `allow` says, so the host is one of the finding's facts: an acceptance of a job that already used `model-keys` before this change stops matching after it;
  - a credential under a name `env` names, or written in `run`, is passed to the command. So is one of the step's `env` written into `run` through the `env` context (`${{ env.ANTHROPIC_API_KEY }}`, `${{ format('{0}', env.KEY) }}`), which GitHub fills with the step's own `env` when it writes the inputs, whatever `model-keys` says; the whole `env` context written into `run` (`${{ toJSON(env) }}`) is "cannot tell";
  - one under a name neither input names, and written into no input, reaches neither.

  A key given to the proxy and a credential passed to the command are both evidence that the agent is the confined command, and **neither stops the control from being verified**: the network is limited as the allow-list (and the provider's host) says. Beside a cleared finding the report now names the credentials passed to the command, the provider channel for each model key (anything the command sends the provider, and whatever the provider is asked to fetch or connect to: remote MCP servers, URLs), and the job's log and artifacts, which no network limit stops. Some names the action would refuse are "not met": a model key, a GitHub token or another name AWF withholds under `env`, something that is not a variable name, a name `model-keys` does not take (another provider, another case), a model key no `env` sets. Others that also make it refuse at run time are not read (a name under `env` set nowhere, an empty key, a value with a line break, a reserved name such as `PATH`), and such a step is judged as if the action ran. `env` or `model-keys` computed when the job runs or not written as text, a computed step `env` holding a credential, two names that differ only in case or a name not written as text (`true:`) holding a credential, a credential (or an `env` value holding one) in another input, or a credential anywhere else in the step is "cannot tell". OBAAF-GHA-005's fourth control says, whatever its verdict, where each credential it could place goes, what it could not place and what would make the action refuse; a key out of the command's reach does not clear OBAAF-GHA-005. A credential passed to the command can make a listed host act for it (a token that can start a workflow, for one), and the report says so.
- **Only commits at or after the floor may be listed as released commits of the action** (`egress_action_floor` in `src/obaaf/data/detection.yaml`): a test refuses an older one against the repository's history, and CI's test job now fetches the full history to check it. The floor was the merge of slice 2c.4 (`f0bfbd7`), then slice 2c.6’s last change to the action (`7c1bded`), which included the fixes for the runner’s sockets and the copy’s links. The [listed action pin](#reviewed-egress-action-pin) meets the current floor (`f3b50d4`).
- **Installing an agent's CLI before the action is not running it** (slice 2c.8, decision D-053). The checker's agent patterns match a package's name, so `npm install -g @anthropic-ai/claude-code` in a step before the action made the control "not met", and the natural way to use the action with Claude Code could not be cleared. A step before the action whose script does nothing but install `@anthropic-ai/claude-code`, `@openai/codex` or `@google/gemini-cli` globally (`npm install -g`, and until the review of #248 also `pnpm add -g`, `yarn global add` and `bun add -g`; a version and a few options that take no value allowed; `sudo` only with `-E`, `-H` or `-n`) and print the CLI's version is no longer taken for running the agent there. The step may have no `env` or `working-directory`, and the job and workflow no `env` and no `defaults.run`, since each can make the same words run something else. Not read, because the workflow does not show it: what earlier steps write to `GITHUB_ENV`, `GITHUB_PATH` or the home directory, and package-manager configuration in the working directory (`pnpm`, `yarn`, `bun`). A step that names such a package in any other form (another command, an option with a value, a local install, `$`, quotes, a pipe, `&`, a glob, a backslash, a trailing comment, another shell, an action) is now "cannot tell" where it was "not met"; one that also runs an agent (`claude -p`, `npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx`, a path into the package such as `…/claude-code/cli.js`), or any such step after the action, is still an agent outside. Which jobs are agent jobs does not change. On a scratch adaptation of the first adopter's `byo-live.yml`, its install step as written (`sudo npm install -g @anthropic-ai/claude-code` and `claude --version`) is now read as an install.
- **GitHub's native egress firewall**: beside a cleared finding the report now says that what a step prints to the job's log or saves as an artifact is not blocked, as well as what is sent to an allowed host.
- The sentence "GitHub-hosted runners have no native egress allow-list" is corrected in the rule's text, R7, the agent template and its README, and `docs/inference-proxy.md`.
- On this repository, its 16 risky fixtures and Expectrail's CI files at `0509d73`: the same findings, word for word, before and after.

### Release policy

- This repository's own release policy now sets `agents.since` to the commit of release 0.3.0, the first release that passed the full `obaaf verify release` gate. Once this is on `main`, a release checks commits from OBAAF's agent lane (a record trailer, a record file, or the effect lane's identity) from that commit to the released one, and no longer over the whole history (D-025). There were none in the history up to 0.3.0. Commits written with an AI assistant and merged through ordinary review are not what this check counts. Nothing changes for adopters.
- **Between releases, the version on `main` is a development number** (`0.4.0.dev0` on the way to 0.4.0). `main` said 0.3.0 while holding changes 0.3.0 does not have, so `obaaf --version` and the version written into reports, records and baselines from an install of `main` named a release they did not come from. With a development number on `main` it would have uploaded one, and PyPI never accepts the same file name twice.

### Dependencies

- **The `keys` extra now requires cryptography 46.0.5 or later** (it was 42). Earlier versions do not check that a binary-curve (SECT) public key lies in the curve's prime-order subgroup ([CVE-2026-26007](https://osv.dev/GHSA-r6ph-v2qm-q3c2)). OBAAF loads the keys a release policy names with `load_pem_public_key` and does not restrict their curve, so with those versions a policy that named such a key could accept a forged signature. The keys are chosen by the policy's owner, so this is hygiene rather than a way in for an outsider. An environment that holds cryptography between 42 and 46.0.4 must upgrade it to install the extra.
- The pinned install used by the `setup-obaaf` action moves to setuptools 84.2.1 and cryptography 50.0.2, the versions Dependabot's pull requests #42 and #40 asked for, with the hash lock regenerated from PyPI. PyYAML stays at 6.0.3 (#43). The floors for setuptools (`>=77`, the first that reads the SPDX licence expression) and PyYAML (`>=6.0`, past every published fix) do not change.

### Fixed

- **`runs-on: ${{ matrix.os || 'ubuntu-latest' }}` is resolved** (slice 2d.7, issue #141, decision D-056). The checker resolved only `${{ matrix.x }}`, so this form, used by `pallets/flask` among others, was a medium OBAAF-GHA-013 on every job a pull request can start, even where every label the matrix gives is GitHub-hosted. The expression is now read from its tokens: `matrix.x` and `matrix.x || 'label'` are resolved against a matrix written out in the file, and the default counts wherever a row may lack the value or give an empty one. A key of the matrix that is not plain ASCII text (`True:`, a computed key, `ſ`), a value YAML 1.2 could read as a number or false (`0o0`), or a YAML merge key (`<<`) in the file leaves the labels unresolved. So OBAAF-GHA-013 can appear where it did not, in the plain `${{ matrix.os }}` form too: the old reading resolved two cases wrongly, a matrix key computed when the job runs (`os: ${{ fromJSON(...) }}`) beside `include` entries that set it (only the `include` values were read) and an `include` written as one expression or holding an entry that is one (it was passed over); and a key that is not plain ASCII text, a value YAML 1.2 could read as other than text (quoted `'0'` included), or a merge key anywhere in the file, even in an unrelated step, now leaves the labels unresolved. A label that ends in a line break is no longer taken for a hosted one. On `pallets/flask`'s workflows at `49943b5`: one medium finding fewer. On this repository, its fixtures and templates, and Expectrail's files: no change.
- **Signature keys outside the documented set are refused when they are loaded.** OBAAF documents ECDSA P-256 and P-384, Ed25519 and RSA for `signing: keys` and `obaaf dsse assemble`, but took a key on any elliptic curve (verifying P-521 with SHA-384, for example) and loaded a DSA, Ed448 or X25519 key only to fail when verifying. Each is now refused with an error that names the file and the kind of key, by `obaaf dsse assemble` (exit 1) and by `obaaf verify release` alike. A binary-curve key, which the cryptography library cannot load since its version 47, ended `obaaf dsse assemble`, `obaaf verify release` and `obaaf verify agent-run` in a traceback; it is the same error now. P-256 is verified with SHA-256 and P-384 with SHA-384, as before.
- `obaaf check --write-baseline` ended in a Python traceback when a job id contained a lone surrogate character (a name YAML can spell and Unicode cannot encode). The baseline is now written, as valid UTF-8, and read back.
- Two more tracebacks, both in 0.3.0: `--write-baseline` to a directory that does not exist, and a v0.1 baseline whose `rule` or `severity` is a list. Each is now an error message and exit code 2. So is `obaaf check --output` to a path that cannot be written.
- An `ignore` entry dated with spaces around a quoted date (`until: " 2027-01-31 "`) is read as that date; 0.3.0 refused it.
- **The website publishes every schema at its `$id`** (slice 4.6, issue #176). D-007 says each JSON Schema's `$id` resolves to the schema, but the site build published only the predicate types' schemas, so `https://www.obaaf.com/schemas/settings-snapshot/v0.1.json` was missing. The build now publishes every schema OBAAF ships, and stops on one whose `$id` does not name a `.json` file under `https://www.obaaf.com/schemas/` or is another schema's. The site's questionnaire names its canonical address. Without JavaScript, which writes its questions, it now says so and points to `spec/self-assessment.md` and `obaaf assess`; before, it showed an empty form.

## [0.3.0] - 2026-11-12

**Upgrading from 0.2.0: a gate that passed can fail without the workflows having changed.** Several changes make the checker report what it missed before. The largest are "Lanes" and "Expressions" below. Among the smaller ones: a repository that has a Jenkinsfile now has it checked along with its workflows, and an agent command line with options before the prompt flag, such as `claude --model x -p ...`, now makes a job an agent job (both under "Jenkins (advisory)"); an unknown setting in `.github/obaaf.yml` is refused ("Protected secrets"); and a path with nothing to check is an error, not a pass ("Checker"). Baselines are new in this release. One written from `main` before the release can go stale under "Lanes" or "Expressions" and has to be regenerated with `--write-baseline`.

### Lanes

A job now gets the rules of every lane it belongs to. Before, a job had exactly one lane, chosen in a fixed order (agent, effect, release, untrusted), so a job that did two things was checked for one of them. An independent reviewer found the first two cases on 2026-11-11; the rest are the same class, found while fixing it and in a second review of the fix.

- **A job that runs an agent and publishes** was checked as an agent job only: the release rules (OBAAF-GHA-006, 014, 015, 016, 017) did not run on it. It is now in both lanes.
- **A job declared an agent job that also publishes** was checked as a release job only, and the declaration was dropped: no OBAAF-GHA-003, 005 or 020. The same held for any declared lane on a job the checker had already placed in another. A declaration now adds a lane and never replaces one.
- **A declaration could remove a finding.** Declaring a pull request job `release` or `effect` moved it out of the untrusted lane and dropped OBAAF-GHA-011. So did adding an upload step. A job that runs only for pull requests (`pull_request`, `merge_group`) is now in the untrusted lane whatever else it is.
- **A job that uses a release environment and can be started by a pull request or another untrusted event** was not a release job: an environment whose name says release, production, publish, deploy or a store made a job a release job only when no untrusted trigger could start it, which is the case OBAAF-GHA-015 exists for. With `on: pull_request_target` and `environment: production` the job was shown as `trusted (default)`. The environment now decides on its own. Because more jobs are now judged by the name, one kind of name is no longer taken for a release environment: a name in which `non` or `pre` does not follow a letter a to z (case ignored) and stands before `prod` with at most one of `-`, `_`, `.` or a space between: `nonprod`, `aws-non-prod`, `pre-production`. A push job with such an environment got the release rules before and does not now. `canon-prod` and `AppNonProd` are still release environments, because there `non` follows a letter. Every other name is matched as it was, anywhere in the name and in any case.
- **An agent started from a repository script** was detected only in jobs with no other lane. It is now detected in any job.
- **Two declarations for one job.** A lane in `.github/obaaf.yml` hid the job's own `OBAAF_LANE`, a per-job entry hid a per-file entry, and a job's `OBAAF_LANE` hid the workflow's. All of them now count.
- **A declaration that did nothing was ignored without a word.** Case and surrounding space no longer matter (`OBAAF_LANE: Agent` is `agent`, in a workflow, in `lanes:` and for a Jenkins stage). These are now listed in the report's notes: a value that is not a lane (a misspelling, an expression, an empty value) in a workflow, a Jenkinsfile or `lanes:`; `OBAAF_LANE` in a step's `env`, a container's or a service's, where a workflow does not read it; for a file the run reads, a `lanes:` entry that names a job or Jenkins stage the file does not have; and, when a repository is checked, a `lanes:` entry for a file that is not there. An entry for a file outside the run (another file when one file is checked, a Jenkinsfile when only workflows are checked) is not looked at. Notes do not change the exit code.
- **A Jenkins stage's declarations hid each other.** A `lanes:` entry for a stage replaced the stage's own `OBAAF_LANE`, and a stage's `OBAAF_LANE` replaced the pipeline's, so `lanes: {Jenkinsfile#Ship: trusted}` on a stage declared `release` removed OBAAF-JEN-005 and OBAAF-JEN-012. Every `agent` and `release` declaration that reaches a step now counts, as in a workflow; on a Jenkins stage the other lanes change nothing. A `lanes:` entry for an outer stage now also reaches the stages nested in it, and an entry for the file (`Jenkinsfile`), which did nothing, reaches every stage. A declared stage now also covers a step whose code is not in the file (a shared-library step) unless the step is in a `post`, `catch` or `finally` block, and a stage declared `release` covers the `sshPublisher` and `ftpPublisher` steps, which the guide told adopters to declare and the checker then ignored; before, a declaration reached only shell steps.
- **OBAAF-JEN-012 could be reported at medium when a step published with no check at all.** It is reported once for a Jenkinsfile, and it went to the first publishing step that lacked a full check. When that step had a provenance check, the finding was medium and a later step that nothing checked was not mentioned. It now goes to the first step with no check, and to a step with a provenance check only when there is none.
- **One workflow checked with the repository's configuration** (`obaaf check .github/workflows/ci.yml --config .github/obaaf.yml`) lost its `lanes:` entries, because the checker called the file `ci.yml` and the configuration calls it `.github/workflows/ci.yml`. Both names now match.
- **A note could be silenced.** The note about a job whose name suggests agent work was printed only for jobs in no lane, so declaring `untrusted` removed it. It is now printed for any such job that is not in the agent lane, and reads "are not in the agent lane".
- **`lanes:` that is not a mapping.** `lanes: 5` and `lanes: true` stopped the checker with a Python traceback, and a list gave an error that did not name the setting. Each is now a configuration error that says `lanes` must be a mapping. An empty value still declares nothing. A configuration file that is not valid YAML was a traceback as well, and is now a configuration error.
- **A step name that contains a line break** could make one line of `--lanes` or of the text report look like two, the second of them invented. Text taken from the files checked is now printed on one line, with the line break shown as `\n`. The JSON and SARIF output carry the text unchanged.

What an adopter will see on upgrading:

- New findings on jobs that are in more than one lane, and on jobs that use a release environment and can be started by a pull request or another untrusted event. `--lanes` names the extra lanes: `agent (…; also release: …)`.
- For a job whose lanes did not change, the same findings with the same messages, so baseline entries still match. Two things are kept as they were for that reason: a job that is declared into a lane it is also inferred into shows the declaration as the reason, and OBAAF-GHA-017, which is reported once per workflow, stays on the first publishing job that is not also an agent or effect job when there is one.
- The exception: a declaration that used to be ignored is read now. That is one written in another case or with spaces (`OBAAF_LANE: Agent`), one that stood behind another declaration for the same job (only the first was read, even when its value was not a lane), and a `lanes:` entry for a workflow checked on its own. If the job was already in the lane it names, the job's agent findings quote the declaration as the reason (`set by OBAAF_LANE`) where they quoted what the job runs, or gain or lose the words about `trusted`, and a baseline entry for them has to be regenerated.
- In a Jenkinsfile, more advisory findings where more than one declaration reaches a stage or a declared stage calls a shared-library step. OBAAF-JEN-005 and OBAAF-JEN-012 are reported once for a file and can move to another stage when that happens. OBAAF-JEN-012 can also move, and rise from medium to high, in a Jenkinsfile with no declaration at all: when one step publishes after a provenance check and a later one publishes with no check, the finding is now about the later one.
- New notes for declarations that do nothing. Notes appear in the text and JSON output and with `--lanes`; the SARIF output does not carry notes yet.

The Jenkins analyser still decides what a stage does step by step, with its own code. What changed there is how it reads declarations and which step OBAAF-JEN-012 is reported on.

### Expressions

Several spellings that no rule reported are now reported. They were found by reading the checker and by an independent review of the first fix. None has been run on GitHub.

- **Secrets.** Secret references are read from an expression's tokens, not matched as text. `secrets.*`, and any other use of the `secrets` context that is not one literal name (for example `contains(secrets, 'x')`), counts as every secret (OBAAF-GHA-001, 005, 024). A secret referenced anywhere in a job is found, including in `outputs`; before, only `env`, `with`, `secrets`, `container`, `services` and `steps` were read.
- **Where an expression ends.** An expression is no longer cut short at a `}}` inside a string, as in `${{ format('}}{0}', secrets.KEY) }}`, which hid whatever followed from every rule that reads expressions.
- **OBAAF-GHA-010.** The rule keeps its text patterns and adds a second pass over the expression's tokens. It now follows a wildcard or computed index (`github.event.*.title`, `github.event.issue.*`, `github.event[inputs.kind].body`), a property of a group or of a function's result (`(github.event.issue).title`, `toJSON(github.event.issue || 1)`), `${{ env.NAME }}` when NAME is set from an outsider-written field, directly, through other env values or through the matrix, and `${{ matrix.x }}` when the job's matrix is built from such a field. It does not follow values set at run time (`GITHUB_ENV`), values passed between jobs or into reusable workflows and composite actions, scripts other than `run` and `actions/github-script`, an `env:` written as one expression that itself reads env or matrix values, or a `with:` written as one expression.
- **Files the checker cannot read are errors, which fail the check:** an expression nested more than 64 levels deep, a text with too many unfinished expressions, a file too large to read in the memory available, a value only an explicit YAML tag produces (`!!set`, `!!pairs`, `!!omap`, `!!binary`, or text under `!!null`), a job or step that is not a mapping, and a file containing U+0085, U+2028 or U+2029 (YAML readers disagree on whether these end a line).

Other changes in behaviour: any string given for `secrets:` on a reusable-workflow call counts as `inherit`; `secrets["KEY"]` (double quotes, which GitHub rejects) and an index that is not a name count as every secret; an expression with no closing `}}` is read to the end of its text; text inside a string, such as `format('secrets.KEY')`, is no longer mistaken for a secret reference (OBAAF-GHA-010 still reports a field named inside a string, as before). Because `obaaf attest` records the secrets a job can read and `obaaf verify release` checks that record, a job that names a secret only in a place that was not read before is now recorded as holding it. Findings for workflows that use none of these spellings are unchanged (checked on this repository's workflows, fixtures and templates, and on Expectrail).

### Protected secrets

- GHA-024 hardening, after an independent review: a computed secret index (`secrets[format(...)]`, `secrets[matrix.k]`) counts as every secret for all rules; the `secrets` context matches in any case; overlapping `protected_secrets` entries all apply; environment names compare case-insensitively; reusable-workflow callers get advice they can follow, and `secrets: inherit` is no longer reported; globs need three letters or digits; unknown configuration settings are refused. The published test set shows the configuration a fixture is checked with.
- New rule OBAAF-GHA-024. List secrets under `protected_secrets` in `.github/obaaf.yml` (optionally with the environment that must hold each one), and the checker reports every job that uses one without declaring that environment. Anyone with write access can read a repository secret by pushing a workflow on a branch; the GitHub settings guide now says so and describes how to keep such secrets in an environment limited to the default branch. Test fixtures can carry a configuration in an `# obaaf-config:` line.

### Baselines

### Jenkins (advisory)

- `obaaf check` now reads Jenkinsfiles (`Jenkinsfile`, `Jenkinsfile.<name>`, `Jenkinsfile-<name>`, `<name>.jenkinsfile`, and globs in `jenkins.files`) alongside workflows, or alone with `--platform jenkins`. A syntax-only parser reads the Groovy without running any of it (D-034). Fifteen rules, OBAAF-JEN-001 to OBAAF-JEN-015, cover credentials that change requests or an agent can reach, builds on the controller and shared agents, agent stages that push or publish, pipeline code from unapproved revisions, approvals, host access from containers and pods, agent egress, unpinned images, libraries and agent CLIs, Groovy-interpolated untrusted text and secrets, moving artifact references, publishing after a failed check, missing release verification, signing keys, and webhook tokens in the file. Each maps to profile requirements and agent controls in the catalog.
- Every Jenkinsfile gets a coverage result per rule (pass, fail, ignored, unknown, not applicable) in text and JSON output, with the reason for each unknown. Controller settings and shared-library code are reported as unknown, never as a pass, and the report states that exit 0 is not a conformance decision (D-036). See [docs/jenkins.md](docs/jenkins.md).
- `templates/jenkins/obaaf-audit.Jenkinsfile` runs the audit as a Jenkins job.
- New configuration: `jenkins.files`, `jenkins.exclude` and `agents.steps`; lane overrides and ignore entries take a Jenkins stage as `file#stage` and `job: <stage>`. `--lanes` lists Jenkins stages.
- OBAAF-REPO-001 also covers Jenkinsfiles, and is retitled "CI definition files have no code owner".
- Release lane on Jenkins (D-037): `templates/jenkins/obaaf-release-build.Jenkinsfile` builds a protected tag with no credentials in a project that builds only tags; `obaaf-release-publish.Jenkinsfile`, a separate job read from the default branch with no parameters, finds the tag build that started it, signs SLSA provenance and the build record through a key service, verifies, waits for a named approver and verifies again before uploading. A `signing: keys` policy example is included.
- `obaaf dsse prepare` and `obaaf dsse assemble` sign records with a key that stays in a key service: `prepare` writes the bytes (or digest) to sign, `assemble` accepts the service's signature (raw or base64, DER or r||s), checks it against the public key and writes the DSSE envelope.
- `obaaf verify release` reads Jenkins evidence: `--approvals` takes the publishing build's JSON from the controller, `--release-run` the JSON of the build that produced the artifacts. The publishing build must have been started by that build alone, which must be the tag build of `release.jenkins_project` and have checked out the release commit. Whoever started either build cannot approve; with `release.approvers` set, only listed people count (on GitHub too). Replays, stage restarts, builds started by hand, unclassified causes and incomplete evidence are blocked.
- Records written in a Jenkins build name it in `run` (controller, job, build URL), marked as self-reported, and the build record says its source came from the Jenkins release job.
- Agent CLI patterns accept options before the prompt flag or subcommand (`claude --model x -p ...`, `codex -m o3 exec`). This also applies to workflows, where such jobs were previously left out of the agent lane.

### Checker

- `obaaf check .github/workflows`, the form the website quickstart shows, checked zero files and passed, because discovery expected a repository root. The checker now accepts a repository root, its `.github` directory or its `.github/workflows` directory, and keeps repository-relative paths. When nothing is found, `obaaf check` exits 2 and says nothing was checked, instead of passing.

### Draft corrections

The following corrections are recorded in the draft. Remaining issues are listed below.

- `obaaf proposal check` reads the patch with Git as well as its own parser, decodes quoted file names, matches protected paths without regard to case, refuses renames, copies, unusual file modes and paths under names starting with `.`, and with `--repo` tests the patch against a temporary index. Four patch forms that previously reached protected files are now refused. The comment filter is stricter.
- The effect lane is split into an `approve` job, which verifies the agent-run record against every proposal file and the snapshot, and an `apply` job, which holds write access but cannot sign. Approvals by anyone who wrote the agent's inputs no longer count.
- Releases are published by a new `obaaf-publish.yml`, which runs from the default branch, verifies before the approval and again after it, and requires the released commit to be on the protected branch. Agent commits are checked from a baseline in the policy rather than from the previous tag.
- The release verifier fails closed on missing certificate fields, requires `source_refs`, ignores a bad extra attestation when a valid one exists, ties each agent record to the commit that adds it, checks it is used once, requires the exact approved diff by default, and checks the agent run's cache, environment and runner. Its `--gh-json` option is removed.
- The checker no longer lets a negated condition, a declared lane or a match-everything ignore entry hide findings, reports unknown runner labels, finds script injection written with index syntax or `toJSON`, treats GitHub Script artifact downloads as effect jobs, does not count a verification whose failure is ignored, and reports provenance-only checks and declared-but-unenforced egress.
- The setup action pins its build backend and installs `cryptography` for key-based verification. The snapshot's default floor is Public, and membership alone no longer raises a label. The binary manifest records symbolic links.
- The generated specifications keep the papers' qualifiers (for example "Build L3, for Tier A" and "PS.4 (draft 1.2)"). Status statements for FR3, FR4, FR7, FR10, FR11 and NFR3 now say what version 0.1 does not do. Guides for items 1.2, 1.6, 2.3, 2.5, 2.10, 3.3, 4.1 and 4.3 are corrected, and the employer-name test no longer contains the names.
- Second round: the checker now sees steps inside `parallel` groups, does not count a `background` verification as a gate, does not narrow triggers through jobs a `success() || …` condition can bypass, requires both checks for an effect job, and reports step forms it cannot read. The verifier compares an agent commit with the approved patch by applying the patch to the commit's parent, refuses other changes in the records directory, shallow clones, and a `--range` that overrides the policy's baseline, and no longer skips the protected-branch check when it lacks the release commit. More agent configuration files are protected. The documents say that the author has not yet reviewed version 0.1, what Free, Pro and Team plans can and cannot do, and that the agent's pull requests need to be reopened to start their checks.
