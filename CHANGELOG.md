# Changelog

All notable changes to OBAAF. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow semantic versioning: drafts are numbered 0.x, and version 1.0 follows the first pilot.

## [Unreleased]

**Upgrading from 0.3.0: a gate that uses a baseline or an ignore entry will fail until its acceptances are completed.** Each needs an owner, and one whose reason has fewer than four letters or digits, or whose date is more than 366 days ahead, no longer counts. Nothing about the workflows has to change, and one command converts a baseline. See "The lifecycle of a finding" below. Three more changes can turn a passing gate red without a baseline being involved: an agent job whose egress control is a blocking Harden-Runner step is now reported under OBAAF-GHA-020 as "cannot tell", where it used to pass; a job whose `if:` only looked like a test of the event is now checked for every event that can start it; and an input written in another case (`REF:` for `ref:`) is now read. See "Controls", "Which events can start a job" and "Inputs in any case" below. And a lane declaration that does nothing, which 0.3.0 listed in a note, is now a finding, high in most cases, so it fails a gate until it is corrected or accepted: see "A lane declaration that does nothing is a finding". The reports also begin differently, and a script that reads the first line of the text report or the `ignored:` lines will see other text: see "Reports begin with the accepted risk"; the text report also ends with the version, and `obaaf check --lanes` now fails on a file it could not read: see "The first run says what it did not read". Six rules about what a job can reach were attacked and tightened, which can fail a gate on a `permissions` value or event name GitHub does not document, a callable agent workflow, a caller with `secrets: inherit`, or an acceptance of a secrets finding on a job with an environment: see "What a job can reach: six rules attacked". Four rules about what a run checks out were attacked the same way, which can fail a gate on a checkout or a script that brings in a pull request's code in a spelling OBAAF did not read, on a ref it cannot read in a privileged workflow ("cannot tell", medium), on a job a pull request starts beside other triggers that keeps its token, on `allow-unsafe-pr-checkout` written as an expression, on an agent job on a review event or with `ref: ${{ github.sha }}` (the merge commit), on a job whose agent CLI is run by its path, or on an acceptance of one of these four rules written before the change: see "What a run checks out: four rules attacked". Not released; Expectrail and anyone else pinned to a commit or to 0.3.0 see no change until they move. [docs/upgrading.md](docs/upgrading.md) has what to do, case by case, and one upgrade from start to finish.

### Files the checker could not read

Slice 2d.8, from #155; decision D-059.

- **A `CODEOWNERS` file that is there and cannot be read is an error for that file** (status 1), in `obaaf check` and `obaaf check --lanes`, and so is a place GitHub looks for one (`.github/`, the root, `docs/`) that cannot be looked in. Before, `obaaf check` ended in a traceback and `--lanes` ended 0. OBAAF-REPO-001 and 002 are not reported while it cannot be read. A link that leads to no file (dangling, to a directory, a loop) is still taken for no file, as before.
- **An agent instruction file that cannot be read is an error for that file.** Before, it was skipped in silence, so OBAAF-INS-001 passed a file nobody had read. Instruction files that are links are still not looked at (older than this change).
- **A directory that cannot be listed or entered is a note** naming it, because agent instruction files in it were not looked for. It is a note, not an error: git cannot check out a directory its owner cannot list, so only a local run meets one. Before, `obaaf check` ended in a traceback on a directory it could list and not enter.
- **`obaaf check --lanes` refuses the options `obaaf check` refuses before it reads anything** (`--fail-on` with a value it does not know, a `--baseline` that cannot be read, `--owner`, `--reason` or `--expires` without `--write-baseline`, `--baseline` with `--write-baseline`), and refuses `--write-baseline` and `--output`, which it never used: status 2. Before, it listed the jobs and ended 0. `--lanes` now runs the repository rules to find unreadable files, so it walks the repository as `obaaf check` does and takes longer on a large one (on 100,000 files, about 3.6 s where it took 0.3 s with `--platform github`).

### Triggers, scripts and release jobs: three rules attacked

Slice 2d.2d; decision D-061. Two reviewers that did not write them tried to get past OBAAF-GHA-010, 013 and 015: one in run `skua` (115 attempts, 38 ways past, recorded as classes only), and two in run `ruff` after the first round of fixes (149 attempts, 60 ways past and 10 false positives). Every attempt of run `ruff` is recorded in [docs/bypass-attempts.md](docs/bypass-attempts.md), and every way past that is fixed is a test (`tests/test_trigger_script_release_bypasses.py`).

- **OBAAF-GHA-010 knows more outsider-written fields**: an edited title's or body's old value (`changes.title.from`), an issue or discussion transferred here, a review comment's `path` and `diff_hunk`, a commit's committer and the files it adds, removes or changes, a gollum page's title and summary, a discussion's answer, a fork's description, `workflow_run.head_repository`, `workflow_run.path` and its pull requests' branches, a merge group's commit, and the commits and branches of `check_suite`, `check_run` and `status` events.
- **It reads more of what a step runs**: its `shell` and the job's or workflow's `defaults.run.shell`, the egress action's `run` under spellings of its path that do not make it the control (`actions/egress/`, `actions/./egress`, a doubled slash), and the inputs of the actions under `script_inputs` in the detection data (`azure/cli` and `azure/powershell` `inlineScript`, `appleboy/ssh-action` `script`, the retry actions' `command`, and others), in any letter case.
- **It follows values between jobs**: a job's `outputs` written in the file, read as `needs.<job>.outputs.<name>` in a script or an env value, through other outputs; and an `env:` written as one expression that reads the matrix or env.
- **Its severity**: high in a reusable workflow (the caller's event is not read), on `commit_comment`, `check_suite`, `check_run` and `status`, and for a commit's text on `push`, `merge_group` and a `workflow_run` narrowed to pushes, in every spelling (`toJSON(github)`, a computed path); a merged pull request's title and branch name are in its merge commit's message.
- **Every field a step reaches is a fact** (`fields`), with the expressions that reach them (`expressions`) and the job's triggers, so an accepted step that later expands one more field, expands it another way, or that a new event can start, is a new finding. The checker still does not work out whether an expression gives text or only true or false; naming the expression keeps an acceptance of `contains(github.event.issue.title, 'bug')` from covering a later `${{ github.event.issue.title }}`.
- **OBAAF-GHA-013 takes a label for GitHub-hosted only when GitHub names it** (`HOSTED_LABELS`: the standard runners and the macOS larger runners); before, any `ubuntu-*`, `windows-*` or `macos-*` label was. `self-hosted` is found in any case, with spaces round it, and as a word of a label with spaces or commas. A job that calls a reusable workflow is no longer reported as running on no labels.
- **A runtime selector is informational only as `head.repo.full_name == github.repository && <runner> || '<hosted>'`**, only on pull request events and only in a job that runs no agent; any other selector naming `self-hosted` is medium. `head.repo.fork && 'ubuntu-latest' || 'self-hosted'` (from issue #19) is now medium: a pull request whose fork was deleted has no `head.repo`, and the selector then picks the self-hosted runner. The selector and the label sets a matrix gives are facts.
- **OBAAF-GHA-015 recognises more release jobs**: the commands and actions listed under "upgrading" (`gh release edit`, `git push --tags`, `aws <options> s3 cp`, `pnpm -r publish`, `uv publish`, `pypa/gh-action-pypi-publish` and others), read in `run`, github-script and `docker://` steps, with continued lines joined and quotes taken out; and environments named `live`, `prd`, `cd`, `pypi`, `npm`, `crates` or `pages` as a word, or by any name a matrix or the text values of an expression give. Words that only hold the letters of a release word (`kitchen`, `switch`, `restore`, `keystore`, `datastore`, `firestore`, `reproducible`, `product`) no longer make a release environment; `AppProd` and `euproduction` still do. These lists also decide the release lane, so OBAAF-GHA-006, 014, 016 and 017 see the same jobs.
- **Its severity agrees with OBAAF-GHA-001's**: medium when only pull request events can start the job (a fork's run gets no secrets and a read-only token), medium when it names an environment in plain text, which may require a reviewer; high otherwise. Why it is a release job, the steps that make it one and its environment are facts.
- **A job that may release is reported**: one an outside event can start that has `packages: write`, a publishing secret by name, a step using `docker/build-push-action` or another `publishing_actions` entry, or an environment named by an input or a function is OBAAF-GHA-015 case `capability`, medium (low on pull request events only). `id-token: write` alone is not counted: OBAAF's own templates use it to sign and attest.
- **Not fixed, and stated in each rule's description:** local reusable workflows and composite actions (slice 2d.4), agents the checker does not recognise (slice 2d.5), whether an expression gives only true or false, a command named in an `echo` taken for one that runs, the `env` of a `parallel` group, `id-token: write` used to deploy, and the repository's default token permissions.

### What a run checks out: four rules attacked

Slice 2d.2c; decision D-060. A reviewer that did not write them tried to get past OBAAF-GHA-002, 011, 012 and 019 with 106 workflows, and 57 got through; every attempt is recorded in [docs/bypass-attempts.md](docs/bypass-attempts.md), and every way past is a test (`tests/test_checkout_bypasses.py`).

- **A checkout's `ref` and `repository` are read as expressions** (OBAAF-GHA-002 and 012): in any letter case, with index syntax, through `format`, `join`, `fromJSON` and `toJSON`, and through `env` on the step, job or workflow. The fork's repository with no `ref`, and the pull request's number used to build `refs/pull/N/...`, are the pull request's code. Before, only plain spellings were matched as text.
- **A ref the checker cannot read to a value, in a workflow an outsider's event starts, is "cannot tell" at medium**: OBAAF-GHA-002 case `checkout-unresolved`, OBAAF-GHA-012 case `unresolved`. This is the usual `issue_comment` pattern (a step asks the API for the head commit and the checkout takes its output). If the value is not a pull request's code, accept the finding and say why.
- **Scripts are read by what their commands do** (OBAAF-GHA-002 and 012). A script is split as a shell splits it, command by command; a command that brings code in (git after global options and their values, by path or quoted, with `fetch`, `pull`, `clone`, `checkout`, `reset`, `show`, `apply` and others; `gh pr checkout`; `gh repo clone`; `patch`; `gh api`, curl or wget of an archive, contents, a diff or the pull request's patch address) is case `fetch`, high, when the same command names the pull request's code: an expression or `env` value, the event file, `gh pr view`, `gh pr diff`, `GITHUB_HEAD_REF`, its number, a variable set earlier in the step, or a file an earlier command wrote from one of these. With a step's or job's output instead, case `fetch-unresolved`, medium. Comments are dropped, continued lines are joined, a quoted script given to `sh -c` is read again, a `docker://` step's `entrypoint` and `args` are read, and a script in another language (Python, Node, PowerShell, github-script) is split roughly with git counted anywhere, even inside a string. The name of a branch being created is not read. Before, one spelling of each command was matched.
- **OBAAF-GHA-012's merge-commit case covers `pull_request_review` and `pull_request_review_comment`**, and a `ref` of `github.sha`, `github.ref` or `github.ref_name`; a `ref` with the word `base` in it is no longer skipped when it also names the head (`head.sha || base.sha`).
- **OBAAF-GHA-011 covers every job an outsider's event can start**, not only jobs that every trigger puts in the untrusted lane (`on: [pull_request, workflow_dispatch]` was silent). It no longer reports `persist-credentials` written as `${{ false }}`, `${{ 'false' }}` or `off`: actions/checkout keeps the token only for `true`.
- **OBAAF-GHA-019 counts any value but a plainly false one**, an expression included (`${{ true }}` was silent).
- **A "cannot tell" finding is identified with everything in the file its value can depend on**: the workflow's and the job's env, the job's strategy, its earlier steps and the jobs it needs, as one digest. An acceptance of it no longer covers the same checkout after any of them changes.
- **New facts, so acceptances written before the change no longer name these findings**: OBAAF-GHA-002 has what was read and the job's and step's `if:`; OBAAF-GHA-011 the credential kept (the job token, or the token or SSH key given to checkout), the triggers, whether the job runs an agent and what the job token can write; OBAAF-GHA-012 the triggers, the `if:` and what was read; OBAAF-GHA-019 the triggers and the value. A v0.1 baseline (0.3.0) still names them, because each finding carries the message 0.3.0 wrote for it, and `obaaf baseline migrate` carries such entries over.
- **An agent CLI run by its path or quoted** (`$HOME/.local/bin/claude -p`, `"claude" -p`) makes an agent job (lane assignment), for the CLIs matched with a prompt flag or subcommand (claude, gemini, codex, opencode, copilot); `aider` and `cline` are matched as before. Such a job gets the agent rules.
- **This repository's own check** accepts the escape tests' kept-token checkout, now covered by OBAAF-GHA-011, with an `ignore` entry in a new `.github/obaaf.yml`.

### What a job can reach: six rules attacked

Slice 2d.2b; decision D-058. Two reviewers that did not write them tried to get past OBAAF-GHA-001, 003, 004, 005, 018 and 024; every attempt is recorded in [docs/bypass-attempts.md](docs/bypass-attempts.md), and every way past is a test.

- **Permissions written in a form GitHub does not document fail the check** (an error for the file, status 1) and are read as the widest grant they could be: a scope name in another case (`Contents:`, `ID-TOKEN:`), a level other than `read`, `write` or `none` (`WRITE`, `" write"`), a string other than exactly `read-all` or `write-all` (`Write-All`, `write`, an expression, `" read-all"`). Before, each was read as no permissions at all (or, for `" read-all"`, as read-all), with no word. `permissions:` with no value is taken as not written, so a job's empty `permissions:` no longer hides a workflow-level `write-all`.
- **An agent job that declares no permissions in a workflow another can call (`workflow_call`)** is reported as holding what the calling job grants: OBAAF-GHA-003 and OBAAF-GHA-004, case `inherited`. OBAAF-GHA-004 said nothing before.
- **OBAAF-GHA-001 is lowered to medium only by an environment named in plain text.** An environment named by an expression (`tmp-${{ github.run_id }}`, `${{ github.event.pull_request.head.ref }}`), which GitHub creates on first use with no protection rules or the event's author can pick, keeps it high.
- **OBAAF-GHA-024 reports `secrets: inherit`** to a reusable workflow as it reports a protected secret passed by name. It compares environment names by the case of A to Z only; a name equal only under Unicode case folding (the Kelvin sign, `ß`, the long s), or a number or true or false that could be the name in another reader's spelling, is unconfirmed (medium); a blank or missing name is no environment; a list or a mapping is not a name. Two `protected_secrets` entries for one secret name in different case are a configuration error (status 2); before, the second silently replaced the first.
- **OBAAF-GHA-018 reports a job that can read every secret** (a computed name, `toJSON(secrets)`, `secrets: inherit`), new case `any-secret`. It joins a command continued on the next line (backslash, PowerShell backtick, cmd caret) before matching, and knows more: `gpg2`, `/usr/bin/gpg`, `gpg.exe`, options before `--import`, `.P12` and `.pfx` in any case, `Import-PfxCertificate`, the actions `crazy-max/ghaction-import-gpg` and `apple-actions/import-codesign-certs`, and secrets named like `CSC_LINK`, `MACOS_CERTIFICATE`, `KEY_STORE`. `gpg --import-ownertrust` is no longer taken for a key import.
- **The job's environment is part of OBAAF-GHA-001, 005 and 018 findings about secrets**, because a secret of the same name in another environment is another secret: an acceptance written for the job in `sandbox` no longer covers it in `production`. A job with no environment is identified as before.
- **An event under `on:` not written in lower-case letters and underscores** (`Pull_Request_Target`, a mapping inside the list) is an error for the file; before, it was dropped without a word.
- **Fixed: a job whose environment is a number of thousands of digits** no longer ends `obaaf check` in a traceback.

### The first run says what it did not read

Slice 3.2a; decision D-057.

- **`obaaf check --lanes` reports what it could not read**, and ends with status 1 wherever `obaaf check` reports an error for a file: one it could not read or parse (its jobs are missing from the list), an input given twice under two spellings, an expression too deep to read. Each is an `error:` line on standard error, in `obaaf check`'s words. A path with no workflow or Jenkinsfile, or one that is not there, is status 2. A Jenkinsfile part of whose pipeline was not analyzed is a `note:` that a stage may be missing, and does not change the status, as for `obaaf check`. Before, `--lanes` ended with 0 and said nothing in every one of these cases, although it is the command a team runs to confirm that every agent job is seen.
- **The text report ends with the version that wrote it**: `Checked by obaaf 0.4.0.dev0.` The JSON and SARIF reports already named it.
- **A text report written with no configuration file says what that leaves out**, in two lines before the version: that a job counts as an agent job only when it runs an agent tool OBAAF knows or sets `OBAAF_LANE: agent` (run `--lanes`, declare the others with `OBAAF_LANE` or in `.github/obaaf.yml`, which a check of one file looks for from that file's folder unless it is given with `--config`), and that zizmor, actionlint, poutine and GitHub's code scanning default setup find workflow mistakes OBAAF does not look for. Not in JSON or SARIF. The `obaaf-pipeline-check.yml` template passes a configuration file on pull requests (`{}` when the target branch has none), so there the two lines do not appear.
- **Fixed: `obaaf check` ended in a traceback on a workflow file it could not read** (an I/O error, not a parse error); it is now an error for the file, status 1.

### CI integration

- **New page [docs/ci-integration.md](docs/ci-integration.md)** (slice 3.4): `obaaf check` as a required check on pull requests, with its SARIF report in code scanning beside CodeQL's default setup, and as a pre-commit hook. The workflow it gives is the `obaaf-pipeline-check.yml` template with its pin filled in, which reads the checker configuration from the branch a pull request targets; a test keeps the two the same and runs the checker on it, runs the page's failing example, and checks that every `obaaf` command on the page and in the workflow parses and every `--fail-on` value is one the checker accepts. Not run: the workflow on a GitHub runner, an upload to code scanning, a required check in a ruleset. OBAAF still has no hook definition of its own (`.pre-commit-hooks.yaml`): the page uses a local hook.
- **The `obaaf-pipeline-check.yml` template reads the target branch's configuration under all three names** the checker reads (`.github/obaaf.yml`, `.github/obaaf.yaml`, `obaaf.yml`). Before, a repository whose configuration was at either of the other two had its pull requests checked with none: no lane declarations, so fewer findings on a pull request than on a push. The step now also decides it is a pull request from the event, not from a directory `.obaaf-base` being there, and removes such a directory a pull request brings before it checks out the target branch's configuration. **It fails the job when the configuration it would read on the target branch is a link** (the sparse checkout brings the link and not its target), so a repository that keeps its configuration behind a link must make it a regular file. It also runs on the `edited` event of a pull request, so one moved to another target branch is checked again against that branch (title and description edits run it too). Not run on GitHub.

### The lifecycle of a finding

The first adopter's gate asked one question of every finding, "is it new?", and the answer was always to accept it: all 38 findings in its baseline were accepted in a file that names nobody, gives no reason and never expires, and the file was regenerated three times in a day to add more. This changes what accepting a finding takes, and what a finding is.

- **A finding is new, accepted, fixed, or one the checker cannot tell about.** JSON output has `state` on every finding and a `summary` of the counts. Text output prints a line under a finding that was accepted by a baseline entry, that is named by an entry that does not count, or that has controls; a finding with no such line is new. "Fixed" means every control that clears the finding was read and verified, and "cannot tell" means one of them could not be read; a finding the checker cannot tell about fails the check like a new one. Two rules report controls, OBAAF-GHA-005 and OBAAF-GHA-020 (see "Controls" below); every other finding is new or accepted.
- **An acceptance needs an owner, a reason and an expiry date, in an `ignore` entry and in a baseline entry alike.** The owner is a user (`@name`), a team (`@org/team`) or an e-mail address; only its form is checked. The reason needs at least four letters or digits. The date must not have passed and must be at most 366 days ahead. An entry that lacks one of the three, has expired, or is dated further ahead accepts nothing: its finding counts as new, and the report says under the finding what the entry lacks.
- **`ignore` entries need `owner:`.** A configuration written for 0.3.0 still loads, and its entries ignore nothing until an owner is added to each. `until: 2999-01-01` no longer works either. An `until` that is not a plain date (`2027-01-31T10:00:00Z`, `20270131`) is now a configuration error on every Python version; a time of day there used to end in a traceback when the entry matched a finding.
- **New baseline format, `obaaf-baseline/v0.2`.** An entry holds what the finding is (rule, file, job, step, which of the rule's cases, and the values it is about, such as the secrets a job receives), the severity it was accepted at, and the owner, reason and expiry date. It has no fingerprint and no message: the fields a reviewer reads are the acceptance. Entries no longer depend on how a rule's message is worded, so a release that rewords one does not break a baseline. Three kinds of finding still carry text: for OBAAF-GHA-003 the reason the job is an agent job is part of the finding, as the text the checker shows, so an acceptance stops covering the job when that text changes (another recognised action, a command in another step, a declaration added), and it does not tell agents apart beyond that; for OBAAF-INS-001 each hidden character is identified with a digest of the line it is on (a line ends at a line feed or a carriage return), so the same character with other text on its line is another finding; and Jenkins findings are still identified by their whole message. An entry does not cover a finding that has become more severe than the entry says.
- **`obaaf-baseline/v0.1` files (written by 0.2.0 and 0.3.0) are still read, and accept nothing.** Each entry still finds its finding, so the report can say what the file used to cover, but with `--fail-on low` the check fails until the file is converted. `obaaf baseline migrate FILE --owner … --reason … --expires …` converts it: it carries over the findings the old file covers that are still found, and accepts nothing else.
- **`--write-baseline` takes `--owner`, `--reason` and `--expires`, and never renews an acceptance by itself.** Entries of the file it replaces that are still valid keep their own owner, reason and date. Only findings that no valid entry accepts get the ones given on the command line, and without them nothing is written (exit 2). It refuses to write over a v0.1 file, and over any existing file that is not a baseline (0.3.0 wrote over whatever was there, `/dev/null` included).
- **JSON output** keeps every field it had. New: `state`, `kind`, `facts`, `acceptance` and `controls` on a finding, `summary`, `baseline.format`, and `fixed` (findings cleared by verified controls, which are no longer in `findings`). SARIF results carry `obaaf-state`.

What an adopter will see on upgrading:

- With a v0.1 baseline: every finding the baseline covered is reported as new, with the line "Not accepted: the baseline entry that names this finding does not count", and the report ends with the `obaaf baseline migrate` command to run. After converting, the same findings are accepted again, each with an owner, a reason and a date.
- With `ignore` entries: each finding an entry used to ignore is reported, with "because it names no owner", until `owner:` is added. An entry whose reason has fewer than four letters or digits (`reason: ok`), or whose `until` is more than 366 days ahead, stays without effect after that, and the report says which.
- With neither: no change in findings or exit codes. Messages are word for word what they were (compared on this repository, its fixtures and templates, and Expectrail at `16edb91`).

### Controls

The first adopter had the same two findings on each of its 19 agent jobs, a secret in the job (OBAAF-GHA-005) and no egress restriction (OBAAF-GHA-020), and the only thing it could do with any of the 38 was accept it. Both findings now name the controls that would clear them and say what the checker established about each. **Neither can be cleared yet**, and the report says which control stands in the way.

- **OBAAF-GHA-005, for a job that references secrets, lists four controls**, and is fixed only when all four are verified: `secrets-protected` (each secret is listed in `protected_secrets` and the job declares the environment named there), `environment-restricted` (the secrets are stored only in that environment and only protected branches may use it), `no-outsider-input` (no pull request, issue or comment can start the job, no checkout step names a pull request's ref, and no expression or `if:` reads a field an outsider writes) and `egress-enforced` (a control the checker recognises limits the job's network access to an allow-list). Each is reported as verified, not met or cannot tell. The guide has [what is read for each and what is not](docs/checker-configuration.md#controls).
- **`environment-restricted` is never verified.** It is a repository setting. `obaaf audit` reads environments and their branch rules, and `obaaf check` does not use what it reads yet, so it is "cannot tell"; for a job that declares no environment it is "not met".
- **`egress-enforced` is never verified.** A job with no blocking egress control, with one behind an `if:`, with one that is not the job's first step on its own (it starts after other steps, in a `parallel` group or in the background), or with only an `OBAAF_EGRESS` declaration is "not met". A `step-security/harden-runner` step with `egress-policy: block` and no `if:`, as the job's first step, is "cannot tell": whether it limits the agent depends on its version and on the job being unable to undo it with sudo or a container, and the checker reads neither yet.
- **OBAAF-GHA-020 is now reported for every agent job**, with that one control. This is the one place where a workflow that passed is now reported: a job with a blocking Harden-Runner step and no `if:` had no OBAAF-GHA-020 finding, whatever the step's version and wherever it stood in the job, even after the agent. It now has one: "cannot tell" when the monitor is the job's first step, "not met" when it is not. Either fails a gate at `--fail-on low` until it is accepted with an owner, a reason and an expiry date. A baseline entry that accepts the "cannot tell" case is for the workflow file as it stood, byte for byte (the finding carries the first 32 characters of the file's SHA-256), so it stops covering the job when the monitor is repinned, moved or changed in any way, and also on any other change to that file. An ignore entry holds until its date, as before. The three cases reported before keep their messages and their identity, so a baseline entry for one still matches.
- **A proxy that holds the model key is not counted as a control.** Two exist (the Agent Workflow Firewall's, and `openai/codex-action`'s); neither has been run here, so neither is credited.
- **A workflow compiled by GitHub Agentic Workflows (`.lock.yml`) is read like any other workflow file** and gets no credit for how it was made.
- Text output lists the controls under a finding, one to a line, verdict first. JSON output has `id` on each control. For a finding that lists controls the line "Architecture: fixing this means adopting the agent and effect lanes" is no longer printed: the controls are the other way to clear it.

On the first adopter's workflows at `b4e07bc`, with its own configuration: all 19 agent jobs have `secrets-protected` verified; 11 have `no-outsider-input` verified and 8 "cannot tell" (seven check out a second repository, one checks out a ref computed when the job runs); all 19 have `environment-restricted` "cannot tell" and `egress-enforced` "not met". So all 38 findings are still new, and what each job lacks is an egress control.

**A fifth control for OBAAF-GHA-005: the agent's command cannot read the job's secrets** (slice 2c.7, decision D-055). A limit on the network does not stop an agent that holds a key from printing it to the job's log or leaving it in an artifact, so the four controls could all hold with the key in the agent's hands.

- **`key-out-of-reach`** is verified only where every secret of the job (`GITHUB_TOKEN` aside, as for the finding's list of secrets) is set in the `env` of steps that use OBAAF's egress action, at a commit OBAAF lists as released (none is listed yet), on GitHub-hosted `ubuntu-24.04`, and goes to AWF's API proxy (named in `model-keys`) or to nothing the command runs. A secret passed to the command, given to another step, to the job outside its steps or to the workflow's `env`, or a job with no step that uses the action is "not met"; GitHub's native firewall holds no key, so a job on it is "not met" here although its egress control is verified. The step that uses the action holds the key in its own process, outside the sandbox, and the action's own bash steps run there with it, so an agent or a credential in a step that can run before or beside it (earlier, in its `parallel` group, or beside a `background` step) is "not met", as is a job that can request OIDC tokens or gives its token the `models` permission; and a variable bash or the loader obeys (`BASH_ENV`, `PATH`, `LD_PRELOAD` and others), or `ACTIONS_ALLOW_UNSECURE_COMMANDS`, in an `env` (issue #139), a step before or beside it whose script names `GITHUB_ENV` or `GITHUB_PATH` or may leave a process running (read from the words in the script; a detached process or a write spelt otherwise is not seen), service containers given volumes or options, a secret the checker cannot place, another runner, a container, the Agent Workflow Firewall run from a script, and a job that calls a reusable workflow are "cannot tell".
- **Where each credential given to the action goes** is now said in this control's detail, whatever its verdict; it was in the fourth control's (`egress-enforced`) since slice 2c.5.
- **No finding, message, exit status or acceptance changes.** Controls are not part of what a finding is, so every baseline entry and ignore entry that matched OBAAF-GHA-005 still matches, and a job that moves its key from the command to the proxy keeps its acceptance. The finding still cannot be cleared: `environment-restricted` is never verified by `obaaf check`. A finding that was "cannot tell" because every control was verified or could not be read becomes "new" where the agent holds the key (a job with a Harden-Runner step and a key in the agent's `env`, for one); either fails a gate unless accepted. JSON output has a fifth entry under `controls`; the text report says "it is cleared when all 5 are verified". On this repository, its 16 risky fixtures, its templates and Expectrail's files at `13e8f70`, with and without its baseline: the same findings, states and exit statuses before and after, with `key-out-of-reach` "not met" on every OBAAF-GHA-005 that lists controls.

### Reports begin with the accepted risk

With 38 findings accepted and none new, the first adopter's gate printed its per-file listing and, near the end, "38 finding(s) accepted by the baseline, 0 new". A reader of the log saw a green check and "0 new". The three reports now say first how much risk is accepted, at what severity, by whom and until when. Which findings are reported, their states and the exit status do not change, with two exceptions: a command that ended in a traceback on ASCII output, and a check that crosses midnight (the last two points of this list). The guide has [an example and what each line means](docs/checker-configuration.md#accepted-risk).

- **Text output has new first lines.** `Accepted risk: N finding(s) are accepted and do not fail the check (...)`, then one line for each owner with how many findings they accepted and the first date one of their acceptances runs out, how many were accepted by baseline entries and how many by ignore entries, and the nearest expiry date; or `Accepted risk: none.` Then `Other findings:` with the counts of new, cannot tell and fixed, and a count of errors when there are any. A baseline entry that no longer matches a finding is counted there too, since it can fail a check whose findings are all accepted. Every line the report had before is still there, below these, in the same words, with the four exceptions that follow (the fourth is the Jenkins coverage lines, further down).
- **A file's path is printed in quotes where it heads its findings, unless, with characters that do not print written as escapes, it is made only of visible ASCII characters** (letters, digits and punctuation, no space). That line starts in the first column, like the lines the checker writes in its own words, and a directory could be named `Accepted risk: none. ...` or `Baseline: 38 finding(s) accepted by the baseline, 0 new.`, with spaces or with characters that only look blank, and read as one. A path such as `.github/workflows/ci.yml` is printed as before; `.github/workflows/my build.yml` and `.github/workflows/übersicht.yml` are now in quotes.
- **A finding ignored by configuration is listed with its owner**: `ignored: RULE path:line - accepted by OWNER until DATE: REASON`, where it was `ignored: RULE path:line - REASON (until DATE)`.
- **The `obaaf baseline migrate` command the report prints for an old baseline repeats the `--config` and `--platform` the check was given**, where it said to give them "if any".
- **A warning before an acceptance expires.** Acceptances that run out within 30 days are listed as `Expiring soon:`, the soonest first, in text, in JSON (`acceptedRisk.expiringSoon`) and as a warning in SARIF. Until now nothing warned: the gate went red on the day after the date. `--expiry-warning DAYS` changes the window and `--expiry-warning 0` turns the list off. It never changes the exit status.
- **JSON output** keeps every field it had, under the same name. New: `acceptedRisk` (the numbers above, and `asOf`, the day they were counted from), placed with `summary` before the findings, and `daysLeft` in the `acceptance` of a finding when it is valid.
- **SARIF output.** The run has `properties` with `obaaf-accepted-risk` and `obaaf-summary`, and an `invocations` entry whose notifications begin with the accepted risk and carry the expiry warning, the errors, a baseline in the old format, baseline entries that no longer match, and the notes; `executionSuccessful` is `false` when something could not be read. Until now SARIF carried none of these. A result for an accepted finding has a suppression with `"status": "accepted"` and a justification that names the owner and the date (a finding ignored by configuration had a suppression with the reason and the date and no owner; one accepted by a baseline had none), and `obaaf-acceptance` in its properties. Every other result has `"suppressions": []`, which is how SARIF says "not suppressed". A result that has controls carries them in `obaaf-controls`.
- **The message of a SARIF result is longer** for a finding that is accepted, that is named by an entry that does not count, or that has controls: after the finding's own sentence it says who accepted it and until when, or why the entry does not count, and then each control with its verdict. The `message` in JSON and the text report are unchanged. GitHub's documentation lists the fields code scanning uses, and suppressions, notifications and the property bags of a run and of a result are not among them, so the message is where a reader of code scanning can see that a finding was accepted. That is from GitHub's page, read on 2026-11-12; no upload to code scanning was made to check it.

- **Jenkins coverage lines print a path, an error and a reason on one line.** A directory whose name contains a line break could put lines of its own into the text report, 0.3.0 included; such a character is now shown as an escape, as it already was everywhere else in the report.
- **A letter the output cannot show is printed as an escape.** `obaaf check` ended in a traceback when standard output was ASCII and a job, a path or an owner had a letter outside it (seen with `--lanes` and with the text report). Standard output and standard error now write such a letter as an escape, `\xf8` for `ø`, in every command; only `check` and `baseline migrate` were tried. A command that ended that way exited 1, and now exits as its findings decide.
- **Every acceptance in a report is judged on one day.** Ignore entries were judged while the check ran and baseline entries when the baseline was applied, a moment later, so a check that crossed midnight could accept one entry dated that day and refuse another. The day is now read once, while the check runs, and `obaaf check --baseline` judges the baseline on it. So when midnight falls between the two, a baseline entry gets another answer than before, in either direction: one whose last day is the day the check read is accepted, and one dated 367 days after that day is refused, where each was the other way round. `--write-baseline` and `obaaf baseline migrate` still read the clock again when they decide what to write, as before. `obaaf.checker.baseline.apply` refuses a `today` that differs from the day of a result `check` made.

What this does not do: it does not tell the reader whether the check passed (the exit status does; the report has never printed it), and the accepted-risk total is not shown by GitHub code scanning, going by the same page.

### A lane declaration that does nothing is a finding

A job is an agent job to the checker when the checker recognises its agent or when the repository declares it one, with `OBAAF_LANE` or under `lanes:`. A declaration that does nothing (`OBAAF_LANE: agnet`, a `lanes:` entry for a job that was renamed) leaves the job without the agent rules, and 0.3.0 said so only in a note at the end of the report, which changes no exit code: the gate stayed green on a job nobody was checking. It is now a finding with a rule of its own.

- **New rule, `OBAAF-CFG-001`, "Lane declaration that does nothing"**, the first of a family for the checker's own configuration. It reports the declarations 0.3.0 listed in a note as ignored: `OBAAF_LANE` set to a value that is not a lane in a job's `env`, the workflow's `env` or a Jenkinsfile (a misspelling, an expression, an empty value, or in a Jenkinsfile a value computed when the build runs; in a Jenkinsfile, where it reaches at least one step); `OBAAF_LANE` in a step's `env`, a container's or a service's, where it is not read; and a `lanes:` entry whose value is not a lane, or that names a job or Jenkins stage its file does not have, or a file that is not there. One kind of note is not a finding: an entry for a Jenkins stage that is in the file and holds no step (see "Fixed with it").
- **Two declarations that 0.3.0 said nothing about are reported too**: the variable under another spelling in a job's `env` or the workflow's `env` (`obaaf_lane`, `OBAAF-LANE`, a name with a space after it), which is read under its exact name only; and `OBAAF_LANE` in the `env` of a `parallel` group of steps. A `lanes:` key that is not text (`5:`, `true:`), which is never looked up, was listed in a note when a repository was checked; it is a finding now, also when one file is checked on its own.
- **It is reported where the declaration is written**, on its line: in the workflow or Jenkinsfile, or in the configuration file on the line of the `lanes:` entry. A declaration that reaches a job or a step through a YAML alias or a merge key is reported on the first line of that job or step. A report can therefore list `.github/obaaf.yml` among the files with findings; it is not counted among the workflow files checked.
- **Severity: high, and low where nothing can be missing.** The checker cannot know which findings are missing because of the declaration, and the agent lane has high-severity rules, so a lower severity would let a gate set to `--fail-on high` pass a job whose agent rules never ran. It is low when the declaration names `trusted` (which adds no rule even where it is read); when it is written where it is not read, or under another spelling, in a job that is in the lane it names anyway; and when it is a `lanes:` entry for a Jenkins stage that is not there and names `untrusted` or `effect`, which change nothing on a stage. The category is authority.
- **It is fixed by correcting or deleting the declaration, and it can be accepted with a baseline entry**, which carries an owner, a reason and an expiry date and names the declaration: the file it is written in, the job and step, the names of the stages a Jenkinsfile's declaration reaches, the `lanes:` key, the variable's name where that is misspelt, and the value. The line number and the wording are not part of it. Two declarations that agree in all of these are told apart only by count: each needs an entry. Two Jenkins stages with the same label (the name, with the stages it is nested in) are one stage to the checker, here as elsewhere.
- **An `ignore` entry cannot accept it, and one that names `OBAAF-CFG-001` is a configuration error** (exit 2). An `ignore` entry accepts a rule in a file, whatever the finding says. For this rule that would be every lane declaration in the file, including ones not written yet: a reviewer of this change accepted one `lanes:` entry that way, then renamed an agent job and misspelt its lane, and the check still passed.
- **The notes no longer list these declarations**, in the text report, in `notes` of the JSON report and among the notifications of the SARIF report. They are in `findings` and in SARIF `results`, so GitHub code scanning can show them. `obaaf check . --lanes` still prints them as notes on standard error, now with the file, the line and the rule: `--lanes` lists lanes and reports no findings.
- **The example configuration no longer declares anything.** `templates/github-actions/obaaf.yml.example`, which `obaaf templates install` writes as `.github/obaaf.yml`, had a `lanes:` entry for `.github/workflows/nightly.yml#package`, a file the templates do not install, and an `ignore` entry for another. Both examples are comments now. A repository that installed the templates with 0.3.0 and kept the file as it was has that `lanes:` entry, and gets one high finding for it.
- **Fixed with it:** a `lanes:` entry for a workflow or a Jenkinsfile whose own path contains `#` was cut at the first `#`, so the note said the entry named a file that was not read although the lane had been applied; the key is now matched against the files of the run, and against the files outside it. A `lanes:` entry for a Jenkins stage that holds no step the checker records (`steps { }`, or only a `script` that sets a variable) was listed as naming a stage the file does not have; a stage with a block is now a stage an entry may name, and a stage written without one (`stage 'Build'`), which holds no step, still is not. And `OBAAF_LANE: 0xFF…`, a number of more than 4,300 digits, as a value or as a `lanes:` key, ended `obaaf check` in a traceback; it is reported like any other value that is not a lane.

Not reported, as before: in a Jenkinsfile, the variable under another spelling, and an assignment (`env.OBAAF_LANE = 'agent'`), which is not read as a declaration; and a second configuration file (the checker reads the first of `.github/obaaf.yml`, `.github/obaaf.yaml` and `obaaf.yml` that exists).

What an adopter will see on upgrading:

- A repository with such a declaration and a gate at the default `--fail-on medium`, or stricter: the check fails (exit 1) where it passed, with the finding and its fix. Correcting the declaration can bring the findings it was hiding; that is the point.
- A gate at `--fail-on never`: no change in the exit code; the finding is in the report.
- A script that reads `notes`, or the "Lane declaration ignored" lines of the text report: those lines are gone from `obaaf check`. The text after "Lane declaration ignored:" on `--lanes` is worded differently.
- **Expectrail** has one: `.github/obaaf.yml` gives `.github/workflows/byo-smoke.yml#byo-smoke` the lane `probe`. It is deliberate there: the project's own audit script reads `probe` from the file as a lane of its own, and OBAAF has always ignored it. On a copy of its files at `776ddd3`, with its pinned command, the report gains exactly one finding (`OBAAF-CFG-001`, high, `.github/obaaf.yml` line 36) and loses the note; the exit code was already 1 because of its old-format baseline. When it moves its pin it can accept the finding in its baseline with an owner, a reason and a date, or declare the job `trusted` and keep its own list of probes elsewhere.

### Which events can start a job

Many rules ask which events can start a job, and a job's `if:` can rule an event out. That was decided by searching the text of the `if:` for `github.event_name == '...'`, so text that only looked like such a test removed an event, and every rule that depends on the event (OBAAF-GHA-001, 002, 007, 011, 013 and 015, one case of 012, the severity of 008 and 010, and whether a job builds pull requests) was silent or too mild for a job that does run on it. The condition is now read from its tokens. With `on: [pull_request_target, workflow_dispatch]`, each of these was read as "runs on `workflow_dispatch` only" and is now read as running on both:

- **The test inside a string**: `if: ${{ 'github.event_name == "workflow_dispatch"' != '' }}`, which is always true, and the same text as an argument of `format`.
- **A comparison of the comparison**: `if: github.event_name == 'workflow_dispatch' == false`, which is true on every event except the one named.
- **Text outside `${{ }}`**: `if: ${{ github.event_name == 'workflow_dispatch' }} && ${{ true }}`, a `${{ }}` followed by a space, and a `|` block, whose line break is outside it. GitHub reads each as a text, and a text that is not empty is true.
- **A job that needs a gate and can outrun it**: a job that `needs` a job limited to one event was limited to that event too, unless its `if:` said `always()`, `failure()`, `cancelled()`, `!success()` or `success() || ...`. `success() == false`, `!(success())` and `success()` passed to a function also let it run when the gate was skipped, and were not seen. The same reading decides whether a check in an earlier step or a needed job really stops a release or an applied proposal (OBAAF-GHA-016, 021, 022).
- **A called workflow**: with `on: workflow_call`, `if: github.event_name == 'pull_request_target'` was read as "never runs". In a called workflow `github.event_name` is the caller's event, so no test rules `workflow_call` out.

What rules an event out now: a comparison of `github.event_name` with a text, `==` or `!=`, either way round, alone or joined to other conditions by `&&` and `||`. So the reader is also more exact than it was: a condition with a negation elsewhere in it (`github.event_name == 'push' && !contains(...)`), the text first (`'push' == github.event_name`) and `github['event_name']` now narrow, where before they did not, which can remove a finding from a job that never runs on the event. A comparison with a letter outside ASCII is not read, because what GitHub's comparison makes of it has not been established. A status function still counts wherever the text has it, inside a string and outside `${{ }}` included, as before. Nothing here has been run on GitHub: it rests on GitHub's documentation of expressions and of `if:`.

### Inputs in any case

GitHub hands an action its inputs as environment variables named in upper case, so `REF:` and `ref:` under `with:` are the same input. The checker read input names exactly as written, so a rule that looks at an input did not see one spelt in another case: with `on: pull_request_target`, a checkout with `REF: ${{ github.event.pull_request.head.sha }}` was not reported by OBAAF-GHA-002, `Allow-Unsafe-PR-Checkout: true` not by OBAAF-GHA-019, and an agent job's checkout of the pull request not by OBAAF-GHA-012. The same held for the cache inputs OBAAF-GHA-006 reads and for a monitor's `egress-policy`; and `Persist-Credentials: false` was not seen, so OBAAF-GHA-011 was reported where it should not have been. Input names are now read with A to Z in either case. A step that gives the same input twice in two spellings is an error: the checker cannot tell which value GitHub uses. So is an input name with a letter outside ASCII, since what GitHub's upper-casing makes of one is not established. Found by the review of the controls above; not run on GitHub.

### Settings audit

- New command `obaaf audit`: reads the GitHub settings that workflows depend on and records them in a snapshot file (`obaaf-settings-snapshot/v0.1`). It reads rulesets and who may bypass them, the rules in force on the default branch, classic branch protection, environments and which branches may deploy to them, the names of environment, repository and organisation secrets, Actions permissions, the workflow token's default permissions, approval for fork pull requests, Actions policies, and how many accounts hold each role. The rules that judge what it read are below.
- Every setting is recorded as read, partly read, not read or not applicable. A setting that was not read is listed by name with the reason and with what GitHub's reference says a caller needs; it is never left out. An answer that does not have the documented shape is recorded as not read: a field whose absence could pass for "none" must be there. In a value, `null` means not known, a part that does not apply is left out, and a known "none" is written out. Every snapshot is checked against its schema before it is written or reported, and a value the schema refuses makes that setting not read.
- Read-only by construction: the client sends GET requests and has no other verb. A token is taken from the environment (`GH_TOKEN`, `GITHUB_TOKEN` or `--token-env NAME`), never from the command line, and is sent only to the API address the audit was started with. It is in no output, and is cut out of any answer that echoes it. With no token the audit reads what GitHub shows anyone about a public repository and asks for nothing else.
- An empty list of who may bypass a ruleset is never recorded as "nobody": GitHub shows the real list only to a caller with write access to the ruleset, and it is not established what it sends anyone else. The audit can show that someone may bypass; it cannot yet show that nobody may.
- `obaaf audit --from-snapshot FILE` reports from a saved snapshot with no network, after checking the file against a schema that covers every value. `--fail-on-unread` exits 1 when a setting that applies was not read in full. Reading nothing at all (repository not found, rate limited at the first request) exits 1, and so does any failure the command did not foresee.
- Tested from recordings written by hand from the examples in GitHub's REST reference, and from two recordings of what GitHub itself answered a caller with no token, for this repository and for the first adopter's. Run against GitHub by a workflow in this repository, with the workflow's own token and with no token: the settings GitHub shows anyone were read, and the administrative ones were refused and reported as not read. It has not been run with a token that can read the administrative settings. See [docs/settings-audit.md](docs/settings-audit.md).

### Settings rules

The settings audit read settings and judged nothing. It now applies rules to them. `obaaf audit` is still in no release.

- **Fifteen rules, `OBAAF-SET-001` to `OBAAF-SET-015`.** Twelve compare a setting with something a workflow in the repository uses or assumes: the environment a job names, the checks its jobs report, the events that start it, the secrets it reads. Three read settings only, because what they are about is what every workflow's result feeds: who may bypass a branch's rules (`004`), whether its required approvals can be given (`005`), and whether a workflow can give one (`013`; a workflow on any branch can ask for the token, so the files here decide nothing).
- **The settings behind the first adopter's six incidents each have a rule**: an environment any branch may use (`OBAAF-SET-001`), a ruleset bypass that covers whoever authors changes (`OBAAF-SET-004`), required approvals that cannot be given (`OBAAF-SET-005`), a required-checks list that leaves out jobs that run on every pull request (`OBAAF-SET-008`), an Actions policy that blocks an event a workflow uses (`OBAAF-SET-009`), and a reusable workflow passed a secret its caller cannot read (`OBAAF-SET-011`). Also: a job outsiders can start that names an environment with no reviewers (`002`), a protected secret that is also a repository or organisation secret (`003`), a required check nothing reports (`006`) or that does not report on every pull request (`007`), the `pull_request_target` change of 2026-12-02 (`010`), the default token permissions (`012`), a workflow that can give a required approval (`013`), fork pull requests (`014`) and the pinning requirement (`015`).
- **A rule answers "cannot tell" when a setting or a workflow file it needs was not read**, or is in a form it does not understand, and says what was missing. The report begins with the findings and the count of what could not be told, has one line for every rule (findings, cannot tell, no finding with what was compared, or does not apply with the reason), and never says "pass". Every rule reads at least one setting GitHub shows only to a token; with no token, five of them (`001`, `002`, `006` to `008`) can still give findings from what anyone may read.
- **The workflow files come from a clone.** They are read from the directory the command is given when it is the top level of a clone whose origin remote names the repository audited, or when the directory is named on the command line. The settings of one repository are not compared with the workflows of whichever clone the command was started in; then the twelve rules that need the files answer "cannot tell".
- **`obaaf audit` now fails on findings.** New options: `--fail-on high|medium|low|never` (default `medium`), `--fail-on-cannot-tell`, `--no-fixes`. A commit of the earlier audit exited 0 whenever the repository was read, unless `--fail-on-unread` or `--expected` failed it; pass `--fail-on never` for that. **`--format json` is now a report** (`obaaf-settings-audit/v0.1`: `summary`, `rules`, `results`, `workflows`, and the snapshot under `snapshot`), where it was the snapshot itself; `--snapshot-out` still writes the snapshot.
- **A settings finding cannot be accepted.** There is no baseline and no `ignore` for `obaaf audit`. Each finding names a change to a setting or a workflow that clears it, and a job that is meant to be advisory says so with `continue-on-error: true`. A finding someone decides to keep stays in the report and can only be kept out of the exit status with a higher `--fail-on`.
- **What it rests on.** Tested from recordings: GitHub's own answers to a caller with no token for this repository and the first adopter's, and answers written by hand for everything a token would show. The rules about Actions policies read the one form the hand-written recording has; no real policy has been seen, and GitHub's pages on them could not be re-read when the rules were written. Several sentences about what GitHub does rest on the author's knowledge and were not re-read; the guide lists them. Not run: the audit with a token that can read the administrative settings. An independent review of the first version found 24 faults in the rules by running them, most of them a "no finding" where a rule had not looked; each is fixed and pinned by a test. Its first finding is on this repository: the job `dependency-lock` runs on every pull request and is not a required check; a maintainer chose to keep it advisory, so it now has `continue-on-error: true` and the audit no longer reports it.
- A character that prints as a blank without being a space (the braille blank, the Hangul fillers) is now written as a question mark in the audit's report, like a control character: a run of them could push the rest of a name to the start of a terminal's next line.
- **Every parameter of a ruleset's pull-request rule is read or named** (flagship slice 2b.5). `OBAAF-SET-005` and `OBAAF-SET-013` used to read the count of approvals and the code-owner flag and pass over the rest in silence: the first adopter's `require_extra_approval_for_unattributed_changes: true` changed nothing in the report. The nine parameters GitHub's REST reference lists (read on 2026-11-13) are now each placed in the code, and a parameter that is not among them, or a known one in another form (a field the reference does not list included), makes `OBAAF-SET-005` "cannot tell" for its branch, and `OBAAF-SET-013` too where workflows may approve pull requests, naming it and its value, whatever the value, unless the count alone is a finding. A "cannot tell" given for another reason, and a finding by count, name it as well. A team that `required_reviewers` asks for an approval, and `require_last_push_approval` where no approval is counted (on a ruleset or a classic protection rule), are "cannot tell" too. `require_extra_approval_for_unattributed_changes` is read as GitHub's pages describe it: nothing on a ruleset that counts zero, which the rule's note now says (the first adopter's case), and one more approval than that ruleset's count for a pull request Copilot opens without a person otherwise. `OBAAF-SET-005` is now "cannot tell", where it said "no finding" or "does not apply", for a branch that requires a code owner's review and whose count alone is no finding: who the code owners are is not read. What GitHub's pages establish about each parameter is in the guide, under "The parameters of a pull-request rule".
- **Every rule type of a ruleset, and every field of classic branch protection, is read or named** (flagship slice 2b.6). The rules about a branch's requirements read two rule types, `pull_request` and `required_status_checks`, and passed over every other, and classic protection was read into a fixed form that dropped any field GitHub adds. The 25 types of GitHub's REST reference (read on 2026-11-13) are now each placed in the code; a type that is not among them makes `OBAAF-SET-005` to `OBAAF-SET-008` "cannot tell" for its branch, naming it, whatever its parameters, and `OBAAF-SET-013` too where workflows may approve pull requests (a finding by count stays a finding and names it); `OBAAF-SET-004` names it among what a bypass skips, or cannot tell where it is a ruleset's only such rule. A field of classic protection that the reference does not show (a field of an entry of its required checks included), or a known one in another form that the reader would otherwise record as not known and pass over (an object that is something else, a flag that is not true or false or has no value; some other forms make the whole setting unread), is kept in the snapshot under `other_fields`, with its value, and has the same effect; so does a parameter of a ruleset's `required_status_checks` rule, or a field of one of its checks, outside the reference, for the check rules. Changes in what the rules report: a bypass of a ruleset that only requires deployments, code quality, coverage or licence compliance is now an `OBAAF-SET-004` finding (it was passed over); `OBAAF-SET-006` is "cannot tell" for each rule that makes a merge wait for deployments, workflows, code scanning, code quality, coverage or licence compliance, and `OBAAF-SET-007` for a merge queue, because what gives those results is not compared with the workflow files; a finding of `OBAAF-SET-008` names those six (not the queue); `OBAAF-SET-005` is "cannot tell" where it said "no finding" on a branch with a rule of type `update` (only those who may bypass may push), classic push restrictions or a locked branch, and its finding says Copilot's review may count where a `copilot_code_review` rule is in force. The settings report prints a rule type it does not know in quotation marks. Messages name what could not be read: "a classic protection rule may ask for more" was said whatever the gap, a ruleset's count included. **Snapshot:** `other_fields` is written only when there is one, so earlier snapshots still load and still match; a version before this one refuses a snapshot that has it. On GitHub's recorded answers for this repository and the first adopter, the report is unchanged. The guide's section is "Rule types and classic fields the rules do not know".

### Settings drift

A setting can change without any file changing, and every real incident in the first adopter's first two days was a setting. There was no way to notice one changing.

- **`obaaf audit --expected FILE` compares the settings with a snapshot you committed** (written earlier by `--snapshot-out`) and reports every difference as a finding, `OBAAF-DRIFT-001`: one for each part that differs (a ruleset, an environment, a branch, a secret's name, a field), with each change listed as "was …, now …", "new" or "gone". The report begins with the comparison and is followed by the usual report. Exit 1 if anything differs.
- **What could not be compared fails too.** A setting, or a part of one, that one side read and the other did not is "not compared", never "no drift", and exits 1, in both directions: the committed snapshot holds it and this run could not read it (other access, a refusal, a rate limit), or this run read it and the committed snapshot did not (GitHub left it out then, or someone marked it as not read in the file). So does a comparison in which nothing was compared. Only what neither side read in full is "not covered", listed, and not a failure (of an environment both read in part, the rest is compared).
- Lists are compared without regard to their order and values as JSON, so `true` is not `1` and `null` is not `false`. Only the `settings` part is compared.
- The committed file is checked like `--from-snapshot`, and must also be of the repository audited and the same API address (checked before any request), may not give two rulesets, environments, policies or secrets one id or name, must hold data for exactly the branches it lists, and may name at most 50 branches; otherwise exit 2. Its branches are audited along with the default one. `--snapshot-out` and `--output` may not name the same file as `--expected`.
- `--format json` with `--expected` puts the comparison, with every change, under `drift` in the audit's JSON report (`obaaf-settings-audit/v0.1`, see "Settings rules" above), beside the rules' results and the live snapshot.
- The rules of "Settings rules" run in the same command. The template and this repository's job pass `--fail-on never`, so they fail on drift and not on a rule's finding; run the rules as a gate in a job of their own.
- New optional template [`templates/github-actions/optional/obaaf-settings-drift.yml`](templates/github-actions/optional/obaaf-settings-drift.yml) runs the comparison daily with the workflow's own token; its first run keeps the snapshot to commit, so no file is written by hand. `obaaf templates install` does not install it. This repository runs it as `.github/workflows/settings-drift.yml`. See [docs/settings-audit.md](docs/settings-audit.md#drift).
- Nothing changes for anyone who does not pass `--expected`, except two things found on the way: a snapshot file with a number too large to be finite (`1e999`) is refused, where it was read as infinity and could crash `--format json`; and an unusable `--from-snapshot` file is named in the error.

### Egress control

The first adopter had OBAAF-GHA-020, "agent job without an egress restriction", on all 19 of its agent jobs, and no control it could apply: OBAAF shipped none, and the checker credited none it could verify.

- **New action [`actions/egress`](actions/egress/action.yml)** runs one command with its network limited to a list of host names, on GitHub-hosted Linux runners. It runs the command under GitHub's Agent Workflow Firewall v0.29.13 (binary pinned by SHA-256, images by digest), with no `sudo`, none of the runner's environment except the variables you name, and writes limited to a scratch copy of the workspace, its own home and its own `TMPDIR`; what AWF itself lets the command write is deleted after the run, or the step fails. A probe inside the sandbox must fail to get out before the command starts. Names the proxy refused are listed in the job summary. See [docs/egress-control.md](docs/egress-control.md) for how to use it and exactly what it blocks and does not.
- **Escape tests** in `.github/workflows/egress-escape-tests.yml` try 29 ways out (unlisted hosts, addresses, other resolvers, DNS over HTTPS, raw sockets, a TLS handshake with no name, child and background processes, `sudo`, the Docker socket, data in a host name, and the runner's own programs listening in its `/tmp`) and the ways a command could leave something for a later step. Each is tried outside the sandbox first, and the verdict comes from a packet capture on the runner's external interface. They run on every change to the action and weekly.
- **A refused name no longer leaves the runner in a DNS query** (slice 2c.4). AWF's proxy looked up every name it was asked for before refusing an unlisted one, so a confined command could send data out in the names it asked for. The action now runs its own resolver on the runner for the proxy, answering only names the allow-list covers and refusing every other name on the runner. Two more escape tests ask the proxy for a name holding a label, over HTTPS and over plain HTTP, and the judge requires both names among the resolver's refusals and no query carrying the label outside the runner; two more look a name up from the command itself, which never left the runner and is now asserted; and the judge fails if any unlisted name the attempts use is seen in a DNS query. The plain HTTP attempt of 2c.2 now names the proxy: curl reads only the lower-case `http_proxy`, which AWF does not set, so it had gone direct. New outputs: `dns-refused` and `dns-log`. A name under a listed name still goes to the listed domain's DNS servers; the API host of a model key is answered exactly, not its subdomains.
- **Model keys through AWF's API proxy** (slice 2c.4). The new input `model-keys` takes `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` from the step's `env` and gives them to AWF's API proxy, never to the command, which gets a base URL pointing at the proxy and a placeholder key. The proxy reaches the provider's API host whatever `allow` says. The providers' hosted web search and fetch tools are refused by the proxy, in requests whose body it parses as JSON (by AWF's source, it forwards other bodies and WebSocket upgrades unchecked). Tested with made-up keys: each provider refused the key itself (401), neither key was in the command's environment or in the files searched, and a request with Anthropic's `web_fetch` tool was refused by the proxy (403). Not refused: remote MCP servers named in a request, and other ways of asking the provider to fetch a URL. Under `env`, model keys are still refused, now with a pointer to `model-keys`; other providers' keys are refused under both.
- **The runner's own programs in its `/tmp` are out of the command's reach** (slice 2c.6, decision D-054). AWF mounts the runner's `/tmp` into the sandbox, and a read-only mount does not stop a connection to a socket. On GitHub-hosted runners `/tmp` holds .NET diagnostic sockets, which answered a request from outside the sandbox and can make a .NET program dump its memory or load a library, and .NET debugger pipes. The action now makes every socket and pipe there that the runner's user could write unwritable for the run, and the probe fails if the command can still write one. Three new escape tests: none accepted a connection or was writable from inside.
- **Only files and directories are handed back** (slice 2c.6). After the run every symbolic link, pipe, socket and device file in the scratch directory is deleted and named in the new output `removed` (plain path characters only), so a later step that reads or uploads the copy cannot be pointed at the runner's own files. The copy loses the repository's own links too (`node_modules/.bin`, for one).
- **A workspace where a checkout kept its token is refused again** (slice 2c.6). `actions/checkout` v6 and later keep it in a file that `.git/config` includes, not in an `extraheader`, so the old check missed it. The `config` and `config.worktree` files of every repository in the workspace are now read for either, and for a remote URL with a password; the new output `refused` says `credential` when this refuses a workspace (other refused inputs leave it empty).
- **`denied` is plain text** (slice 2c.6): a refused name is taken from the request's target, not the `Host` header the command chose, and kept to the characters of a host name.
- **The listed host's answer is not required to be 200.** The escape test's request to `api.github.com` got 403 inside and outside the sandbox on one run (GitHub's limit for requests without a token); the judge now requires curl to finish (which checks the server's certificate) with any HTTP answer.
- **What it does not do:** it confines one command, not the job; data sent to a listed host is not stopped, nor data in a name under a listed name, which reaches that domain's DNS servers; with a model key, data sent to the provider is not stopped, and a provider can be asked to connect elsewhere for the agent (remote MCP servers, a URL to fetch), which nothing here refuses; IPv6 could not be tested on hosted runners, which had no IPv6 route.
- **The checker reads it, and two controls can now clear OBAAF-GHA-020** (decision D-050). Every control a job might have is read, and the best one stands:
  - **GitHub's native egress firewall** clears it when every run of the job is on `ubuntu-24.04-firewall` and `.github/egress-firewall.yaml` sets `mode: enforce`. A missing or misspelt file, `mode: log`, or a token without `contents` permission is "not met". A file the checker cannot read to the end, an `allow` entry that is not a plain host name or that is or has under it a public suffix, a workflow other workflows can call, or a job on labels the checker cannot name is "cannot tell". The policy file is read only when a repository is checked.
  - **OBAAF's egress action** clears it at a commit OBAAF lists as released, with a written allow-list that has no public suffix at or under any name (the [public suffix list](https://publicsuffix.org/) now ships in `src/obaaf/data/`, under its own licence, MPL-2.0), on GitHub-hosted `ubuntu-24.04`, with the agent as its command and no step but `actions/upload-artifact` after it or beside it. **No commit is listed yet, so today the action is "cannot tell".** Where the agent runs is read from where credentials go: a secret or `github.token` given in the workflow to another step or to the job's or workflow's `env`, `id-token: write`, a token with the `models` permission, or an agent the checker recognises in another step is "not met"; undeclared token permissions, or no credential anywhere and no agent recognised inside the action, is "cannot tell". `actions/cache` with the output or `/tmp` is "not met"; an earlier step that names `/tmp`, uses `&` as an operator, or mentions a container engine, a terminal multiplexer or a detaching command (`nohup`, `at` and others) is "cannot tell"; a process started another way is not read. A job whose only agent command is inside the action's `run` input is now an agent job.
  - **Harden-Runner is "cannot tell" at best**, because whether the repository is one its tier covers is not in the workflow. It is "not met" at a listed commit before v2.16.0, with `sudo` or containers left to the job (`disable-sudo-and-containers` not `true`), or in a container on a GitHub-hosted runner, a new case, `weak-monitor`. Its version is read from a list of its release commits that OBAAF ships, never from a tag or a comment, so a tag is "cannot tell" whatever it says.
  - **The Agent Workflow Firewall run from a script** (`awf ... --` where a command starts) is recognised, as "cannot tell", or "not met" with `--enable-dind`.
  - A cleared finding says what the control does not stop. For the action: anything sent to a listed host, and data in a name under a listed name (since slice 2c.4, a name the proxy refuses no longer leaves the runner).
- **The checker reads the action's `model-keys` and `env` inputs** (slice 2c.5, decision D-052). Until now any credential given to the action's own step made the control "cannot tell". Each one is now placed as the action reads its inputs:
  - a key set in the step's `env` under a name `model-keys` names goes to AWF's API proxy, which the command can use and cannot read. The finding shows the provider's API host after the allow-list, as `api.anthropic.com (through AWF's API proxy)`, because the proxy reaches it whatever `allow` says, so the host is one of the finding's facts: an acceptance of a job that already used `model-keys` before this change stops matching after it;
  - a credential under a name `env` names, or written in `run`, is passed to the command. So is one of the step's `env` written into `run` through the `env` context (`${{ env.ANTHROPIC_API_KEY }}`, `${{ format('{0}', env.KEY) }}`), which GitHub fills with the step's own `env` when it writes the inputs, whatever `model-keys` says; the whole `env` context written into `run` (`${{ toJSON(env) }}`) is "cannot tell";
  - one under a name neither input names, and written into no input, reaches neither.

  A key given to the proxy and a credential passed to the command are both evidence that the agent is the confined command, and **neither stops the control from being verified**: the network is limited as the allow-list (and the provider's host) says. Beside a cleared finding the report now names the credentials passed to the command, the provider channel for each model key (anything the command sends the provider, and whatever the provider is asked to fetch or connect to: remote MCP servers, URLs), and the job's log and artifacts, which no network limit stops. Some names the action would refuse are "not met": a model key, a GitHub token or another name AWF withholds under `env`, something that is not a variable name, a name `model-keys` does not take (another provider, another case), a model key no `env` sets. Others that also make it refuse at run time are not read (a name under `env` set nowhere, an empty key, a value with a line break, a reserved name such as `PATH`), and such a step is judged as if the action ran. `env` or `model-keys` computed when the job runs or not written as text, a computed step `env` holding a credential, two names that differ only in case or a name not written as text (`true:`) holding a credential, a credential (or an `env` value holding one) in another input, or a credential anywhere else in the step is "cannot tell". OBAAF-GHA-005's fourth control says, whatever its verdict, where each credential it could place goes, what it could not place and what would make the action refuse; a key out of the command's reach does not clear OBAAF-GHA-005. A credential passed to the command can make a listed host act for it (a token that can start a workflow, for one), and the report says so.
- **Only commits at or after the floor may be listed as released commits of the action** (`egress_action_floor` in `src/obaaf/data/detection.yaml`): a test refuses an older one against the repository's history, and CI's test job now fetches the full history to check it. None is listed yet. The floor was the merge of slice 2c.4 (`f0bfbd7`); since slice 2c.6 it is that slice's last change to the action (`7c1bded`), so no commit without the fixes for the runner's sockets and the copy's links can be listed.
- **Installing an agent's CLI before the action is not running it** (slice 2c.8, decision D-053). The checker's agent patterns match a package's name, so `npm install -g @anthropic-ai/claude-code` in a step before the action made the control "not met", and the natural way to use the action with Claude Code could not be cleared. A step before the action whose script does nothing but install `@anthropic-ai/claude-code`, `@openai/codex` or `@google/gemini-cli` globally (`npm install -g`, `pnpm add -g`, `yarn global add`, `bun add -g`; a version and a few options that take no value allowed; `sudo` only with `-E`, `-H` or `-n`) and print the CLI's version is no longer taken for running the agent there. The step may have no `env` or `working-directory`, and the job and workflow no `env` and no `defaults.run`, since each can make the same words run something else. Not read, because the workflow does not show it: what earlier steps write to `GITHUB_ENV`, `GITHUB_PATH` or the home directory, and package-manager configuration in the working directory (`pnpm`, `yarn`, `bun`). A step that names such a package in any other form (another command, an option with a value, a local install, `$`, quotes, a pipe, `&`, a glob, a backslash, a trailing comment, another shell, an action) is now "cannot tell" where it was "not met"; one that also runs an agent (`claude -p`, `npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx`, a path into the package such as `…/claude-code/cli.js`), or any such step after the action, is still an agent outside. Which jobs are agent jobs does not change. On a scratch adaptation of the first adopter's `byo-live.yml`, its install step as written (`sudo npm install -g @anthropic-ai/claude-code` and `claude --version`) is now read as an install.
- **GitHub's native egress firewall**: beside a cleared finding the report now says that what a step prints to the job's log or saves as an artifact is not blocked, as well as what is sent to an allowed host.
- The sentence "GitHub-hosted runners have no native egress allow-list" is corrected in the rule's text, R7, the agent template and its README, and `docs/inference-proxy.md`.
- On this repository, its 16 risky fixtures and Expectrail's CI files at `0509d73`: the same findings, word for word, before and after.

### Release policy

- This repository's own release policy now sets `agents.since` to the commit of release 0.3.0, the first release that passed the full `obaaf verify release` gate. Once this is on `main`, a release checks commits from OBAAF's agent lane (a record trailer, a record file, or the effect lane's identity) from that commit to the released one, and no longer over the whole history (D-025). There were none in the history up to 0.3.0. Commits written with an AI assistant and merged through ordinary review are not what this check counts. Nothing changes for adopters.
- **Between releases, the version on `main` is a development number** (`0.4.0.dev0` on the way to 0.4.0). `main` said 0.3.0 while holding changes 0.3.0 does not have, so `obaaf --version` and the version written into reports, records and baselines from an install of `main` named a release they did not come from. In SARIF, `semanticVersion` is the pre-release form, `0.4.0-dev.0`. The generated documents and the self-assessment form say when a development version generated them, instead of saying it is in use with pilot teams. That includes the self-assessment form on the website, which is built from `main`: from now on it names the development version, except while `main` sits on the commit of a release. Nothing changes in a release that is installed.
- **The release workflow refuses a version that is not the tag, and a development version bound anywhere but TestPyPI.** A tag `v0.4.0` on a commit whose package still says `0.4.0.dev0` now stops in the first job, before anything is signed or uploaded, and so does any run of a development version whose repository-url input is not TestPyPI's address. Forgetting to set the version before tagging used to be harmless, because PyPI would have refused a second 0.3.0. With a development number on `main` it would have uploaded one, and PyPI never accepts the same file name twice.

### Dependencies

- **The `keys` extra now requires cryptography 46.0.5 or later** (it was 42). Earlier versions do not check that a binary-curve (SECT) public key lies in the curve's prime-order subgroup ([CVE-2026-26007](https://osv.dev/GHSA-r6ph-v2qm-q3c2)). OBAAF loads the keys a release policy names with `load_pem_public_key` and does not restrict their curve, so with those versions a policy that named such a key could accept a forged signature. The keys are chosen by the policy's owner, so this is hygiene rather than a way in for an outsider. An environment that holds cryptography between 42 and 46.0.4 must upgrade it to install the extra.
- The pinned install used by the `setup-obaaf` action moves to setuptools 84.2.1 and cryptography 50.0.2, the versions Dependabot's pull requests #42 and #40 asked for, with the hash lock regenerated from PyPI. PyYAML stays at 6.0.3 (#43). The floors for setuptools (`>=77`, the first that reads the SPDX licence expression) and PyYAML (`>=6.0`, past every published fix) do not change.

### Fixed

- **`runs-on: ${{ matrix.os || 'ubuntu-latest' }}` is resolved** (slice 2d.7, issue #141, decision D-056). The checker resolved only `${{ matrix.x }}`, so this form, used by `pallets/flask` among others, was a medium OBAAF-GHA-013 on every job a pull request can start, even where every label the matrix gives is GitHub-hosted. The expression is now read from its tokens: `matrix.x` and `matrix.x || 'label'` are resolved against a matrix written out in the file, and the default counts wherever a row may lack the value or give an empty one. A key of the matrix that is not plain ASCII text (`True:`, a computed key, `ſ`), a value YAML 1.2 could read as a number or false (`0o0`), or a YAML merge key (`<<`) in the file leaves the labels unresolved. So OBAAF-GHA-013 can appear where it did not, in the plain `${{ matrix.os }}` form too: the old reading resolved two cases wrongly, a matrix key computed when the job runs (`os: ${{ fromJSON(...) }}`) beside `include` entries that set it (only the `include` values were read) and an `include` written as one expression or holding an entry that is one (it was passed over); and a key that is not plain ASCII text, a value YAML 1.2 could read as other than text (quoted `'0'` included), or a merge key anywhere in the file, even in an unrelated step, now leaves the labels unresolved. A label that ends in a line break is no longer taken for a hosted one. On `pallets/flask`'s workflows at `49943b5`: one medium finding fewer. On this repository, its fixtures and templates, and Expectrail's files: no change.
- **Signature keys outside the documented set are refused when they are loaded.** OBAAF documents ECDSA P-256 and P-384, Ed25519 and RSA for `signing: keys` and `obaaf dsse assemble`, but took a key on any elliptic curve (verifying P-521 with SHA-384, for example) and loaded a DSA, Ed448 or X25519 key only to fail when verifying. Each is now refused with an error that names the file and the kind of key, by `obaaf dsse assemble` (exit 1) and by `obaaf verify release` alike. A binary-curve key, which the cryptography library cannot load since its version 47, ended `obaaf dsse assemble`, `obaaf verify release` and `obaaf verify agent-run` in a traceback; it is the same error now. P-256 is verified with SHA-256 and P-384 with SHA-384, as before.
- `obaaf check --write-baseline` ended in a Python traceback when a job id contained a lone surrogate character (a name YAML can spell and Unicode cannot encode). The baseline is now written, as valid UTF-8, and read back.
- Two more tracebacks, both in 0.3.0: `--write-baseline` to a directory that does not exist, and a v0.1 baseline whose `rule` or `severity` is a list. Each is now an error message and exit code 2. So is `obaaf check --output` to a path that cannot be written.
- An `ignore` entry dated with spaces around a quoted date (`until: " 2027-01-31 "`) is read as that date; 0.3.0 refused it.

## [0.3.0] - 2026-11-12

**Upgrading from 0.2.0: a gate that passed can fail without the workflows having changed.** Several changes make the checker report what it missed before. The largest are "Lanes" and "Expressions" below. Among the smaller ones: a repository that has a Jenkinsfile now has it checked along with its workflows, and an agent command line with options before the prompt flag, such as `claude --model x -p ...`, now makes a job an agent job (both under "Jenkins (advisory)"); an unknown setting in `.github/obaaf.yml` is refused ("Protected secrets"); and a path with nothing to check is an error, not a pass ("Checker"). Baselines are new in this release. One written from `main` before the release can go stale under "Lanes" or "Expressions" and has to be regenerated with `--write-baseline`.

### Lanes

A job now gets the rules of every lane it belongs to. Before, a job had exactly one lane, chosen in a fixed order (agent, effect, release, untrusted), so a job that did two things was checked for one of them. An independent reviewer found the first two cases on 2026-11-11; the rest are the same class, found while fixing it and in a second review of the fix.

- **A job that runs an agent and publishes** was checked as an agent job only: the release rules (OBAAF-GHA-006, 014, 015, 016, 017) did not run on it. It is now in both lanes.
- **A job declared an agent job that also publishes** was checked as a release job only, and the declaration was dropped: no OBAAF-GHA-003, 005 or 020. The same held for any declared lane on a job the checker had already placed in another. A declaration now adds a lane and never replaces one.
- **A declaration could remove a finding.** Declaring a pull request job `release` or `effect` moved it out of the untrusted lane and dropped OBAAF-GHA-011. So did adding an upload step. A job that runs only for pull requests (`pull_request`, `merge_group`) is now in the untrusted lane whatever else it is.
- **A job that uses a release environment and can be started by a pull request or another untrusted event** was not a release job: an environment whose name says release, production, publish, deploy or a store made a job a release job only when no untrusted trigger could start it, which is the case OBAAF-GHA-015 exists for. With `on: pull_request_target` and `environment: production` the job was shown as `trusted (default)`. The environment now decides on its own. Because more jobs are now judged by the name, one kind of name is no longer taken for a release environment: a name in which `non` or `pre` does not follow a letter a to z (case ignored) and stands before `prod` with at most one of `-`, `_`, `.` or a space between: `nonprod`, `aws-non-prod`, `pre-production`. A push job with such an environment got the release rules before and does not now. `canon-prod` and `AppNonProd` are still release environments, because there `non` follows a letter. Every other name is matched as it was, anywhere in the name and in any case.
- **An agent started from a repository script** was detected only in jobs with no other lane. It is now detected in any job.
- **Two declarations for one job.** A lane in `.github/obaaf.yml` hid the job's own `OBAAF_LANE`, a per-job entry hid a per-file entry, and a job's `OBAAF_LANE` hid the workflow's. All of them now count.
- **A declaration that did nothing was ignored without a word.** Case and surrounding space no longer matter (`OBAAF_LANE: Agent` is `agent`, in a workflow, in `lanes:` and for a Jenkins stage). These are now listed in the report's notes: a value that is not a lane (a misspelling, an expression, an empty value) in a workflow, a Jenkinsfile or `lanes:`; `OBAAF_LANE` in a step's `env`, a container's or a service's, where a workflow does not read it; for a file the run reads, a `lanes:` entry that names a job or Jenkins stage the file does not have; and, when a repository is checked, a `lanes:` entry for a file that is not there. An entry for a file outside the run (another file when one file is checked, a Jenkinsfile when only workflows are checked) is not looked at. Notes do not change the exit code.
- **A Jenkins stage's declarations hid each other.** A `lanes:` entry for a stage replaced the stage's own `OBAAF_LANE`, and a stage's `OBAAF_LANE` replaced the pipeline's, so `lanes: {Jenkinsfile#Ship: trusted}` on a stage declared `release` removed OBAAF-JEN-005 and OBAAF-JEN-012. Every `agent` and `release` declaration that reaches a step now counts, as in a workflow; on a Jenkins stage the other lanes change nothing. A `lanes:` entry for an outer stage now also reaches the stages nested in it, and an entry for the file (`Jenkinsfile`), which did nothing, reaches every stage. A declared stage now also covers a step whose code is not in the file (a shared-library step) unless the step is in a `post`, `catch` or `finally` block, and a stage declared `release` covers the `sshPublisher` and `ftpPublisher` steps, which the guide told adopters to declare and the checker then ignored; before, a declaration reached only shell steps.
- **OBAAF-JEN-012 could be reported at medium when a step published with no check at all.** It is reported once for a Jenkinsfile, and it went to the first publishing step that lacked a full check. When that step had a provenance check, the finding was medium and a later step that nothing checked was not mentioned. It now goes to the first step with no check, and to a step with a provenance check only when there is none.
- **One workflow checked with the repository's configuration** (`obaaf check .github/workflows/ci.yml --config .github/obaaf.yml`) lost its `lanes:` entries, because the checker called the file `ci.yml` and the configuration calls it `.github/workflows/ci.yml`. Both names now match.
- **A note could be silenced.** The note about a job whose name suggests agent work was printed only for jobs in no lane, so declaring `untrusted` removed it. It is now printed for any such job that is not in the agent lane, and reads "are not in the agent lane".
- **`lanes:` that is not a mapping.** `lanes: 5` and `lanes: true` stopped the checker with a Python traceback, and a list gave an error that did not name the setting. Each is now a configuration error that says `lanes` must be a mapping. An empty value still declares nothing. A configuration file that is not valid YAML was a traceback as well, and is now a configuration error.
- **A step name that contains a line break** could make one line of `--lanes` or of the text report look like two, the second of them invented. Text taken from the files checked is now printed on one line, with the line break shown as `\n`. The JSON and SARIF output carry the text unchanged.

What an adopter will see on upgrading:

- New findings on jobs that are in more than one lane, and on jobs that use a release environment and can be started by a pull request or another untrusted event. `--lanes` names the extra lanes: `agent (…; also release: …)`.
- For a job whose lanes did not change, the same findings with the same messages, so baseline entries still match. Two things are kept as they were for that reason: a job that is declared into a lane it is also inferred into shows the declaration as the reason, and OBAAF-GHA-017, which is reported once per workflow, stays on the first publishing job that is not also an agent or effect job when there is one.
- The exception: a declaration that used to be ignored is read now. That is one written in another case or with spaces (`OBAAF_LANE: Agent`), one that stood behind another declaration for the same job (only the first was read, even when its value was not a lane), and a `lanes:` entry for a workflow checked on its own. If the job was already in the lane it names, the job's agent findings quote the declaration as the reason (`set by OBAAF_LANE`) where they quoted what the job runs, or gain or lose the words about `trusted`, and a baseline entry for them has to be regenerated.
- In a Jenkinsfile, more advisory findings where more than one declaration reaches a stage or a declared stage calls a shared-library step. OBAAF-JEN-005 and OBAAF-JEN-012 are reported once for a file and can move to another stage when that happens. OBAAF-JEN-012 can also move, and rise from medium to high, in a Jenkinsfile with no declaration at all: when one step publishes after a provenance check and a later one publishes with no check, the finding is now about the later one.
- New notes for declarations that do nothing. Notes appear in the text and JSON output and with `--lanes`; the SARIF output does not carry notes yet.

The Jenkins analyser still decides what a stage does step by step, with its own code. What changed there is how it reads declarations and which step OBAAF-JEN-012 is reported on.

### Expressions

Several spellings that no rule reported are now reported. They were found by reading the checker and by an independent review of the first fix. None has been run on GitHub.

- **Secrets.** Secret references are read from an expression's tokens, not matched as text. `secrets.*`, and any other use of the `secrets` context that is not one literal name (for example `contains(secrets, 'x')`), counts as every secret (OBAAF-GHA-001, 005, 024). A secret referenced anywhere in a job is found, including in `outputs`; before, only `env`, `with`, `secrets`, `container`, `services` and `steps` were read.
- **Where an expression ends.** An expression is no longer cut short at a `}}` inside a string, as in `${{ format('}}{0}', secrets.KEY) }}`, which hid whatever followed from every rule that reads expressions.
- **OBAAF-GHA-010.** The rule keeps its text patterns and adds a second pass over the expression's tokens. It now follows a wildcard or computed index (`github.event.*.title`, `github.event.issue.*`, `github.event[inputs.kind].body`), a property of a group or of a function's result (`(github.event.issue).title`, `toJSON(github.event.issue || 1)`), `${{ env.NAME }}` when NAME is set from an outsider-written field, directly, through other env values or through the matrix, and `${{ matrix.x }}` when the job's matrix is built from such a field. It does not follow values set at run time (`GITHUB_ENV`), values passed between jobs or into reusable workflows and composite actions, scripts other than `run` and `actions/github-script`, an `env:` written as one expression that itself reads env or matrix values, or a `with:` written as one expression.
- **Files the checker cannot read are errors, which fail the check:** an expression nested more than 64 levels deep, a text with too many unfinished expressions, a file too large to read in the memory available, a value only an explicit YAML tag produces (`!!set`, `!!pairs`, `!!omap`, `!!binary`, or text under `!!null`), a job or step that is not a mapping, and a file containing U+0085, U+2028 or U+2029 (YAML readers disagree on whether these end a line).

Other changes in behaviour: any string given for `secrets:` on a reusable-workflow call counts as `inherit`; `secrets["KEY"]` (double quotes, which GitHub rejects) and an index that is not a name count as every secret; an expression with no closing `}}` is read to the end of its text; text inside a string, such as `format('secrets.KEY')`, is no longer mistaken for a secret reference (OBAAF-GHA-010 still reports a field named inside a string, as before). Because `obaaf attest` records the secrets a job can read and `obaaf verify release` checks that record, a job that names a secret only in a place that was not read before is now recorded as holding it. Findings for workflows that use none of these spellings are unchanged (checked on this repository's workflows, fixtures and templates, and on Expectrail).

### Protected secrets

- GHA-024 hardening, after an independent review: a computed secret index (`secrets[format(...)]`, `secrets[matrix.k]`) counts as every secret for all rules; the `secrets` context matches in any case; overlapping `protected_secrets` entries all apply; environment names compare case-insensitively; reusable-workflow callers get advice they can follow, and `secrets: inherit` is no longer reported; globs need three letters or digits; unknown configuration settings are refused. The published test set shows the configuration a fixture is checked with.
- New rule OBAAF-GHA-024. List secrets under `protected_secrets` in `.github/obaaf.yml` (optionally with the environment that must hold each one), and the checker reports every job that uses one without declaring that environment. Anyone with write access can read a repository secret by pushing a workflow on a branch; the GitHub settings guide now says so and describes how to keep such secrets in an environment limited to the default branch. Test fixtures can carry a configuration in an `# obaaf-config:` line.

### Baselines

- `obaaf check --write-baseline FILE` records the current findings; `obaaf check --baseline FILE` reports them but fails only on new findings, or on baseline entries that no longer match (so fixes are locked in). Findings match without line numbers. JSON output marks `baselined` and lists stale entries, and SARIF output sets `baselineState`, only when a baseline is used. See docs/checker-configuration.md#baseline. Each entry's fingerprint is recomputed from its visible fields on load (a mismatch is refused), stale entries follow the `--fail-on` threshold and category, and expired ignores are never written into a baseline.

### Fixed

- A negated status function in a job's `if:` (for example `!cancelled() && github.event_name == 'workflow_dispatch'`) no longer stops the checker from narrowing the job's triggers by its event test. Any other negation still does.

### Jenkins (advisory)

- `obaaf check` now reads Jenkinsfiles (`Jenkinsfile`, `Jenkinsfile.<name>`, `Jenkinsfile-<name>`, `<name>.jenkinsfile`, and globs in `jenkins.files`) alongside workflows, or alone with `--platform jenkins`. A syntax-only parser reads the Groovy without running any of it (D-034). Fifteen rules, OBAAF-JEN-001 to OBAAF-JEN-015, cover credentials that change requests or an agent can reach, builds on the controller and shared agents, agent stages that push or publish, pipeline code from unapproved revisions, approvals, host access from containers and pods, agent egress, unpinned images, libraries and agent CLIs, Groovy-interpolated untrusted text and secrets, moving artifact references, publishing after a failed check, missing release verification, signing keys, and webhook tokens in the file. Each maps to profile requirements and agent controls in the catalog.
- Every Jenkinsfile gets a coverage result per rule (pass, fail, ignored, unknown, not applicable) in text and JSON output, with the reason for each unknown. Controller settings and shared-library code are reported as unknown, never as a pass, and the report states that exit 0 is not a conformance decision (D-036). See [docs/jenkins.md](docs/jenkins.md).
- `templates/jenkins/obaaf-audit.Jenkinsfile` runs the audit as a Jenkins job.
- New configuration: `jenkins.files`, `jenkins.exclude` and `agents.steps`; lane overrides and ignore entries take a Jenkins stage as `file#stage` and `job: <stage>`. `--lanes` lists Jenkins stages.
- OBAAF-REPO-001 also covers Jenkinsfiles, and is retitled "CI definition files have no code owner".
- Release lane on Jenkins (D-037): `templates/jenkins/obaaf-release-build.Jenkinsfile` builds a protected tag with no credentials in a project that builds only tags; `obaaf-release-publish.Jenkinsfile`, a separate job read from the default branch with no parameters, finds the tag build that started it, signs SLSA provenance and the build record through a key service, verifies, waits for a named approver and verifies again before uploading. A `signing: keys` policy example is included.
- `obaaf dsse prepare` and `obaaf dsse assemble` sign records with a key that stays in a key service: `prepare` writes the bytes (or digest) to sign, `assemble` accepts the service's signature (raw or base64, DER or r||s), checks it against the public key and writes the DSSE envelope.
- `obaaf verify release` reads Jenkins evidence: `--approvals` takes the publishing build's JSON from the controller, `--release-run` the JSON of the build that produced the artifacts. The publishing build must have been started by that build alone, which must be the tag build of `release.jenkins_project` and have checked out the release commit. Whoever started either build cannot approve; with `release.approvers` set, only listed people count (on GitHub too). Replays, stage restarts, builds started by hand, unclassified causes and incomplete evidence are blocked.
- Records written in a Jenkins build name it in `run` (controller, job, build URL), marked as self-reported, and the build record says its source came from the Jenkins release job.
- Agent CLI patterns accept options before the prompt flag or subcommand (`claude --model x -p ...`, `codex -m o3 exec`). This also applies to workflows, where such jobs were previously left out of the agent lane.
