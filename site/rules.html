obaaf check

The rules are in the catalogue, not on this page.

A finding is a report of a pattern in a file. It does not certify the repository. Release 0.3.0 reads GitHub Actions workflows, Jenkinsfiles, CODEOWNERS, and agent instruction files, plus its own configuration file, .github/obaaf.yml, and a baseline file if you give one. Jenkins results in that release are advisory. Exit 0 on a Jenkinsfile is not a conformance decision, because controller settings are not in the file.

Use the catalogue that matches the command you run. This page does not copy either file, so a later commit cannot leave a second copy behind.

Release 0.3.0

The catalogue at tag v0.3.0. Read it when you run obaaf 0.3.0. The file's opening still says the project is in active adoption with pilot teams. That is not what the evidence supports. One documented adopter is a project of one of the authors.

The development version

The catalogue on main. This site is built from the main branch, so that is the catalogue of the code this site calls the development version. obaaf docs build --check, run in the project's CI, keeps that file in step with the checker. It can gain rules and change wording. A rule id, a fix sentence, or a clearing rule there is not a promise about what obaaf 0.3.0 prints.

obaaf audit is a command in the development version. It reads the repository settings its token, or no token, lets it see, and compares them with what the workflows assume. It names every setting it could not read, and a rule that needed one answers "cannot tell" instead of passing. By default those answers do not change its exit status; --fail-on-cannot-tell and --fail-on-unread make them fail it. It is not a command in release 0.3.0. obaaf --help in that release lists assess, check, snapshot, manifest, proposal, attest, record, dsse, verify, templates, docs, and catalog.

Where release 0.3.0 and the development version differ

These are facts about release 0.3.0, which does not change, and about the development version as run and read on 2026-11-14. A later change to the development version is written in its catalogue.

OBAAF-GHA-020

OBAAF-GHA-020 is the finding that a job running an AI agent has no restriction on where it can connect. Release 0.3.0 does not report it for an agent job that has a step-security/harden-runner step with egress-policy: block and no if. On 2026-11-14, obaaf 0.3.0 checked a job whose step used that action at v2.12.0 with that setting: the report had no OBAAF-GHA-020. Two OBAAF-GHA-008 findings remained, because the actions were not pinned to a commit. The same step behind an if still produced OBAAF-GHA-020. That release does not look at the action's version, at disable-sudo-and-containers, or at whether the step is first.

A further file pinned the same action to the commit below, which the development checker lists as v2.16.0, made it the job's first step, set disable-sudo-and-containers to true, and pinned the agent action as well. obaaf 0.3.0 printed no findings and exited 0.

The development version, the same day, still reported OBAAF-GHA-020 on the v2.12.0 file. The control is not met, because sudo and containers are kept. On the pinned file it says it cannot tell, because whether the repository is public, or covered by a paid tier, is not in the workflow. In obaaf check, cannot tell is not a pass: the finding stays and that file exited 1. The development version also needs the step to be the job's first; as a later step the control is not met.

The development checker clears OBAAF-GHA-020 for GitHub's native egress firewall only when all of these hold: obaaf check is run on the repository, not on a single file; every run of the job, matrix runs included, is on ubuntu-24.04-firewall; .github/egress-firewall.yaml sets mode: enforce and allows only plain host names, none of which is a public suffix or has one under it; the job's token has contents permission; the job calls no reusable workflow; and no other workflow can call this one. That clearing is not in release 0.3.0, and the development checker still reports OBAAF-GHA-013 (medium) for that runner label, as if it were self-hosted, so a medium gate still fails. OBAAF's own egress action, also development only, stays "cannot tell" until a released commit of it is listed, and none is listed.

OBAAF-GHA-005

OBAAF-GHA-005 is the finding that a secret, such as a model provider's key, is available to a job that runs an AI agent. Release 0.3.0's catalogue says to keep the model credential in an inference proxy outside the job and pass no secrets to the agent job. OBAAF ships no inference proxy.

The development version lists five controls on the finding and clears it only when it has verified all five. One of them is that the secrets are stored only in an environment that only protected branches may use. That is a repository setting obaaf check does not read, so the development version cannot clear OBAAF-GHA-005 either; the finding can only be accepted. A model key given to the Agent Workflow Firewall's API proxy through the egress action's model-keys input can satisfy another of the five, but only at a released commit of the action, and none is listed.

An ignore entry

Release 0.3.0 ignores a finding when the entry has a rule, a path, a reason, and an until date that has not passed. It does not require an owner. The development version still requires the reason and the date, and it does not ignore the finding unless the entry also names an owner, written as @user, @org/team or an e-mail address, the reason has enough letters or digits, and the date is no more than 366 days ahead.

obaaf attest

In release 0.3.0 and the development version, obaaf attest writes the predicate of an in-toto statement, and the whole statement with --statement-out. It signs neither, and it signs no agent run. A separate configured job can sign a statement through GitHub's attestation action.
