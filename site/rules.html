obaaf check

The rules are in the catalogue, not on this page.

A finding is a report of a pattern in a file. It does not certify the repository. Release 0.3.0 reads GitHub Actions workflows, Jenkinsfiles, CODEOWNERS, and agent instruction files, plus its own configuration file, .github/obaaf.yml, and a baseline file if you give one. Jenkins results in that release are advisory. Exit 0 on a Jenkinsfile is not a conformance decision, because controller settings are not in the file.

Use the catalogue that matches the command you run. This page does not copy either file, so a later commit cannot leave a second copy behind.

Release 0.3.0

The catalogue at tag v0.3.0. Read it when you run obaaf 0.3.0. The file's opening still says the project is in active adoption with pilot teams. That is not what the evidence supports. One documented adopter is a project of one of the authors.

The development version

The catalogue on main. The published site is built from main. For a preview built from another revision, consult spec/checker-rules.md at that revision. obaaf docs build --check, run in the project's CI, keeps that file in step with the checker. It can gain rules and change wording. A rule id, a fix sentence, or a clearing rule there is not a promise about what obaaf 0.3.0 prints.

obaaf audit is a command in the development version. It reads the repository settings its token, or no token, lets it see, and compares them with what the workflows assume. It names every setting it could not read, and a rule that needed one answers "cannot tell" instead of passing. By default those answers do not change its exit status; --fail-on-cannot-tell and --fail-on-unread make them fail it. It is not a command in release 0.3.0. obaaf --help in that release lists assess, check, snapshot, manifest, proposal, attest, record, dsse, verify, templates, docs, and catalog.

Where release 0.3.0 and the development version differ

The comparisons for OBAAF-GHA-020 and OBAAF-GHA-005 describe release 0.3.0 and the development version as run and read on 2026-11-14. Files of the same kind, written again and checked on 2026-11-17, gave the same results with the development version of that day. A later change to the development version is written in its catalogue.

OBAAF-GHA-020

OBAAF-GHA-020 reports when the checker cannot verify a supported network restriction for an agent job. Release 0.3.0 does not report it for an agent job that has a step-security/harden-runner step with egress-policy: block and no if. On 2026-11-14, obaaf 0.3.0 checked a job whose step used that action at v2.12.0 with that setting: the report had no OBAAF-GHA-020. Two OBAAF-GHA-008 findings remained, because the actions were not pinned to a commit. The same step behind an if still produced OBAAF-GHA-020. That release does not look at the action's version, at disable-sudo-and-containers, or at whether the step is first.

A further file pinned the same action to the commit below, which the development checker lists as v2.16.0, made it the job's first step, set disable-sudo-and-containers to true, and pinned the agent action as well. obaaf 0.3.0 printed no findings and exited 0.

The development version, the same day, still reported OBAAF-GHA-020 on the v2.12.0 file. The control is not met, because sudo and containers are kept. On the pinned file it says it cannot tell, because whether the repository is public, or covered by a paid tier, is not in the workflow. In obaaf check, cannot tell is not a pass: the finding stays. OBAAF-GHA-020 is low, so with --fail-on low that file exited 1; at the default threshold, medium, it exits 0 with the finding printed. The development version also needs the step to be the job's first; as a later step the control is not met.

The development checker clears OBAAF-GHA-020 for GitHub's native egress firewall only when all of these hold: obaaf check is run on the repository, not on a single file; every run of the job, matrix runs included, has ubuntu-24.04-firewall as its only runner label; the policy file is named exactly .github/egress-firewall.yaml, is YAML the checker can read, and has no key but mode, allow and no-default-urls; it sets mode: enforce and allows only plain host names, none of which is a public suffix or has one under it; the job's token has contents permission; the job calls no reusable workflow; and no other workflow can call this one. That clearing is not in release 0.3.0. The development checker, like release 0.3.0, takes that label for a GitHub-hosted runner, so OBAAF-GHA-013 does not report it. OBAAF's own egress action, also development only, stays "cannot tell" until a released commit of it is listed, and none is listed.

OBAAF-GHA-025

OBAAF-GHA-025 is development only, added on 2026-11-18. It is the finding that a job running an AI agent installs or runs a tool at a version that can change. One case is a script downloaded while the job runs and given to a shell, such as curl -fsSL https://example.com/install.sh | bash, whatever the script installs. The other is an agent CLI the catalogue names, installed or run by a package manager without an exact version, or updated. One example is npm install -g @anthropic-ai/claude-code. Both are high. A step whose scripts are too long for the checker to read is medium. Only agent jobs are read. On the same two workflows, release 0.3.0 reports neither case.

OBAAF-GHA-026

OBAAF-GHA-026 is development only, added on 2026-11-19. It is the finding that a step gives an AI agent's action a setting the tool's own documentation warns about. A finding that matches a literal value quotes that documentation and names the file, commit and lines it was read from. It knows eleven settings, of six actions. For openai/codex-action, safety-strategy: unsafe and allow-users: "*" are high, and safety-strategy: read-only is medium. For anthropics/claude-code-action, allowed_non_write_users: "*" is high. Any other nonempty literal value of that input, allowed_bots: "*" and show_full_output: true are medium, and so is show_full_output: true on anthropics/claude-code-base-action. An empty allowed_non_write_users gives no finding. The cited allowed_bots warning concerns public repositories; the checker reads the input without checking repository visibility. Since a later change the same day, gemini_debug: true on google-github-actions/run-gemini-cli, qwen_debug: true on QwenLM/qwen-code-action (read as GitHub's fromJSON reads it, so '"true"' counts) and enable-uv-cache: true or auto on OpenHands/extensions/plugins/pr-review are medium.

For an input it cannot resolve, such as an expression, the checker reports a medium finding explaining what it cannot determine. This case has no documentation quotation. An unaccepted finding fails the default medium gate. Release 0.3.0 has no such rule.

Since 2026-11-19 it also reads command-line options a tool's own files warn about, where a step runs the tool or in claude_args and codex-args: Claude Code's --dangerously-skip-permissions, --allow-dangerously-skip-permissions and --permission-mode bypassPermissions and Codex's --dangerously-bypass-approvals-and-sandbox or --yolo are high; Codex's --dangerously-bypass-hook-trust and Gemini CLI's --yolo, -y, --y, --approval-mode yolo and --approvalMode yolo are medium. Where a step names the tool and runs it in a way the checker cannot read (a variable outside quotes, an expression or xargs in the command, a command it cannot name, another shell), it reports a medium "cannot tell" finding. A quoted variable such as "$PROMPT" is read as one word that is not an option. Since a later change the same day it also reads, as high, Qwen Code's --yolo, -y and --approval-mode yolo, Kilo Code's --auto and its hidden --yolo and --dangerously-skip-permissions, Cline's --yolo, -y, --zen and --auto-approve with any value but false, GitHub Copilot CLI's --allow-all-tools, --allow-all and --yolo, and OpenHands' --always-approve, --yolo and --headless and any beginning of them; and, as medium, Qwen Code's --insecure, Copilot CLI's --show-secrets, --trust-folder, --share-gist and --share, Continue's cn --auto, OpenCode's --hostname 0.0.0.0 and goose's --dangerously-unauthenticated; PR-Agent's --config-branch given $GITHUB_HEAD_REF is high. For the other eleven agent tools it knows, their own files at the commits read warn about no setting or option, or could not be read, and the data says which. A dangerous mode a tool runs in by default, with no option, is not reported. Because AWS's Copilot CLI and pressly's goose share those programs' names, a copilot or goose command it cannot read is not "cannot tell" where the step runs only that other tool's own commands.

OBAAF-GHA-005

OBAAF-GHA-005 is the finding that a secret, such as a model provider's key, is available to a job that runs an AI agent. Release 0.3.0's catalogue says to keep the model credential in an inference proxy outside the job and pass no secrets to the agent job. OBAAF ships no inference proxy.

When the job receives named secrets, the development version lists five controls on the finding and clears it only when it has verified all five. A job that only declares an environment gets the finding with no controls listed, and it cannot be cleared. One of the five controls is that the secrets are stored only in an environment that only protected branches may use. The development checker can verify that setting using obaaf check --settings FILE with complete observations from the checked repository, taken within the last 30 days. A model key given to the Agent Workflow Firewall's API proxy through the egress action's model-keys input can satisfy another of the five, but only at a released commit of the action, and none is listed.

An ignore entry

Release 0.3.0 ignores a finding when the entry has a rule, a path, a reason, and an until date that has not passed. It does not require an owner. The development version still requires the reason and the date, and it does not ignore the finding unless the entry also names an owner, written as @user, @org/team or an e-mail address, the reason has enough letters or digits, and the date is no more than 366 days ahead.

The same in both

In release 0.3.0 and the development version, obaaf attest writes the predicate of an in-toto statement, and the whole statement with --statement-out. It signs neither, and it signs no agent run. A separate configured job can sign a statement through GitHub's attestation action.
