OBAAF-GHA-001 Secret available to a workflow started by untrusted input

high

The workflow can be started by people without write access (for example through pull_request_target, issue_comment, issues or workflow_run) and a job references a repository or organization secret. Anyone who can steer that job, through its code or through text it reads, can read the secret. Jobs behind an environment are reported at medium severity, because environment secrets are released only after required reviewers approve. Pull-request workflows are reported at low severity: forks receive no secrets, but branches pushed by anyone with write access do.

Fix, as the catalogue states it: Move the step that needs the secret into a workflow that runs only after review (for example on a push to a protected branch, or behind an environment with required reviewers), and pass only data, never secrets, out of the untrusted workflow.

OBAAF-GHA-002 Untrusted code checked out in a privileged workflow

high

A pull_request_target, workflow_run or comment-triggered workflow checks out or fetches the code of a pull request. These workflows run with the base repository's token, secrets and cache scope, so building or running that code hands them to its author (a "pwn request").

Fix, as the catalogue states it: Build pull-request code in a pull_request workflow, which runs with a read-only token and no secrets. If a privileged step must follow, pass results through artifacts and treat them as untrusted data.

OBAAF-GHA-003 Agent job can write

high

A job that runs an AI agent holds write permissions, or does not declare its permissions and so may inherit write access. Text the agent reads can then direct those writes.

Fix, as the catalogue states it: Give the agent job `permissions: {contents: read}` (plus other read permissions it needs) and apply its proposals in a separate effect job behind a protected environment.

OBAAF-GHA-004 Agent job can request cloud credentials

high

A job that runs an AI agent has `id-token: write`, so the agent can request an OIDC token and exchange it for cloud or signing credentials.

Fix, as the catalogue states it: Remove `id-token: write` from the agent job. Sign the agent-run record in a separate job that the agent cannot influence.

OBAAF-GHA-005 Secret available to an agent job

high

Release 0.3.0 says: A job that runs an AI agent references a secret, inherits secrets, or uses an environment whose secrets it receives. Prompt injection can make the agent disclose any secret in its environment. Its fix text says to keep the model credential in an inference proxy outside the job and pass no secrets to the agent job. OBAAF ships no inference proxy. The next paragraph is this checkout, not 0.3.0.

This checkout, not release 0.3.0. A job that runs an AI agent references a secret, inherits secrets, or uses an environment whose secrets it receives. Prompt injection can make the agent disclose any secret in its environment. When the job references secrets, the finding lists five controls and is cleared only when the checker has verified all five. (1) Each secret is listed in `protected_secrets` and the job declares the environment named there. (2) The secrets are stored only in that environment and only protected branches may use it; this is a repository setting, which `obaaf check` does not read, so it is reported as "cannot tell". (3) No pull request, issue or comment can start the job, no checkout step names a pull request's ref, and no expression or `if:` in the job reads a field someone without write access can write. (4) A control the checker recognises limits the job's network access to an allow-list (as OBAAF-GHA-020 reads it). (5) The agent's command cannot read any of the job's secrets (`GITHUB_TOKEN` aside, which OBAAF-GHA-003 covers), because a key the agent can read can leave in the job's log or an artifact whatever the network allows: verified only where every secret of the job is set in the `env` of steps that use OBAAF's egress action, at a commit OBAAF lists as released, on the runner it was tested on, and goes to AWF's API proxy (named in `model-keys`) or to nothing the command runs; it says where each credential given to such a step goes, whatever its verdict. A secret passed to the command, given to another step or to the job's or the workflow's `env`, a job with no confined command (GitHub's native firewall holds no key), or an agent or a credential in a step that can run before or beside the step that holds the key is "not met". That step holds the key outside the sandbox, so what could reach it there is "cannot tell": a variable bash or the loader obeys (`BASH_ENV`, `PATH`, `LD_PRELOAD` and others), or `ACTIONS_ALLOW_UNSECURE_COMMANDS`, in an `env`, a step before or beside it whose script names `GITHUB_ENV` or `GITHUB_PATH` or may leave a process running (read from its words), a parallel step, and service containers given volumes or options. The second control is never verified by `obaaf check`, so today the finding can be accepted and cannot be cleared. Not read for the third control: what a script, an action other than `actions/checkout` or the agent itself fetches while the job runs, apart from a few commands the checker knows (`gh pr checkout`, `git fetch` of `pull/N/head`); a workflow that starts this one with `workflow_dispatch` and passes on text an outsider wrote; a value handed over through `needs.*.outputs`; and the callers of a reusable workflow, which are reported as "cannot tell".

Fix, as the catalogue states it: Either keep the model credential in an inference proxy outside the job (see docs/inference-proxy.md) and pass no secrets to the agent job, or, where the finding lists its controls, make all five hold: list each secret in `protected_secrets` with its environment and declare that environment on the job; keep the secrets only in that environment and limit it to protected branches; start the job only from `push`, `workflow_dispatch`, `schedule` or `release`, with no pull-request checkout; and run the agent's command under OBAAF's egress action with its host names in `allow` and an Anthropic or OpenAI key in `model-keys`, set in that step's `env` and nowhere else in the job, so that the network is limited and the command never holds the key. Until the checker can verify all five, accept the finding with an owner, a reason and an expiry date.

OBAAF-GHA-006 Release job can read a shared cache

high

A release job restores a GitHub Actions cache, directly or through a setup action that caches by default, and its `cache-mode` does not forbid it. Caches can be written by other workflows on the same branch or the default branch, so a poisoned entry would reach the release build. A release job with no cache step but no `cache-mode: none` is reported at low severity.

Fix, as the catalogue states it: Set `cache-mode: none` on release jobs and remove cache restore steps, or regenerate derived data inside the release lane.

OBAAF-GHA-007 Low-trust workflow can write the default-branch cache

high

The workflow runs on triggers that outsiders can start (for example pull_request_target, issue_comment or workflow_run) and declares a write-capable `cache-mode`. Code or an agent steered by an outsider could then poison caches that release workflows restore, as in the Clinejection case. GitHub gives some of these triggers read-only cache access by default (pull_request_target, issue_comment, and workflow_run runs that follow a pull request from a fork), but not every case, and this rule cannot see the default a job gets when it declares nothing.

Fix, as the catalogue states it: Remove the write-capable `cache-mode`, or set `cache-mode: none` (or `read`) explicitly for jobs in this workflow.

OBAAF-GHA-009 Token permissions not declared

medium

Neither the workflow nor the job declares `permissions`, so the job token gets the repository or organization default, which may include write access.

Fix, as the catalogue states it: Declare `permissions: {}` or `permissions: {contents: read}` at the top of the workflow and grant each job only what it needs.

OBAAF-GHA-010 Untrusted event text expanded inside a script

high

A script interpolates text that an outsider controls, such as an issue title, a pull-request title or body, a branch name or a commit message, with `${{ }}`: written plainly, with index syntax, in any letter case, through `toJSON` or another function given the event object, through a group (`(github.event.issue).title`), or through a wildcard or computed index (`github.event.*.title`, `github.event[inputs.kind].body`). `${{ env.NAME }}` counts when the step, job or workflow sets NAME from one of these fields, directly or through other env values or the matrix, and `${{ matrix.x }}` when the job's matrix is built from one. Not followed: values set while the job runs, values passed between jobs or into reusable workflows and composite actions, scripts other than `run` and `actions/github-script`, an `env:` written as one expression that itself reads env or matrix values, and a `with:` written as one expression. The text becomes part of the script before the shell runs, so it can run commands. This is how the Nx compromise began.

Fix, as the catalogue states it: Pass the value through an environment variable (`env: TITLE: ${{ github.event.issue.title }}`) and use it quoted in the script (`"$TITLE"`), so the shell treats it as data.

OBAAF-GHA-011 Checkout leaves the job token on disk

medium

In an agent job or a job started by untrusted input, actions/checkout persists the job token for later git commands. Any code or agent that runs later in the job can read it.

Fix, as the catalogue states it: Add `persist-credentials: false` to the checkout step.

OBAAF-GHA-012 Agent reads instructions from the change under review

high

The agent job checks out the pull request's version of the repository, so instruction files, rules files and MCP configuration come from the change being reviewed. The change can then rewrite what the agent obeys during its own run.

Fix, as the catalogue states it: Check out the protected base branch for instruction files (for example `ref: ${{ github.event.pull_request.base.sha }}`), and give the agent the pull request's changes only as data captured by the snapshot step.

OBAAF-GHA-013 Self-hosted runner used for untrusted work

high

A job that pull requests, outside events or an agent can drive runs on a self-hosted runner. Unless the runner is ephemeral, code from that job can persist on the host and tamper with later builds, as in the PyTorch case. Runner labels that are not standard GitHub-hosted labels (custom labels, larger runners, unresolved inputs) are reported at medium, because the checker cannot tell whether they are self-hosted. An unresolved runtime expression explicitly mentioning both a standard hosted label and self-hosted alternatives is informational: it needs review, but does not prove an unsafe runner was selected. Literal matrices that include a self-hosted pool still produce a high finding. If you verify the selector and runner lifecycle, record the evidence in a job-scoped, expiring `ignore` entry (see the checker configuration guide). A declaration is not verification of runtime isolation.

Fix, as the catalogue states it: Run untrusted and agent jobs on GitHub-hosted or ephemeral runners, and keep persistent self-hosted runners for the release lane only.

OBAAF-GHA-014 Release job not behind a protected environment

medium

A release job that uploads or publishes does not reference an environment, so no person has to approve it and its credentials are not held back until approval.

Fix, as the catalogue states it: Reference an environment (for example `environment: release`) configured with required reviewers, self-review prevention and no administrator bypass.

OBAAF-GHA-015 Release workflow started by untrusted input

high

A release workflow can be started by pull requests, comments, issues or another workflow's run, so unreviewed changes or outsiders can reach the release lane.

Fix, as the catalogue states it: Start release workflows only from pushes to protected branches or tags, published releases, or manual dispatch by maintainers.

OBAAF-GHA-016 Upload without a provenance check

high

A release job uploads or publishes artifacts without first verifying their provenance, approvals and agent-run records in an earlier step of the same job or in a job it depends on.

OBAAF-GHA-017 Release builds without provenance

OBAAF-GHA-018 Signing key available to build steps

OBAAF-GHA-021 Agent output applied without verifying its record

high

A job applies agent output with write permissions, but neither it nor a job it needs references an environment, so no person other than the requester has to approve the change.

OBAAF-GHA-023 Template placeholder left in a workflow

The workflow still contains an OBAAF template placeholder (OBAAF_OWNER or an all-zero commit SHA), so it will not run as intended.

OBAAF-GHA-024 Protected secret used outside its environment

high

The checker configuration lists the secret under protected_secrets, but a job references it without declaring the environment that holds it. Anyone with write access can read every repository secret by pushing a branch with a new workflow, so a secret worth protecting must live only in an environment whose deployment branches are limited to the default branch (or that requires reviewers), and every job that uses it must declare that environment. A job that can take every secret counts as using each protected secret: that is any use of the secrets context other than one literal name, such as toJSON(secrets), secrets.* or secrets[...] with a computed index. A job that calls a reusable workflow cannot declare an environment, so passing it a protected secret is reported; secrets: inherit is not, because it never passes an environment's secrets. Every matching entry applies, so a looser pattern cannot relax a stricter one. An environment named by an expression cannot be confirmed and is reported at medium severity. The checker cannot see where the secret is stored or the environment's branch rule; check both in the repository settings.

Fix, as the catalogue states it: Keep the secret only in the environment named in protected_secrets, limit that environment's deployment branches to the default branch, delete any repository or organization copy, and add `environment: <name>` to every job that uses it (see docs/github-settings.md#secrets).

OBAAF-CFG-001 Lane declaration that does nothing

high Not in release 0.3.0.

A lane declaration puts a job in a lane (untrusted, agent, effect, release) so that the lane's rules apply to it. This one changes nothing, so the job, stage or file it was written for gets none of the rules it was meant to add, and every other finding on that job can be missing without the report showing it. The cases: OBAAF_LANE, in a job's env, the workflow's env or a Jenkinsfile, set to a value that is not a lane (a misspelling such as `agnet`, an expression, an empty value, or in a Jenkinsfile a value computed when the build runs; in a Jenkinsfile, where the declaration reaches at least one step); the variable under another spelling in a job's env or the workflow's env (`obaaf_lane`, `OBAAF-LANE`); OBAAF_LANE set in a step's env, a container's or a service's, where the checker does not read it; and an entry under `lanes:` in the checker configuration whose value is not a lane, or that names a job or Jenkins stage its file does not have, or a file that is not there. The finding is reported where the declaration is written: in the workflow or Jenkinsfile, or in the checker configuration. It is high because the checker cannot know which findings are missing: the agent lane alone has high-severity rules. It is low when nothing can be missing: the declaration names `trusted`, which adds no rule even where it is read; it is written where it is not read, or under another spelling, in a job that is in the lane it names anyway; or it is an entry for a Jenkins stage that is not there and names `untrusted` or `effect`, which change nothing on a stage. An entry for a file outside the run (another file when one file is checked, a Jenkinsfile when only workflows are checked) is not looked at. An ignore entry cannot accept this finding, because it would accept every such declaration in the file it names; a baseline entry, which names the one declaration and its value, can.

Fix, as the catalogue states it: Correct the declaration or delete it. The value is one of untrusted, agent, effect, release or trusted, and the variable is spelled OBAAF_LANE. In a workflow it belongs in the job's env or the workflow's env; in a Jenkinsfile, in an environment block or a withEnv around the steps. A `lanes:` entry names a workflow's file and job as `obaaf check . --lanes` prints them, and a Jenkinsfile's stage by the file and the stage's own name (`Jenkinsfile#Ship`). Run `obaaf check . --lanes` afterwards and confirm the lane (see docs/checker-configuration.md#a-declaration-that-does-nothing).

OBAAF-JEN-001 Credentials available to change-request code or an AI agent

high

A credential binding (withCredentials, an environment credentials() entry, sshagent, or a wrapper step that takes a credentialsId) surrounds build steps that a change request can reach, or an AI agent. The steps run the change's own code, so its author can read the credential even when Jenkins takes the Jenkinsfile from a trusted branch; an agent can be told to disclose it. Stages that run only for change requests and agent stages are high; stages that nothing in the Jenkinsfile keeps away from change requests are medium, because whether the job builds pull requests is job configuration. Conditions the checker cannot evaluate are reported as unknown.

Fix, as the catalogue states it: Bind credentials only in stages that change requests cannot reach (for example `when { branch 'main' }` or `when { not { changeRequest() } }`, and better in a separate job that builds only protected branches), and never around an agent. Keep the model credential in an inference proxy outside the agent's workload.

OBAAF-JEN-002 Build steps on the controller or on agents shared with privileged work

high

A stage runs on the built-in node (label `built-in` or `master`), where build code can read $JENKINS_HOME and the keys that decrypt every stored credential; or one persistent agent label serves both work that change requests reach and a stage that holds credentials or publishes, so code from a change request can tamper with the later privileged build. Steps on the controller that change requests or an agent can steer are high; others are medium. `agent any` and computed labels are reported as unknown, because which agents exist is controller configuration.

Fix, as the catalogue states it: Set the built-in node's executors to 0 and run builds on agents. Give change-request and agent work ephemeral agents (a Kubernetes pod or a fresh container per build) and keep persistent agents with privileged labels for protected-branch and release work only.

OBAAF-JEN-003 AI agent stage can push, start jobs or publish

high

A stage that runs an AI agent also pushes to the repository, starts another job with the build step, or publishes, in the same workspace. What the agent wrote or was told then reaches the effect without review. Builds started with the build step run as SYSTEM unless build authorization is configured, so job permissions shown to people do not limit them.

Fix, as the catalogue states it: Keep the agent stage inert: let it write a proposal (a patch or bundle) as an artifact, and apply it in a separate job that verifies the agent-run record and the proposal (`obaaf verify agent-run`, `obaaf proposal check`) behind an input step with a named submitter.

OBAAF-JEN-004 Pipeline code from an unapproved revision

high

The pipeline loads code that the Jenkinsfile's reviewers did not approve: a shared library at a version taken from a branch name, parameter or other run-time value (a trusted global library runs outside the Groovy sandbox), or Groovy loaded from the workspace with `load` or evaluated from a file in a stage that change requests reach. For a change request the workspace holds the change's own files. Library trust, version overrides and Replay permission are controller configuration and are reported as unknown.

Fix, as the catalogue states it: Pin libraries to a reviewed commit (`@Library('lib@<40-character SHA>')`) and disallow version overrides for privileged jobs. Read pipeline code with `readTrusted` and `evaluate`, or move it into a pinned library, instead of `load` from the workspace. Restrict Run/Replay on jobs that hold credentials.

OBAAF-JEN-005 Release without an approval by a named person

medium

An input step sets no submitter, so any user with Build permission on the job can approve it, including the person who started the build; or the pipeline publishes with no input step before the publish. Whether approvers are independent of the requester, and whether an approval is bound to the exact artifacts, is reported as unknown.

Fix, as the catalogue states it: Put an input step with `submitter` set to a release group before the publish, keep the requester out of that group, and bind the approval to artifact digests (for example with `obaaf verify release`).

OBAAF-JEN-006 Build container or pod can reach the host

high

A docker or Kubernetes agent runs privileged, mounts the Docker socket or host paths, shares the host's network, PID or IPC namespace, or adds powerful capabilities. Code in the container can then take over the host and every build on it. Agents that run change-request code or an AI agent are high; others are medium. Pod templates defined on the controller (inheritFrom) and pod files outside the checkout are reported as unknown.

Fix, as the catalogue states it: Remove the privileged settings. Build images with a rootless builder (for example BuildKit rootless or Kaniko) instead of the host's Docker socket, and run untrusted and agent work in pods without host mounts, host namespaces or extra capabilities, enforced by an admission policy.

OBAAF-JEN-009 Untrusted text interpolated into a command

high

A sh, bat or powershell step builds its script with Groovy interpolation (`"${...}"`) or concatenation of text that others control: a change request's title, source branch or author name (high), build parameters (medium), or branch and tag names (low), directly or through a variable assigned from them, or commit text read with git log. The value becomes part of the command before the shell runs. Parameters passed to other jobs from such values are reported at medium.

Fix, as the catalogue states it: Use single-quoted Groovy strings and let the shell expand the value: `sh 'echo "$CHANGE_TITLE"'`, with the value in the environment (it already is for CHANGE_* and parameters, or set it with withEnv).

OBAAF-JEN-010 Artifact from another build used by a moving reference

high

A pipeline that publishes copies artifacts from another job by a selector that moves (the default last successful build, last completed, latest saved, a permalink or a workspace) and does not check their digests before publishing, so a different build's output can be published. High when the same stage publishes.

Fix, as the catalogue states it: Copy from a specific build number recorded with the approval, and check the artifacts' sha256 digests against the signed build record (`obaaf verify release`) before publishing.

OBAAF-JEN-011 Publishing can run after a failed or skipped check

high

A publish step sits in a post condition that runs after failure (always, failure, unstable, unsuccessful, changed, regression, aborted, cleanup) or in a Scripted catch or finally block, or a check before the publish ignores its own failure (catchError, warnError, returnStatus, `|| ...`). The publish can then run after verification failed or was skipped.

Fix, as the catalogue states it: Publish only in steps that run after every check succeeded (in a later stage, or in post { success }), and let a failed check stop the build.

OBAAF-JEN-012 Publish without a provenance check

high

The pipeline publishes without first verifying provenance, approvals and agent-run records in an earlier step whose failure stops the build. A provenance-only check such as `cosign verify-attestation` is reported at medium.

Fix, as the catalogue states it: Run `obaaf verify release` in a step before the publish, without catchError, warnError, returnStatus or `|| true`, so a failure stops the build.

OBAAF-JEN-013 Secret interpolated into a command

medium

A sh, bat or powershell step puts a bound secret into its script with Groovy interpolation. The secret then appears in the command line, where other processes on the agent can read it, and escaping it breaks easily. The Jenkins documentation warns against this.

Fix, as the catalogue states it: Reference the secret as a shell variable inside a single-quoted Groovy string, for example `sh 'curl -u "$USER:$TOKEN" ...'`.

OBAAF-JEN-014 Signing key available to build steps

high

A credential binding whose ID or variable names signing material (a code-signing certificate, keystore or private key), or a command that imports a key, makes the key readable by every step in its scope. High when the stage also publishes.

Fix, as the catalogue states it: Sign through a key service or HSM-backed signing service called by a dedicated signing stage or job, so no build step can read the private key.

OBAAF-JEN-015 Webhook trigger token written in the Jenkinsfile

high

A webhook trigger (for example GenericTrigger) has its token written in the Jenkinsfile. The token alone authorizes a request, so anyone who can read the repository can start the job and choose every value the trigger reads from the request, and the Generic Webhook Trigger plugin runs token-started builds as SYSTEM. High when the pipeline holds credentials, publishes or runs an AI agent.

Fix, as the catalogue states it: Take the token from a Jenkins credential (`tokenCredentialId`), rotate the exposed one, and verify the sender with the plugin's HMAC whitelist so forged payloads are rejected.

OBAAF-REPO-001 CI definition files have no code owner

medium

No CODEOWNERS rule covers the workflow files or Jenkinsfiles, so a change to how the project builds, releases or runs agents does not need an owner's review.

Fix, as the catalogue states it: Add CODEOWNERS rules for `/.github/workflows/` and every Jenkinsfile, and require code-owner review on protected branches (see templates/github-actions/CODEOWNERS.example).

OBAAF-REPO-002 Agent instruction files have no code owner

medium

The repository contains files that steer AI agents (for example AGENTS.md, CLAUDE.md, rules files or MCP configuration) that no CODEOWNERS rule covers.

Fix, as the catalogue states it: Add CODEOWNERS rules for every agent instruction file and require code-owner review on protected branches.

OBAAF-INS-001 Hidden characters in an agent instruction file

high

An agent instruction or configuration file contains invisible or direction-changing Unicode characters. Reviewers cannot see them, but agents read them, which was the vector in the Rules File Backdoor case.

OBAAF-GHA-008 Action or container not pinned to a full digest

medium

A third-party action, reusable workflow or container image is referenced by a tag or branch, which its publisher, or anyone who compromises the publisher, can move. Release, effect and agent jobs are reported at high severity. Ordinary jobs with explicitly limited token permissions, no secrets and no privileged outside trigger are reported at low severity. This checkout, not release 0.3.0. Nothing the checker can verify limits the agent job's network access. The finding is reported for every agent job, with the one control that clears it, and it is cleared only when the checker read that control from the workflow and the repository and every condition that makes it hold. Two controls can be verified: GitHub's native egress firewall (the job runs on `ubuntu-24.04-firewall` and `.github/egress-firewall.yaml` sets `mode: enforce`), which covers the whole job from outside the runner; and OBAAF's egress action (`actions/egress`) at a commit OBAAF lists as released, with a plain allow-list with no public suffix at or under a name, the agent as its command (no other step and no `env` of the job is given a credential, and the job cannot request OIDC tokens) and no step but `actions/upload-artifact` after it. Each credential given to the action's step is placed as the action reads its inputs: a model key named in `model-keys` goes to AWF's API proxy, whose provider host is then shown after the allow-list, and one named in `env` or written in `run` (also through `${{ env.KEY }}`) is passed to the command; a name the action refuses in a way the checker reads is "not met", and a credential it cannot place is "cannot tell". OBAAF lists no released commit of the action yet, and lists only commits at or after the last change flagship slice 2c.6 made to it. Harden-Runner is "cannot tell" at best, because the repository's tier is not in the workflow, and "not met" at a listed release before v2.16.0 or with `sudo` and containers left to the job; its version is read only from a commit OBAAF lists. The Agent Workflow Firewall run from a script is "cannot tell". A policy declared in `OBAAF_EGRESS`, or a control behind a condition, is reported too, so it is not mistaken for enforcement. A baseline entry that accepts "cannot tell" is for the workflow file as it stood, byte for byte. A cleared finding still says what the control does not stop.

Fix, as the catalogue states it: Run the agent job on GitHub's native egress firewall (`runs-on: ubuntu-24.04-firewall` with a `.github/egress-firewall.yaml` in `enforce` mode) where the repository can use it, or wrap the agent's command in OBAAF's egress action with the host names it needs, or use GitHub Agentic Workflows for a new agent workflow. Under OBAAF's action, give an Anthropic or OpenAI key in `model-keys` rather than passing a key to the command in `env`, so that the command never holds it. Ephemeral self-hosted runners behind a network policy also limit egress, but outside what the checker reads: record them with an ignore entry that names an owner, a reason and an expiry date.

OBAAF-JEN-007 AI agent stage without an egress restriction

low

Nothing in the Jenkinsfile limits the network access of a stage that runs an AI agent, and Jenkins has no egress control of its own. A policy declared in `OBAAF_EGRESS` is reported too, so a declaration is not mistaken for enforcement.

Fix, as the catalogue states it: Run the agent in a Kubernetes pod in a namespace whose NetworkPolicy allows only the inference proxy, with no route to the controller, cloud metadata or the cluster API. When the network enforces it outside the Jenkinsfile, record that with an expiring ignore entry.

OBAAF-JEN-008 Image, library or agent CLI not pinned

medium

A container image is referenced by a tag instead of a sha256 digest, a shared library is loaded at its default version or at a branch or tag, or an agent CLI is installed without a fixed version. Whoever controls the tag, branch or registry entry then chooses the code that runs. References used by agent or publishing stages are high; stages with credentials are medium; others are low.

Fix, as the catalogue states it: Pin images to `@sha256:` digests, libraries to a full commit SHA, and agent CLIs to an exact version (for example `npm install -g @anthropic-ai/claude-code@1.2.3`), and update the pins through reviewed changes.
