obaaf check

The rules are in the catalogue, not on this page.

A finding is a report of a pattern in a file. It does not certify the repository. Release 0.3.0 reads GitHub Actions workflows, Jenkinsfiles, CODEOWNERS, and agent instruction files. Jenkins results in that release are advisory. Exit 0 on a Jenkinsfile is not a conformance decision, because controller settings are not in the file.

Use the catalogue that matches the command you run. This page does not copy either file, so a later commit cannot leave a second copy behind.

Release 0.3.0

The catalogue at tag v0.3.0. That tag does not move. Read it when you run obaaf 0.3.0. The file's opening still says the project is in active adoption with pilot teams. That is not what the evidence supports. One documented adopter is a project of one of the authors.

The development version

The catalogue on main. obaaf docs build --check keeps that file in step with the checker. It can gain rules and change wording. A rule id, a fix sentence, or a clearing rule there is not a promise about what obaaf 0.3.0 prints.

obaaf audit is a command in the development version. It reads repository settings it can see and compares them with the workflows. What it cannot read is "cannot tell", and cannot tell is not a pass. It is not a command in release 0.3.0. obaaf --help in that release lists assess, check, snapshot, manifest, proposal, attest, record, dsse, verify, templates, docs, and catalog.

Where release 0.3.0 and the development version differ

These are facts about release 0.3.0, which does not change, and about the development version as run and read on 2026-11-14. The development catalogue on main is where a later change is written down.

OBAAF-GHA-020

Release 0.3.0 does not report OBAAF-GHA-020 for an agent job that has a step-security/harden-runner step with egress-policy: block and no if. On 2026-11-14, obaaf 0.3.0 checked a job whose step used that action at v2.12.0 with that setting: the report had no OBAAF-GHA-020. Two OBAAF-GHA-008 findings remained, because the actions were not pinned to a commit. The same step behind an if still produced OBAAF-GHA-020. That release does not look at the action's version, at disable-sudo-and-containers, or at whether the step is first.

A further file pinned the same action to the commit below, which the development checker lists as v2.16.0, set disable-sudo-and-containers to true, and pinned the agent action as well. obaaf 0.3.0 printed no findings and exited 0.

The development version, the same day, still reported OBAAF-GHA-020 on the v2.12.0 file. The control is not met, because sudo and containers are kept. On the pinned file it says it cannot tell, because whether the repository is public, or covered by a paid tier, is not in the workflow. Cannot tell is not a pass.

The development checker is written to clear OBAAF-GHA-020 when the job runs on ubuntu-24.04-firewall and .github/egress-firewall.yaml sets mode: enforce, with a token that can read the file. That clearing is not in release 0.3.0. OBAAF's own egress action stays "cannot tell" until a released commit of it is listed, and none is listed. A model key placed behind AWF's API proxy does not clear OBAAF-GHA-005. OBAAF ships no inference proxy. OBAAF-GHA-005 still cannot be cleared.

OBAAF-GHA-005

Release 0.3.0's catalogue says to keep the model credential in an inference proxy outside the job and pass no secrets to the agent job. OBAAF ships no inference proxy.

An ignore entry

Release 0.3.0 ignores a finding when the entry has a rule, a path, a reason, and an until date that has not passed. It does not require an owner. The development version still requires the reason and the date, and it does not ignore the finding unless the entry also names an owner and the reason has enough letters or digits.

obaaf attest writes an in-toto statement. It does not sign that statement, and it signs no agent run. A separate configured job can sign a statement through GitHub's attestation action.
