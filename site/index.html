01 / THE FRAMEWORK

More than a checklist.

OBAAF is a specification and a working command-line toolchain for build-pipeline and AI-agent assurance.

A 34-question assessment gives a team its tier and a ranked plan. A checker inspects GitHub Actions workflows, code-ownership coverage, and agent instruction files. Signing and verification tools produce and check cryptographic records of every build and every agent run. Reference pipeline templates put the architecture into practice.

Know the scope

The checker does not scan application source code for vulnerabilities. A passing check is not a security certification. The framework is a public draft.

02 / THE TOOLCHAIN

Four commands,
one small package.

obaaf assess

A 34-question self-assessment returns your tier and a ranked list of fixes. Runs locally; answers never leave your machine.

obaaf check

Lints GitHub Actions workflows against the R1–R8 controls for the risky settings behind real supply-chain attacks. Text, JSON, or SARIF.

obaaf attest

Writes a signed in-toto record of each agent run (inputs, authority, outputs) through GitHub's keyless Sigstore. No long-lived key.

obaaf verify

Blocks a release, or an agent-authored change, unless its provenance, approvals, and signed records all check out.

A small, auditable Python package with few dependencies. It runs locally. Your answers and code stay on your machine. See the full CLI and schemas on GitHub.

03 / THE DUAL LANE

Let agents propose.
Keep the authority.

The dilemma that stalls AI adoption in CI: how do you let an agent write code without giving it push access? OBAAF splits the work into lanes the platform itself enforces. The agent runs at the trust level of the text that steered it: read-only, no secrets, no way to write. Its only output is a proposal. A separate, deterministic job applies it, under a different identity, only after a person who is not the requester approves.

Each lane is a separate job with its own identity, so the CI platform enforces the boundary independently of the agent. The agent lane holds a read-only token, no secrets, and no ability to request OIDC tokens; its egress is meant to reach only an inference proxy. The attestation step signs the agent-run record in a job the agent cannot influence. Integrity rises only through certified endorsement: an approval by someone other than the requester, then an ordinary reviewed merge. Read the R1–R8 spec ↗

05 / A CHECK IN PRACTICE

The build passed.
The workflow needed a fix.

A limited demonstration on a Netflix clone shows why application checks and configuration checks serve different purposes.

A version tag can move to different code. OBAAF flags this action because it is not pinned to an exact revision.

Pinning selects exact code; it does not prove that code is safe. Both reports include one documented exception for the trusted auditor's private-access key, expiring January 9, 2027. This was not a full framework or studio validation.

06 / WHEN AGENTS JOIN THE PIPELINE

Eight controls
for agent authority.

The core principle: adding text to an agent's context must never add authority. The eight controls (R1–R8) make that enforceable. Installing the checker does not automatically enforce them all; some need platform settings and the reference templates.

R1 Record where inputs come from

Label inputs by trust and preserve the exact snapshot an agent reads.

R2 Match permissions to input trust

Public content must not give an agent access to secrets or protected changes.

R3 Give each run a temporary identity

Use narrowly scoped credentials for each invocation, separate from human accounts.

R4 Separate proposals from changes

A separate process checks and applies proposals after the required approval.

R5 Protect agent instruction files

Review instructions and load them from the protected base branch.

R6 Verify tools and models

Pin tool dependencies to immutable revisions and check provenance where available.

R7 Isolate runs and restrict network access

Use fresh environments and control shared state and outbound connections.

R8 Keep signed records of agent runs

Bind inputs, authority, outputs, and approvals to verifiable run records.

07 / YOUR ADOPTION PATH

A first project.
A manageable plan.

Organize the work around people.

  1. Complete the self-assessment with your team.
  2. Choose a few achievable improvements and assign owners.
  3. Ask an engineer to pilot the checker on one repository.
  4. Agree which findings should block merges and how exceptions are reviewed.
  5. Reassess after 90 days, using updated evidence.

Start with a local check.

Install the CLI and run the checker on one repository; both read your code locally:

pip install git+https://github.com/Obaaf/OBAAF
obaaf check path/to/project --fail-on medium

Review findings locally, pilot CI, then make the agreed audit status required before merging. For the agent and release lanes, install the pinned templates and set up the environments. Private access needs credentials kept away from untrusted PR code.

OBAAF does not currently offer a managed onboarding service. It is free and open; adopt each component on its own.

08 / RESEARCH & STANDARDS

Built on the record,
not on claims.

OBAAF's controls come from two companion research papers, and the framework is built to interoperate with the standards teams already report against, rather than inventing its own cryptography.

PAPER 1Untrusted Text, Trusted Tokens

Bounding the authority of AI agents in software build pipelines. The source of R1–R8.

PAPER 2Build Assurance for Games

A game-build integrity profile mapping SSDF and SLSA to real studio pipelines.

INTEROPin-toto · SLSA · Sigstore

Signed in-toto predicates; SLSA v1.2 and NIST SSDF crosswalks; keyless Sigstore attestation.

THREATSTen mapped incidents

Real 2025–2026 agent and build compromises, each mapped to the controls that prevent or contain it.

Read the draft papers, the threat model, and the agent controls. The agent-run and approval schemas are proposed for community review as an open standard for AI-agent attestations.
