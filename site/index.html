Open Build and Agent Assurance Framework

What an agent job can reach.

OBAAF is an open framework and command-line toolchain. For a job that runs an AI agent or publishes a release, release 0.3.0 reads the workflow file and reports what that job can reach, with the evidence in the finding.

It is not the only tool that asks this. In the measured comparison of 2026-11-13, ci-agent-audit and OBAAF both reported token-permission and egress findings on two agent fixtures, and ci-agent-audit reported a prompt input OBAAF did not. For other mistakes in workflow files, the project's position is zizmor first, CodeQL where code scanning is on, actionlint for plain mistakes, and poutine for scripts piped into a shell. OBAAF does not replace them. The record is in the landscape.

Three ideas.

What a job can reach

A job can hold a token, a secret, and a way off the machine. Release 0.3.0 reads those facts in the workflow file. It does not watch the job run.

Whether a control is real

A name in the file is not a check that the control holds. The checker in release 0.3.0 says it reads workflow files and repository settings that live in files, naming CODEOWNERS and agent instruction files, and that it runs locally and sends nothing over the network. This session did not trace that. There is no obaaf audit command in that release, so branch protection and rulesets are outside it, and it does not watch the job run.

What a finding can and cannot say

The finding above is one low report about one action in one file. A passing check is not a certification. The checker does not scan application source for vulnerabilities.

How the three fit

Check, audit, and enforcement are not the same command.

The dashes move along the line that joins the three, and only there, so they stay visibly separate. If you asked for less motion, the line is solid and still. The labels are the explanation. This page has not been checked in a browser yet. That is a later slice.

obaaf check

In release 0.3.0 it reads GitHub Actions workflows, Jenkinsfiles as an advisory auditor, CODEOWNERS, and recognized agent instruction files. obaaf check --help in that release lists text, JSON, and SARIF. It does not edit the files and it does not configure a merge gate. The checks on this page were given local files. For Jenkins, exit 0 is not a conformance decision: controller settings are not in a Jenkinsfile, and what the checker cannot see is unknown.

obaaf audit

Development only, not in release 0.3.0. It reads repository settings it can see and compares them with the workflows. What it cannot read is "cannot tell", and cannot tell is not a pass. This page is not a live audit.

obaaf attest

Writes an in-toto statement. A separate configured job signs it through GitHub's Sigstore. The command does not sign every agent run, and it does not by itself establish a model identity. No hosted signing was run for this page.

obaaf verify

Exits so a caller can refuse a release or a proposal. The command does not upload, and it does not block some other upload path. "No provenance, no upload" is true only when the upload step is written to stop on that failure.

The install and the two checks above were run in this session, on obaaf 0.3.0 and again on 0.4.0.dev0. obaaf check --help was read on 0.3.0. Attest, verify, and audit were not run here. Audit is not a command in 0.3.0's help. The attest and verify sentences follow the website truth table, including its record that a local agent-run statement had no signatures field and that verify's exit does not itself upload. Direct dependencies of the package are PyYAML and jsonschema. Cryptography is installed with the keys extra. Transitive packages are additional, and installation downloads them.

What this release does not do.

OBAAF ships no inference proxy. An optional egress action in the development checkout can restrict the command it wraps, where someone configures it. A name under an allowed name can still be queried. With a real model key, the provider can still be asked to fetch a URL or reach a remote server. The test of that path used made-up keys, which the providers refused. That action is not in release 0.3.0.

On the development checker, OBAAF-GHA-020 can be cleared when the job runs on ubuntu-24.04-firewall and .github/egress-firewall.yaml sets mode: enforce, with a token that can read the file. OBAAF's own action stays "cannot tell" until a released commit of it is listed, and none is listed. A model key placed behind AWF's API proxy does not clear OBAAF-GHA-005. That proxy is not OBAAF's inference proxy, and OBAAF ships none. OBAAF-GHA-005 still cannot be cleared. None of this clearing behaviour is in release 0.3.0.

An acceptance with an owner, a reason, and an expiry date is development only. An acceptance is a recorded decision, not proof that a risk was removed.

There is one documented adopter, and it is a project of one of the authors. This page does not say that pilot teams are using it, and it does not say how long a person takes to read a result.

A separate tool

The assessment scores answers. It does not verify them.

Open the questionnaire

Thirty-four questions, answered yes, no, unknown, or, where the item allows it, not applicable. The tier names are Accounted, Controlled, Verified, and Assured. They describe the rubric and the supplied answers, not controls OBAAF has verified. Game studios are the worked example.

The questionnaire this site builds is from the development checkout, 0.4.0.dev0, not from release 0.3.0. Its note says it is a development version and not a release. It does not say "pilot teams". The form in release 0.3.0 does, and this page does not adopt that sentence. The generated form still says "Thirty-four yes-or-no questions" and "A tier describes controls in place", and its script can say "Would have prevented". The truth table cuts or narrows those. Changing the form is not this slice. Reassessing after 90 days is a suggestion in the adoption guide, not a result the tool measured.
