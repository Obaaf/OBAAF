Open Build and Agent Assurance Framework

What an agent job can reach.

OBAAF is an open framework and command-line toolchain. For a job that runs an AI agent or publishes a release, release 0.3.0 reads the workflow file and reports what that job can reach, with the evidence in the finding.

It is not the only tool that asks this. In the measured comparison of 2026-11-13, the OBAAF run was 0.4.0.dev0 at commit c04d811. ci-agent-audit and that run both reported token-permission and egress findings on two agent fixtures, and ci-agent-audit reported a prompt input that run did not. The same two fixture files, checked with obaaf 0.3.0, each report OBAAF-GHA-003 and OBAAF-GHA-020. For other mistakes in workflow files, the project's position is zizmor first, CodeQL where code scanning is on, actionlint for plain mistakes, and poutine for scripts piped into a shell. OBAAF does not replace them. The record is in the landscape.

Try the released package

Python 3.10 or later. Installation downloads packages. The check reads a file on the machine and does not edit it. No action was run.

python -m pip install obaaf==0.3.0
obaaf --version
obaaf check unpinned.yml --fail-on low
obaaf check pinned.yml --fail-on low

Run on 2026-11-14 at 03:44 UTC, in a clean environment, with the package from PyPI. obaaf --version printed obaaf 0.3.0. The first check exited 1. The second exited 0.

Three ideas.

Isolate the build. Record what goes into a release. Give agents only the access each task needs.

Isolate the build

The source tree of release 0.3.0 has the release-lane workflow templates. obaaf templates install copies them when it is run from a clone of that release. The wheel does not carry those files. It reports a release job that an untrusted trigger can start (OBAAF-GHA-015) and a release job that can read a shared cache (OBAAF-GHA-006). The check reads the workflow file. It does not run the build, and it does not place the job on its own machine.

Record what goes into a release

Release 0.3.0 has obaaf attest, including a build record, and obaaf manifest. obaaf attest writes an in-toto statement. It does not sign it, and it signs no agent run. A separate configured job can sign a statement through GitHub's Sigstore. The command does not establish a model identity.

Give agents only the access each task needs

Release 0.3.0 treats a job as an agent job from the action or command it runs, or from a lane declaration. It reports write permission (OBAAF-GHA-003), a request for an OIDC token (OBAAF-GHA-004), and a secret the job can read (OBAAF-GHA-005). A secret listed under protected_secrets and used outside the named environment is OBAAF-GHA-024. The check does not take the access away. The fix text for OBAAF-GHA-005 says to keep the model credential in an inference proxy. OBAAF ships none. An action that wraps the agent's command and can restrict it is development only, and no released commit of it is listed.

How the three fit

Check, audit, and enforcement are not the same thing.

Release 0.3.0 is the check. Audit, and the one control that enforces a limit on a command, are development only.

Check

In release 0.3.0. It reads files and reports.

Audit

Development only. Not a command in release 0.3.0.

Enforcement

The egress action, development only. It is not in release 0.3.0.

obaaf check

In release 0.3.0 it reads GitHub Actions workflows, Jenkinsfiles as an advisory auditor, CODEOWNERS, and recognized agent instruction files. obaaf check --help in that release lists text, JSON, and SARIF. It does not edit the files and it does not configure a merge gate. For Jenkins, exit 0 is not a conformance decision: controller settings are not in a Jenkinsfile, and what the checker cannot see is unknown.

obaaf audit

Development only, not in release 0.3.0. It reads repository settings it can see and compares them with the workflows. What it cannot read is "cannot tell", and cannot tell is not a pass.

Records, and a caller's exit, are not enforcement.

obaaf attest

Writes an in-toto statement. It does not sign that statement, and it signs no agent run. A separate configured job can sign a statement through GitHub's Sigstore. The command does not by itself establish a model identity.

obaaf verify

Exits so a caller can refuse a release or a proposal. The command does not upload, and it does not block some other upload path. "No provenance, no upload" is true only when the upload step is written to stop on that failure.

Direct dependencies of the package are PyYAML and jsonschema. Cryptography is installed with the keys extra. Transitive packages are additional, and installation downloads them.

What this release does not do.

OBAAF ships no inference proxy. With a real model key, the provider can still be asked to fetch a URL or reach a remote server. An optional egress action in this checkout can restrict the command it wraps, where someone configures it. A name under an allowed name can still be queried. That action is not in release 0.3.0, and no released commit of it is listed.

Release 0.3.0 does not report OBAAF-GHA-020 for an agent job that has a step-security/harden-runner step with egress-policy: block and no if. On 2026-11-14, obaaf 0.3.0 checked a job whose first step was step-security/harden-runner@v2.12.0 with that setting: the report had no OBAAF-GHA-020. Two OBAAF-GHA-008 findings remained, because the actions were not pinned to a commit. The same step behind if: github.ref == 'refs/heads/main' still produced OBAAF-GHA-020. That release does not look at the action's version, at disable-sudo-and-containers, or at whether the step is first. The checker in this checkout still reports OBAAF-GHA-020 on that same v2.12.0 file. The control is not met, because sudo and containers are kept. A further file, whose first step was step-security/harden-runner pinned to fa2e9d605c4eeb9fcad4c99c224cee0c6c7f3594 (the commit this checkout lists as v2.16.0), with egress-policy: block and disable-sudo-and-containers: true, and whose agent action was also pinned, made obaaf 0.3.0 print no findings and exit 0. This checkout still reports OBAAF-GHA-020 on that file. It says it cannot tell, because whether the repository is covered by a Harden-Runner tier is not in the workflow. Cannot tell is not a pass. A step of that name is not, in this checkout, enough to drop the finding.

On this checkout, OBAAF-GHA-020 can be cleared when the job runs on ubuntu-24.04-firewall and .github/egress-firewall.yaml sets mode: enforce, with a token that can read the file. That clearing is not in release 0.3.0. A model key placed behind AWF's API proxy does not clear OBAAF-GHA-005. That proxy is not an inference proxy shipped by OBAAF. OBAAF-GHA-005 still cannot be cleared.

Release 0.3.0 already ignores a finding when an ignore entry has a reason and an until date that has not passed. Requiring an owner, and refusing a reason the checker judges too short, are not in that release. An acceptance is a recorded decision, not proof that a risk was removed.

There is one documented adopter, and it is a project of one of the authors. This page does not say that several teams are using it, and it does not say how long a person takes to read a result.

A separate tool

The assessment scores answers. It does not verify them.

Open the questionnaire

Thirty-four questions, answered yes, no, unknown, or, where the item allows it, not applicable. The tier names are Accounted, Controlled, Verified, and Assured. They describe the rubric and the supplied answers, not controls OBAAF has verified. Game studios are the worked example.

The questionnaire linked here still says "Thirty-four yes-or-no questions", says a tier describes controls in place, and can say "Would have prevented". Those are not claims the evidence supports. Issue 152 tracks the form. Reassessing after 90 days is a suggestion in the adoption guide, not a result the tool measured.
