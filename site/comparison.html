Where OBAAF does not try to be the only tool.

This page is a short reading of the landscape. It is not a new comparison. The positioning section was written on 2026-11-11. Measurements of Checkov, Semgrep and ci-agent-audit were added on 2026-11-13. The positions are proposals until the maintainers accept them.

OBAAF is a small open-source project with one adopter, and that adopter is its author's own. Asking what an agent job in CI can reach is not OBAAF's alone. ci-agent-audit does. Wiz and Aikido say their products detect misconfigured agents in CI. Neither was tested for that landscape.

On 2026-11-13 the landscape's H2 runs recorded that ci-agent-audit's AIA005 and AIA006 overlapped token-permission and egress findings on two agent fixtures, and that AIA001 identified prompt input that run did not. The OBAAF run in that measurement was 0.4.0.dev0 at commit c04d811. This page does not repeat every cell of those runs. The two fixture files are clinejection-triage.yml and promptpwnd-issue-agent.yml.

The aim, and what is true now

The landscape's position, as a thing being built towards, is: for jobs that run an AI agent or publish a release, say what each job can reach, check that a claimed control is real in the workflow file, in the repository's settings, and while the job runs, and show the evidence. For everything else, point at the tool that already does it.

One sentence in that section still says that today OBAAF reads files only, reads no settings, and enforces nothing while a job runs. The rows under it are later. In the development version, not in release 0.3.0, obaaf audit reads repository settings it can see, and an optional egress action exists. The development checker is written to clear OBAAF-GHA-020 when the job runs on ubuntu-24.04-firewall and .github/egress-firewall.yaml sets mode: enforce, with a token that can read the file. OBAAF's own action stays "cannot tell" until a released commit is listed, and none is listed. A model key behind AWF's API proxy does not clear OBAAF-GHA-005. OBAAF ships no inference proxy.

Release 0.3.0 is a file check, and it does one more thing with egress than that sentence says. On 2026-11-14 it did not report OBAAF-GHA-020 for an unconditional step-security/harden-runner step set to egress-policy: block. It does not look at the action's version, at disable-sudo-and-containers, or at whether the step is first. The same step behind an if was still reported. The development version still reported OBAAF-GHA-020 on both of those files. The detail is on the rules page. The full commit used for the pinned file is there too.

What the landscape says to use instead

These are documented recommendations from that page. None of the other tools named below was run for the landscape. The recommendation rests on the other project's documentation, as read for that comparison. Each block is one row of that table: the area, what the landscape says to use, and where it says OBAAF stands.

General mistakes in workflow files

Use zizmor first. CodeQL where code scanning is on. actionlint for plain mistakes. poutine for scripts piped into a shell. OBAAF does not replace them. The 2026-11-13 measurements covered Checkov, Semgrep and ci-agent-audit, not this whole list.

What a job can reach on the network

Use GitHub's native egress firewall where a repository has it. Otherwise the Agent Workflow Firewall. Harden-Runner or Cimon where a team already runs one. The landscape says none of those was run for the comparison. OBAAF's own wrapper is development only, with the limits above.

Who and what can start a workflow

Use GitHub's workflow execution protections. The landscape says this has not been run against a real policy. obaaf audit can compare a readable policy with the workflows. It is development only. Where the policy cannot be read the result is "cannot tell".

Pinning actions

Use GitHub's workflow lockfiles and its policy for pinning to a commit. Chainguard Actions is named as a commercial option in open beta. OBAAF keeps its report of unpinned actions, OBAAF-GHA-008. It does not know about lockfiles.

Writing a new agent workflow

Use GitHub Agentic Workflows. OBAAF's templates are a worked example, not the recommended start.

Signing what was built

Use GitHub artifact attestations and gh attestation verify. obaaf attest writes an in-toto statement. It does not sign that statement, and it signs no agent run. A separate configured job can sign through GitHub's attestation action.

Skills, MCP servers, instruction files

Use Snyk's agent-scan, Agent Threat Rules, agent-audit, and promptwarden. OBAAF keeps two small rules about instruction files.

A whole organisation's settings

Use Legitify, OpenSSF Scorecard, or one of the enterprise products in the landscape. obaaf audit is the repository's own workflows, not an organisation standard, and it is not in release 0.3.0.

Other CI systems

poutine reads GitLab, Azure DevOps and Tekton. Release 0.3.0's checker is GitHub Actions, plus advisory Jenkins.

The landscape, written 2026-11-11, says a third of its GitHub Actions rules report what larger tools report too. That sentence is the landscape's. The H2 source commit is c04d811.
