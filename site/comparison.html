Where OBAAF does not try to be the only tool.

This page is a short reading of the landscape. It is not a new comparison. The positioning section was written on 2026-11-11. Measurements of Checkov, Semgrep and ci-agent-audit were added on 2026-11-13. The positions are proposals until the maintainers accept them.

OBAAF is a small open-source project with one adopter, and that adopter is its author's own. Asking what an agent job in CI can reach is not OBAAF's alone. ci-agent-audit does. Wiz and Aikido say their products detect misconfigured agents in CI. Neither was tested for that landscape.

On 2026-11-13 the landscape's measured runs recorded that ci-agent-audit's AIA005 and AIA006 overlapped token-permission and egress findings on two agent fixtures, and that AIA001 identified prompt input that run did not. The OBAAF run in that measurement was 0.4.0.dev0 at commit c04d811. This page does not repeat every cell of those runs. The two fixture files are clinejection-triage.yml and promptpwnd-issue-agent.yml.

The aim, and what is true now

The landscape's position, as a thing being built towards, is: for jobs that run an AI agent or publish a release, say what each job can reach, check that a claimed control is real in the workflow file, in the repository's settings, and while the job runs, and show the evidence. For everything else, point at the tool that already does it.

One sentence in that section says that today OBAAF reads files in the repository only: no settings, nothing enforced while a job runs, and a control is accepted because the file names it. That is still true of release 0.3.0. The rows under it are later, and describe the development version, which is not in a release: obaaf audit reads the repository settings it can see; an optional egress action exists; and the checker clears OBAAF-GHA-020, the finding that an agent job's network is not restricted, for GitHub's native egress firewall in enforce mode, under conditions the rules page lists. OBAAF's own action stays "cannot tell" until a released commit of it is listed, and none is listed. OBAAF-GHA-005, a secret available to an agent job, cannot be cleared in either version. OBAAF ships no inference proxy.

In release 0.3.0, for egress, "a control is accepted because the file names it" means Harden-Runner. On 2026-11-14 it did not report OBAAF-GHA-020 for an unconditional step-security/harden-runner step set to egress-policy: block. It does not look at the action's version, at disable-sudo-and-containers, or at whether the step is first. The same step behind an if was still reported. The development version still reported OBAAF-GHA-020 on both of those files. The files, and the full commit of the pinned Harden-Runner step, are on the rules page.

What the landscape says to use instead

These are the landscape's recommendations. It ran zizmor, actionlint, poutine, Octoscan and OpenSSF Scorecard on 2026-11-11, CodeQL's queries for GitHub Actions in its second part, and Checkov, Semgrep and ci-agent-audit on 2026-11-13. Where a block below says a tool was not run, the recommendation rests on that project's documentation. Each block is one row of the landscape's positioning table: the area, what it says to use, and where it says OBAAF stands.

General mistakes in workflow files

Use zizmor first. CodeQL where code scanning is on. actionlint for plain mistakes. poutine for scripts piped into a shell. OBAAF does not replace them. All four were run for the landscape.

What a job can reach on the network

Use GitHub's native egress firewall where a repository has it. Otherwise the Agent Workflow Firewall. Harden-Runner or Cimon where a team already runs one. The landscape says none of those was run for the comparison. OBAAF's own wrapper is development only, with the limits above.

Who and what can start a workflow

Use GitHub's workflow execution protections, not run for the landscape. In the development version, obaaf audit compares a policy it can read with the triggers the workflows use. The landscape says that rule has never been run against a real policy. Reading a policy takes administrator access, so most runs answer "cannot tell".

Pinning actions

Use GitHub's workflow lockfiles and its policy for pinning to a commit, neither run for the landscape. Chainguard Actions is named as a commercial option in open beta, not run. OBAAF keeps its report of unpinned actions, OBAAF-GHA-008. It does not know about lockfiles.

Writing a new agent workflow

Use GitHub Agentic Workflows, not run. OBAAF's templates are a worked example, not the recommended start.

Signing what was built

Use GitHub artifact attestations and gh attestation verify, not run for the landscape because they need the GitHub API or a signed artifact. obaaf attest writes the predicate of an in-toto statement, or the whole statement with --statement-out. It signs neither, and it signs no agent run. A separate configured job can sign through GitHub's attestation action.

Skills, MCP servers, instruction files

Use Snyk's agent-scan, Agent Threat Rules, agent-audit, and promptwarden, none of them run. OBAAF keeps two small rules about instruction files.

A whole organisation's settings

Use Legitify, OpenSSF Scorecard, or one of the enterprise products in the landscape. Of these, only Scorecard was run; Legitify needs a token, and the enterprise products were read about only. obaaf audit reads only the settings the repository's own workflows depend on. It does not check an organisation against a standard, and it is not in release 0.3.0.

Other CI systems

poutine reads GitLab, Azure DevOps and Tekton. Release 0.3.0's checker is GitHub Actions, plus advisory Jenkins.

The landscape, written 2026-11-11, says a third of its GitHub Actions rules report what larger tools report too. That sentence is the landscape's. The OBAAF commit measured on 2026-11-13 is c04d811.
