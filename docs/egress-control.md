# Egress control for agent jobs

*Built in flagship slice 2c.2 (2026-11-13) as the action [`actions/egress`](../actions/egress/action.yml); slice 2c.4 (the same day) closed the proxy's DNS channel and added model keys. What this page says holds is what the escape tests in [`.github/workflows/egress-escape-tests.yml`](../.github/workflows/egress-escape-tests.yml) showed on GitHub-hosted `ubuntu-24.04` runners, in the runs it links. Statements about the Agent Workflow Firewall's internals come from its source at v0.29.13 (commit `62b7e8f`) or its pages, and say which. Slice 2c.1 wrote the design on 2026-11-12 without running anything; where running it settled a question, the answer is under [What running it settled](#what-running-it-settled).*

## In short

`actions/egress` runs one command with its network limited to a list of host names. Everything else the command tries is refused, and the refused names are listed in the job summary. It runs the command under GitHub's Agent Workflow Firewall (AWF, `github/gh-aw-firewall`, MIT), pinned by OBAAF, in AWF's default mode: the command's container sits on a Docker network with no route out, and a Squid proxy that allows only the listed names is its one way out. The command runs with no privileges (`sudo` refuses), sees none of the runner's environment except variables the workflow names, and can write only to a scratch copy of the workspace, its own home and its own `TMPDIR`, which the action deletes or hands back as output. The runner's own workspace, home directory, `/tmp` and file-command files are out of its reach.

On a hosted runner, OBAAF's CI tries 26 ways out from inside it (22 since slice 2c.2, and four ways to put data in a DNS query since slice 2c.4). Each is first tried outside the sandbox, where all but the two IPv6 ones get out; inside, a packet capture on the runner's external interface saw none of them leave, and the listed host's own server answered a request. The two IPv6 attempts could not be tested, because the runner itself had no IPv6 route.

Since slice 2c.4 the proxy's resolver is the action's own, on the runner, and answers only names the list covers (and, with a model key, the provider's API host, exactly): **a name the command asks the proxy for no longer leaves the runner in a DNS query unless the list covers it** (asserted by the escape tests, below). Before, every name asked of the proxy over HTTPS left the runner in a query, which was a channel for data. Names the command looks up itself did not leave before either, and still do not; the tests now assert that too. A model key can now be given to AWF's API proxy with `model-keys`: the command calls the proxy, never sees the key, and the proxy reaches the provider whether or not `allow` lists it.

It does not make an agent safe to hold a secret. Anything it can send to a listed host it can send there, and with a model key, anything it can send to the provider it can send there; and it confines one command, not the job. Read [What it blocks, and what it does not](#what-it-blocks-and-what-it-does-not) before relying on it.

## Using it

```yaml
jobs:
  review:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@<commit> # pin it
        with:
          persist-credentials: false   # the action refuses a workspace whose .git/config holds a token
      - id: agent
        uses: Obaaf/OBAAF/actions/egress@<commit> # pin it to a commit
        env:
          REVIEW_TARGET: ${{ github.event.pull_request.number }}
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        with:
          allow: api.github.com          # the host names your command needs
          env: REVIEW_TARGET
          model-keys: ANTHROPIC_API_KEY  # for AWF's API proxy, not for the command
          run: ./scripts/run-agent.sh
      - uses: actions/upload-artifact@<commit>
        with:
          name: agent-output
          path: ${{ steps.agent.outputs.workspace }}
```

- **`allow`** (required): host names, separated by commas, spaces or new lines. A name covers its subdomains, so `github.com` allows every account and repository on GitHub. Plain names only: an entry with `*`, an address, a port, a scheme, a path, a trailing dot or a single label is refused before anything runs.
- **`run`** (required): the command, run with `bash -e` in a copy of the workspace.
- **`env`**: names of variables from the step's `env` to pass in. Nothing else of the runner's environment reaches the command, `GITHUB_TOKEN` and `ACTIONS_RUNTIME_TOKEN` included. Refused: variables that change how a shell, a loader or the network behaves (`PATH`, `HOME`, `LD_PRELOAD`, `BASH_ENV`, the proxy variables, `GIT_SSH_COMMAND` and others); the runner's file-command variables; names AWF reads as its own configuration (starting `AWF_`, `OTEL_` or `FOUNDRY_`, ending `_API_TARGET`, `_API_BASE_PATH`, `_BASE_URL` or `_ENDPOINT_OVERRIDE`; an OpenTelemetry endpoint, for one, would be added to the proxy's allow-list); names starting `ACTIONS_`, `SQUID_` or `OBAAF_EGRESS_`; and **model keys and GitHub tokens** (below). The list follows AWF v0.29.13's names by pattern. AWF reads a few more names from the same file that choose how its API proxy talks to a provider rather than what the proxy allows (`COPILOT_PROVIDER_TYPE`, `COPILOT_MODEL`, `GOOGLE_GENAI_USE_VERTEXAI` and others); those are passed.
- **`model-keys`**: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or both, set in the step's `env`. They go to AWF's own environment, and AWF gives them to its API proxy, a sidecar container the command can reach and cannot look inside (AWF v0.29.13, `src/commands/resolve-credentials.ts`). What the command sees instead, read from inside the sandbox in the escape tests: `ANTHROPIC_BASE_URL` and `OPENAI_BASE_URL` pointing at the sidecar (`http://<address>:<port>`), `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY` and `CODEX_API_KEY` holding AWF's placeholders, and `CLAUDE_CODE_API_KEY_HELPER`; neither key is in its environment or in any file it can read that the test searched. AWF sets them for Claude Code and Codex (`src/services/credentials/`); an agent that reads `ANTHROPIC_BASE_URL` or `OPENAI_BASE_URL` works unchanged, and one that sends requests to `api.anthropic.com` itself is refused like any unlisted host (the escape tests try it). No real agent was run. **The sidecar reaches the provider's API host (`api.anthropic.com`, `api.openai.com`) whatever `allow` says**: AWF lets the sidecar through its proxy with a rule of its own (`src/squid/config-sections.ts`, `from_api_proxy`), and the action's resolver answers that one host for it (not its subdomains). AWF's other providers (Gemini, Vertex, Copilot, Foundry) and the GitHub tokens are refused under both inputs: untested.
- **The providers' hosted web tools are refused, in requests AWF's proxy can read.** With a key, an agent could ask the provider to search or fetch the web for it, and the provider's servers would make the request, out of the proxy's sight. The action sets AWF's policy for them to `enabled: false` (`apiProxy.hostedWeb` in AWF's configuration), and the API proxy then refuses an HTTP request whose body it parses as JSON and that carries Anthropic's `web_search`/`web_fetch` tools or OpenAI's hosted web search, before it reaches the provider (AWF v0.29.13, `containers/api-proxy/claude-hosted-web.js`, `codex-hosted-web.js`). The escape tests show the refusal for Anthropic's `web_fetch`; OpenAI's was not tested. By AWF's source, a body it cannot parse as JSON is forwarded unchanged (whether a provider would accept such a body was not tried), and a WebSocket upgrade is forwarded with the key without this check (`containers/api-proxy/server-factory.js`).
- **Model keys under `env` are refused**, and point you to `model-keys`: AWF withholds them from the command, so passed in `env` they would vanish. A key under a name AWF does not know is passed to the command like any other variable, and the command can then send it to any listed host.
- **Outputs:** `workspace` (the copy the command ran in and could change), `scratch`, `log-dir` (the proxy's log, outside the scratch directory), `denied` (names the proxy refused), `dns-refused` (names the proxy's resolver refused, which went no further than the runner), `dns-log` (the resolver's log), `exit-code`, and `confined`, which is `true` only when the step's status is the command's own. The step fails with the command's exit status. It fails with status 3, and the command does not run, if the probe described below gets out, if the sandbox or the resolver does not start, or if the runner's file-command files changed; it also fails with status 3 if the resolver stops before the command ends.
- **Treat what the command wrote as data.** Upload it, diff it, read it; do not run or load anything from `steps.<id>.outputs.workspace` or `scratch` in a later step of the same job, because later steps have the full network. That includes running `git` in the copy: the command can write its `.git/config` and `.git/hooks`. The checker reads this (below).

Linux x64 runners with Docker only. It downloads AWF's binary from GitHub's release page and its images from `ghcr.io`, so those must be reachable from the runner. A run takes about 40 seconds longer than the command, most of it pulling the images.

**Not tried:** an agent that is itself an action (it cannot be wrapped; see below), a real model key or a model call that succeeds (the tests use made-up keys, which each provider refuses), self-hosted or larger runners, `ubuntu-22.04`, a repository larger than OBAAF's.

## What it blocks, and what it does not

Each "blocked" line is an attempt in the escape tests that got out when made outside the sandbox and was not seen leaving the runner when made inside it, judged from a packet capture on the runner's external interface (the interface of its IPv4 default route, through which Docker's traffic also leaves; the job logs the runner's routes, and IPv6 had no route at all). The confined command's own exit statuses are recorded and decide nothing. The runs: [43432030855](https://github.com/Obaaf/OBAAF/actions/runs/43432030855) (commit `4a25d1b`) and [43431555704](https://github.com/Obaaf/OBAAF/actions/runs/43431555704) (`06ea5bb`), both with every check described here, including the cleanup and the `confined` output; [43425789742](https://github.com/Obaaf/OBAAF/actions/runs/43425789742) (`2b02f3d`) and [43425073087](https://github.com/Obaaf/OBAAF/actions/runs/43425073087) (`9bb65cb`) gave the same verdicts on the attempts before those were added. For the four DNS attempts of slice 2c.4 and the model keys: [43515192176](https://github.com/Obaaf/OBAAF/actions/runs/43515192176) (`d1c7b14`, every check described here) and [43514653982](https://github.com/Obaaf/OBAAF/actions/runs/43514653982) (`873c375`, all but the check of grep's exit status). Before the plain HTTP attempts named the proxy, [43510290810](https://github.com/Obaaf/OBAAF/actions/runs/43510290810) (`9140abf`) passed, and [43509583061](https://github.com/Obaaf/OBAAF/actions/runs/43509583061) (`c7caf43`) blocked every attempt but failed on two checks the change itself had made wrong: it did not expect the resolver's log, and it required a 200 from `api.github.com`, which answered 403 inside and outside the sandbox. The pull request of each slice names the run on its last commit.

**Not testable on a hosted runner:** IPv6. The runner had no IPv6 route out, so the same attempts outside the sandbox did not get out either (a direct connection to `[2606:4700:4700::1111]:443`, `dig -6 @2620:fe::fe`). Inside, the container has an IPv6 address only on its loopback interface and no IPv6 route. That is evidence, not a test; on a runner with IPv6 it would need testing.

**Not blocked, by design or by limit:**

- **Anything sent to a listed host.** "If it can reach an allowed destination, it can send that data there" (AWF's documentation). A listed name covers its subdomains. Allowing `github.com` allows uploading to any repository on it.
- **A different `Host` behind an allowed name.** Recorded, not asserted: a request to `https://api.github.com/` with `Host: example.org` reached GitHub's server, which answered 400. The proxy sees only the name in the TLS handshake. A server that routes by `Host` (a shared CDN front) would route it.
- **Data in a name under a listed name.** The action's resolver answers every name the list covers, subdomains included, and passes it to the runner's resolver, so a query for `<data>.api.github.com` leaves the runner and reaches the DNS servers of `github.com`. That is a channel to whoever runs the DNS for a listed name, which is why a listed name should be one whose DNS nobody but its owner runs; a name under which anyone can register a host (the public suffix list, private section included: `github.io`, `workers.dev`) gives that channel to anyone. Since slice 2c.3 the checker does not credit the action when its list has such a name.
- **With a model key: anything sent to the provider.** The sidecar reaches the provider's API host whatever `allow` says, and the agent's requests carry whatever the agent puts in them. The API proxy refuses the hosted web search and fetch tools in the requests it can read (above), but **not every way a provider can be asked to connect elsewhere**: AWF v0.29.13's API proxy has no rule for remote MCP servers named in a request (nothing in `containers/api-proxy/` handles `mcp_servers`), and Anthropic documents an [MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector) by which a Messages API request names a remote MCP server for Anthropic's servers to connect to (page found by search on 2026-11-13, not read in full). Other request features that make a provider fetch a URL (an image or a document given by URL, for one) are not refused either. So with a real key, an agent can probably have the provider carry data to a server of its choosing. Not tested: the made-up keys are refused before any of this. Give an agent a key only where the provider may see everything the agent can read.
- **The resolver's own limits.** It answers names under the listed ones, and the API host of each model key exactly; it refuses every other name, and any label holding a byte other than a letter, digit, hyphen or underscore, so a label with a dot inside cannot pass for a listed name. What it passes on is rebuilt from the query's ID, its recursion flag and its one question; nothing else in the message (other sections, EDNS options, trailing bytes) goes further. It logs what it allowed and refused. It listens on Docker's `docker0` bridge address during the step only, and runs as `nobody` after binding port 53 with `sudo`, which the command cannot use. The command cannot reach it (its only route is AWF's internal network); AWF's proxy and any other container on the runner can, and can get answers for the listed names and each model key's API host only.
- **What the command does with what it can read.** It can read the copy of the workspace, the system directories (read-only) and the variables it was given. Give it no secret it does not need. This control does not clear OBAAF-GHA-005.
- **The job's log and its artifacts.** What the command prints goes to the job's log, and what it writes in the copy of the workspace leaves with any later `actions/upload-artifact` step that saves it. Neither is network traffic from the sandbox, so nothing here stops it, and whoever can read the run's logs and artifacts (anyone, in a public repository) can read it. GitHub tries to hide a secret's value in logs, but a command that writes it in pieces, or in a form GitHub does not recognise, gets it past that. A credential passed in `env` can leave this way; a model key in `model-keys` cannot, because the command never has it, unless the workflow itself writes it into `run` (`${{ env.ANTHROPIC_API_KEY }}`), which the checker reports as passed to the command.
- **Other steps of the job.** It confines one command. Every other step, and every post step, runs with the full network.
- **The runner itself.** AWF's container is "not a security boundary against runner-host compromise" (AWF's documentation). A kernel exploit from inside is out of scope.

**AWF's API proxy, tested with made-up keys.** The behaviour job gives the action two made-up keys (`sk-ant-api03-…`, `sk-proj-…`, generated in the run and not secrets), with neither provider in `allow`. From inside, the command sends a request to each provider through the sidecar. The sidecar adds the key and sends the request on, and each provider refuses the key itself: Anthropic answers 401 `authentication_error`, OpenAI 401 `invalid_api_key`. The proxy's log shows the sidecar's `CONNECT` to both hosts, the action's resolver answered both, and the command's own `curl https://api.anthropic.com/` is refused. A request carrying Anthropic's `web_fetch` tool is refused by the sidecar with 403 `claude_hosted_web_disabled` before it reaches Anthropic. Neither key is in the command's environment, in the files the test searched (its home, `TMPDIR`, the copy, `/tmp`, `/home`, `/run`, `/etc`, `/var`), or in the proxy's or the resolver's log. AWF itself writes the keys into its `docker-compose.yml` in its working directory (its own source says so, `src/sensitive-paths.ts`); AWF hides that directory from the command behind an empty mount, and the action deletes it after the run.

## What running it settled

Slice 2c.1 left five questions for this slice. The answers come from the escape tests' facts, which the attempts script records from inside the sandbox, and from AWF's source at v0.29.13.

1. **Which mode runs by default: network isolation, with no `sudo`.** In v0.29.13 the default ("strict security") forces `--network-isolation` and the API proxy on, and turns `--enable-dind`, `--dns-over-https` and host access off with a warning (`src/commands/validators/security-mode.ts`). The run log shows the networks `awf-net` and `…_awf-ext`; inside, the only route is `172.30.0.0/24`. `awf` ran as the runner user, without `sudo`. The documentation site's description (`sudo awf` and host firewall rules) is the `--legacy-security` mode, which the action never passes.
2. **Whether `sudo` does anything inside: no.** `NoNewPrivs` is 1 and the effective capability set is empty; `sudo -n -l` answers that the "no new privileges" flag prevents it from running as root.
3. **Where the command can write.** With AWF's defaults: the workspace, the host's `/tmp`, and the tool directories under the home directory (`.cache`, `.config`, `.local/bin` and others; `src/config/sandbox-mount-policy.json`), all read-write. That is enough to plant a program for a later step. The action narrows it: it points AWF at a home directory under one scratch directory in `/tmp`, runs the command in a copy of the workspace there, and gives AWF its own option `filesystem.allowWrite` with only that directory, which makes every other host mount read-only. Inside, writable: the scratch directory (the copy, `TMPDIR`, and the home and its tool directories); `/dev/shm`, AWF's `/tmp/gh-aw/…` paths and AWF's working directory, which are `tmpfs` in the container and never reach the runner's disk; and two kinds of place that do reach the runner's disk: the top of the command's home, which AWF backs with a directory it creates beside its working directory (`work-chroot-home`), and AWF's log and session directories, mounted at `$HOME/.copilot/logs` and `$HOME/.copilot/session-state`, which AWF itself moves into its temporary directory when it cleans up (`src/artifact-preservation.ts`; with the runner's defaults that is the host's `/tmp`, where they would stay). The action gives AWF a temporary directory inside `RUNNER_TEMP/obaaf-egress/<run>/`, deletes everything there but the proxy's log after the run (with `sudo` where AWF made a directory as root, which the command cannot use), and fails the step if it cannot. The behaviour job checks that files written to the home and to both AWF directories are found nowhere under `RUNNER_TEMP` or `/tmp`. Read-only or absent inside: `/tmp` outside the scratch directory, `/home/runner`, the rest of `RUNNER_TEMP`, the runner's file-command files, the real workspace, `/usr/local/bin`, `/opt`.
4. **IPv6 and DNS for an unlisted name.** No IPv6 route inside. DNS goes to Docker's resolver at 127.0.0.11; names the command looked up itself were not seen leaving the runner. Names it asked the proxy for over HTTPS were, until slice 2c.4 gave the proxy the action's own resolver (below).
5. **Can the action keep what the command wrote away from later steps and post steps?** Yes, as far as the tests reach: the places a later step or post step would run or load (the files listed under "Changing what later steps see") did not change, AWF's directories under `RUNNER_TEMP` are deleted, and what is in the scratch directory is reached through the action's outputs. The condition the action cannot enforce is the workflow's: a later step that runs or loads something from the output runs it with the full network. Since slice 2c.3 the checker does not credit the control in that case.

Two findings about AWF on the way, neither a weakness in the confinement: with the host's `/tmp` read-only, Docker could not create the mount points for AWF's hidden `/tmp/gh-aw/…` directories, so the action creates them first; and after the run AWF tries to repair file ownership with the image's tag rather than its digest, which fails with a warning when the image was pulled by digest.

## What the action adds to AWF

1. **Everything pinned.** AWF's binary by SHA-256 and each of its nine images by digest, read from the release's `checksums.txt` and `containers.txt`, which its `release-identity.txt` binds to the tag. A new AWF version is a change to `egress.py` and must pass the escape tests. The action does not check AWF's signatures or attestations at run time; the SHA-256 is the check.
2. **A fixed command line.** No input reaches an AWF option. `--enable-dind`, `--env-all`, `--legacy-security`, `--enable-host-access`, `--ssl-bump` and `--upstream-proxy` are never passed, and AWF runs with only `PATH`, `HOME` and `LANG` in its environment, so it finds no proxy to chain through and no token to pass on.
3. **A plain allow-list.** As above.
4. **Writes narrowed** to the scratch directory, and AWF's own writable directories deleted after the run, as above.
5. **A probe before the command.** Inside the same sandbox, immediately before the command, it tries a direct address, a direct IPv6 address, an unlisted host with and without the proxy, `sudo` and the Docker socket. If any succeeds, the command does not run and the step fails with status 3.
6. **Workflow commands stopped** while the command's output is printed, with a token the command cannot know, and the step fails if `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_OUTPUT`, `GITHUB_STATE` or `GITHUB_STEP_SUMMARY` changed while it ran.
7. **A record.** Names the proxy refused go in the job summary and the `denied` output; the proxy's log stays in `log-dir`.
8. **A resolver that answers only listed names** (slice 2c.4). AWF's proxy, Squid, resolves every name it is asked for before it refuses an unlisted one: AWF v0.29.13 puts an access rule of type `dst` (`acl allow_api_proxy_ip dst <address>`, for the API proxy) ahead of the rule that refuses unlisted names (`src/squid/config-sections.ts`, `src/squid/config-generator.ts`), and Squid must know a name's address to test a `dst` rule. So with the runner's resolver, the names asked of it over HTTPS and refused left the runner in queries (run [43425789742](https://github.com/Obaaf/OBAAF/actions/runs/43425789742); plain HTTP through the proxy was not tested until 2c.4). The order of AWF's rules cannot be changed from outside it, and the API proxy cannot be turned off in its default mode. So the action starts its own resolver, gives AWF its address with `--dns-servers`, and checks before the command starts that it refuses the probe's unlisted name and answers the first listed one. It forwards a listed name to the runner's resolver and answers every other name `REFUSED` itself. It is not the command's own resolver: in network-isolation mode AWF gives the command's container Docker's resolver (`127.0.0.11`; `src/compose-network.ts`), which did not pass names on in the tests; if a newer Docker does, the escape tests' `dns-default-*` attempts fail.
9. **Model keys only to the API proxy** (slice 2c.4): `model-keys` puts them in AWF's environment, never in the command's, and the hosted web tools are refused (above).

## How others do it, and where they are the better choice

**GitHub Agentic Workflows (gh-aw)** runs its agents inside AWF too, so the confinement is the same mechanism. The difference is the rest: gh-aw is a whole way of writing agent workflows (its compiler generates the job, an MCP gateway gives the agent its tools, and the agent's changes come out as "safe outputs" that a later job applies), while this action wraps a `run` command in a workflow that already exists. **For a new agent workflow, gh-aw is the better choice** (decision F-21, confirmed by the maintainer on 2026-11-12). This action is for the jobs that exist already, like the first adopter's 19, which start their agents from their own code.

**Harden-Runner** works differently. Its community agent for Linux (`step-security/agent`, read at commit `1ff3fa6`, 2026-11-03) runs on the runner's own virtual machine and covers every step of the job: it points the runner's DNS at a proxy of its own that answers only for allowed names, adds an `iptables` rule accepting each address an allowed name resolved to, in the `OUTPUT` chain and in `DOCKER-USER`, rejects and logs the rest, and with `disable-sudo` or `disable-sudo-and-containers` removes `/etc/sudoers.d/runner` and Docker's sockets. So it filters by address, after a name was resolved, where AWF filters by name at a proxy. **Harden-Runner is the better choice when the whole job must be covered**, including agents that are actions and post steps; it needs v2.16.0 or later with `sudo` and containers removed, or a step with `sudo` can undo it, and its free tier covers public repositories only ([landscape](landscape.md), part 2). Its source was read; it was not run here.

**GitHub's native egress firewall** (`runs-on: ubuntu-24.04-firewall`, technical preview) sits outside the runner's virtual machine, so nothing in the job can touch it, and it covers every step and post step. **Where a repository can use it, use it and not this action.** Not tried here.

**Cimon** (Cycode) also covers the whole job, with an eBPF sensor whose source the pages read do not show. **Self-hosted runners behind a network policy** put the boundary outside the machine, which AWF's own page recommends for self-hosted runners.

## What the checker credits (slice 2c.3)

`obaaf check` reads this action in an agent job and reports what it established under OBAAF-GHA-020; the full list is in [the checker's guide](checker-configuration.md#egress-controls). In short, the finding is cleared only when, for every step that uses the action:

- the action is used from a commit OBAAF lists as released. **None is listed yet**, so today the best the action gets is "cannot tell". A maintainer lists a commit once the escape tests have passed on it (`egress_action_releases` in `src/obaaf/data/detection.yaml`). A copy in your repository (`./actions/egress`) is not taken for the action;
- the allow-list is written out, with no expression, and has no name that is, or has under it, a public suffix from the public suffix list, private section included (names under which anyone can register a host, such as `github.io` or `workers.dev`, and `amazonaws.com`, which has `s3.amazonaws.com` under it). OBAAF ships the list as `src/obaaf/data/public_suffix_list.dat`;
- the job runs on GitHub-hosted `ubuntu-24.04`, not in a container;
- the agent is the action's command. The checker recognises few agents by name, so a job could wrap `true` and run its agent in an ordinary step; it reads where the agent runs from where credentials go. No other step, and no `env` of the job or the workflow, may be given a secret or `github.token`; the job may not be able to request OIDC tokens or give its token the `models` permission, because any step can use those without being handed anything; and no other step may run an agent the checker recognises. A step before the action that only installs an agent's CLI (`sudo npm install -g @anthropic-ai/claude-code`, then `claude --version`) is not taken for running it (slice 2c.8); anything more in that step and it is. A job in which no credential reaches the command or AWF's API proxy is "cannot tell", unless the checker recognises the agent in the action's `run` input or a script it runs: an agent that needs no key could be anywhere;
- every credential given to the action's own step is placed, as the action reads its inputs (slice 2c.5, decision D-052): one in the step's `env` under a name `model-keys` names goes to AWF's API proxy, and the finding shows the provider's API host after the allow-list (`api.anthropic.com (through AWF's API proxy)`), because the proxy reaches it whatever `allow` says; one under a name `env` names, or written in `run` (also through `${{ env.KEY }}`, which holds the step's own `env`), is passed to the command. Either one is evidence that the agent is the command, and neither stops the finding from being cleared; what each leaves open is said beside it (below). A name the action refuses in a way the checker reads (a model key under `env`, a provider `model-keys` does not take, a model key no `env` sets) is "not met", and other refusals are not read; inputs computed when the job runs, two names that differ only in case, or a credential anywhere else in the step are "cannot tell". The checker reads the inputs as the action does from the merge of slice 2c.4 (`f0bfbd7`) on, so a commit before it is never listed (`egress_action_floor`, enforced by a test);
- no step but `actions/upload-artifact` runs after it or beside it. Anything else could run or load what the command wrote, and the checker cannot tell reading from running, so it is "cannot tell"; `actions/cache` with the output or `/tmp`, anywhere in the job, is "not met". Steps before it may not name `/tmp`, the scratch directory or the outputs (their post steps run after it), or use `&` as an operator or mention a container engine, a terminal multiplexer or a detaching command (listed in [the checker's guide](checker-configuration.md#egress-controls)), because those can leave a process running; a process started another way is not read.

Beside a cleared finding the report says what the action does not stop: anything sent to a listed host, naming the credentials passed to the command; data in a name under a listed name, which the action's resolver passes on to that name's DNS servers; with a model key, the provider channel, naming the key and the provider's host (below); and anything the command prints to the job's log or leaves for `actions/upload-artifact` to save. (Until slice 2c.4 it also named data in any host name asked of the proxy; that channel is closed.) OBAAF-GHA-005's controls say where each of the step's credentials goes, whatever their verdict, and what the checker could not place: a model key in `model-keys` is out of the command's reach unless the workflow writes it into `run`, a credential in `env` is not. Neither clears OBAAF-GHA-005 (plan slice 2c.7 is to decide whether a key out of the agent's reach should count there).

## Not done

- IPv6 was not testable on the runners used.
- No real model key or successful model call went through the sandbox: the API proxy is tested with made-up keys, which each provider refused. Remote MCP servers named in a request, and other provider features that make the provider connect elsewhere, are not blocked by anything here (above).
- Only `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` are accepted; AWF's other providers and authentication by OIDC are untested and refused.
- Only `ubuntu-24.04` hosted runners. Not tried: `ubuntu-22.04`, larger runners, self-hosted runners, ARC.
- An agent that is itself an action cannot be wrapped.
- The source of Cimon's sensor was not read; Harden-Runner and GitHub's native firewall were not run.
