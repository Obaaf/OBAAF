# F7 Provenance

Control family F7 binds every release artifact to the source, assets, manifest, SDKs and builder that produced it, and checks that record at the last moment the studio controls: just before upload. Once a platform re-signs and distributes a build, no one downstream can tell a tampered build from a clean one. It covers profile requirements [G7.1](../../spec/profile.md#g71-emit-signed-provenance), [G7.2](../../spec/profile.md#g72-verify-provenance-before-upload) and [G7.3](../../spec/profile.md#g73-archive-releases-read-only).

This is draft guidance for OBAAF version 0.1. The studio pilot will test and revise it. Terms are explained in the [glossary](../glossary.md).

<a id="item-3-1"></a>
## Item 3.1: Signed provenance

**Why.** Build-time tampering leaves the source clean, so detecting it needs evidence about the build itself. Attackers inside build environments shipped signed, trojanized installers in the [3CX case](https://cloud.google.com/blog/topics/threat-intelligence/3cx-software-supply-chain-compromise).

**Do this on GitHub Actions.** Use the [release template](../../templates/github-actions/workflows/obaaf-release.yml). Its attest job, separate from the build job, signs two attestations for every artifact:

- SLSA provenance, generated by GitHub's attest-build-provenance action;
- an OBAAF build record, written by `obaaf attest build-record`, that adds the asset revision, the binary-manifest digest, the SDK versions and the isolation tier.

Both are signed through GitHub's Sigstore with the workflow's identity, using a certificate issued for that job that expires within minutes, so no long-lived provenance key exists to steal. Artifact attestations need a public repository or GitHub Enterprise Cloud; see [GitHub settings](../github-settings.md#plan-limits).

**Do this on another CI system.** Generate the same records with `obaaf attest slsa` and `obaaf attest build-record`. Sign them as DSSE envelopes (the signed-envelope format that in-toto attestations use) with a key held in a cloud key service or hardware module: `obaaf dsse prepare` writes the bytes to sign, the key service signs them, and `obaaf dsse assemble` checks the signature and writes the envelope. Then set `signing: keys` in the release policy. On Jenkins, the [release templates](../jenkins.md#the-release-lane-on-jenkins) do all of this.

**Keep as evidence.** The provenance and build record of the latest release.

<a id="item-3-2"></a>
## Item 3.2: Automatic provenance check before upload

**Why.** Provenance that nobody checks protects nobody. A check in a separate step before upload flags files the release lane did not build. In the APT41 and PipeMon cases, such a check would have flagged files that did not come from the release lane (Paper 2, Table 7).

**Do this.**

- Write a release policy, starting from [obaaf-policy.example.yaml](../../templates/github-actions/obaaf-policy.example.yaml): which workflow may sign, from which refs, which isolation tiers are allowed, how many approvals a release needs.
- Run `obaaf verify release` before the upload step, and let a failure stop the job. The [publish template](../../templates/github-actions/workflows/obaaf-publish.yml) does this twice, from the default branch: once before anyone approves, with the result in the run summary, and again, with the approvals, right before the upload. It blocks the upload when provenance, the build record, the required approvals or an agent record is missing or does not verify, or when the released commit is not on the protected branch (FR6).
- Test it once: put an artifact the release lane did not build into a release, and confirm the upload is blocked.

**Keep as evidence.** The pipeline step and its log for the latest release.

<a id="item-3-9"></a>
## Item 3.9: Read-only release archive

**Why.** A read-only archive lets you prove later exactly what you shipped, compare it with a suspected tampered build, and investigate an incident.

**Do this.**

- After each release, copy the artifacts, debug symbols, provenance and build record to storage where no pipeline or user identity can change or delete them for a set period. Object storage with object lock or immutability policies offers this.
- Give the pipeline permission to add files but not to delete or overwrite them.

**Keep as evidence.** The archive's permissions or retention settings, and the latest release in it.
