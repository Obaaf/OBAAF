# Upgrading OBAAF

What changes when you move to a newer OBAAF, and how to do it so that a gate that turns red tells you something. OBAAF is 0.x: a release may change what passes. Release 0.3.0 showed the need. The code after it turns a passing gate red in several ways without a line of the workflows having changed, each on purpose.

## Checking an agent job against saved settings

Run `obaaf check . --settings FILE` with the audit snapshot from the repository you are checking. Keep the file inside that repository and check the whole repository: a single-file scan, `--lanes`, or a snapshot outside it (a file link from outside included) leaves the environment control at "cannot tell", because the checker cannot then check who owns the file. OBAAF-GHA-005 records its UTC date and tests exclusive secret storage and protected-branch access. Refresh observations older than 30 days. An unread setting carries its reason into the finding. Review the other four controls and any separate code-ownership finding. When verification clears a finding covered by a baseline, its entry becomes stale and can fail the gate at the configured severity. Review and remove the obsolete entry. The shipped catalogue lists one commit of the egress action, so the credential-isolation control can be verified for a job that pins it ([Reviewed egress action pin](../CHANGELOG.md#reviewed-egress-action-pin)).

Checkout and tool-pin suggestions repeat the selected snapshot when the fix can use it. Use `obaaf fix . --settings FILE` for paperwork with the same evidence. A fix needs the snapshot in the repository working tree so it can check the file and its ownership in a private copy. A path through a linked directory is interpreted where that directory leads. If the snapshot is outside the repository or under `.git`, the report gives manual guidance. Select a snapshot in the working tree and rerun the check before using its fix suggestions. A single-workflow check still cannot verify snapshot ownership. The generated blocking gate and egress draft do not support this option.

## Versions, and what to pin

- **A release** has three numbers (`0.3.0`). It is on PyPI (`pip install obaaf==0.3.0`) and has a tag (`v0.3.0`).
- **The development build** at `80db1e6` on `flagship` reports `0.4.0.dev0`. Development commits can share a version, so record the commit as well. The development text report ends with `Checked by obaaf VERSION.`; JSON and SARIF reports, baselines and generated documents also record the version.
- **Pin what your gate runs**: a release from PyPI, or the `setup-obaaf` action at a full commit SHA. A gate that follows `main` can fail because OBAAF changed, on a day nobody chose.
- How a release is made is in [releasing.md](releasing.md). What each release changed is in the [changelog](../CHANGELOG.md).

## How to upgrade

Move the pin in a pull request of its own, so that the gate runs once with the new version and nothing else changes with it.

1. Read the section below for the version you are moving to.
2. With the new version, run the report without failing on finding severity: `obaaf check . --fail-on never`, with `--baseline FILE` if your gate uses one. Read its first lines and anything marked "Not accepted".
3. Run your gate's own command and look at the exit status. If it is 1, the report says why: each finding that counts says under it what its acceptance lacks, and an old baseline is named with the command that converts it.
4. Do what the section says: convert the baseline, complete the `ignore` entries, correct the declarations.
5. Run the gate's command again. Commit the pin together with the changed baseline and configuration, and have the baseline reviewed like a workflow.

## From 0.3.0 to the prospective 0.4.0 release

Nobody is affected until they move: a repository pinned to 0.3.0 or to a commit sees no change. This section becomes the note for 0.4.0 when that is released, and may gain entries until then.

### Set up a first GitHub Actions check

From the repository root, run `obaaf init` (run in a folder inside a Git repository, it names the repository's top folder). Review the proposed agent lanes, the secret names it lists for review, and the diff for both files. Init declares an agent lane only for a job the checker would not put in that lane by itself, such as one found only by a model-provider key. It lists the jobs the checker finds unaided, with the checker's reason, and declares them too when the checker does not also find their agent in the files of the last commit, outside submodules, as Git stores them: a script that is untracked, ignored, in a submodule, edited since the commit or stored through LFS is not in the checkout the generated workflow checks. Commit your workflows and scripts before running init, or it declares more than it needs to. An undeclared job stays an agent job only while the checker can still see its agent, and a check of one workflow file on its own reads neither the repository's scripts nor its local actions. Run `obaaf init --apply` to create `.github/obaaf.yml` and `.github/workflows/obaaf-pipeline-check.yml`. If either file differs from the proposal, init prints the differences and stops before creating either file. A repository using another supported configuration path must reconcile that file first.

Init reads GitHub workflow files locally, with the local composite actions and repository scripts the checker reads. It proposes agent lanes for jobs with recognized model-provider key names, and for catalogued tools the checker does not itself place in the agent lane. A job that makes a single provider health check or calls a perception model can hold such a key, so review each proposed lane. It proposes a secret’s required environment when all observed uses identify the same literal environment. Check where the secret is actually stored in GitHub before accepting the proposal. A computed environment, multiple environments or a reusable workflow parameter leaves the name for review. Check for agents the checker cannot see, such as a command built from a variable or a script fetched or generated during the job.

The generated workflow pins the development checker to a commit on `flagship`. It checks pull requests against configuration from their target commit, checks pushes with their own configuration, and reports the findings in the job log. Finding severity leaves the first job green. A checker or setup error can still fail the job. A pull request can still change the workflow file itself, because GitHub runs a pull request's copy of it, so that pull request's own report can differ; code-owner review of `.github/`, required by a branch rule, keeps such a change from merging.

Init ends with the checker’s to-do list and the command to preview fixes. For a repository path that cannot be shown on one line, follow the instruction from inside that repository. A first preview checks the proposed files on a temporary copy and labels that result. If the copy is unavailable, it identifies the reason and shows the current repository. Apply shows the installed configuration and workflow’s findings.

#### Optional companion checks

Add `--with-scanner` once for each companion you want in the preview. Supply the same options when applying it. For example:

```sh
obaaf init --with-scanner zizmor --with-scanner actionlint
obaaf init --with-scanner zizmor --with-scanner actionlint --apply
```

`--with-scanner poutine` enables poutine independently. The default workflow includes OBAAF alone. If you already applied a workflow, a new selection produces a conflict and a diff. Review that diff and edit your existing workflow to adopt the steps you want. New scanner steps start with `exec 2>&1` so diagnostics and findings reach the runner on one stream between the matching workflow-command markers. Steps written by development builds before this change lack that line; to update them, preview init with your existing scanner selections and review the scanner changes in the diff. Switching the gate threshold keeps the installed scanner steps, in either form.

With `--with-scanner poutine`, poutine 1.1.6 reports “Github Action from Unverified Creator used” (severity note) for `Obaaf/OBAAF/actions/setup-obaaf` in the generated workflow, even though the action is pinned to a commit. The note concerns the action owner’s verification status; the step still succeeds. In your own runs it appears in the `Report poutine findings` step. [Example from OBAAF’s CI](https://github.com/Obaaf/OBAAF/actions/runs/44905703077/job/136850680136), which runs that step’s script on a test repository and prints its output with a `| ` prefix.

Each selected step pulls an upstream Linux/amd64 image by digest, then scans the checkout mounted read-only with the container’s network disabled. A failed pull fails the step. The scanner receives no GitHub token. Findings appear in the Actions log. A scanner startup or analysis error can fail its step. A pull request can change what a scanner reports: the scanners read the pull request’s own files, zizmor honours inline `# zizmor: ignore[...]` comments, and actionlint, according to its documentation, still parses a repository’s `.github/actionlint.yaml`, so a malformed one can fail its step. Only OBAAF’s own step reads its configuration from the target. Zizmor uses offline audits with configuration loading disabled. Actionlint checks the workflow syntax, disables its shellcheck and pyflakes integrations, and treats its documented finding status (1) as successful. Poutine analyzes the local repository with its built-in rules and the release check disabled. Actionlint and poutine receive an empty configuration created outside the checkout.

These are the versions measured in the landscape comparison. The digests are the Linux/amd64 image manifests; to check one, run `docker manifest inspect --verbose IMAGE:VERSION` against the official registry and compare its `linux/amd64` entry. The init template targets the standard x86-64 Ubuntu runner. OBAAF's CI runs each generated step's script as written against its pinned image on GitHub's `ubuntu-latest` runner, in an advisory job (`scripts/check_companion_scanner.py`). It runs the step alone, on a fresh one-commit repository rather than on a checkout made by `actions/checkout` ([#333](https://github.com/Obaaf/OBAAF/issues/333)). On ARM runners an amd64 image does not start without emulation.

### Preview the changes to your OBAAF files

In the development build, start with `obaaf fix .`. Pass the same configuration, baseline, platform and threshold as your check; the configuration and baseline must be inside the repository. The preview groups the proposed changes and runs the check on a private copy. It shows the diff it could verify and gives a reason for each change it withheld.

To see which old acceptances would carry over, supply the owner, reason and expiry you intend to record. For example, replace the values in this command before using it.

```sh
obaaf fix . --baseline .github/obaaf-baseline.json --fail-on low \
  --owner @YOUR-TEAM --reason "Your reason for retaining these risks" --expires YYYY-MM-DD
```

Read every finding under “You are accepting risk” and every listed removal. The preview leaves the original files untouched. To make the change, add `--apply` on Linux, or `--patch FILE` on any system ([Save a proven edit as a patch](#save-a-proven-edit-as-a-patch)). For CODEOWNERS, decide who should approve each listed path and make that change by hand.

### Pin a directly installed agent tool

OBAAF-GHA-025 keeps one to-do group for tool installs. The counts show how many direct install occurrences are candidates and how many findings need manual review. The preview's final proof determines which candidates can change. With a legacy baseline, migrate it first. Resolve unmatched baseline and ignore entries with their owners, then rerun the check to get checkout and pin commands. The check's report does not list unmatched ignore entries: the paperwork preview, `obaaf fix` with the check's path and options and without `--pin` or `--tighten`, names each one and proposes its removal, and the to-do gives that command. A check of one file, of the `.github` or `.github/workflows` folder, or of one platform cannot tell an entry for a finding elsewhere from an unmatched one, so the to-do asks for a check of the whole repository first. Select the exact version your team has reviewed and use the same path, configuration, baseline, platform and threshold as the check. For example, if your team has selected version `1.2.3`:

```sh
obaaf fix . --pin @openai/codex=1.2.3 --baseline .github/obaaf-baseline.json --fail-on low
```

The edit appends the supplied version to the package in a literal `npm install -g PACKAGE` workflow step. A separate version query for the installed CLI may follow. OBAAF also recognizes the `sudo` form when followed by that query. It leaves scripts, indirect invocations, shared YAML and other install forms for manual review. Choose one package per invocation. The preview does not look up the version, download the package or execute the workflow.

Use `--candidate NAME` from the preview to request one occurrence. On Linux with extended-attribute support, add `--apply` to write a proven diff to clean tracked targets. On macOS or Windows, add `--patch reviewed.patch` to the preview and apply it with Git ([Save a proven edit as a patch](#save-a-proven-edit-as-a-patch)). OBAAF reports affected acceptances and retains the original files when the named edit cannot be proven. A request in which the proof withholds every candidate exits 1. When some are proven, the withheld ones are listed and the command exits 0. For a UTF-8 workflow, an unknown candidate name exits 2. If the workflow cannot be decoded as UTF-8, the fixer can identify the reported job and package but cannot verify a step number. A request naming that job and package is withheld with exit 1. A repeat is a successful no-op when the checked files show the requested direct install at the exact selected version (with `--patch` it exits 1, as there is nothing to save). Other packages can still need work. An unresolved manual install of the same package, an absent package or a conflicting directly installed version cannot establish that the request is satisfied. A malformed package or version exits 2.

### Tighten credentials on a checkout

Run `obaaf fix . --tighten checkout-credentials` with the same gate options, including its baseline. The command previews a literal `persist-credentials: false` on directly identified checkout steps reported by OBAAF-GHA-011. Review later Git operations that use the checkout credential. A checker proof reads the workflow without running those steps.

The preview gives each candidate a name based on its workflow, job and step number. To request one checkout by name, copy the displayed name and supply it to `--candidate`. For example:

```sh
obaaf fix . --tighten checkout-credentials --candidate '.github/workflows/ci.yml#build/step-1' \
  --baseline .github/obaaf-baseline.json --fail-on low
```

If the change disturbs accepted findings, the report gives the count and identifies the affected rules and locations. If it leaves unmatched entries, it names them. Review the entries with their owner, make any separately approved changes, and rerun the named preview with the same gate options. Add `--apply` to write a proven diff to clean tracked targets. An unresolved named request exits 1 and leaves the files untouched.

### Save a proven edit as a patch

To save a proven paperwork, baseline, checkout, package-pin or gate edit, add `--patch FILE` to its preview. This is how to make the change on macOS and Windows, where `--apply` does not run. Choose a new file: an existing one is refused. The command writes only the patch, and exits 1 when there is no proven edit to save. Then, with the files as the preview saw them, read the patch and run `git apply -v --check FILE` before `git apply -v FILE` from the top folder of the Git work tree (for a folder outside any work tree, from the checked folder). Git skips, without an error, any path outside the folder it runs in; with `-v` it says so, printing `Skipped patch` for each file it leaves alone (and, when applying, `Applied patch` for each it changes). Git applies the patch without rerunning OBAAF's proof, so run the checker again before committing.

`--patch` needs the checked folder to be the top folder of the Git work tree, or a folder outside any work tree, which OBAAF takes to be one where neither it nor a folder above it holds `.git`. Git reads a patch's paths from the top, so a patch made from a folder below it would change other files, or none. Where there is a `.git`, Git must run and confirm either that the folder is the top or that there is no repository: with no `git` on the `PATH`, or a repository Git will not read (one owned by another user, say), `--patch` is refused, as `--apply` is. It is also refused while `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_DISCOVERY_ACROSS_FILESYSTEM` or `GIT_ATTR_SOURCE` is set. These checks run Git with your Git configuration, including any given in the environment (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT` and the rest) and the files it includes, so they see the attributes and ignore rules your `git apply` will use. A target that Git's index marks assume-unchanged or skip-worktree, or that Git ignores, is refused, because Git would not show the change; so is one with a `filter`, `ident` or `working-tree-encoding` attribute, as with `--apply`. On Windows, a proof tree that holds a reparse point (a junction or a link) or a hard-linked file is refused.

The patch holds the proven bytes, including CRLF line endings and a missing final newline. Git can still write a file that differs from them, where `--apply` would not:

- with `core.autocrlf=true` (Git for Windows sets it by default), or a `text`, `eol` or `crlf` attribute, Git can convert the file's line endings as it writes it;
- with `apply.whitespace` set to `fix` or `strip`, Git changes whitespace in the added lines; add `--whitespace=nowarn` to both commands to keep them as proven (with Git's default, `warn`, it reports whitespace errors in added lines and applies them as written);
- Git replaces the file, so its extended attributes are not kept and its permissions can change (a `0600` file came back `0644` in a test).

### Preview confinement for one agent job

Run `obaaf fix egress --job NAME` using the job ID under the workflow’s `jobs` key. If your installed catalogue lists no released egress-action commit, the command explains the hold and stops.

Once a release commit is listed, the command can draft a recognised agent run step and show the control verdicts from a private copy. For a harness the checker cannot identify, or when several steps run an agent, supply the exact name or ID with `--step 'Run review'`. The same selection works with `--brief`. Only that step is confined: another step that runs an agent stays outside, and the verdicts say so. The preview keeps the job’s original text around the chosen run step, including comments and scalar spelling. Because the job is printed as it is written, a job that holds a character Python does not count as printable (other than a tab and a line ending), in a value or a comment, or a carriage return that is not part of a CRLF line ending, is refused; escapes such as `\u200B` in a quoted value are printed as written. If multiple workflows use the same job ID, supply the workflow file as the path. The draft requires manual review. Replace the reserved host placeholder with the hosts the command needs, taking into account that each host also permits its subdomains. After adopting the draft, the action’s `denied` output identifies other hosts the command tried to reach.

Because `obaaf fix egress` selects this command, write a repository folder named `egress` as `./egress` in other `obaaf fix` commands. The commands OBAAF prints already do.

Generate a Markdown work order on a branch you trust with `obaaf fix egress --job NAME --brief`. This option shares the draft’s release hold. Once available, it prints the job and step location as labelled data, the proposed credential placement, the checker’s predicted verdicts and a command for verifying the edit. Reasons for unresolved controls and egress-action conditions appear as bounded, quoted diagnostic data, except that a control's own reason is left out when the egress action also reports conditions; the ordinary preview shows it. Supply any path variables from your trusted check invocation. Review the result before removing an obsolete acceptance.

### Enable the generated workflow’s gate

After reviewing outstanding findings and any acceptances, commit the generated workflow. Run the preview from the repository root and review its diff and count. On Linux with extended-attribute support, the second command applies that edit. On macOS or Windows, add `--patch reviewed.patch` to the preview and apply it with Git ([Save a proven edit as a patch](#save-a-proven-edit-as-a-patch)).

```sh
obaaf fix --gate medium
obaaf fix --gate medium --apply
```

Choose `low`, `medium`, or `high`. The proof checks the current repository with that threshold and leaves existing acceptances alone. The gate uses `.github/obaaf-baseline.json` when present. Supply `--baseline FILE` on both invocations to use another existing baseline. Without a baseline, each outstanding finding at the threshold counts. Creating acceptances remains a separate, explicit decision.

On a pull request, the checker uses configuration from the exact target commit. It honors a baseline entry only when both commits contain the same entry, including its owner, reason and expiry. Fix a finding and remove its entry in the same pull request. Removing an entry while the finding persists makes the finding count again. A new or changed entry cannot grant an acceptance on that pull request. If either commit lacks the baseline, every outstanding finding at the threshold counts. On pushes, the checker uses the pushed repository’s own policy and reports stale entries. A policy read failure stops the job. The preview can upgrade an earlier, unedited init workflow and preserves the generated companion steps. For a custom workflow it prints the threshold and target-branch policy instructions for a manual edit. Apply requires a clean tracked workflow.

Enabling a gate or changing its threshold keeps the workflow’s checker commit. For a gate-capable generated workflow, take the exact commit from the new init preview and update the `Obaaf/OBAAF/actions/setup-obaaf@` line in a separate reviewed change. Keep the existing baseline path, threshold, target-branch policy steps and companion checks. Automatic gate changes recognise a generated workflow, from the template of any build since gate support, that installs the commit it was generated with (`4e2ba22` for the first template, `8caddd6` for the one that reads a settings snapshot) or the commit in the current init template. After you move the pin to another commit, a later change of the template's commit leaves threshold changes to a manual edit. Moving the pin does not add the steps of a later template: a workflow from before `8caddd6` does not read a settings snapshot ([ci-integration.md](ci-integration.md#a-required-check-in-github-actions)).

For the original report-only workflow that predates gate support, run init with the same companion options. It reports a conflict and shows the proposed workflow as a diff against yours. Adopt the proposed workflow whole to continue reporting and keep automatic gate activation available. A team ready to block can first enable the gate with its existing checker, then update the pin. Verify the resulting report or gate on a push and a pull request before merging.

### What can turn a passing gate red

| What you have | What happens | What to do |
| --- | --- | --- |
| A baseline written by 0.2.0 or 0.3.0 (`obaaf-baseline/v0.1`) | It is still read and accepts nothing: every finding it covered counts as new, marked "Not accepted" | `obaaf baseline migrate FILE --owner OWNER --reason REASON --expires YYYY-MM-DD`, once. It carries over the findings the old file covers that a new entry may accept, and accepts nothing new |
| An `ignore` entry with no `owner:` | It ignores nothing, and the finding is reported with "because it names no owner" | Add `owner:` (`@user`, `@org/team` or an e-mail address) |
| An `ignore` entry whose reason has fewer than four letters or digits, or whose `until` is more than 366 days ahead | It ignores nothing, and the report says which | Give a reason; bring the date within a year |
| An `ignore` entry whose `until` is a date in another spelling (`20270131`) | A configuration error, exit status 2. (A time of day, `2027-01-31T10:00:00Z`, ended 0.3.0 in a traceback when the entry matched a finding; it is the same error now) | Write `YYYY-MM-DD` |
| A lane declaration that does nothing: `OBAAF_LANE: agnet`, `OBAAF_LANE` in a step's `env`, a `lanes:` entry for a job that is not there | 0.3.0 listed it in a note. It is the finding `OBAAF-CFG-001`, high in most cases, and fails the default gate | Correct or delete it, then run `obaaf check . --lanes`. Correcting it can bring the findings it was hiding. To keep it, accept it in the baseline; an `ignore` entry cannot accept this rule and is a configuration error if it names it |
| An agent job whose egress control is a blocking `step-security/harden-runner` step | 0.3.0 reported no `OBAAF-GHA-020` for it. It is now reported. It is "not met" when the step is not the job's first, runs behind an `if:`, is at a commit OBAAF lists as a release before v2.16.0, leaves `sudo` or containers to the job, or the job runs in a container on a GitHub-hosted runner; otherwise "cannot tell" (a tag or an unlisted commit included). A baseline entry written for "cannot tell" before slice 2c.3 stops counting where the monitor is now "not met", because that is another case of the rule | Set `disable-sudo-and-containers: true` and pin a release from v2.16.0 on, then accept it again; or move the job to GitHub's native egress firewall or OBAAF's egress action, which can clear it |
| A baseline accepts OBAAF-GHA-020 for a job already using [the listed egress action pin](egress-control.md#using-it) | If the job meets the egress control conditions, the checker clears the finding. Its stale baseline entry can now fail a gate at `--fail-on low`. | Review the cleared finding, remove its obsolete baseline entry and rerun the gate. |
| A baseline accepts OBAAF-GHA-005 for a job that uses the listed pin, and the check runs with `--settings` | If all five controls verify, the finding clears and its baseline entry no longer matches. OBAAF-GHA-005 is high, so the stale entry can fail the default gate (`--fail-on medium`). | Review the cleared finding, remove its obsolete baseline entry and rerun the gate. |
| An agent job with a step that runs only `pnpm add -g`, `yarn global add`, `bun add -g`, or `npm install -g` of a `.tgz`, `.tar` or `.tar.gz` "version", of an agent's CLI before OBAAF's egress action or the agent's step on GitHub's firewall | It was read as installing only (D-053). It is now "cannot tell" for the egress control and `key-out-of-reach` (D-134): pnpm, yarn and bun read configuration from the working directory, and npm installs a tarball "version" as a file from it | Install with `npm install -g` from the registry, by version or tag, not from a file; or accept the finding |
| An agent job with an `actions/cache` step before OBAAF's egress action whose `path` is an expression, has a `..` part, starts `~` and a user's name, or is an absolute path outside `/home` | It is now "cannot tell" for the egress control: such a path can reach `/tmp` without naming it (D-134) | Write the path out as a plain path in the workspace or under `/home`, or move the cache to another job |
| A job whose agent CLI is only in the `run` input of OBAAF's egress action, or in a script that input runs | It is now an agent job, with the agent rules (OBAAF-GHA-003, 005, 020 and the rest) | Fix or accept the findings; OBAAF-GHA-020 can be cleared by the action itself (see "Egress control" in the changelog) |
| An agent job that runs `awf ... --` in a script (where a command starts, outside a comment), with an accepted `OBAAF-GHA-020` | The finding is now the case `awf` ("cannot tell"), not `none`, so an acceptance of `none` no longer names it | Accept it again |
| A job whose `if:` only looked like a test of the event (the test inside a string, compared with `false`, or outside `${{ }}`) | It is now checked for every event that can start it, and can have findings it did not have | Fix the findings, or write the `if:` as a plain comparison of `github.event_name` |
| An input written in another case under `with:` (`REF:` for `ref:`) | It is read as the input it is, so a rule that looks at it now sees it | Fix the finding |
| A release policy (`signing: keys`) or `obaaf dsse assemble --public-key` that names a key outside ECDSA P-256 and P-384, Ed25519 and RSA (P-521, secp256k1, DSA, Ed448, X25519, a binary curve) | The key is refused when it is loaded, with an error naming the file, and `obaaf verify release` and `obaaf dsse assemble` end with status 1. Before, a key on another prime curve was accepted, a binary-curve key ended both commands in a traceback (with the pinned cryptography 50.0.1), and the other kinds failed later | Sign with a P-256, P-384, Ed25519 or RSA key and name its public key in the policy |
| A step that gives one input twice under two spellings (`ref:` and `REF:`) | An error for the file, and exit status 1 whatever `--fail-on` says: the checker cannot tell which value GitHub uses | Keep one of the two |
| A step that runs `obaaf check --lanes` | It ends with 1 where `obaaf check` reports an error for a file (it could not be read or parsed, an input given twice, an expression too deep), and with 2 when the path has no workflow or Jenkinsfile or is not there; it ended with 0 in every case (slice 3.2a) | Fix the file the `error:` line names, or the path |

`obaaf audit` is in no release, so nothing about it can change for someone on 0.3.0. Since slice 2d.2g (decision D-066) a run can fail where it passed: an environment limited to a branch (the default branch too) that has no rule requiring an approval is a finding; the GitHub Actions app as a ruleset's bypass actor is high; a required check whose only job is in a workflow GitHub does not run (Actions off, an unpinned action under the pinning requirement, an event an enforced policy blocks) is a finding when the requirement names GitHub Actions, every workflow file was read, and no job's token may write checks or statuses (or Actions is off), and "cannot tell" otherwise; a protected secret also stored in an environment open to every branch is high; a 64-digit ref under the pinning requirement is reported. Some answers become "cannot tell" (required checks reported only through `pull_request_target`, for `OBAAF-SET-007`, job names and matrix values that YAML 1.2 reads otherwise, policies with repository conditions, a repository with `.github/workflows/actions.lock`), which fails only with `--fail-on-cannot-tell`. Since slice 2b.7 (decision D-076) more answers become "cannot tell": a required check whose only job is in a file GitHub may not run, which now includes a file that uses another repository's action or reusable workflow while only selected actions may run, unless the list as written allows it (GitHub's own actions where they are allowed, or an entry that is the reference itself; a wildcard entry is not matched), a file that calls another repository's reusable workflow under `selected`, whatever the list says, a file with a local action, a `docker://` image or an empty `uses` under `selected` or `local_only`, a file with a job id that has a character outside ASCII or is 100 characters or more, or a job whose `uses` is empty, a file that calls a workflow with `$/` or with `uses: ./` alone, a file in a cycle of calls and one that starts more than three nested calls; and a file with a job id outside GitHub's form (`bad id:`, `1abc:`) is now one GitHub refuses, whose jobs no rule counts. It can fail where it passed: a workflow called with `$/` is now read, so `OBAAF-SET-002` and `OBAAF-SET-011` can report its jobs where they said "cannot tell" about the caller; `OBAAF-SET-012` reports a called workflow's jobs when one of its callers is written with `$/` and declares no permissions; and `OBAAF-SET-007` weighs a job in a file GitHub may not run, so its findings (a paths filter, activity types, no run on a pull request's commit) come back for such a file. And it can pass where it failed: every rule that reads workflow files gives "cannot tell" for a file with a job id GitHub refuses, where it gave that file's findings; `OBAAF-SET-008` is "cannot tell" for a job in a file GitHub may not run; `OBAAF-SET-007` is "cannot tell" where another job may report the check on a route that gives no finding (a dispatch, a branch pattern, `pull_request_target`, no filter; in a file GitHub may not run or may read otherwise, or under names that could not be written out, included), or a second paths or activity-type filter may cover what the first leaves out; `OBAAF-SET-012` no longer reports an undeclared `$/` caller of a workflow whose jobs all declare their permissions; and `OBAAF-SET-002` and `OBAAF-SET-011` can answer "no finding" about a `$/` call where they said "cannot tell". If you run it from a commit after 0.3.0: it now applies rules and ends with status 1 on a finding at medium or above (`--fail-on never` gives the old status), and `--format json` prints a report with the snapshot under `snapshot`, where it printed the snapshot; with `--expected`, the comparison is under `drift` in that report, where it printed a document of its own, `obaaf-settings-drift/v0.1` ([the settings audit](settings-audit.md)).

Since slice 2b.9 (decision D-140) `OBAAF-SET-011` follows GitHub's page on reusing workflows, and an `obaaf audit` can fail where it passed: a job that calls a workflow of this repository without passing a secret that an environment holds and a job there reads is a medium finding, whatever that job declares (a called workflow gets only what its caller passes). It can pass where it failed: a secret kept only in an environment and passed by name (`NAME: ${{ secrets.NAME }}`) to a called job that declares that environment is no longer a finding, and a call to a workflow in another repository, or one that was not read, is "cannot tell" where it was a finding or did not apply. To clear the new finding, pass the secret from the caller by name or with `secrets: inherit`, and declare the environment on the called job; do not copy the secret to the repository.

Since slice 2b.9b (decision D-141) `obaaf audit` also reads each environment's custom deployment protection rules (`/environments/{name}/deployment_protection_rules`, one request more per environment; anyone may read it for a public repository). An `obaaf audit` can pass where it failed: an environment any branch may use that has a custom rule and no required reviewers is medium where it was high, and a narrower limit beside one (a wildcard, a tag pattern, a branch anyone with write access can push to), `OBAAF-SET-002` beside one, and `OBAAF-SET-003`'s copy behind one are "cannot tell" where they were findings, which fails only with `--fail-on-cannot-tell`. A protection rule of a type the audit does not know counts the same, where it counted for nothing. No custom rule makes a finding or raises a severity; where the custom rules could not be read, or a snapshot from before this read is given with `--from-snapshot`, each finding stands and says that it may overstate. **It can also fail where it passed**: an environment that a job or `protected_secrets` names and the list does not have is a finding again (`OBAAF-SET-001` medium, `OBAAF-SET-003` high) when a part of another environment, its branch patterns or now its custom rules, could not be read, where it was "cannot tell"; and `OBAAF-SET-003`'s low finding for an entry that protects nothing in its environment is given there, where it was left out with no word. **A drift check can fail where it passed**: a committed snapshot taken before this read holds no custom rules, so its environments are "not compared" (`not_recorded`) until you take the snapshot again with the same access and commit it. **An earlier `obaaf` refuses a snapshot this version writes**, whose environments carry the new field `custom_protection_rules`: if your workflows pin an earlier checker and pass `--settings`, take the snapshot with the version they pin. If the custom rules could not be read, `environments` is only partly read, as when an environment's branch patterns could not be read; what `obaaf check --settings` then answers is in the next paragraph. A drift check where both sides read an environment only in part now fails on a part that only one of them read, which it compared as a change or, in between, left out.

Since #385 (decision D-104, with a proposed clarification) `obaaf check --settings` uses a partly read environment list for the environment control of OBAAF-GHA-005 when the parts not read are outside that control. Custom deployment protection rules not read, the named environment's own or another's, and another environment's branch patterns not read, in a snapshot from any version since the audit read each, no longer make the control "cannot tell": it is "verified" when the secret's name is only in the named environment and only protected branches may use it, and "not met" when, for example, that environment permits any branch, does not hold the secret, or is not in the list. Before, each was "cannot tell" (in a snapshot from before slice 2b.9b, the missing custom rules never stopped the control). **This can fail a gate that passed**: if it verifies the last control of OBAAF-GHA-005, the finding is fixed and a baseline entry that accepted it no longer matches. The selected-branch patterns of the named environment (or of one whose name differs only in letter case) not read, and a problem under a name the list does not hold, still leave it at "cannot tell".

### What a script that reads the output will notice

- **The text report begins differently**: `Accepted risk: ...` and `Other findings: ...` come first. **It also ends differently**: the last line is `Checked by obaaf VERSION.`, with an action list just above it. An unconfigured check explains its limits before that list. Add `--summary` to a text gate command (it refuses `--format json` or `sarif`, `--lanes` and `--write-baseline`) for a shorter view with the same exit status. It opens with the accepted risk and includes scan errors, an old-format baseline and stale baseline warnings. The line `Baseline: N finding(s) accepted by the baseline, M new.` is unchanged.
- **`obaaf check --lanes` can end with 1 or 2**: 1 when `obaaf check` would report an error for a workflow or Jenkinsfile (it could not be read or parsed, an input is given twice, an expression is too deep to read), each an `error:` line on standard error, with the jobs of a file that could not be read or parsed left out of the list; 2 when the path has no workflow or Jenkinsfile, or is not there. A Jenkinsfile part of whose pipeline was not analyzed is a `note:` and does not change the status, as for `obaaf check`. It ended with 0 in every case before.
- **The `ignored:` lines** read `ignored: RULE path:line - accepted by OWNER until DATE: REASON`.
- **A path is printed in quotes** where it heads its findings, unless it is made of visible ASCII characters with no space.
- **The notes no longer list lane declarations that do nothing**; they are findings. In JSON they are in `findings` and no longer in `notes`.
- **JSON keeps every top-level field and every field of a finding.** New: `acceptedRisk` and `summary` before the findings; `state` on every finding, `kind` and `facts` where the rule gives them, `acceptance` where a baseline or ignore entry names the finding, and `controls` where it has any; `fixed`, when there are any, a list of findings cleared by controls the checker verified, which are no longer in `findings`; `todo`, the outstanding findings grouped by what they need (see [checker-configuration.md](checker-configuration.md)). The entries under `baseline.stale` are the baseline's own entries, so with a converted baseline they have `owner`, `reason` and `expires`, and `kind` and `facts` where the finding had them, and no longer `fingerprint` or `message`; the `no longer found:` lines of the text report end differently for the same reason.
- **SARIF**: an accepted finding has a suppression, and its message says who accepted it. Errors and notes are notifications of the run.
- **`--write-baseline`** needs `--owner`, `--reason` and `--expires` for anything it newly accepts (exit status 2 without them), and does not write over a file that is not a baseline. It ends with 1 when it leaves out a finding at or above `--fail-on` that a check with the new baseline would then fail on (slice 3.2b; above).
- **Each finding in the text report has a `Why:` line** under its message: one sentence from the rule's `why` in the catalogue (slice 3.2b). `--no-fixes` leaves it out with the `Fix:` line, so a report written with `--no-fixes` is unchanged. JSON has the same sentence as `why` on every finding, and SARIF begins each rule's help with it (`Why it matters: ...`).
- **`obaaf audit`'s text report has a `Why:` line** just before each rule's `Fix:`: one sentence from the rule's `why` (slice 3.2c). `--no-fixes` leaves it out with the fix. In its JSON report each entry under `rules` has `why` and `fix`; the format name is unchanged.
- **`obaaf audit`'s list of what was read quotes names** (slice 2b.8): required checks, patterns, reviewers, secrets, events and paths are in double quotes, and a single value such as a ruleset's enforcement or the default branch is quoted unless it is one plain word. A script that reads those lines, for example to pick out the required checks, must take the quotes off; the JSON report is unchanged and is the place to read values from.

### One upgrade, start to finish

A repository with two workflows, a baseline written by 0.3.0 that accepts its four findings, and one job declared `OBAAF_LANE: agnet`. With 0.3.0 its gate, `obaaf check . --baseline .github/obaaf-baseline.json --fail-on low`, passes: "4 finding(s) accepted by the baseline, 0 new", and a note about the declaration. With the development checker the same command ends with status 1:

```text
Baseline: 0 finding(s) accepted by the baseline, 5 new.
  The baseline is in the old format (obaaf-baseline/v0.1). Its entries name no owner, reason or expiry date, so none of them accepts a finding. Convert it once, saying who accepts these findings, why and until when:
    obaaf baseline migrate .github/obaaf-baseline.json --owner OWNER --reason REASON --expires YYYY-MM-DD
```

Migration carries over a legacy match only when a new baseline entry may accept it. Its receipt names each match it leaves open and explains why. A finding no entry can accept is one: when the baseline has no code owner, an entry for the missing ownership would let the file vouch for itself, so give the file an owner. A finding waiting on an ignore entry that has expired or is not valid (a 0.3.0 ignore entry names no owner) is another: renew, complete or remove that ignore entry, where the decision was made. An old entry that names a finding a valid ignore entry accepts is counted and not carried over. When it can carry over no match and leaves at least one open, migration exits 1 and preserves both the input and any separate `--output` file: act on the receipt and run it again. Once the findings the old file named have all gone, it has nothing left to carry over; delete it.

Convert the baseline:

```bash
obaaf baseline migrate .github/obaaf-baseline.json \
  --owner @my-org/build --reason "Inherited on adoption; tracked in issue 12" --expires 2027-03-31
```

It answers "4 finding(s) carried over" and "1 finding(s) were not in the old baseline and are not accepted by the new one". The gate still ends with status 1, now for one finding:

```text
    12  HIGH   OBAAF-CFG-001  Lane declaration that does nothing  [job triage]
```

Correct `agnet` to `agent`. The job is an agent job now, and the gate ends with status 1 for three findings nobody had seen: `OBAAF-GHA-003` (the agent job can write), `OBAAF-GHA-005` (a secret in an agent job) and `OBAAF-GHA-020` (no egress restriction). In a real upgrade you would fix what can be fixed first. Here nothing is fixed and all three are accepted, to show what the command does:

```bash
obaaf check . --write-baseline .github/obaaf-baseline.json \
  --owner @my-org/build --reason "Agent job found on upgrade; its controls are tracked in issue 31" --expires 2027-01-31
```

"3 finding(s) newly accepted by @my-org/build until 2027-01-31, 4 kept with the owner, reason and expiry date they had." The gate passes, and its first line says what that pass rests on: "Accepted risk: 7 finding(s) are accepted and do not fail the check (3 high, 2 medium, 2 low)".

`tests/test_adoption_path.py` runs this sequence.

### The first adopter

Expectrail is maintained by one of OBAAF's authors. Its gate runs this command:

```bash
obaaf check . --baseline .github/obaaf-baseline.json --fail-on low --no-fixes
```

On 2026-11-19 UTC the development checker at `80db1e6` ran that command on a read-only copy of the public Expectrail source at `6bc5dce7`, with one restricted path excluded. It exited 1 with **69 new findings (46 high, 3 medium, 20 low) and zero accepted**. Of the 69, 37 were named by baseline or ignore entries that did not count. Separately, the report listed 19 baseline entries that no longer matched a finding. Twelve of the 69 findings were OBAAF-GHA-025. These counts describe that checkout and checker commit. The result after migration and the result with the final release have yet to be measured on that checkout.

An earlier migration exercise on 2026-11-12 explains how the command behaves. On a copy of Expectrail at `776ddd3`, the development checker of that day counted 40 findings. Migrating the baseline alone accepted 38 and left two new. One was named by an ignore entry without an owner. The other came from the lane declaration `byo-smoke.yml#byo-smoke: probe`; Expectrail used `probe` as a label for its own script. [Recorded migration exercise](https://github.com/Obaaf/OBAAF/pull/110)

For a similar gate:

1. Run `obaaf baseline migrate .github/obaaf-baseline.json --owner OWNER --reason REASON --expires YYYY-MM-DD` using the owner, reason and expiry approved by the maintainer.
2. Review ignore entries and complete each acceptance that still applies. For a project-specific lane label, move it out of OBAAF's lane declarations or record why the configuration finding is accepted.
3. Rerun the gate. Review new findings and stale entries individually before committing changes to the baseline or configuration.
